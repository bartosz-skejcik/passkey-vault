Passkey Vault · iOS · phases 38–40

The vault, all six types

Field models are transcribed from packages/pv-ui/vault/types.ts — the actual source of truth — not invented. Every colour comes from ios/brand/tokens.json. Light and dark alternate so both appearances are covered across the set.

One rule the whole screen set rests on

Type is carried by shape. State is carried by colour. Your tokens reserve colour for meaning — weak, stale, breached, shared — so tinting item types by hue would spend the same vocabulary twice and leave a red card ambiguous between “credit card” and “compromised”. Fallback glyphs are therefore monochrome in PVTextMuted on a PVSurfaceAlt tile.

Logins, passkeys and cards do not use glyphs at all — they use their real mark, mirroring packages/pv-ui/components/ItemIconTile.tsx. Logins and passkeys resolve a favicon from the item's own domain; cards get a brand tile detected locally from the number. Everything else falls back to the monochrome glyph, and so does any favicon that fails to load.

Rule (inherited, not invented here)Why it is load-bearing
Direct to the item's own domain. Never a proxy, never pv-server. https://<domain>/favicon.ico, no-referrer. The zero-knowledge favicon rule, already a hard constraint in 17-UI-SPEC.md. A Google/DDG favicon service would hand a third party the list of every site in the vault; routing through pv-server would hand it to the server this product promises never sees your vault.
Card brands are drawn locally from detectCardBrand(number). The component's own comment: "nothing about a saved card ever leaves the client to render its glyph." No network request may be tied to a card.
The favicon tile stays light in dark mode. Found in a live review, not in theory: GitHub's favicon is black and disappeared entirely on a dark tile. The frame keeps a light ground in both appearances.
Failed hosts are cached and not retried. FAILED_FAVICON_HOSTS — a site without a favicon must not re-request on every scroll.

One iOS-specific hazard the web version does not have. The rule says uncached. On iOS the default URLSession writes to a persistent on-disk URLCache — which would leave a favicon file for every site in the vault sitting in the app container, readable while the vault is locked. That is vault contents at rest, leaked by the icon layer. Use an ephemeral session (or in-memory-only cache) for favicon loads, and load lazily so only visible rows fetch.

The single exception among the remaining glyphs is passkey, in PVPasskey teal — because in this product “passwordless” is a semantic, not a category. It is the one type whose colour is telling you something rather than labelling something.

The bottom bar is the system's, not ours

A floating glass tab bar with the search capsule detached to its right is what TabView + Tab(role: .search) renders on iOS 26. None of it is hand-drawn — and it must not be. Verified against the SDK rather than assumed:

APIAvailableModule
Tab(role: .search)iOS 18.0+SwiftUI
glassEffect(_:in:)iOS 26.0+SwiftUICore — not SwiftUI
tabBarMinimizeBehavior(_:)iOS 26.0+SwiftUI
tabViewBottomAccessoryiOS 26.0 / 26.1+SwiftUI

Two consequences worth holding onto. First, the deployment target is iOS 18.0 (locked by IOS-03 because PRF requires it), so the floating glass rendering appears only on iOS 26 — on 18–25 the identical code falls back to a standard tab bar. That is a graceful degradation, not a fork: the view body is the same and only the .tabBarMinimizeBehavior modifier needs an #available guard.

Second, glassEffect lives in SwiftUICore. Grepping SwiftUI.swiftinterface for it returns nothing, which reads exactly like “this doesn't exist” — the same shape as landmine L-1. Do not conclude the API is missing from the wrong module's absence, and do not reach for it here anyway: hand-rolling glass onto a custom bar is both iOS 26-only and a fight with the system that stock TabView already wins.

The knock-on, after adopting Bevel's arrangement: ＋ owns the detached capsule and search moves to the accessory pill above the bar, so the FAB and the list-header search field both disappear. The nav bar is left holding only the account pill.

The bar filters types; the avatar owns the account

Settings, Family and Sign out live in a context menu held on a profile avatar at the top right, which frees the whole bottom bar for item types: All · Logins · Cards · Codes · Passkeys. Lock now is in that menu too — it is the one action a password-manager user wants instantly, and burying it in Settings makes the safest habit the slowest one.

Two honest costs, so neither is discovered later.

CostDetail
Two types have no tab — solved in All Six types, five slots. identity and note get no tab, so All is section-headed by type with a scrubber down the right edge — every type is one tap from the default screen. The ＋ grid covers creation; the scrubber covers retrieval. That was the actual hole: an earlier version of this page claimed the grid alone made the missing tabs survivable, which was wrong — it only fixed making a note, never finding one.

Implementation note, corrected: an earlier version of this page claimed SwiftUI has no public section-index API and that a UIKit bridge was needed. That was wrong. sectionIndexLabel(_:) and listSectionIndexVisibility(_:) are both public — the claim came from a grep whose output was truncated before the public declarations appeared, so absence-in-the-first-five-lines got read as absence. The real constraint is availability: both are iOS 26.0+, and this app targets 18.0. So the index is native on 26 and needs a ScrollViewReader.scrollTo overlay below it — or simply does not appear there.

And it takes text, not symbols. The label is Text/String, documented as "typically only a single character", so the glyph strip drawn in an earlier revision is not buildable. It is letters: L C 2 P I N — with Codes indexed as 2 because Cards and Codes collide on C.
It departs from the platform convention iOS tab bars are for distinct sections, not content filters; Apple's own guidance treats filtering as a job for a picker or scope bar. This is a deliberate departure, not an oversight. It reads well here because the vault genuinely is the app — there are no other sections once the account moves to the avatar — but it is the one place this design knowingly leaves the HIG.

The list and its dock

Structure borrowed from Bevel, because they solved the same problem well: accessory pill on top, filter bar plus a detached action capsule below, collapsing to circle · pill · circle on scroll. Every part of it is stock — TabView, Tab(role:), tabViewBottomAccessory, tabBarMinimizeBehavior(.onScrollDown).

What this set surfaces for planning

Camera permission is missing TOTP QR scanning needs NSCameraUsageDescription, which is not declared in the project today. It is the second and only other real permission this app needs.
Generator is a port, not wiring No generator exists in pv-core or pv-wasm. DR-38-A owns the call; either way it is real work, and doing it in Swift leaves two implementations to keep in sync.
Identity address round-trip The flat address string stays authoritative for the extension's autofill. An iOS save that writes only the structured fields silently breaks desktop filling.
Undecryptable is a tampering signal VaultItem.undecryptable already exists and the codebase reads it as tampering. It must be shown, not filtered out of the list.
