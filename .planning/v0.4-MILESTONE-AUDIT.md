# Milestone v0.4 — Family & Sharing — Audit

**Status:** `gaps_found`
**Audited:** 2026-08-09
**Phases:** 21–27 (7 of 7 executed)

## Verdict

The milestone's **hard cryptographic core is done and proven to an unusually high standard**: the
asymmetric identity layer, per-recipient Collection Key fan-out, scope-bound AAD, correctly-scoped
atomic re-key with an adversarial fault-injection proof, and the EXT-10 signature-counter spike that
falsified its own requirement's premise. Phase 25's and Phase 27's verifications independently
re-derived their proofs rather than trusting them.

What is **not** done is the last mile on three user-visible promises. All three are the same shape and
it is this milestone's documented signature failure mode: **a server capability that no client
reaches.** Phase 23 shipped `/api/sync/shared` with zero consumers and it took until Phase 26 to wire
one; Phase 26 shipped sharing that worked one-way. The pattern recurred twice more and was not caught
by any single phase's verification, because each phase verified its own scope honestly and the gap
lives *between* phases.

**Recommendation: do not complete the milestone yet.** Blocker 2 is a silent data-corruption path —
a recipient's capture-update on a directly-shared item re-encrypts it under the wrong key and the
owner permanently loses their own item. Blocker 3 means "removal severs access" is true of the server
and false of both clients. Neither is a polish item.

## Blockers

### 1. SHARE-06 is unreachable by any user
`revoke_access` and `revoke_share` exist, are authorized, and are tested — and no client calls either.
REQUIREMENTS.md records SHARE-06 as **Complete (Phase 22)**, which is a phase-scoped truth (the server
half) written down as an end-to-end one. Combined with WINDOWS #13 (no way to add a member to an
existing collection), a shared collection's membership is effectively **write-once**: you can create a
share and never adjust it.

### 2. The extension can silently corrupt a directly-shared item
`confirmUpdateLogin` dispatches on `collectionId != null`. A directly-shared item has
`collectionId: null` and `sharedToMe: true`, so it falls to the personal branch and is encrypted with
the **recipient's** User Key. The server stores ciphertext unexamined; a direct share at `edit`
satisfies `RequireEdit`, so the write succeeds. The owner can then never decrypt their own item.

Web refuses this exact operation (`DirectShareNotEditableError`, with a comment noting no
encrypt-as-recipient primitive exists). The extension writes `sharedToMe` and never reads it.

**This is a Phase 27 gap, and it slipped through for a traceable reason:** 27-07's scope was framed
around collection-scoped dispatch and the read-only refusal. The direct-share case was never named, so
neither the plan, its mocked tests, nor 27-11's live write proof (which used a *collection* item)
exercised it. The phase verified 14/14 against its own must-haves and was right to — the case was
outside them.

### 3. Removal and suspension never purge either client's cache
The 404 that proves the server severed access is the same 404 both clients read as "no family," which
latches shared-sync off for the session and thereby prevents the purge that would drop the cached
plaintext. A removed member keeps autofilling shared credentials until lock. Suspension does not even
latch — its non-404 rejection reads as transient, so it retries silently forever.

No phase owns this seam: Phase 23 wrote the latch before Phase 25 created the removal path.

## Suggested closure

One phase closes all three blockers — they are three instances of one seam (client-side consumption of
server-side sharing state) and share fixtures and test harness:

1. **SHARE-06 client** — API-client wrappers plus a revoke affordance in the web sharing overview.
   Consider WINDOWS #13 (add-to-existing-collection) alongside it; together they make membership
   editable rather than write-once.
2. **Direct-share write refusal in the extension** — read `sharedToMe`, refuse the write the way web
   does. Extend to `persistUpdatedProviderItem` (Warning 3) while the shape is fresh, before EXT-10's
   counter path ever activates and makes it live.
3. **404 → purge, before latch** — distinguish "no family" from "removed from family" and purge the
   decrypted cache on the latter; give suspension a signal at all. Live-prove with the existing
   two-extension harness, which already provisions exactly this scenario.
