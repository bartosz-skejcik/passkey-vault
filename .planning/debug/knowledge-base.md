## rekey-order-dependent-hang — a tags-less decrypted item plaintext wedges the whole vault store, surfacing as a 120s Playwright "hang"
- **Date:** 2026-08-06
- **Error patterns:** TypeError: fields.tags is not iterable, item.fields.tags is not iterable, Test timeout of 120000ms exceeded, waiting for item-form-login to be detached, Failed to save item. Please try again., no cached Collection Key for collection, order-dependent e2e failure, hang after collection re-key
- **Root cause(s):** `normalizeItemFields` (packages/pv-ui/vault/types.ts) — the single designated normalization boundary for decrypted item plaintext — did not enforce the `CommonFields.tags: string[]` invariant; it set `tags` only for the raw-passkey wire shape and returned every other shape untouched; **AND** a residual collection-scoped item whose plaintext was written without a `tags` key (by web/e2e/delete-account.spec.ts's member-self-deletion test, which unlike its sibling does not delete the singleton owner account) survived in that owner's vault. Both conditions were required (AND-gate), plus a third ordering condition: the crash only fires on the SECOND sync merge, once the collections store has cached the Collection Key so the row actually decrypts and is admitted to `items`. Consequence: `recomputeAllTags()`'s unguarded `for (const tag of item.fields.tags)` throws on every store mutation — and in `createVaultItem` the throw lands AFTER `POST /api/vault/items` returned 201, so the UI reported a failed save over a successful one and left the form mounted, which Playwright waited out for its full 120s timeout. **Explicitly NOT a server defect** — no WAL contention, no lock, no pool exhaustion, no hung fetch (all eliminated with direct evidence).
- **Fix:** Added `withCommonFieldInvariants` and split the shape logic into `normalizeItemShape`, so every path out of `normalizeItemFields` guarantees an iterable `tags`. Fixed at the trust boundary, not at the crash site — `applySyncSnapshot`'s flatMap was verified to be the only writer of server-decrypted plaintext into the store, and five other unconditional `fields.tags` dereferences (DetailPanel, ItemForm, toCsv) are covered by the same one change.
- **Files changed:** packages/pv-ui/vault/types.ts, web/src/lib/vault/types.test.ts, web/src/lib/vault/store.test.ts
- **Why not caught:** No gate existed for this class. Decrypted plaintext is untrusted input in a zero-knowledge vault (the server validates nothing, and collection items are authored by OTHER members' clients — extension today, Android/iOS on the roadmap), but nothing tested `normalizeItemFields` against a plaintext missing `CommonFields`. Typechecking cannot help: `JSON.parse(...) as ItemFields` is an unchecked assertion at exactly this boundary. The e2e suite could not catch it either until Plan 26-13a fixed an unrelated 422 that had been short-circuiting the only spec that produced such a row — the defect was latent and unreachable for its whole life.
- **Recurrence guard:** `web/src/lib/vault/types.test.ts#CommonFields.tags invariant (untrusted-plaintext hardening)` — parameterized over the boundary neighbors (absent / undefined / null / non-array scalar) and over every non-login item type; plus `web/src/lib/vault/store.test.ts#untrusted decrypted plaintext — a tags-less item must not wedge the store`, which asserts the user-visible harm directly (createVaultItem must not reject after its POST already succeeded; deleteVaultItem must stay usable so the bad row remains removable). Both verified to fail without the fix (7 failed / 45 passed) and pass with it (52/52).

**Transferable lesson:** when an e2e failure looks like a *hang*, check whether the request actually completed before theorizing about locks or contention. Here every API call returned 200/201 and the "hang" was a mounted error form. A 5s `busy_timeout` and a 30s `acquire_timeout` also mean a genuine SQLite/pool wedge can only ever surface as an *error* at 5s or 30s — never as a silent 120s hang. The timeout duration itself was evidence against the leading hypothesis.
