<objective>
Close a genuine architecture gap this phase's own tracer surfaces: today `store.ts::decryptItemRow`
unconditionally calls `decryptItem(uk, ...)` (the personal-scope function) on EVERY row `GET
/api/vault/items` returns — including collection-scoped rows the server's `fetch_items_for` union
already includes. A collection-scoped item's `enc_key`/`enc_data` are bound to a DIFFERENT key (the
collection's own `CollectionKey`) and a different AAD scheme (`encrypt_item_for_collection`'s
scope-bound AAD, KEY-03) — decrypting with the personal `UserKey` always fails, and today's code has
no branch that could do anything else, because it does not even know an item's `collection_id`
(Plan 26-01 just added that field to the wire).

Also wires A-5 (this phase's inherited obligation #3): `/api/sync/shared` has been fully
implemented and tested since Phase 23 with zero client consumer.

Purpose: Without this, "share a folder" (SHARE-01) means the folder can be CREATED but its
contents are permanently unreadable by anyone, including its creator — not a working feature.
Output: A `lib/vault/collections.ts` store mirroring `useFolders()`'s existing shape, and a
store.ts that correctly dispatches decryption by scope and reacts to a co-member's shared edit.
</objective>
