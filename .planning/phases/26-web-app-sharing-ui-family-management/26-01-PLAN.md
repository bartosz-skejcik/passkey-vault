<objective>
Fix the WR-09 wire-contract defect (25-CONTEXT.md's A-1, STATE.md's inherited Phase 25 blocker): `collections::create` currently mints the collection's `id` server-side AFTER the client has already encrypted `enc_name` with AAD bound to that id, so no real client can ever produce a decryptable collection name. This is the hard prerequisite the whole phase sequences around — every later plan that creates or reads a shared folder depends on this contract being correct. Also add the `collection_id` field vault items are missing on the wire, which every later decrypt-dispatch, filtering, and "already in a shared folder" UI decision in this phase needs.

Purpose: Prove the sharing feature's foundational crypto contract end-to-end — client-minted id, AAD-bound encryption, server persistence, and decryption — before any UI is built on top of a contract that might still be broken. This is the phase's tracer: it touches every layer (server route, wire shape, WASM crypto, client API) with one thin, real, verified slice.
Output: A working `POST /api/vault/collections` contract a real browser client can use; `collection_id` present on every vault item row; a real-WASM regression test that would have caught WR-09 and now proves it fixed.
</objective>

  (Uuid-v4 shape check adapted from the invite_id length/charset check there).

  NOTHING RETURNING` idiom — apply the identical shape to collections::create's own INSERT.

  the reason this plan exists.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Client → `POST /api/vault/collections` | Client now supplies a resource id that becomes a DB primary key — untrusted input crosses here for the first time on this endpoint |
| Client → `GET /api/vault/items` | Additive metadata field only — no new trust boundary |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-26-01 | Tampering | `collections::create`'s client-minted `id` | medium | mitigate | UUID-v4 shape validation before any DB work (fails closed, `ApiError::BadRequest`); PK uniqueness enforced by SQLite; a malformed/malicious id can never reach the INSERT |
| T-26-02 | Information Disclosure | Collision handling | low | mitigate | `ON CONFLICT DO NOTHING RETURNING` intercepts the collision explicitly and maps to `ApiError::Conflict` — never lets a raw `sqlx::Error` (which could differ in message/timing from a generic 500) fall through the blanket `From<sqlx::Error>` mapping |
| T-26-03 | Repudiation | Two clients racing the same UUID | low | accept | `crypto.randomUUID()`'s collision probability is cryptographically negligible; the 409 path exists for the theoretical case and a buggy/malicious client retrying with a fresh id, not as a realistic operational concern |
</threat_model>
