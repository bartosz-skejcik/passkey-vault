# Phase 26 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **Scope note.** This is the largest UI phase in v0.4 — nine surfaces, several genuinely new (no
> prior visual language to extend). All of them reuse the same tokens, row shells, and dialog shell
> already shipped through Phase 25; nothing here introduces a new hue, radius, or type scale.
> `components.json` is absent and shadcn is not part of this stack (DaisyUI 5 + `packages/pv-ui`,
> unchanged across every prior UI-SPEC) — the shadcn init gate is not applicable and was not
> re-asked.
>
> **Surfaces this phase owns:**
>
> 1. **Item-level Share entry point** — `ItemContextMenu.tsx` (new "Share…" entry, mirrors "Move")
>    and `DetailPanel.tsx` (new header icon button, mirrors Edit/Delete).
> 2. **Folder-level Share entry point** — a new "Shared folders" `Sidebar.tsx` section (parallel to
>    the existing personal "Foldery" section) plus a "Share this folder" action on an existing
>    personal folder row.
> 3. **`ShareDialog.tsx` (new)** — the one dialog both entry points open: recipient multi-select +
>    access-level picker (read-only / full-edit / hidden-password) + the hidden-password disclosure
>    sub-step.
> 4. **Hidden-password disclosure** (D-2) — a one-time blocking sub-step inside `ShareDialog`, then a
>    quiet persistent inline note on every later use.
> 5. **`AvatarStack.tsx` (new)** — the shared-item/folder marker (D-3), used in `ItemRow.tsx`,
>    `DetailPanel.tsx`, the Sharing overview, and (icon-only variant) the Sidebar's shared-folder rows.
> 6. **Sharing overview** (D-1) — a new `SharingOverviewPanel.tsx`, opened the same way
>    `SettingsPanel` is, grouped "By folder" / "By person".
> 7. **Identity fingerprint display** (D-4, SC 4) — extends `FamilyTab.tsx`'s Members section (Phase
>    25) with a "Your fingerprint" card and a per-row fingerprint reveal, six-word format.
> 8. **`CollectionPicker.tsx` (new, extracted/shared)** — the real collections picker that finally
>    discharges Phase 24's three dissolved UI-SPEC backstops (#4/#5/#6) and enables the "coming in a
>    later version" collection-scoped invite option in `FamilyTab.tsx`.
> 9. **KEY-01 client trigger** (SC 5) — no new visible surface in the success case; the one
>    user-visible consequence of failure is specified in Phase-Specific Notes §5.
>
> **This phase is not uniformly security UI.** Only the hidden-password disclosure sub-step (§4) is —
> per `docs/UI-DESIGN.md`'s "security UI zawsze czytelne, playfulness nigdy w dialogach bezpieczeństwa"
> rule, that one sub-step uses plain DM Sans, calm tone, no icons implying danger. Everything else
> (the share dialog shell, the sharing overview, the avatar stack, the fingerprint card) is ordinary
> product UI and may use the same warm, low-key visual language as the rest of the vault — it must
> just stay inside the existing token set.

## Spacing Scale

Declared values (must be multiples of 4) — identical numeric scale to every prior phase, **no new exception**:

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon-to-label gaps, avatar-stack ring width |
| sm | 8px | Compact inline gaps (access-level radio to its label, fingerprint word gap component) |
| md | 16px | Dialog form field vertical rhythm, sharing-overview card internal padding |
| lg | 24px | Dialog/panel internal padding (`p-6`, matching every existing modal and `SettingsPanel`) |
| xl | 32px | Vertical gap between Sharing-overview's "By folder"/"By person" toggle and its list |
| 2xl / 3xl | 48px / 64px | Unused this phase |

**Exception — 12px (`gap-3` / `py-3`), reused not new:** shared-folder Sidebar rows and Sharing-overview
list rows use the exact `flex min-h-16 items-center gap-3 rounded-box border border-base-300 px-4 py-3`
shell Phase 25 already established for `SessionsTab`/`PasskeysTab`/member rows — the fourth row type to
adopt it, kept identical for the same reason Phase 25 gave: visual continuity across every row-shaped
list in this codebase, not a per-phase reinvention.

**Avatar-stack overlap — `-space-x-2` (−8px):** a multiple of 4, not a new exception; the overlapping-
circle idiom (D-3) needs a negative margin between siblings, and −8px is the smallest overlap that keeps
each avatar's edge visually distinct at the 20px diameter this spec uses (see §5 below) without the
stack reading as a single blob.

## Color

Unchanged 60/30/10 split and exact OKLCH/hex values from `docs/UI-DESIGN.md` / `packages/pv-ui/tokens.css`
— **no new hue**. One new *semantic* use of an already-reserved color, stated so it is not mistaken for
an oversight:

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | base-300 | Page canvas (unchanged) |
| Secondary (30%) | base-100/base-200 | `ShareDialog`/`SharingOverviewPanel` surfaces, shared-folder row background — reused verbatim |
| Accent (10%, coral `#E16540`) | primary | `ShareDialog`'s submit CTA (`btn btn-primary`, matches every other constructive-progression CTA in this codebase), the Sidebar's "+ new shared folder" trigger (matches the existing personal-folder "+ new folder" trigger's `text-primary`-on-hover treatment) |
| **New use this phase — secondary (błękit `#8DCDFF`)** | text-secondary / border-secondary | **Reserved exclusively for the passive "this is shared" signal**: the small `Share2` icon shown next to a shared folder's name in the Sidebar (icon-only variant, see §5), and the avatar-stack's outer ring color when rendered at icon-scale. `docs/UI-DESIGN.md` already reserves secondary for "wykresy (linie), linki, info-akcenty" (charts, links, info-accents) — a passive metadata signal ("this thing is shared") is exactly an info-accent, not a call to action, so this is the doc's own reserved bucket applied to a new element, not a new hue. Teal (`accent`, `#00CDB7`) stays reserved for passkey semantics only, per the doc's explicit "konsekwentnie" rule — it is never repurposed to mean "shared," which would collide with every existing passkey badge in the item list. |
| Warning (`#FFBE00`) | not used this phase | The hidden-password disclosure is deliberately **not** styled as a warning (see below) — it is a factual disclosure, not an alert. |
| Destructive (`#FF5861` error) | text-error | Unused in this phase's own surfaces (no destructive action is introduced here — revocation already shipped in Phase 25/22); reused only if a share-creation network error needs the existing `role="alert" text-error` pattern, same as every prior phase's error copy. |

**Hidden-password disclosure is deliberately neutral, not amber/red — explicit deviation from a naive
"this needs a warning color" instinct, stated so it isn't mistaken for an oversight.** D-2's own framing
is that hidden-password is a completely normal, supported access level with one honestly-stated limit —
not a danger the user is being warned away from. Coloring it amber/red would misrepresent it as risky
relative to the other two levels, which is exactly the dishonesty UX-03 exists to avoid in the other
direction (never *overstating* protection is only half the honesty contract; never *understating* a
legitimate feature as a hazard is the other half). The disclosure sub-step therefore uses a plain `Info`
icon in `text-base-content/70` (neutral), never `AlertTriangle`/`text-warning`/`text-error`.

**Accent reserved for:** `ShareDialog`'s submit CTA and the Sidebar's new-shared-folder trigger, both
named above. **Secondary reserved for:** the passive shared-indicator icon/ring, named above. Nothing
else in this phase's scope competes for either budget.

**Copywriting honesty constraints (hard requirements, re-stated for the checker):**

1. `share.hiddenPasswordDisclosureBody` must never be shortened, softened, or reworded to imply the
   password is hidden from the recipient in any cryptographic sense — it is the phase's D-2/UX-03
   safety-critical string, same class of requirement as Phase 25's `member.removeHonestyWarning`.
2. `share.hiddenPasswordInlineNote` must render on **every** occasion hidden-password is the selected
   access level, not only the first — "persistent," per D-2, means it never goes away, not that it fades
   after the blocking modal is dismissed once.
3. `identity.fingerprintUnavailable` must never be worded as an error ("failed to load") — a member who
   has not yet unlocked since v0.4 upgraded is an expected, honest state, not a fault.
4. No copy anywhere implies a folder-level share and an item-level share are the same grant — the
   Sharing overview and both dialogs must keep the "folder" vs "item" language distinct throughout
   (matches SC 1's own two-independent-mechanisms framing).

## Phase-Specific Notes

### 1. Cross-phase obligations this UI-SPEC discharges (traceability)

- **WR-09 / A-1 (25-CONTEXT.md's locked architecture decision) is a prerequisite for E3's folder-create
  variant, not a separate task this spec re-describes.** `collections::create` today mints the
  collection id server-side AFTER the client has already encrypted `enc_name` bound to that id, so no
  client can currently produce a decryptable folder name (confirmed live in Phase 25 UAT — every folder
  in the removal-disclosure list rendered as `Folder "<uuid>"`). The fix (client generates the UUID,
  encrypts `enc_name` bound to it, sends both) is a `crates/pv-server/src/routes/collections.rs`
  change, not a UI change — but `ShareDialog`'s folder-create submit path is the FIRST real client
  call site that needs it to work end-to-end. The plan must land the fix before or alongside this
  dialog, never build the dialog against the broken contract and defer the fix again.
- **The three dissolved Phase 24 UI-SPEC backstops (#4/#5/#6) are discharged by E8/`CollectionPicker`
  above** — resolved, not merely re-flagged.
- **Phase 24's collection-scoped invite "coming in a later version" copy retires in this phase** — see
  E8's last row. `invite.scopeFolderComingSoon`/`invite.scopeFolderUnavailableNote` keys are removed
  from the dictionary (not left dead) once `CollectionPicker` is wired in; `FamilyTab.test.tsx`'s
  existing assertions against the disabled state must be updated accordingly, not left asserting a
  now-false claim.
- **A-5 (`/api/sync/shared` client consumer) has no dedicated visual surface of its own** — it is what
  makes E5's avatar stack, E6's overview, and E7's fingerprint reveal show *live* data (a collection
  add/remove reflected without a manual refresh) rather than stale snapshots. Not re-specified here
  beyond that dependency; `sync.ts`'s wiring is a plan/architecture concern.

### 2. Fingerprint copy button — deliberate deviation from the auto-clear convention

Every other copy-to-clipboard action in this codebase (`clipboard.ts`'s `copyWithAutoClear`) exists
because the copied value is a secret (password, TOTP code, recovery key, invite link fragment) that
must not linger on the system clipboard. An identity fingerprint is **not** a secret — it is a
non-reversible, public derivation of an already-published public key, meant to be read aloud or pasted
into an out-of-band channel (a text message, a call transcript) for comparison. Auto-clearing it would
actively work against its own purpose (the recipient needs it to still be on their clipboard when they
paste it into that other channel, possibly minutes later). `identity.fingerprintCopyAria`'s handler
therefore uses a plain, non-clearing clipboard write — the ONE intentional exception to this codebase's
otherwise-universal auto-clear rule, flagged explicitly here so it is not "fixed" by a future pass that
assumes every copy button in this app must auto-clear.

### 3. Hidden-password ack flag — explicitly not a security control

The `localStorage` flag gating the one-time blocking modal (E4) is a **UX memory**, not an access
control — it decides whether to show an explanatory modal again, nothing more. It has no bearing on
what the server will or won't authorize (`SHARE-05`'s server-side enforcement is entirely independent
and already shipped in Phase 22), and losing it (private browsing, a cleared profile, a new device)
only means the modal reappears once more — never a security regression, only a repeated explanation.

### 4. Avatar-stack and Sharing-overview data source — a real gap, not a rendering branch to invent around

`VaultItem`'s wire shape carries only `is_shared: boolean` (Phase 23) — enough to know an item is
shared, not **with whom**. For a collection-scoped item, "who" is answerable today via the already-
shipped `GET /api/vault/collections/{id}/access` (`CoRecipientRecord[]`, Phase 22). For a personal item
with a direct `item_shares` grant, **no listing endpoint exists** — `POST .../shares` (create) and
`DELETE .../shares/{user_id}` (revoke) are the only two routes; nothing returns the current recipient
set for a given item id. E5's avatar stack and E6's "By folder"/"By person" overview both need exactly
that list for direct shares.

**Requirement for the plan — not optional, not a rendering branch to authorize around:** the plan must
add the missing read path (most naturally `GET /api/vault/items/{id}/shares`, mirroring the collection
endpoint's own shape) rather than approximating "who it's shared with" from data that doesn't carry it,
or silently limiting the avatar stack/overview to collection-scoped shares only. A plan that ships the
avatar stack for folder-shared items but omits it for directly-shared items — without this endpoint
existing — does not conform to this UI-SPEC; SC 3's "shows who a given shared item is shared with"
does not carve out an exception for direct shares.

### 5. KEY-01 failure — the retry mechanism E9 implies

E9 states the only visible consequence of a failed identity-keypair publish is a persistently-unavailable
own fingerprint. For that to ever resolve without asking the user to do anything ceremonial, the plan
must retry `ensureOwnIdentityKeypair` (already idempotent, already handles the two-device race per A-3)
on a **subsequent unlock**, not only the first — a transient failure (one dropped request, one 500)
should self-heal the next time the user opens the vault, with no user action required. This UI-SPEC does
not require a manual "Try again" affordance next to `identity.fingerprintUnavailable` (that would be
inventing a ceremony where the honest answer is "wait for your next unlock, this is temporary and
harmless"), but the plan must not silently give up after one failed attempt and never retry — that would
leave `identity.fingerprintUnavailable` permanently, dishonestly, in place of a value that could exist.
