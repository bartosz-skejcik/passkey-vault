## Phase Goal

**As a** user with a PRF-capable enrolled passkey, **I want to** log in and unlock my vault with a single passkey gesture, **so that** I never have to also type my master password — and when PRF isn't available I still get a clear, working password fallback instead of a dead end.

(Reformatted from ROADMAP.md's Phase 4 Goal line, which predates the `mvp-phase` user-story convention — no new scope invented; every clause traces to ROADMAP.md's four Phase 4 success criteria and 04-CONTEXT.md's locked decisions. Per this run's autonomous-overnight instruction ("resolve ambiguity yourself from project files, never ask interactive questions"), this reformatting was not sent back for confirmation.)

**Vertical-slice note (why this plan is backend-only):** MVP mode calls for vertical feature slices, not horizontal layers. This plan is nonetheless backend-only by hard architectural necessity, not layering-as-habit: a WebAuthn ceremony can only be verified by a real relying-party server holding the real challenge state — 04-CONTEXT.md and 04-RESEARCH.md's Anti-Patterns both lock "never trust an uploaded credential blob" and forbid stubbing `finish_passkey_authentication`. There is no safe way to fake this ceremony client-side without violating the zero-knowledge/real-verification invariant this whole phase exists to prove. Plan 04-02 (Wave 2) is the actual vertical slice: it consumes these endpoints end-to-end and is the point at which a real user gains new capability. This mirrors Phase 3's own accepted precedent (03-01 backend ceremony endpoints → 03-03 frontend orchestration), which shipped under this same `mode: mvp` phase setting.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Anonymous client → `passkey-login/start\|finish` | Fully untrusted, unauthenticated input — the ceremony itself, not a session token, is the only proof of identity |
| Bearer-session client → `unlock/start\|finish` | Authenticated but still untrusted for WHICH credential completes the ceremony — `SessionUser` proves account ownership, not which passkey will respond |
| Server ↔ SQLite | Trusted boundary — only opaque `passkey_json`/`prf_wrapped_uk` blobs cross it, server never parses `prf_wrapped_uk`'s contents |
