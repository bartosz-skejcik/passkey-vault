## Phase Goal

**As a** user with a PRF-capable enrolled passkey, **I want to** log in and unlock my vault with a single passkey gesture, **so that** I never have to also type my master password — and when PRF isn't available I still get a clear, working password fallback instead of a dead end.

(Same Phase Goal restatement as 04-01-PLAN.md — see that plan's note on sourcing/autonomous-mode handling. This plan is the one that actually delivers it: after this plan, a real user gains the capability described above. 04-01 was the unavoidable backend precondition.)

<objective>
Wire Plan 04-01's four new endpoints into the unlock/login screen exactly as UI-DESIGN.md Screen 1 and 04-CONTEXT.md's Area 2/3 fallback taxonomy specify: a shared `PasskeyUnlockButton` above the password field on both `LoginForm` (fresh browser) and `UnlockOverlay` (reload/auto-lock), a pure orchestration module (`login.ts`, mirrors Phase 3's `enroll.ts` convention) that never touches React state, and the one-shot `prfUnavailable` flag that lets a post-login "no PRF" landing carry an honest explanation instead of looking like an ordinary reload.

Purpose: this is the plan that turns Plan 04-01's backend ceremonies into the actual demoable outcome — a user who can log in and unlock with one gesture, or land on a clearly-explained password fallback.
Output: `login.ts` + `errors.ts` + `prfUnavailable.ts` (new lib modules), `PasskeyUnlockButton.tsx` (new component), `LoginForm.tsx`/`UnlockOverlay.tsx` (extended), full PL/EN dictionary coverage, and component/unit test coverage for every fallback tier.
</objective>
