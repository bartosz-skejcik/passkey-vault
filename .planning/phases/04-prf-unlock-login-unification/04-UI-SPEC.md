## Color

Unchanged 60/30/10 split and hex/OKLCH values from Phase 1–3 (`vault-dark` default, full `vault-light` parity). This phase puts the project's teal semantic token on a **button surface** for the first time — previously teal only appeared on icons/badges (Phase 2's passkey-placeholder `KeyRound`, Phase 3's PRF badge/enrollment-ceremony `Fingerprint`).

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#1F1F1F` base-300 dark (light: Phase 2's fixed `base-300`) | Page canvas behind `AuthCard`, unlock-overlay scrim base |
| Secondary (30%) | `#262626` base-100 / `#212121` base-200 | `AuthCard`/`UnlockOverlay` card surface — unchanged |
| Accent (10%, coral `#E16540`) | primary | **Unchanged usage only** — the existing password-submit buttons (`Zaloguj się` on `LoginForm`, `Odblokuj` on `UnlockOverlay`'s pending-fast-path and password-form branch) stay coral `btn-primary`, exactly as Phase 2 defined. No new coral usage this phase. |
| Destructive | `#FF5861` error | Tier-3 mid-ceremony genuine-failure text (`unlock.passkeyFailed`) — reuses the *exact* existing `<p className="text-sm text-error">` treatment both components already use for password errors, not a new banner component. |

**Teal (`#00CDB7`, DaisyUI `accent` token) — extended this phase to a button fill, still locked to passkey meaning only:**
- `PasskeyUnlockButton`'s fill (`btn btn-accent`, `accent-content` text) on both `LoginForm` and `UnlockOverlay`, idle and busy states. This is the literal implementation of UI-DESIGN.md's Screen 1 spec ("duży tealowy przycisk 'Odblokuj passkeyem'") — the single largest teal-fill surface shipped yet, but the *meaning* (passkey-capable action) is unchanged from Phase 2/3's reservation, not a new carve-out.
- `Fingerprint` icon inside the button (idle: `accent-content`-matching/inherits button text color; busy: same color, paired with an animate-spin `Loader2`, identical visual grammar to `EnrollPasskeyDialog.tsx`'s step icons).
- Teal is **not** used for the tier-1/tier-2 fallback explainer text (that stays neutral `base-content/70`, per the "no fake success, no hard failure" doctrine Phase 3 already established for `prf_capable: false` — an unavailable-PRF state is honest, not a passkey-branded call-to-action).

**Two accent-weight buttons on one screen is intentional, not a Color-dimension violation:** the teal `PasskeyUnlockButton` and the coral password-submit button are two *different* reserved semantic tokens (passkey-action vs. primary-submit-action), each used for exactly one meaning, each appearing exactly once per screen state. This is the same "dual-path" pattern the UI-DESIGN.md spec itself calls for ("Dwie równorzędne ścieżki") — not two competing accents fighting for the same 10% budget.

**Fallback-tier text colors (all non-alarming except tier 3):**
- Tier 1 (no WebAuthn support) and Tier 2 (`prf_wrapped_uk === null` / zero PRF-capable passkeys) explainer copy: `text-base-content/70` (Body-role neutral, same tone as Phase 3's `enroll.step*Waiting` secondary copy) — never warning-yellow, never error-red. This mirrors Phase 3's explicit "no fake success, no hard failure" ruling, now extended from enrollment-time to login-time.
- Tier 3 (genuine mid-ceremony failure, not cancellation): `text-error`, matching the destructive row above — this *is* a real failure (network/hardware error), unlike tiers 1–2, so it earns the error color, same as every other failure state in this app.
- Cancellation (`NotAllowedError`): **no color, no text at all** — a silent re-enable is not a "state" with a copy row.

## Phase-Specific Notes

### Component decomposition — `PasskeyUnlockButton`

A single shared, **pure presentational** component (per 04-RESEARCH.md's Recommended Project Structure — `web/src/components/auth/PasskeyUnlockButton.tsx`), no ceremony orchestration inside it:

```
Props: {
  label: string;          // context copy — "unlock.passkeyLoginCta" or "unlock.passkeyCta"
  state: "idle" | "busy";
  onClick: () => void;
  disabled?: boolean;     // true while a real submit (password path) is also in flight
}
```

- **idle:** full-width `btn btn-accent`, `Fingerprint` (16–18px, `aria-hidden="true"`) leading the label text.
- **busy:** same button, `disabled`, `Fingerprint` + `Loader2` (`animate-spin`, `-right-2 -top-2` offset — identical composition to `EnrollPasskeyDialog.tsx`'s step icons) replacing the idle icon, label text switches to `unlock.passkeyBusy` ("Potwierdź w przeglądarce…") so the user gets live feedback that their browser/OS prompt is the thing to look at, not the app.
- Component does **not** render at all (see Tier 1 below) when `window.PublicKeyCredential === undefined` — the caller (`LoginForm`/`UnlockOverlay`) makes that capability check and conditionally mounts/omits `PasskeyUnlockButton`, rather than the component rendering a disabled variant of itself.

### Fallback-tier visual mapping (AUTH-09, three tiers per 04-CONTEXT.md Area 3)

| Tier | Trigger | Visual treatment | Component state |
|---|---|---|---|
| 1 — no WebAuthn support | `window.PublicKeyCredential === undefined`, checked once at mount | `PasskeyUnlockButton` **not rendered at all**. A single `unlock.passkeyUnsupported` line (`text-sm text-base-content/70`) sits where the button would have been, in the same slot, same vertical rhythm. Divider still renders below it (leads into the password form as the sole path). | N/A — button absent, not disabled |
| 2 — PRF unavailable | Either (a) `passkey-login/finish` returns `prf_wrapped_uk: null`, or (b) `unlock/start` returns 404 (zero PRF-capable passkeys) | `PasskeyUnlockButton` **stays rendered and clickable** (parity with LoginForm's "always show the button" principle — a different enrolled passkey might work). A muted `unlock.prfUnavailableExplainer` line renders **between the divider and the password field**, and the password field receives `autoFocus`. No color change to the button itself. | idle |
| 3 — genuine mid-ceremony failure (not cancellation) | `navigator.credentials.get()` rejects with anything other than `NotAllowedError`, or `passkey-login/start`\|`finish` (or `unlock/start`\|`finish`) rejects at the network/server level | `unlock.passkeyFailed` renders as `text-sm text-error` **directly below the `PasskeyUnlockButton`**, same visual slot the existing password-form error `<p>` already uses one section down — two independent error slots can coexist (passkey-path error above, password-path error below), never merged into one ambiguous message. Button returns to idle/clickable. | idle (re-enabled) |
| — (not a tier) User cancellation | `isNotAllowedError(e)` true | **No visual change at all** beyond the button silently returning to idle. No banner, no color, no copy. | idle |

### Screen layout order (UI-DESIGN.md Screen 1: "duży tealowy przycisk … i pole master password poniżej")

**`LoginForm`** (fresh browser/no session — top to bottom):
1. Email field (`auth.emailLabel`, required, pre-filled from `getStoredEmail()` when present but always editable) — must be entered/valid before the passkey ceremony can be scoped, so it sits above the button as a natural prerequisite, not a layout violation of "button first."
2. `PasskeyUnlockButton` (`unlock.passkeyLoginCta`) — or the Tier-1 explainer line in its place.
3. Tier-2 explainer line (only when the flag is set — see Fallback-tier table) / Tier-3 error line (only on genuine failure).
4. `divider` — `unlock.orDivider` ("lub"/"or").
5. Password field (unchanged, `font-mono`).
6. Coral `btn btn-primary` submit (`auth.loginSubmit`, unchanged).
7. `auth.toggleToRegister` link (unchanged).

**`UnlockOverlay`**, `pending === null` branch only (reload/auto-lock, no pending material) — top to bottom:
1. `PasskeyUnlockButton` (`unlock.passkeyCta`) — or Tier-1 explainer.
2. Tier-2 / Tier-3 lines as above.
3. `divider`.
4. Password field + coral submit (unchanged).

**`UnlockOverlay`**, `pending !== null` branch (password *or* PRF login just completed in the same tab, one more click finishes the unwrap) — **zero visual change, zero new code**. Per 04-RESEARCH.md's Pattern 5, a successful PRF login also lands here via the existing `setPendingUnlock` call — the existing one-button "Odblokuj" fast-path already handles it. `PasskeyUnlockButton` is never shown in this branch (there is nothing left to authenticate — only to confirm the unwrap).

### Card shell — unchanged, no new pattern

Both `AuthCard.tsx` (Login/Register) and `UnlockOverlay`'s own inline card markup keep their existing 400px/16px-radius/1px-border/24px-padding vocabulary. No new modal, no new drawer, no new scrim treatment — `PasskeyUnlockButton` and its fallback copy are additive content *inside* the existing card body, per CONTEXT.md's explicit "no full merge of `LoginForm.tsx`/`UnlockOverlay.tsx`" instruction.

### Accessibility

- `Fingerprint`/`Loader2` inside `PasskeyUnlockButton` are `aria-hidden="true"` — the button's own visible text label is the accessible name, following Phase 1–3's "decorative icon inside a labeled control" rule. No new `aria-label` table entry needed since the control is never icon-only.
- The tier-2/tier-3 explainer/error lines are plain `<p>` text in normal document flow — a screen reader encountering the form linearly reaches them naturally; no `aria-live` region is required by CONTEXT and none is added here (an `aria-live="polite"` region would be a reasonable follow-up hardening but is not part of this phase's locked scope).
- Password field `autoFocus` in the Tier-2 case is a genuine usability aid (the user was just told to use their password) — verify it doesn't fight the browser's own focus-after-async-navigation conventions during manual QA; not a design concern, an implementation check.

### Cross-reference — shared helper visibility (not a design decision, flagged so the plan doesn't lose it)

`isNotAllowedError()` currently lives as a **private, non-exported** function inside `web/src/lib/passkeys/enroll.ts` (confirmed by direct read — `04-RESEARCH.md`'s Pitfall #4 predicted this and it is in fact the current state). CONTEXT.md locks reusing this exact helper for the passkey-login/unlock cancellation check. This UI-SPEC doesn't own that file, but flags it here so the planner doesn't have to re-discover it: either export it from `enroll.ts` or hoist it into the `web/src/lib/passkeys/errors.ts` file 04-RESEARCH.md's Recommended Project Structure already proposes.

## Morning review notes

Taste calls this agent made autonomously overnight (04-CONTEXT.md's decisions were binding and are **not** relitigated here — only genuinely open visual/UX choices CONTEXT explicitly flagged as taste calls or left unaddressed). None of these affect the security model, the fallback-tier logic, or the zero-knowledge boundary — they're all presentation-layer and reversible in a follow-up pass.

1. **LoginForm CTA wording kept as CONTEXT's drafted "Zaloguj i odblokuj passkeyem" / "Log in and unlock with passkey"** (both-verbs form), rather than matching `UnlockOverlay`'s shorter "Odblokuj passkeyem." Reasoning: `LoginForm`'s passkey action genuinely does two things in one gesture (creates a session *and* unlocks), so naming both verbs is more accurate there; `UnlockOverlay`'s action is unlock-only (a session already exists), so the shorter form stays precise and the two CTAs are correctly *not* identical strings. Flag if you'd rather they read identically for brand consistency over precision.
2. **Tier 1 (no WebAuthn support) resolved as absent-button, not disabled-button** — `PasskeyUnlockButton` doesn't render at all in this state; a plain explainer line takes its slot instead. Reasoning: a focusable-but-permanently-inert button is a worse a11y/UX signal than "no control here, here's why" — CONTEXT's own wording ("never a clickable dead end") reads more naturally as "no control" than "a control that looks live but isn't." Flag if you'd rather keep a visibly-`disabled` button in place (arguably more honest to "the affordance exists, just not on this device").
3. **New copy drafted for Tier 1 explainer, Tier 3 error banner, and the "lub"/"or" divider** — content direction follows CONTEXT's own "honest, specific, non-alarming" instruction (already used for CONTEXT's own drafted Tier 2 line), but the literal PL/EN phrasing is mine. Bundled into the same morning pass as CONTEXT's own two already-flagged lines (LoginForm CTA wording, Tier 2 explainer wording) so there's one copy-review pass, not several.
4. **Tier 2 (PRF unavailable) keeps `PasskeyUnlockButton` visible and clickable**, rather than hiding/removing it once the flag is set. Reasoning: the signal only tells us *this specific credential/attempt* wasn't PRF-capable — a user with multiple enrolled passkeys might get a different result on retry (native chooser picks a different device), and hiding the button would foreclose that without a real reason. The explainer line sits between the button and the password field rather than replacing the button. Flag if you'd rather the button disappear once tier-2 triggers, framing it as "this account doesn't do PRF login, don't bother again this session."
5. **Divider uses stock DaisyUI `divider` with lowercase "lub"/"or" text**, rather than no divider at all. Reasoning: with two full-width buttons of different colors stacked directly (teal CTA, then eventually the coral submit below a password field), a plain-text "or" gives a one-word explanation for why there are two competing primary-looking actions on one screen — cheap, matches datafa.st's own restrained-but-not-bare aesthetic. Flag if you'd rather drop it for maximum minimalism (UI-DESIGN.md's own "Zero clutteru" instruction could be read either way).
