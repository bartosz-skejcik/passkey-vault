<objective>
Build the Collections resource: creation with the creator's own transactional key-wrap (the
KEY-02 fan-out seed), the add-member endpoint that grows the fan-out by exactly one row per
call, single-share revocation (SHARE-06) at a URL shape that can never be confused with a
future family-member-removal endpoint, and symmetric co-recipient visibility.

SHARE-06's single probe row (category: `unclassified`) returned no applicable shape-taxonomy
category from the deterministic edge-probe classifier. Per the specless-probe-fallback protocol
this stays `unresolved` rather than being force-fit into a category or silently dropped. See the
frontmatter `must_haves.truths` for this plan's best-effort coverage (derived from ROADMAP SC#4
and 22-VALIDATION.md's fixed test name), and the note above for what a future verifier pass
should independently re-check.

Purpose: this is the resource collection_key fan-out actually lives in — everything Plan 22-01
proved about the extractor mechanics and Plan 22-02 proved about identity keypairs converges
here into a real, shareable collection.

`POST /api/vault/collections/{id}/members`, `DELETE /api/vault/collections/{id}/access/{user_id}`,

## Trust Boundaries — ASVS Level 1

| Boundary | Description |
|----------|--------------|
| Client -> `POST /api/vault/collections/{id}/members` | The confused-deputy boundary — a caller with edit access could otherwise wrap-and-store a sealed key for an arbitrary, non-family `recipient_user_id` |
| Client -> `DELETE .../access/{user_id}` | Revocation must be immediately effective on the revoked user's OWN still-valid session — no grace window |
| Any member -> `GET .../access` | Symmetric co-recipient visibility — deliberately broader than owner-only, scoped to "has any access to THIS resource" |
