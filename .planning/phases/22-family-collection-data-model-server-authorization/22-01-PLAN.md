<objective>
Build the phase's foundational security boundary — the generic authorization-extractor
mechanics (SHARE-05/SEC-06) — as a tracer slice through the singleton `families` resource
(FAM-01/02/03), then expand out to a fully-built `Membership<R,M>` generic extractor whose
`Collection`/`Item` resource kinds later plans (22-03, 22-04) reuse without touching this
file again.

**Deviation from 22-RESEARCH.md, recorded here per Claude's Discretion:** RESEARCH.md sketched
`Family` as a plain path-based `ResourceKind`. Family routes in this phase have NO `{id}` path
segment — v0.4 is a strict singleton (CONTEXT.md's locked FAM-01 decision) — so the generic
`Path<String>`-reading `Membership<R,M>` design does not fit. This plan instead builds a
**second, small, pathless extractor `FamilyMembership<M>`** that composes `SessionUser` +
a dedicated `resolve_family_role()` helper (same "exactly one place this logic lives"
discipline as `session.rs::validate_token`), while `Membership<R,M>` itself (built here, used
by Collection/Item resource kinds in 22-03/22-04) stays exactly as RESEARCH.md specified for
resources that DO have a path id. **Second deviation:** `Membership<R,M>`'s own internal path-id
read uses `Path::<HashMap<String, String>>` rather than RESEARCH.md's `Path::<String>` sketch —
verified against pinned axum-0.8.9, `Path<String>` rejects any route with more than one `{...}`
capture, which several later `Membership`-gated routes (22-03/22-04) have. **Third deviation:**
family/collection-mutating routes gated by `FamilyMembership<M>` are folded via a second table,
`family_routes()`, sibling to `membership_routes()` — kept distinct because the two extractors
need different sweep-fixture shapes (path `{id}` vs. none), and both must be swept by Plan
22-05's route-sweep test for SC#2's guarantee to be structural rather than by convention.

**Also corrects 22-CONTEXT.md's schema list** per 22-RESEARCH.md: `vault_items` has NO
`collection_id` column today. This plan's migration adds it (nullable, additive) — without it
the extractor and SHARE-04's "item's current collection" check (Plan 22-04) have nothing to
query.

Purpose: every later plan in this phase (identity, collections, item moves, the route sweep)
builds strictly on top of what this plan ships — the migration, `ApiError::Forbidden`, the
`Membership<R,M>`/`FamilyMembership<M>` extractor mechanics, and the family CRUD surface.
Output: `crates/pv-server/migrations/0014_family_sharing.sql`, `src/routes/membership.rs`,
`src/routes/families.rs`, `ApiError::Forbidden`, the `family_routes()`/`membership_routes()` table
pattern seeded in `mod.rs`, and `tests/family.rs`.
</objective>

## Trust Boundaries — ASVS Level 1

| Boundary | Description |
|----------|--------------|
| Client -> `POST/GET /api/families*` | Untrusted request crosses into the family authorization boundary this plan builds |
| `FamilyMembership<M>`/`Membership<R,M>` -> handler body | The extractor is the ONLY gate; a handler compiling without it in its signature cannot see a shared resource |
| DB row -> `AccessLevel` | `parse_access_level` is the sole trusted decoder for the `CHECK`-constrained `access_level` string |

## STRIDE Threat Register (V4 Access Control / V5 Input Validation / V6 Cryptography)

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-22-01 | Elevation of Privilege | `FamilyMembership<M>`/`Membership<R,M>` | high | mitigate | Generic extractor is the ONLY place a handler can gain access to a family/collection/item resource — a handler without it in its signature cannot compile against that resource, closing the CVE-2026-43639 asymmetric-check class structurally, not by convention |
| T-22-02 | Information Disclosure | 404-vs-403 split | high | mitigate | No membership row at all -> `ApiError::NotFound` (never confirms the family/resource exists); caller with SOME access but insufficient level -> `ApiError::Forbidden` — this exact split is enforced in one place (`Membership`/`FamilyMembership::from_request_parts`), never per-handler |
| T-22-03 | Tampering | `parse_access_level` | medium | mitigate | Explicit non-wildcard `_ => Err` else-arm — an unrecognized DB string (should be impossible given the `CHECK` constraint, but defense in depth) fails closed to `ApiError::Internal`, never silently treated as a valid access grant |
| T-22-04 | Elevation of Privilege | `AccessLevel` comparisons | medium | mitigate | `AccessLevel` deliberately does not derive `Ord` — `RequireEdit::satisfied_by` is an explicit `== AccessLevel::Edit` match, so `HiddenPassword` can never accidentally satisfy an edit-gate via a transitive `<`/`>` comparison a future refactor might introduce |
