## Trust Boundaries — ASVS Level 1

| Boundary | Description |
|----------|--------------|
| Client -> `PUT /api/identity/keypair` | Untrusted `public_key`/`wrapped_secret_key` bytes cross in; only the encoding of `public_key` is validated server-side, never its provenance |
| Server storage -> any future `unseal` call | The zero-knowledge boundary this module's doc comment enforces by convention (no compiler-level guard exists in Rust for "never call this function" beyond code review + the grep audit in Plan 22-05) |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-22-07 | Tampering | `upsert()` public_key validation | medium | mitigate | `IdentityPublicKey::from_bytes` rejects malformed length and small-order encodings before any storage; malformed input never reaches the DB |
| T-22-08 | Information Disclosure | Zero-knowledge boundary | high | mitigate | Module doc comment + Plan 22-05's grep audit assert no `seal`/`unseal`/`unwrap_identity_secret_key` call exists under `crates/pv-server/src` — the server can store but never read plaintext key material |
| T-22-09 | Spoofing | `IdentityPublicKey` provenance (a malicious/compromised server substituting its own key as "the member's") | high | accept | Out of this phase's scope by design — RESEARCH.md and `pv-core/src/identity.rs`'s own doc comments name this as a known limitation mitigated by SEC-05's fingerprint display (Phase 26 UI), not by anything server-enforceable; accepted here with the rationale recorded, not silently ignored |
| T-22-10 | Denial of Service / data corruption | Concurrent keypair generation race | medium | mitigate | `ON CONFLICT DO NOTHING RETURNING` + self-healing canonical-fetch (Task 1) — no lost-update, no crash, no duplicate row; a losing device is told exactly which value to adopt |
