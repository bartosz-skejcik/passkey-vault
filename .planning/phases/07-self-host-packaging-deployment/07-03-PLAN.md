## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Reverse-proxy access logs (nginx/Caddy, outside `pv-server`'s own process/log sink) | Persist whatever the proxy is configured to log, independent of and after `main.rs`'s own `make_span` redaction — a proxy-side gap is invisible to any server-side control |
| `scripts/verify-container.sh`'s deliberately-broken-config sanity check | A throwaway, manually-triggered negative test — must never be left wired into a real CI path in a way that could accidentally ship a broken config as "validated" |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|------------------|
| T-07-07 | Information Disclosure | `deploy/nginx.conf.example` / `deploy/Caddyfile.example` access-log configuration | high | mitigate | Both reference configs strip or drop the query string for `/api/sync/ws` specifically; `scripts/verify-container.sh` asserts the absence of `token=` in each proxy's own access log after a real WS request, not just a prose claim |
| T-07-08 | Denial of Service | Reverse-proxy config silently missing WS-upgrade headers | high | mitigate | `scripts/verify-container.sh`'s WS-handshake assertion catches a missing/incorrect `Upgrade`/`Connection` header pair at doc-authoring/verification time, rather than a self-hoster's real users discovering broken sync reconnects in production |
| T-07-09 | Spoofing / Tampering | A self-hoster copies the example `server_name`/site address (`vault.example.com`) verbatim into a real deployment without customizing `PV_RP_ID`/`PV_ORIGIN` | low | accept | Plan 07-01's `Config::validate()` already rejects an incoherent `PV_RP_ID`/`PV_ORIGIN` pair regardless of what the reverse-proxy config's `server_name` says — the proxy-level placeholder is cosmetic, the actual enforcement point is server-side and already covered |
