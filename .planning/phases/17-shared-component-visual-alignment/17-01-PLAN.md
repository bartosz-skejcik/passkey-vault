<objective>
Resolve `packages/pv-ui`'s first-ever peer-dependency problem before any real `.tsx` component is
promoted into it. `pv-ui` has shipped pure `.ts`/`.css` since Phase 11 with zero runtime peer
dependencies; RESEARCH.md's `## Critical Finding` empirically proved that the moment it ships a
`.tsx` importing both `react` (which has its own `exports` map) and `lucide-react` (which does
not), Vite, Turbopack, and `tsc` all fail to resolve `lucide-react` from a file physically outside
either consumer's own `node_modules` tree -- a genuine, previously-undocumented failure mode, not a
hypothetical. This plan implements RESEARCH.md's verified fix (Option A): give `packages/pv-ui` its
own local `node_modules` for its 4 peer packages, wired into a new bootstrap step mirroring the
existing `predev`/`prebuild: bash ../scripts/build-wasm.sh` pattern, plus the Dockerfile line the
web-builder stage needs to materialize it in the container image. It also lands the Tailwind
`@source` directive both consumers need to pick up any CSS class used inside
`packages/pv-ui/components/**/*.tsx` -- a second, independent problem from module resolution
(RESEARCH.md Pattern 3/Anti-Patterns) that would otherwise silently ship an unstyled component with
zero build error.

**Flagged planner assumption (DS-03, edge-coverage category "unclassified", left unresolved by the
spec-less probe per this phase's planning instructions):** this plan's own smoke-test verification
is the mechanism proving "no duplicate React instance / classes survive content scanning in both
consumers" -- i.e. that `packages/pv-ui`'s own `node_modules/react` resolves to the SAME module
instance the consuming app's own React tree uses (not a second, incompatible React copy), and that
Tailwind's content scanner genuinely reaches `packages/pv-ui/components/**/*.tsx`. Both are asserted
here via live build/test evidence (Task 2), not by design inspection alone, precisely because this
edge case has no other spec-level resolution to lean on.

Purpose: unblock Plan 17-03's actual `ItemIconTile` promotion with a build pipeline that has already
been proven to work for a real `.tsx` importing both `react` and `lucide-react`, on every tool this
project's CI/build surface touches.
Output: `packages/pv-ui` ships a reproducible local `node_modules` for its 4 peer packages; both
consumers' `predev`/`prebuild` and the Dockerfile materialize it automatically; both consumers' CSS
entry points scan `packages/pv-ui/components/**/*.tsx` for Tailwind classes; a throwaway smoke
component proved all of Vite/Turbopack/tsc/WXT-Vite green before being deleted.
</objective>
