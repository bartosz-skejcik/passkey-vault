## Design System

| Property | Value |
|----------|-------|
| Tool | none |
| Preset | not applicable |
| Component library | DaisyUI 5 (web + extension popup React surfaces, Tailwind v4 pipeline); hand-authored CSS-in-JS strings (in-page closed-shadow-DOM overlays — no Tailwind reaches a shadow tree, no component library there by design) |

Phase 17's own goal statement is explicit alignment of that existing system across surfaces — "the smallest real component," not a design-system swap. Introducing shadcn here would contradict CONTEXT.md's "alignment, not redesign" framing and this run's autonomous/no-interactive-prompts constraint. Registry safety gate: not applicable (no registry use in this phase).

### Tile background/foreground tokens — the flagship fix (DS-04, resolves UX-01)

`packages/pv-ui/tokens.css` gains two new custom properties, declared inside the SAME blocks the shadow-DOM `[data-theme]` rewrite adapter (`inpage-theme.ts`) already transforms — no new carrier/stamping mechanism required:

```css
:root,
[data-theme="vault-dark"] {
  /* ...existing tokens unchanged... */
  --pv-tile-bg: oklch(96.7% 0.001 286.375);  /* = Tailwind v4 zinc-100, verified against tailwindcss/theme.css */
  --pv-tile-fg: oklch(44.2% 0.017 285.786);  /* = Tailwind v4 zinc-600, verified against tailwindcss/theme.css */
}

[data-theme="vault-light"] {
  /* ...existing tokens unchanged... */
  --pv-tile-bg: var(--color-base-200);
  --pv-tile-fg: color-mix(in oklch, var(--color-base-content) 70%, transparent);
}
```

**Why new tokens, not a reuse of an existing one:** web's/popup's React `ItemIconTile` already encodes this exact light-flip as Tailwind arbitrary-variant classes — `TILE_BG = "bg-base-200 [[data-theme=vault-dark]_&]:bg-zinc-100"`, `TILE_FG = "text-base-content/70 [[data-theme=vault-dark]_&]:text-zinc-600"` — and those classes are correct and stay **unchanged** in the promoted `pv-ui/components/ItemIconTile.tsx` (Tailwind, not a CSS custom property, is the React component's natural expression; do not convert it to `var(--pv-tile-bg)`). The in-page overlay has no Tailwind inside its closed shadow root, so it needs the identical resolved color expressed as a plain CSS custom property, sourced from `pv-ui` — that is exactly what `--pv-tile-bg`/`--pv-tile-fg` are for, satisfying DS-04's "the value must come from `pv-ui`, not be hand-copied" rule (CONTEXT.md, Claude's Discretion).

**In-page fix target**, `extension/lib/autofill/inpage-overlay.ts`:

```css
.pv-row-icon-tile {
  /* ...unchanged... */
  background: var(--pv-tile-bg);   /* was: var(--color-base-200) — THE dark-tile bug UX-01 names */
}
.pv-row-icon {
  /* new rule, or added declaration */
  color: var(--pv-tile-fg);        /* the fallback type-glyph needs the matching flip too */
}
```

**Scope — every in-page row tile, not just the two UX-01-named surfaces** (CONTEXT.md, locked decision): Surface A (`renderFieldDropdown`) and Surface B (`renderFormPrompt`) both route through the same `buildIconTile()`/`.pv-row-icon-tile` in `inpage-overlay.ts`, so one CSS fix covers both. `generate-popover.ts` and `save-update-toast.ts` render **no icon tile today** (verified by grep, 2026-07-21) — if either ever gains one, it MUST use `--pv-tile-bg`/`--pv-tile-fg`, never a literal or a bare `--color-base-200`.

**Favicon source rule — preserved verbatim, not a divergence to fix:** the in-page tile fetches `${doc.location.origin}/favicon.ico` (the *current page's* own origin), not a per-item resolved hostname. This is intentional, not a gap: every `AutofillMatch` rendered in-page is already origin-gated to the current page by the background match handler (Phase 10, D-02) — "the item's own domain" and "the current page's origin" are the same value in this context. `referrerPolicy="no-referrer"` stays. Do not attempt to route the in-page tile through the shared component's per-item hostname-resolution logic — there is no React/pv-ui component import path inside the shadow root (see DS-04 boundary below).

**Zero-knowledge favicon rule (hard security constraint, applies to BOTH the shared React component and the in-page tile):** every favicon fetch is a direct, uncached request straight to a domain the item/page already legitimately belongs to, with `referrerPolicy="no-referrer"` — **never** a third-party favicon proxy (Google/DDG/`s2` endpoints, etc.), **never** routed through `pv-server`. This is documented in the source headers as a zero-knowledge/privacy invariant (project CLAUDE.md Constraints) and MUST be preserved byte-for-byte through the `ItemIconTile` promotion.

## In-Page Token Contract (DS-04)

**Scope:** every hand-written style value in `extension/lib/autofill/{inpage-overlay,generate-popover,save-update-toast,mismatch-modal,inpage-mount}.ts` that has a corresponding `pv-ui` token MUST reference that token via `var(--...)`.

**Audit method** (mirrors Phase 16's zero-duplication grep-gate precedent — plans must include this as an explicit step): grep the five overlay files for hex/rgb/rgba/oklch color literals and bare radius values, then classify each hit:

- **Has a `pv-ui` token equivalent** (a color already in `tokens.css`, `--radius-box`, `--radius-field`, or the new `--pv-tile-bg`/`--pv-tile-fg` pair above) → replace with `var(--...)`, **adopting** the token's value even where it differs slightly from today's hand-copied number (CONTEXT.md locked decision: "ADOPT the token value... no pixel-freezing drifted values").
- **No `pv-ui` token equivalent** (box-shadow elevation `rgba(0,0,0,0.25|0.35|0.45|0.7)` used for panel drop-shadow and backdrop dimming; generic pill `border-radius: 999px` on the strength-meter track/fill and the toast's badge) → **out of scope this phase.** `pv-ui`/`tokens.css` has no shadow-elevation or generic-pill-radius token today; DS-04's contract covers de-duplicating an existing token, not inventing new token surfaces mid-phase. Leave these literals as-is; note as a future `pv-ui` token-surface candidate if raised again.

**Swept and confirmed already clean** (verified 2026-07-21 — no action needed): `--radius-box`, `--radius-field`, `--color-primary`, `--color-primary-content`, `--color-base-100/200/300/content`, `--color-error`, `--border` are already referenced via `var(...)` consistently across all five overlay files. **The only hand-copied/non-token color drift found in the sweep is `.pv-row-icon-tile`'s unconditional `background: var(--color-base-200)`** (missing the light-flip — the bug UX-01 names) and its sibling `.pv-row-icon` (missing the matching foreground flip). This is the primary — likely only — fix DS-04 requires in this phase.

**Definition of done:** grep for `background:\s*var\(--color-base-200\)` scoped to `.pv-row-icon-tile` returns zero matches; `.pv-row-icon-tile`/`.pv-row-icon` reference `--pv-tile-bg`/`--pv-tile-fg`; no new hex/rgb/oklch color literal is introduced anywhere in the five swept files as a byproduct of this change.
