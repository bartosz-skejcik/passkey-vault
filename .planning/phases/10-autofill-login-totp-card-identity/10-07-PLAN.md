  <files>extension/e2e-fixtures/adversarial-iframe/top.html, extension/e2e-fixtures/adversarial-iframe/attacker-frame.html, extension/e2e-fixtures/adversarial-iframe/legit-login.html, extension/e2e-fixtures/adversarial-iframe/serve.mjs, extension/e2e-fixtures/adversarial-iframe/README.md</files>
  <read_first>.planning/phases/10-autofill-login-totp-card-identity/10-RESEARCH.md, extension/entrypoints/content-relay.content.ts</read_first>
  <action>
  Build a minimal, self-contained, checked-in two-origin harness. Use two genuinely distinct origins so the cross-origin boundary is real — two ports on `127.0.0.1` are sufficient for the browser's origin model (scheme+host+port), and using `localhost` for one and `127.0.0.1` for the other gives two distinct hostnames as an even clearer signal. Pick placeholder names only — this is a security test artifact, never an impersonation of a real brand (frontmatter prohibition).

  `serve.mjs` — a tiny Node `http.createServer` static server (no dependencies) that can be launched twice on two ports (`node serve.mjs 8791 A` / `node serve.mjs 8792 B`), each serving this directory. Set permissive but explicit headers so the iframe embeds (`X-Frame-Options` absent/`ALLOWALL`; do NOT set a `frame-ancestors` CSP that would block the embed — the whole point is to embed cross-origin).

  `top.html` (served as Origin A, e.g. `http://127.0.0.1:8791/top.html`) — the top-level page. Contains: (1) Origin A's OWN login form (`<input autocomplete=username>` + `<input type=password autocomplete=current-password>`), the LEGITIMATE fill target; and (2) an `<iframe src="http://localhost:8792/attacker-frame.html">` — a genuinely cross-origin embed (different host+port) — visually styled to look like part of Origin A's page, containing a login form that mimics Origin A's.

  `attacker-frame.html` (served as Origin B) — the cross-origin iframe's content: a login form (username + password) dressed to look like it belongs to Origin A. This is the frame that MUST NOT receive Origin A's saved credential.

  `legit-login.html` (served as Origin A) — a plain same-origin login page for the positive-path check (the credential SHOULD fill here). Optionally include a TOTP field (`autocomplete=one-time-code`), a card form (proper `cc-*` autocomplete), and an identity form so the one harness exercises all four FILL kinds' positive paths.

  `README.md` — the SC #5 UAT script (Task 2 executes it): how to build+load the unpacked extension (`npx wxt build`, load `.output/chrome-mv3` unpacked), launch both server origins, configure the extension to point at a running `pv-server`, unlock, save a login attributed to Origin A, then the exact click-by-click verification steps and pass/fail criteria. Document the same steps for `wxt build -b firefox` + `about:debugging`, noting Firefox may be unavailable in this environment (10-RESEARCH.md Environment Availability) — Chrome is the blocking pass, Firefox is strongly-recommended-if-available (defer a hard Firefox gate to Phase 13).

  Optionally add a Playwright driver stub (persistent context + `--load-extension`, authorized per project memory) that automates the load+navigate+click sequence to accelerate re-runs — but the durable cross-browser Playwright harness is Phase 13's 13-03, so keep this lightweight and do not over-invest here.
  </action>
