<objective>
Implement the deterministic half of field detection: login (username + password) and TOTP (one-time-code) — the two field families that have a standardized, near-universal markup signal and therefore need no confidence scoring (D-06).

Purpose: FILL-01 and FILL-02 depend on finding the right inputs with a very low false-positive rate. 10-RESEARCH.md Pattern 3 is explicit that these two are deterministic and must NOT be routed through the card/identity scorer — keeping them separate stops the scorer's necessary fuzziness from leaking into the highest-frequency, highest-trust path.
Output: `detect-login.ts` and `detect-totp.ts` as pure, jsdom-tested functions over a DOM root.
</objective>

  <name>Task 1: detect-login.ts — deterministic login/signup form detection</name>
  <files>extension/lib/autofill/detect-login.ts, extension/lib/autofill/detect-login.test.ts</files>
  <read_first>extension/lib/autofill/types.ts, .planning/phases/10-autofill-login-totp-card-identity/10-RESEARCH.md</read_first>
  <behavior>
    - Test 1: a classic `<form>` with `<input name=user autocomplete=username>` + `<input type=password autocomplete=current-password>` returns both elements and `mode: "login"`.
    - Test 2: a page with TWO independent forms (a newsletter form with an email input, and a login form with username+password) pairs the username from the LOGIN form with that form's password field — never the newsletter email. Assert the returned username element is the one inside the login form.
    - Test 3: a signup form (`autocomplete=new-password`, plus a confirm-password field) returns `mode: "signup"`, not `"login"`.
    - Test 4: a password field with NO username sibling (e.g. a second-step "enter your password" screen) still returns the password field with `username: null` — the fill must still work for password-only steps.
    - Test 5: a page with no password input at all returns `null`.
    - Test 6: a `type=password` input that is `disabled`, `readonly`, `hidden`, or has `display:none` on itself is skipped (hidden honeypot/anti-bot fields are common on real login forms and filling them is a tell).
    - Test 7: fields inside a `<form>` are preferred, but a formless login (bare divs, common in SPAs) still resolves by proximity — a username input that is the nearest preceding text/email input to the password field.
  </behavior>
  <action>
  Create `extension/lib/autofill/detect-login.ts` exporting `detectLogin(root: Document | Element): LoginFieldSet | null` where `LoginFieldSet = { mode: "login" | "signup"; username: HTMLInputElement | null; password: HTMLInputElement; confirmPassword: HTMLInputElement | null }`.

  Algorithm (deterministic, NO scoring — D-06):
  1. Query all `input[type="password"]` under `root`. Filter out non-fillable ones: `disabled`, `readOnly`, `hidden`, `type=hidden`, zero-size (`offsetParent === null` is unreliable in jsdom — instead check the `hidden` attribute, `disabled`, `readOnly`, and an inline `display:none`/`visibility:hidden` style; document that full visibility checking is a real-browser concern the content-relay layer may refine).
  2. If none remain → return `null`.
  3. Determine `mode`: `"signup"` when any remaining password field has `autocomplete="new-password"`, or when two or more fillable password fields exist in the same form (the confirm-password shape). Otherwise `"login"`. Export the signup discrimination even though Phase 10 only fills logins — 10-CONTEXT.md's Deferred Ideas records that Phase 11 (CAP-01/CAP-02) must reuse this detector rather than rebuild it, and returning `mode` now is what makes that reuse possible without a second scan.
  4. Choose the primary password field: the first `current-password` if present, else the first fillable password field.
  5. Find the username: within the primary password field's closest `<form>` (or, when formless, within `root`), prefer in order — `autocomplete="username"`, then `autocomplete="email"`, then `input[type="email"]`, then the nearest preceding `input[type="text"]`. Scope the search to the SAME form as the password field whenever a form ancestor exists; this is what stops the multi-form mispairing in Test 2. Never return a username from a different `<form>`.

  Do not import anything from `pv-wasm`, `pv-core`, or the extension's crypto choke-point. This module is DOM-only and runs in the content script's ISOLATED world; it must remain grep-clean of crypto imports (10-PATTERNS.md "Zero-knowledge choke-point").

  Write `detect-login.test.ts` with the 7 behaviors, using jsdom (per-file `// @vitest-environment jsdom` docblock, matching whatever mechanism plan 10-01 configured). Build fixtures as inline HTML strings assigned to `document.body.innerHTML` — no network, no real sites.
  </action>

<task type="auto" tdd="true">
  <name>Task 2: detect-totp.ts — one-time-code detection with a bounded fallback</name>
  <files>extension/lib/autofill/detect-totp.ts, extension/lib/autofill/detect-totp.test.ts</files>
  <read_first>extension/lib/autofill/detect-login.ts, extension/lib/autofill/types.ts</read_first>
  <behavior>
    - Test 1: `<input autocomplete="one-time-code">` is returned regardless of its other attributes — the standardized signal wins outright.
    - Test 2: with no `one-time-code` field, an `<input inputmode="numeric" maxlength="6">` labelled "Verification code" is returned by the fallback.
    - Test 3: an `<input type="password">` is NEVER returned as an OTP field, even if it has `inputmode="numeric"` and a short maxlength.
    - Test 4: an `<input autocomplete="cc-csc" maxlength="3">` (a card CVV) is NEVER returned by the fallback — a checkout page must not have its CVV box treated as a 2FA field.
    - Test 5: a bare `<input inputmode="numeric">` with NO maxlength and no code-ish label is NOT returned (the fallback requires corroboration; an unbounded numeric input is a quantity box as often as a code box).
    - Test 6: returns `null` when nothing qualifies.
  </behavior>
  <action>
  Create `extension/lib/autofill/detect-totp.ts` exporting `detectTotp(root: Document | Element): HTMLInputElement | null`.

  Two tiers, in strict order (10-RESEARCH.md Pattern 3):
  1. **Standardized:** first fillable `input[autocomplete="one-time-code"]`. Return immediately if found.
  2. **Fallback (only if tier 1 found nothing):** an input qualifying on ALL of — not a `type=password`; not `autocomplete="cc-csc"`/`cc-number`/any `cc-*` token; `inputmode="numeric"` OR `type="tel"` OR `pattern` containing `\d`; a `maxlength` between 4 and 8 inclusive; AND a code-ish textual cue within its own `name`/`id`/`placeholder`/`aria-label` or its associated `<label>` text, matched against a small explicit vocabulary — include at minimum: `otp`, `totp`, `2fa`, `mfa`, `code`, `token`, `verification`, `authenticator`, and the Polish `kod` (the product's primary UI language is Polish; a Polish-language site is a first-class case, not an afterthought).

  The `cc-*` exclusion is load-bearing, not defensive padding: a checkout page is exactly where a short numeric field with a `maxlength` of 3-4 lives, and filling a TOTP code into a CVV box would be both a visible bug and a trust breach. Test 4 pins it.

  Bound every string read from the DOM before matching (cap at, say, 200 chars) — these attributes are attacker-controlled input from an untrusted page (10-RESEARCH.md ASVS V5); a pathologically long `aria-label` must not become a performance problem in the matcher.

  Reuse `detect-login.ts`'s fillable-field predicate rather than writing a second one — export it from `detect-login.ts` or lift it into a small shared local helper if that reads better; do not duplicate the logic.

  Write `detect-totp.test.ts` with the 6 behaviors under jsdom.
