<architecture_note>
**READ THIS BEFORE WRITING CODE — two settled decisions that contradict a naive reading of 10-RESEARCH.md.**

**1. Transport topology is popup-driven, not content-driven.** 10-UI-SPEC.md ("Scope Note") resolves 10-CONTEXT.md's open discretion area: Phase 10 adds **no in-page UI**. `content-relay` is a pure DOM sensor/writer. Every gesture and the multi-account picker live in the popup. So the flow is:

```
popup --(runtime.sendMessage: autofill.match/fill)--> background --(tabs.sendMessage {frameId}) --> content-relay
```

NOT the `content-relay -> background` flow 10-RESEARCH.md's System Architecture Diagram draws. That diagram was written against the in-page-affordance option the UI-SPEC subsequently rejected. **Pattern 1 (two-phase match-then-fill) survives intact. Pattern 4 (`sender`-based frame verification) must be RE-DERIVED, not copied** — see (2).

**2. `sender` proves nothing about the target page when the sender is the popup.** In a popup-driven flow the `autofill.fill` request's `sender` is an extension page: `sender.tab` is `undefined` and `sender.frameId` is meaningless. Copying 10-RESEARCH.md Pattern 4's `sender.frameId !== 0` check here would be security theater. The background must instead **independently derive the target frame's origin from platform APIs it queries itself** (`browser.tabs.get(tabId).url`), and address the fill to an explicit `frameId`. `sender`-based verification still applies — but only to messages that genuinely originate from a content script.

**3. Background entrypoint layout is NOT yet settled — confirm before writing paths.** Phase 8 (plan 08-01, executed) shipped `extension/entrypoints/background.ts` as a **flat file**. Phase 9's 09-02-PLAN.md assumes a **directory** (`extension/entrypoints/background/index.ts` + `router.ts` + `vault-session.ts`), which is a legal WXT entrypoint layout but requires converting the flat file. Every `extension/entrypoints/background/*` path in this plan and in 10-04 assumes Phase 9 performed that conversion. **At execution time, check which layout actually exists** (`ls extension/entrypoints/`) and place `frame-guard.ts`/`router.ts` accordingly; if Phase 9 kept the flat `background.ts`, put this plan's background modules in `extension/entrypoints/background/` anyway and have `background.ts` import them — do not block, and record the resolved layout in the SUMMARY. Note also that WXT auto-imports `defineBackground`/`defineContentScript` and provides the `@/` → project-root alias via `.wxt/tsconfig.json`; follow the existing files' conventions rather than adding explicit imports.

**4. Do NOT add `@webext-core/messaging`.** 10-RESEARCH.md recommends it, but Phase 9's 09-02-PLAN.md already locks a hand-rolled typed contract (`Message` union + `MessageResponseMap` + `sendMessage`) and a `switch (message.kind)` router explicitly designed for later plans to extend by adding cases. 10-RESEARCH.md's own Structure Rationale settles the conflict: *"lib/messaging/ext-protocol.ts is additive, not a new file tree… Phase 10's plan should extend that existing ProtocolMap, not create a parallel one — verify Phase 9's actual output before assuming."* Adopting the library now would mean either two parallel messaging systems or rewriting Phase 9's unexecuted contract mid-stream. D-09's requirement is "a typed contract layer" — Phase 9's hand-rolled union already satisfies it. **This is a deliberate, recorded deviation from RESEARCH's Standard Stack; the phase adds zero new npm dependencies.**
