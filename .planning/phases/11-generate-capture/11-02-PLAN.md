Output: `form-detector.ts`, `submit-capture.ts`, both fully unit-tested against synthetic DOM fixtures covering classic forms, SPA `<form>`-less containers, and error-signal suppression.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Page DOM (any world, untrusted) -> ISOLATED content script | `form-detector.ts`/`submit-capture.ts` read page-controlled DOM state (form structure, field values, URL, presence of error elements) — the page can shape all of these inputs adversarially. |
| ISOLATED content script -> background service worker | `content-relay.content.ts`'s outbound call: `sendMessage({kind:'capture.propose', ...})`, self-reporting `frameOrigin` (X-1: `submit-capture.ts` itself is a pure DOM lib with no messaging import; the outbound call is wired in content-relay.content.ts's onSuccess callback, gated per X-4). |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|------------------|
| T-11-04 | Spoofing | `submit-capture.ts` captureFrameOrigin() | high | mitigate | captureFrameOrigin() reads ONLY its own frame's `location.origin`, never `window.top`/`window.parent` (which could be cross-origin-inaccessible or misleading) — the value it self-reports is used purely as a display-copy candidate; Plan 11-03's background handler independently re-derives the trusted top-level origin from `sender.tab.url` and never accepts this plan's self-report as ground truth for the mismatch decision (D-06, full mitigation lands in Plan 11-03/11-05). |
| T-11-05 | Tampering | `submit-capture.ts` success heuristic | medium | mitigate | A page could rapidly mutate its own DOM to force a false-positive "success" signal before real authentication completes. Mitigated structurally: the heuristic only ever triggers a user-facing PROMPT (built in Plan 11-05), never an automatic save — the user must explicitly click Save/Update before any vault write occurs (RESEARCH.md's "Auto-saving on a heuristic without a user-confirm step" anti-pattern). |
| T-11-06 | Information Disclosure | `submit-capture.ts` (captured plaintext in ISOLATED-world variables) | low | accept | The submitted password briefly exists as a plaintext JS value in the ISOLATED content-script world before being relayed once to the background. Accepted: this is the same page the user just typed their own password into; the value is never persisted client-side by this plan, never logged, and is relayed exactly once over the trusted extension-internal messaging channel. |
| T-11-17 | Information Disclosure | `content-relay.content.ts` submit-capture activation | low | mitigate | X-4: `attachSubmitWatcher` is only ever wired up after `isConfiguredServerOrigin()`/`isOriginBlocked(location.origin)` both pass — the user's own configured vault app and any user-blocked origin never get a submit-capture listener at all, mirroring the Phase 10 overlay's identical suppression. |
