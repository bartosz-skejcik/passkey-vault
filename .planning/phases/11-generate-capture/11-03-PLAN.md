<objective>
Implement the background-side brain of Generate & Capture: classify a proposed submit against the already-decrypted vault (new / update / no-op), independently verify the frame-vs-top origin relationship the way only the trusted `runtime.onMessage` sender object allows, and encrypt-then-persist the resulting login item using the exact pattern v0.1's web app already proved correct.

Purpose: This is where CAP-02 ("prompt to save, attributed to the correct origin") and CAP-03 ("detect a password change and offer update, not duplicate") actually decide what happens — and where D-06's origin-mismatch security requirement gets its one authoritative implementation, independent of anything a compromised page or content script could claim. Password-change detection (D-05) is built here as a diff against an already-matched existing item, reusing the same submit-capture plumbing as save-new-login, not a separate feature.
Output: `capture-handler.ts` with classification, origin verification, and encrypt/persist logic, all unit-tested; `capture.propose`/`capture.confirm` wired into the background router.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| ISOLATED content script -> background service worker | `capture.propose`/`capture.confirm` messages arrive here; the browser-attached `sender` object (tab/frame/url) is the only tamper-proof signal available. |
| background service worker -> `chrome.storage.session` | Every persist call must re-read the unlocked-key envelope at call time, never trust an earlier in-memory reference (MV3 idle-kill). |
| background service worker -> pv-server | `createItem`/`updateItem` REST calls carry only the encrypted `{enc_key, enc_data}` blob — never plaintext. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|------------------|
| T-11-07 | Spoofing | `router.ts` capture.propose/capture.confirm handlers | high | mitigate | `topOrigin` is derived exclusively from `sender.tab.url` (browser-supplied, tamper-proof) — the content script's self-reported `frameOrigin` is used only as a display candidate cross-checked against this trusted value, never accepted as the mismatch decision's ground truth (D-06, this is the phase's core mitigation for the Pitfall 7 / historical Bitwarden CVE-class bug). |
| T-11-08 | Tampering | `confirmUpdateLogin` | medium | mitigate | A stale `capture.confirm` replayed after the item was already updated elsewhere (multi-device sync race) is caught by the 409/`isConflictError`/`RevisionConflictError` path reused verbatim from `store.ts` — refetch-and-surface, never a silent overwrite. |
| T-11-09 | Information Disclosure / Denial of Service | `confirmNewLogin`/`confirmUpdateLogin` vs. MV3 idle-kill | high | mitigate | Both functions re-read `chrome.storage.session` at call time and throw `LockedVaultError` on an absent/stale key rather than proceeding with an invalid handle or silently no-op'ing (D-02, project-wide MV3 invariant). |
| T-11-10 | Denial of Service | `classifySubmit` matching scan | low | accept | A page that fires many submit events could trigger repeated linear scans over the decrypted in-memory vault. Accepted: matching is a bounded, in-memory, no-network/no-crypto operation over a single user's own already-decrypted vault — not a meaningful DoS vector for a single-user self-hosted deployment. |

</threat_model>
