<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| ISOLATED content script -> background service worker | `runtime.sendMessage`/`onMessage` — the trusted, browser-mediated internal channel this plan's new message kinds travel over. No page/MAIN-world code sends these messages directly. |
| background service worker -> `chrome.storage.session` | Not touched by generation itself (generator needs no key material) but the same router this plan extends will later carry `capture.*` traffic that does. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|------------------|
| T-11-01 | Tampering | `generate-handler.ts` | low | mitigate | Reject out-of-range `length`/`wordCount` (and any thrown generator error) with a typed `{error}` response rather than letting a malformed request crash the router or hang on an unbounded loop. |
| T-11-02 | Information Disclosure | `generate-handler.ts` | medium | mitigate | The generated password string is never written to `console.log`/`tracing`-equivalent output — it crosses only in the `{password}` response payload back to the requesting content script. |
| T-11-03 | Tampering | `ext-protocol.ts` (all 3 new kinds) | medium | mitigate | Apply the same runtime-shape validation Phase 9's existing message kinds already use to these three new kinds, so a malformed/oversized payload is rejected before it reaches any handler — not just this phase's handlers, but the shared router's overall robustness. |

</threat_model>
