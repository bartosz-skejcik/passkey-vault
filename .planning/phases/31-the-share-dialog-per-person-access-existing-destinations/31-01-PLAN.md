<objective>
Add the two server-side routes 31-RESEARCH.md's Q2 identifies as missing: `PUT /api/vault/collections/{id}/access/{user_id}` and `PUT /api/vault/items/{id}/shares/{user_id}`. Today, changing an already-granted recipient's access level has no server mechanism at all — `add_member`/`create_share` both `INSERT ... ON CONFLICT DO NOTHING`, so a duplicate grant 409s instead of updating. A `collection_keys`/`item_shares` row's `sealed_key` never needs to change for a level edit (it is the SAME Collection Key/Item Key the recipient already holds); this makes the fix a single, narrow `UPDATE ... SET access_level = ?` statement — no re-seal, no client-side crypto, no revoke-then-add intermediate window.

This is Wave 1 because every later ShareDialog plan's "update" dispatch branch calls the client wrapper this plan creates.

Purpose: close the "editable in place" half of MOD-01 — a member who already has access must be able to have their level changed by editing the SAME row they're shown in, not by a client-side revoke-then-re-add pair.
Output: two new PUT routes, byte-identical in authorization shape to their existing grant siblings, full auth-matrix test coverage, and thin client wrappers ready for ShareDialog's dispatch logic.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Authenticated browser client -> new PUT routes | An authenticated but potentially buggy/malicious client sends a level-change request naming an arbitrary (resource, recipient) pair and a chosen access_level string. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-31-01 | Elevation of Privilege | `collections::update_access` | high | mitigate | Reuses `may_grant_access_level`/`RequireEdit::satisfied_by` verbatim from `add_member` — a `read`-only caller cannot grant/edit another recipient beyond what they themselves hold; proven by the full 9-pair matrix (Task 2) and the dedicated self-escalation regression test. |
| T-31-02 | Elevation of Privilege | `collections::update_access` on an `item_bucket` collection | high | mitigate | `enforce_item_bucket_declared_level_bound` applied identically to `add_member` (the same shared definition, `membership.rs::enforce_item_bucket_declared_level_bound`) — a self-escalated contributor (260812-01e's mechanism) cannot use this new UPDATE path to hand another member a level beyond the bucket's own declared level. Both `Declared` and `LegacyUnknown` states covered (Task 2). |
| T-31-03 | Tampering | Request body of both new PUT routes | medium | mitigate | `parse_access_level_from_request` fail-closed validation before any DB work — an unrecognized `access_level` string is a clean 400, never coerced or silently accepted. |
| T-31-04 | Information Disclosure | Wire shape of both new PUT routes | low | accept | Request/response bodies deliberately carry only `{ access_level }` — no `sealed_key` field exists on either struct, so there is nothing for the server to receive, store, or (as ever) unwrap; a future change adding a `sealed_key` field to either route should be treated as a regression against this plan's own stated invariant. |
| T-31-05 | Denial of Service | `UPDATE ... SET access_level` statement shape | low | accept | Single-statement, atomic by SQLite's own guarantee — no intermediate state, no lock contention beyond what any other single-row write already has. |

Package Legitimacy Audit: not applicable — this plan introduces no new npm/cargo/pip dependencies (confirmed by 31-RESEARCH.md's own audit).
