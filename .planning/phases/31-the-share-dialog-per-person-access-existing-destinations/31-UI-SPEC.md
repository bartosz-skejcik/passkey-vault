# Phase 31 — UI Design Contract

> Visual and interaction contract for MOD-01/02/03 + ORG-03 (the share dialog becomes the access
> picture for one destination: one row per family member with a per-person level control that
> includes "brak dostępu", a destination selector above the rows, and honest destination-existing
> semantics). Generated by gsd-ui-researcher, verified by gsd-ui-checker. Read against the real
> `ShareDialog.tsx` (1441 lines) as it stands after Phase 30 + quick task 260812-01e — every
> component/state/string named below is either an existing, cited codebase element or an explicitly
> new one. Out of scope: the Family & Sharing settings surface (Phase 33), the item editor's
> destination picker (Phase 32), the "what am I exposing" inventory (Phase 34).

## Typography

Three sizes, two weights — no new size beyond what the codebase already uses in this file.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Display (inherited dialog title tier) | 20px | 700 | 1.2 |
| Heading (section labels) | 14px | 700 | 1.5 |
| Body (load-bearing honesty paragraphs) | 16px | 400 | 1.5 |
| Label (row identity, meta text) | 14px | 400 | 1.5 |

- **Display (20px/700/1.2)** is unchanged — the same `text-[20px] font-bold leading-[1.2]` dialog
  title (`ShareDialog.tsx:1224`). Not re-derived here.
- **Heading and Label are the same 14px size, differing only by weight** — the codebase's own
  established pattern (`ShareDialog.tsx:1301`/`:1329`, `"text-sm font-bold"` for
  "Komu udostępnić"/"Poziom dostępu" next to plain `"text-sm"` recipient rows). **New in this
  phase:** the destination-selector label ("Miejsce udostępnienia") and each row's "Obecnie: {level}"
  subtitle both use this exact pairing — Heading for the selector's own label, Label for the
  subtitle and the row's email, matching the file's existing convention rather than inventing a
  third weight.
- **Body (16px/400/1.5)** is used exactly once, newly and genuinely: the pending-revocations
  summary paragraph (`share-pending-revocations-summary`) reuses `RevokeShareDialog.tsx:132`'s own
  `text-base` class verbatim — the SAME size its single most load-bearing honesty sentence
  (`share.revokeBody`) already uses. This is a deliberate size match, not a coincidence: both
  sentences carry the identical "this cannot be undone for what they've already seen" weight, and
  reusing the established size for that weight-class of copy is the correct move, not an
  arbitrary escalation from the row-level 14px text around it.

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `base-100`/`base-300` (unchanged) | Dialog card background, unchanged from every prior phase |
| Secondary (30%) | `base-300` border, `base-200` | Row-list `divide-y divide-base-300` separators (replaces the old `max-h-48 overflow-y-auto` flat list — see Scale contract); the new footer's `border-t border-base-300`; the boxed "Cała rodzina" row (unchanged, `rounded-field border border-base-300`) |
| Accent (10%) | `secondary` (`#8DCDFF`) | Reserved for exactly two elements: (1) the "Cała rodzina" row's `Users` icon (unchanged from Phase 30), (2) the **new** `UserCheck` icon prefixing a person row that currently holds access to the chosen destination. Both read as "this row/state is about sharing" — the same accent vocabulary Phase 30 already established (`AvatarStack`'s icon variant, `ItemRow`'s `sharedToMe` marker), extended to one new element rather than a new color. |
| Destructive | `error` (`#FF5861`) | **Genuinely introduced in this phase** (Phase 30 explicitly did not need it). Reserved for exactly three elements: (1) the `UserMinus` icon + row text on a row whose pending value is "Brak dostępu" while its current value is NOT — i.e., an active pending revocation; (2) the `AlertTriangle` icon beside `share-pending-revocations-summary`, mirroring `RevokeShareDialog.tsx:117`'s identical icon+color pairing; (3) `share-error`/`share-partial-error` (unchanged, pre-existing `text-error` role). |

`primary` (koral) stays reserved for the Save/Share submit button (`btn-primary`) only, exactly as
UI-DESIGN.md states ("koral zarezerwowany dla akcji i brandu, nie dla ostrzeżeń") — never applied
to a revocation-adjacent element, even though the submit button is the SAME control that commits a
revocation. The button's **label text**, not its color, is what changes when the pending set
contains removals (see Copywriting Contract) — color signals "this is the primary action", text
signals "here is specifically what it will do", and the two are not conflated.

**Distinguishing "has access" from "no access" is never color-alone**, per the design brief's own
constraint. Three independent, non-color signals compound: (1) icon shape (`UserCheck` vs. no
icon / plain row), (2) a text subtitle ("Obecnie: {level}") that is textually present only on
rows with existing access, (3) the row's own `<select>` value, which starts pre-filled at the
person's real current level rather than at a neutral default. A colorblind user, a screen-reader
user, and a sighted user each reach the same conclusion through a different one of these three
channels.

## Copywriting Contract

Every string below is either an EXACT reuse of an existing key (cited by file:line) or explicitly
marked NEW. **`access.readOnly`/`access.fullEdit`/`access.hiddenPassword` are reused verbatim per
MOD-03 and are never reworded anywhere in this table** — every new string below is additive
vocabulary (a 4th row state, a destination concept, a save-vs-share distinction), never a
rephrasing of those three.

| Element | Copy |
|---------|------|
| Primary CTA — fresh folder creation (destination = "Nowy folder…") | **Unchanged.** `share.ctaFolder` ("Udostępnij folder"/"Share folder", `ShareDialog.tsx:1168`) — this path is byte-identical in meaning to today's folder-create flow. |
| Primary CTA — fresh item share (item currently has zero recipients across all rows) | **Unchanged.** `share.ctaItem` ("Udostępnij item"/"Share item"). |
| Primary CTA — editing an **existing** destination's access picture (destination = an existing shared folder, OR an item that already has ≥1 recipient among the standing rows) | **NEW** `share.ctaSaveAccess`: pl "Zapisz dostęp", en "Save access". This folder/item is already shared with someone — the action is reconciling WHO can see it, not "sharing" it for the first time; MOD-01's own framing ("the dialog becomes the access picture for the chosen destination") is what this CTA states honestly. Selected by: `destination.kind === "existing"` (folder scope) OR (item scope AND at least one row's *current* level is non-null). |
| Row's 4th access-level option (per-row `<select>`, alongside the reused `access.readOnly`/`access.fullEdit`/`access.hiddenPassword`) | **NEW** `access.none`: pl "Brak dostępu", en "No access". A genuinely new state, not a reword of the three protected strings — those describe what a grant DOES; this describes the absence of one, which those three vocabulary items have never needed to express (the old UI expressed "no access" via an unchecked checkbox, never a label). |
| Destination selector label | **NEW** `share.destinationLabel`: pl "Miejsce udostępnienia", en "Destination". |
| Destination selector — "mint new" option | **NEW** `share.destinationNewFolderOption`: pl "Nowy folder…", en "New folder…" — deliberately distinct wording from the pre-existing `folder.pickerCreateNew` ("+ Nowy udostępniony folder", `dictionary.ts:1531`), which is a separate component's BUTTON label, not a `<select>` option; reusing it verbatim inside an `<option>` would read as a stray "+" prefix with no button semantics behind it. |
| Destination selector option-group labels | **NEW** `share.destinationNewGroupLabel`: pl "Utwórz nowy", en "Create new"; **NEW** `share.destinationExistingGroupLabel`: pl "Istniejące foldery", en "Existing folders" — native `<optgroup>` labels, read by screen readers, visually grouping the mint-new option from real existing-folder names so a 15-folder family's `<select>` doesn't read as one undifferentiated list. |
| Row subtitle — has existing access | **NEW** `share.rowCurrentlyLabel` (interpolated `{level}`): pl "Obecnie: {level}", en "Currently: {level}". `{level}` is `t(accessLevelKey(currentLevel))` — i.e. this string interpolates the SAME reused `access.*` vocabulary, never a second copy of those words. Rendered only when the row currently holds a grant; absent entirely otherwise (this absence IS part of the has-access/no-access distinguishing mechanism — see Color). |
| Row — no published identity key (row-level, proactive) | **NEW** `share.rowNoPublishedKey`: pl "Brak opublikowanego klucza — nie można udostępnić.", en "No published key — can't share with them." Renders under a row whose person has `public_key === null`; that row's `<select>` is disabled and locked to `access.none` — see Row Anatomy. This resolves SC5's "refused with an honest message" case for THIS specific cause proactively (before submit is even attempted) rather than reactively (T-25-16's existing throw-before-network guard, `assertRecipientsHavePublicKeys`, stays as defense-in-depth for any row this UI-level guard somehow missed — never removed). |
| Destination unavailable (SC5, the OTHER named refusal cause) | **NEW** `share.destinationUnavailable`: pl "Nie można udostępnić — brak dostępu do klucza tego miejsca docelowego.", en "Can't share — no access to this destination's key." Renders in the same `share-error` slot `submitError` already uses, when the caller's own `getCollection(id).sealed_key` is unexpectedly `null` for the selected existing destination (a genuine, if rare, refusal case new to this phase's "target an existing folder" path — the fresh-create path can never hit this, since the caller always seals their own copy at creation time). Deliberately NOT `share.createFailed`'s retry-inviting copy — this failure is not retryable by simply clicking Save again, mirroring the precedent `FamilyWideKeyPendingError` set in Phase 30 (a known, named cause gets its own honest copy instead of a generic "try again"). |
| Pending-revocations summary (below the row list, above the footer) | **NEW** `share.pendingRevocationsSummary` (interpolated `{count}`, `{names}`): pl "Zapisanie cofnie dostęp {count} os.: {names}. Cofnięcie dostępu nie cofa tego, co już zobaczyli.", en "Saving will revoke access for {count} people: {names}. Revoking access doesn't undo what they've already seen." `{names}` is a comma-joined email list, mirroring `share.partialShareFailed`'s existing join(", ") convention (`ShareDialog.tsx:1396`) — no separate "too many, collapse to count" branch, since no sibling string in this codebase has one either. `{count} os.` sidesteps Polish plural-form agreement exactly as `share.seedFolderSummary`'s "{count} elem." already does. Renders **only** when ≥1 row's pending value is `none` while its current value is not — i.e., only when a real revocation is queued. |
| Hidden-password disclosure — one-time blocking modal | **Unchanged.** `share.hiddenPasswordDisclosureTitle`/`Body`/`Ack` (`dictionary.ts:1197-1208`), same per-account `localStorage` ack mechanism, same blocking `hidden-password-ack` `DialogState` — only the TRIGGER condition changes: fires the first time ANY row's select value becomes `hidden_password` (was: the single global radio becoming `hidden_password`), never per-row. |
| Hidden-password disclosure — quiet inline note, below the list | **Unchanged.** `share.hiddenPasswordInlineNote` (`dictionary.ts:1209`) + `share.hiddenPasswordRecipientFallback` (`dictionary.ts:1223`), reusing the EXACT existing WR-04 multi-subject logic (`ShareDialog.tsx:1161-1166`) re-scoped from "selected recipients" to "rows currently at `hidden_password`": exactly one such row → that person's email; two or more → the generic fallback subject. Renders **once**, below the row list (see Row Anatomy / Scale contract for "below the fold" handling), the moment ≥1 row is at `hidden_password` — never per-row, per the locked decision against "text flooding". |
| Empty state — solo family (no other members at all) | **Unchanged.** `share.noOtherMembers` (`dictionary.ts:1238`). |
| Total failure | **Unchanged.** `share.createFailed`, rendered in `share-error` for any cause other than the two newly-named ones above. |
| Partial failure (some rows' additions/edits did not land) | **Unchanged.** `share.partialShareFailed`, rendered in `share-partial-error`. |
| Revocation confirmation | **No second dialog.** Per the locked "not today's checkbox-then-reveal pattern" spirit and MOD-01's single-submission model (SC1: "a single submission naming two people at two different levels"), a per-row "brak dostępu" toggle does NOT open `RevokeShareDialog` or any other stacked confirm — the row's own visual state (icon + color + "Obecnie" mismatch) plus the pinned `share-pending-revocations-summary` paragraph together carry the same honesty weight `RevokeShareDialog.tsx`'s confirm text does, without a second click. `RevokeShareDialog` itself is untouched and keeps serving `SharingOverviewPanel`'s own single-grant revoke action — a different surface, unaffected by this phase. |
| Destructive confirmation reasoning | Matches `RevokeShareDialog.tsx`'s own documented tier justification verbatim: revocation inside this dialog has the SAME "zero re-key cost from the user's point of view, one clean save-and-done action" shape `RevokeShareDialog` already argues for its own single-step tier — a SECOND confirm step here would be redundant with the pending-revocations summary already shown, not additive safety. |

## Destination Selector Contract (MOD-02, ORG-03)

Rendered **only** for `scope.kind === "folder"`. For `scope.kind === "item"` there is no
destination concept in this phase's scope — a bare item's per-person rows always resolve to
direct `item_shares` grants (`createItemShare`/`revokeItemShare`), exactly as today; moving an
item INTO an existing folder from this dialog is explicitly Phase 32's surface (ORG-01), not this
one's.

```
<div className="flex flex-col gap-1">
  <label htmlFor="share-destination-select" className="text-sm font-bold">
    {t("share.destinationLabel")}
  </label>
  <select
    id="share-destination-select"
    data-testid="share-destination-select"
    className="select select-bordered w-full"
    value={destinationId ?? "new"}
    disabled={sharing}
    onChange={(e) => onDestinationChange(e.target.value)}
  >
    <optgroup label={t("share.destinationNewGroupLabel")}>
      <option value="new">{t("share.destinationNewFolderOption")}</option>
    </optgroup>
    <optgroup label={t("share.destinationExistingGroupLabel")}>
      {editableExistingFolders.map((c) => (
        <option key={c.id} value={c.id} title={c.name}>{c.name}</option>
      ))}
    </optgroup>
  </select>
</div>
{destinationId === null ? (
  /* existing "Nazwa folderu" input + optional seed-from-personal-folder
     summary — UNCHANGED markup, ShareDialog.tsx:1235-1256 */
) : null}
```

- **Not `CollectionPicker` reused as-is — a deliberate, resolved discretion call.**
  `CollectionPicker.tsx` lists every collection `useCollections()` returns (already correctly
  excluding `item_bucket` per 260812-01e), with no `access_level` filter, because its own callers
  (`ItemForm`'s future destination picker) need every collection an item COULD move into,
  regardless of the caller's grant level there. This selector needs a **narrower** set: only
  collections the caller can `RequireEdit` on's server-side gate, since selecting a read-only
  folder here and then submitting would 403 on `addCollectionMember`/`reshareCollectionToNewMember`.
  The filter is `access_level === "edit" && family_wide_kind !== "item_bucket"` — the EXACT
  predicate `SharingOverviewPanel.tsx:315`'s own "By folder" tab already uses for "collections I
  manage." Reusing `CollectionPicker` unfiltered would let a user pick a folder they cannot
  actually grant access to and then fail at submit — a correctness gap, not a convenience trade-off,
  which is why this is a new, small selector rather than an import.
- **`item_bucket` exclusion holds here too**, per the constraint — inherited from the SAME
  `family_wide_kind !== "item_bucket"` filter term, not a second implementation of it.
- **Long folder-name truncation**: every `<option>` carries `title={c.name}` — the one truncation
  mechanism a native `<option>` supports, mirroring `CollectionPicker.tsx`'s own documented
  discharge of this exact concern (#5 in its own header comment).
- **Zero existing editable folders**: the "Existing folders" `<optgroup>` is simply omitted (not
  rendered with a "0" placeholder) — the select still offers "Nowy folder…" as its sole option,
  never a dead end (mirrors `CollectionPicker`'s own zero-one-many discipline, #4 in its header
  comment, adapted to "the group disappears" rather than "the whole control disappears", since
  "mint new" is always a valid choice here).
- **Switching destination resets every row's pending state to that destination's real current
  state.** A pending "brak dostępu" queued against Folder A carries no meaning once the user
  switches to Folder B — carrying it over would silently misrepresent what Save is about to do.
  This is a hard interaction rule, not a nicety: switching destinations must re-fetch
  (`getCollectionAccessList`) and re-render every row from scratch.

## Row Anatomy (MOD-01)

One row per family member (self already excluded, `ShareDialog.tsx:691`'s existing WR-14 filter),
rendered for the per-person mode only — "Cała rodzina" keeps its own single control, unchanged
from Phase 30, and the two modes stay mutually exclusive exactly as shipped
(`toggleFamilyWide`/`toggleRecipient`, `ShareDialog.tsx:717-744`).

```
<ul className="flex flex-col divide-y divide-base-300" data-testid="share-recipient-list">
  {sortedRows.map((row) => (
    <li key={row.userId} data-testid={`share-recipient-row-${row.userId}`}
        className="flex items-center gap-2 py-2">
      {row.currentLevel !== null ? (
        <UserCheck size={14} className="shrink-0 text-secondary" aria-hidden="true" />
      ) : (
        <span className="w-[14px] shrink-0" aria-hidden="true" />  {/* reserves alignment, no icon */}
      )}
      <span className="flex min-w-0 flex-1 flex-col">
        <span className="truncate text-sm" title={row.email}>{row.email}</span>
        {row.currentLevel !== null ? (
          <span data-testid={`share-recipient-row-currently-${row.userId}`}
                className="text-sm text-base-content/60">
            {interpolate(t("share.rowCurrentlyLabel"), { level: t(accessLevelKey(row.currentLevel)) })}
          </span>
        ) : null}
        {row.suspended ? (
          <span className="badge badge-warning badge-outline w-fit">{t("family.statusSuspended")}</span>
        ) : null}
        {row.publicKey === null ? (
          <span data-testid={`share-recipient-row-nokey-${row.userId}`}
                className="text-sm text-base-content/60">
            {t("share.rowNoPublishedKey")}
          </span>
        ) : null}
      </span>
      {row.pendingLevel === "none" && row.currentLevel !== null ? (
        <UserMinus size={14} className="shrink-0 text-error" aria-hidden="true" />
      ) : null}
      <select
        data-testid={`share-recipient-row-select-${row.userId}`}
        className="select select-bordered select-sm w-40 shrink-0"
        value={row.pendingLevel}
        disabled={sharing || row.publicKey === null}
        onChange={(e) => onRowLevelChange(row.userId, e.target.value)}
      >
        <option value="none">{t("access.none")}</option>
        <option value="read">{t("access.readOnly")}</option>
        <option value="edit">{t("access.fullEdit")}</option>
        <option value="hidden_password">{t("access.hiddenPassword")}</option>
      </select>
    </li>
  ))}
</ul>
```

- **Identity on the left, level control on the right** — MOD-01's literal wording. `email`
  (truncated, `title` fallback) plus the `currentlyLabel`/suspended/no-key subtitles stack in one
  flex column occupying the row's remaining width; the `<select>` is `shrink-0`, pinned to the
  trailing edge exactly as the requirement states.
- **A per-row `<select>`, not a segmented control or radio group** — resolved discretion. The
  file's existing GLOBAL level control was a radio group (three visible options, fine for one
  instance). At up to ~15 rows, 15 × 4-way radio groups would be visually heavy and would not fit
  a 400px card without wrapping; a compact native `<select>` (already this dialog's own idiom for
  the destination selector above, and `CollectionPicker`'s established idiom project-wide) keeps
  each row a single line at any row count.
- **Pre-filled at the real current level, never a neutral default** — MOD-01's "shows their real
  current level, and it is editable in place" is satisfied structurally: `row.pendingLevel`
  initializes to `row.currentLevel ?? "none"`, so an untouched row's select already reads the
  truth. Editing is simply changing that value; there is no separate "edit mode" toggle.
- **Disabled + locked to `none` when `publicKey === null`** — see Copywriting Contract's
  `share.rowNoPublishedKey`. This is the row-level, proactive half of SC5's refusal requirement.
- **Suspended members are never filtered out** — mirrors `SharingOverviewPanel`'s A-7 discipline
  (a suspended member's existing grant, if any, still shows and is still editable/revokable; being
  suspended is a family-membership-wide fact shown alongside, never a reason to hide the row).
- **Row order — existing access first, per CONTEXT's "readable at a glance" ask.** Rows with
  `currentLevel !== null` are grouped first (so "who already has what" is visible without
  scrolling past everyone else), each group ordered alphabetically by email. This is a resolved
  discretion call, not left arbitrary, because the alternative (pure alphabetical) would bury a
  15-member family's 2 actual recipients among 13 "brak dostępu" rows.
- **One member (n=1, excluding self)**: renders as a single row, no list chrome beyond the `<ul>`
  wrapper — no special-casing, same markup as any other count.
- **Zero members (n=0, solo family)**: the row list is omitted entirely and `share.noOtherMembers`
  renders in its place — unchanged behavior, `ShareDialog.tsx:1302-1305`.

## Scale & Scroll Contract (1 / 3 / ~15 members, small viewport)

**The dialog card itself becomes the single scroll container; the footer is pinned outside it.**
This is the structural change flagged in Design System above — necessary because this phase's
content (destination selector + up to ~15 rows + a conditional inline note + a conditional
pending-revocations paragraph) can genuinely exceed a comfortable card height, and CONTEXT's own
"no hover, no second click" bar for the hidden-password note must hold even when the row list is
long.

```
<div className="fixed inset-0 z-50 flex items-center justify-center bg-base-300/70 p-4" ...>
  <div className="flex max-h-[85vh] w-full max-w-[400px] flex-col rounded-box border border-base-300 bg-base-100">
    <div className="flex flex-col gap-4 overflow-y-auto p-6">
      {/* title, destination selector, "Cała rodzina" row (unchanged), row list,
          hidden-password inline note, pending-revocations summary, error/partial-error slots —
          everything that was previously inside the single p-6/gap-4 card, now inside THIS
          scrolling region */}
    </div>
    <div className="flex shrink-0 justify-end gap-2 border-t border-base-300 p-4">
      {/* Cancel + Save/Share buttons — UNCHANGED markup, moved out of the scrolling region */}
    </div>
  </div>
</div>
```

- **No nested scroll containers.** The row list does NOT get its own separate
  `max-h-*/overflow-y-auto` (unlike the old `max-h-48` checkbox list) — the whole body scrolls as
  one document flow. This is deliberate: nested scroll regions are the classic source of "the note
  I need is trapped inside an inner scroller I didn't know was there" — exactly the failure mode
  CONTEXT's "what happens if the note is below the fold" question is worried about. With ONE scroll
  region, the SAME gesture that reveals the last row also reveals the hidden-password note and the
  pending-revocations summary beneath it — there is no separate scroll to discover.
- **Cancel/Save stay reachable without scrolling at any row count or viewport size** — the pinned
  footer (`shrink-0`, outside the scroll region) guarantees this; a 15-row family on a short mobile
  viewport still sees the footer immediately, never having to scroll past 15 rows to find Save.
- **1 or 3 members**: the body's natural height stays well under `85vh` on any realistic viewport —

- **~15 members**: the body scrolls; the footer does not move. The hidden-password note and

## Revocation Mechanism — Known Code-Reality Gap for the Planner (MOD-01's sixth proof obligation)

This is not a visual/copy question, but the interaction contract above depends on getting it right,
so it is recorded here rather than left implicit.

**31-CONTEXT.md instructs reusing `buildMemberRemovalBatch`/`removeFamilyMember`
(`web/src/lib/families/rekey.ts`) for the "brak dostępu" revocation.** Reading those functions
against the actual code:

- `buildMemberRemovalBatch(targetUserId, ownUk, isSelf)` resolves collection ids via
  `resolveTargetCollectionIds`, which returns **every** collection the target currently holds a key
  for (`getMemberAccess(targetUserId).collections`) — it is built for, and only ever called for,
  **removing a member from the family entirely** (`RemoveMemberDialog`) or **self-deletion**
  (`DeleteAccountDialog`). Calling it unmodified from this dialog would rekey and evict the target
  from **every** shared folder they hold, not just the one destination row being edited — the
  opposite of MOD-01's "the dialog is the access picture for the CHOSEN destination" framing. This
  needs a collection-scoped variant (e.g. a sibling function taking one `collectionId` rather than
  resolving the target's full access set) before it can be reused correctly.
- The codebase's **existing, already-shipped, already-scoped** mechanism for exactly "revoke one
  person's grant on one folder/item" is `revokeCollectionAccess`/`revokeItemShare`
  (`vault/api.ts:301-318`, SHARE-06/Phase 28), consumed today by `RevokeShareDialog.tsx` from
  `SharingOverviewPanel`. Its own doc comment states explicitly: **"No re-key: only the
  `collection_keys` row is deleted, item ciphertext is untouched."** This is weaker than
  `buildMemberRemovalBatch`'s rotation, by design — it was judged sufficient for SHARE-06 in v0.4.
- **For a direct item share (bare item, no folder)**, `buildMemberRemovalBatch` does not apply at
  all — it only walks collections. `revokeItemShare` is the only mechanism that exists, and its
  server-side `shared_direct_revision` bump already delivers exactly the "loses read access on the
  next completed sync" bound this phase's sixth proof obligation needs — reusing it for the item
  case is both correct and unavoidable.
- **For a folder destination**, the planner must resolve this before implementing: either (a) build
  a `collectionId`-scoped sibling of `buildMemberRemovalBatch` (honoring CONTEXT's literal
  instruction, correctly scoped to one destination), or (b) confirm with the product owner that the
  existing, already-live `revokeCollectionAccess` is in fact sufficient here too (it already
  satisfies the *observable* "loses access on next sync" bound via the client's own cache-purge
  discipline — DEBT-03/VIS-01 — even without key rotation). This UI-SPEC does not resolve that
  architecture question; it is out of a UI researcher's authority. What it DOES fix is the
  **interaction contract that must hold regardless of which mechanism is chosen**: a level EDIT
  (not a fresh grant, not a full revoke) must never pass through an intermediate state where the
  person holds LESS access than either their old or new level and the failure is silently
  swallowed — if the chosen mechanism is a revoke-then-re-add pair, a failure between the two steps
  must be reported with the SAME `failedRecipientLabels`-style honesty a partial share failure
  already gets today, never a silent full loss.

## Level-Change Wire Gap — Second Known Code-Reality Note

`collections::add_member` and `vault::create_share` both use `ON CONFLICT DO NOTHING RETURNING ...`
+ `fetch_optional` → a duplicate grant returns **`409 Conflict`** ("recipient already has access to
this collection") rather than updating the row (`collections.rs:640-642`). **There is currently no
server endpoint that changes an existing recipient's access level in place.** A row whose pending
level differs from its current (non-none) level — an in-place EDIT, not an addition or a removal —
cannot be satisfied by a single `addCollectionMember`/`createItemShare` call today; it needs either
a new update-capable server route, or a client-side revoke-then-add pair (with the atomicity caveat
noted above). This is a planner-level architecture decision, flagged here because it changes what
"submit" must actually do for an edited (not just added/removed) row, and because getting it wrong
silently downgrades MOD-01's "editable in place" claim to "removable and re-addable" in practice.

## Accessibility Contract

- **Destination selector.** Real `<label htmlFor>` + `<select id>` pairing, native `<optgroup>`
  grouping (read by screen readers as distinct regions) — zero custom ARIA needed on the control
  itself, mirroring `CollectionPicker`'s own established idiom.
- **Row `<select>` disabled state.** A row locked to `access.none` because of a missing published
  key uses the native `disabled` attribute (never a custom "looks disabled" style) — screen readers
  announce it as unavailable, consistent with `share-recipient-row-nokey-{id}`'s adjacent text
  explaining why.
- **Pending-revocations summary.** `role="status" aria-live="polite"` — a factual statement of what
  Save will do, not an alarm; mirrors `RevokeShareDialog`'s own error slot's `role="alert"` being
  reserved for actual failures, not for a correctly-functioning pending state. (Contrast: the
  summary states a TRUE, expected consequence of the user's own choices — it is not an error.)
- **`UserCheck`/`UserMinus` row icons.** `aria-hidden="true"` on both — the information they carry
  is fully duplicated in text (`share.rowCurrentlyLabel`'s presence/absence, the select's own
  value), so the icons are decorative reinforcement, never the sole channel, matching this file's
  existing `aria-hidden` discipline on every other inline icon.
- **Scroll region.** The body `<div>`'s `overflow-y-auto` needs no additional ARIA (a plain
  scrollable region, not a listbox or grid) — focus order follows DOM order (destination selector →
  rows top-to-bottom → conditional notes → footer buttons), which already matches visual/reading
  order, so tab order needs no `tabIndex` overrides.
