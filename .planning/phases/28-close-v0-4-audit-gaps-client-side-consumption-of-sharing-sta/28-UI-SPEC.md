# Phase 28 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **Scope note — this is a small surface, and that is the correct size, not an oversight.**
> Phase 28 closes three v0.4 audit gaps (`.planning/v0.4-MILESTONE-AUDIT.md` Blockers 1–3, Warnings
> 1 and 3), and exactly **one** of them is a genuinely new user-facing affordance:
>
> 1. **Revoke a share (SHARE-06, web only)** — a button on a row `SharingOverviewPanel.tsx`
>    (26-UI-SPEC.md's E6) already renders. `getCollectionAccessList`/`listItemShares` are already
>    wired (28-RESEARCH.md §A); this phase adds the two DELETE wrappers and one row action. **No
>    extension surface** — per 28-CONTEXT.md B-3, EXT-06's no-in-popup-forms doctrine holds, and
>    revoke is management, not use.
> 2. **Direct-share write refusal (extension, Blocker 2)** — today a silent wrong-key corruption;
>    after the fix, a refusal the user must see. This is a **capture-toast** state
>    (`extension/lib/autofill/save-update-toast.ts`), not a dialog — the surface that already exists
>    for every capture confirm/update.
> 3. **`hidden_password` edit suppression (extension, Warning 1)** — the same capture-toast surface,
>    a second blocked-write state sharing the same gate (28-CONTEXT.md B-5).
>
> Everything else in this phase (the 404→purge discriminant, the suspend/reinstate revision bump,
> `persistUpdatedProviderItem`'s dormant fix) has **no user-visible surface** — access silently
> stops being served, which is the correct, honest behavior, not a gap in this contract. **WINDOWS
> #13** (add a member to an existing collection) is explicitly excluded — 28-RESEARCH.md found it
> is a second, independent crypto-plumbing task (no "unwrap an existing collection's key and reseal
> it" code path exists client-side yet), not cheap alongside revoke, so it is not designed here.
>
> `components.json` is absent, shadcn is not part of this stack (DaisyUI 5 + `packages/pv-ui`,
> unchanged across every prior UI-SPEC) — the shadcn init gate is not applicable and was not
> re-asked.

**Deliberate non-use of error/warning color — the extension's two blocked-write toast states.** Both
new states (`update.blockedDirectShareBody`, `update.blockedNoEditAccessBody`) render in the
existing `.pv-toast-message` element **without** the `.pv-toast-message-error` modifier — i.e. plain
`base-content`, not `text-error`. This is the same deliberate choice 26-UI-SPEC.md made for the
hidden-password disclosure ("not a danger the user is being warned away from") applied to a new
case: a blocked write is not a fault or a network failure (which `save.failed`/`update.conflict`
correctly do render in error color) — it is an honest, expected, permanent capability boundary. Using
error-red here would misrepresent "you can't do this" as "something went wrong," the same
category error `docs/UI-DESIGN.md`'s "warning nigdy dla akcji, tylko dla stanu" instinct exists to
prevent in the other direction.

**Accent reserved for:** nothing new this phase. **Destructive reserved for:** the revoke
confirmation dialog (icon + confirm button) and the revoke row-action's own failure text, both
named above — nothing else in this phase's scope competes for either budget.

### Destructive-confirmation reasoning (revoke's ceremony weight, decided and justified)

**Decision: revoke gets `DeleteConfirmDialog`'s single-step tier (AlertTriangle icon, one Cancel/
Confirm pair, `btn-error`), not `RemoveMemberDialog`'s two-step tier.**

This codebase already has two distinct destructive-confirmation weight classes, and revoke's own
shape maps cleanly onto the lighter one:

- **Two-step** (`RemoveMemberDialog`, `DeleteAccountDialog`): reserved for actions that are
  irreversible **in a structural sense** — they trigger a cryptographic re-key
  (`member.removeStep2Body`: "the affected keys will be re-encrypted") or erase an account outright.
  The second step exists because undoing the *consequence* (re-inviting someone, restoring an
  account) requires redoing real cryptographic work, not just clicking a button again.
- **Single-step** (`DeleteConfirmDialog`, `PasskeyDeleteConfirmDialog`): reserved for actions that
  are consequential but where the *undo path*, if the owner changes their mind, is cheap — re-share
  the folder/item again, in revoke's case a single `ShareDialog` submission with no re-key at all
  (28-RESEARCH.md §A: "No — item ciphertext is never touched; only the `collection_keys` row is
  deleted").

Revoke has **zero** re-key cost and a one-click undo path (re-share). Giving it `RemoveMemberDialog`'s
two-step ceremony would overstate its blast radius relative to the codebase's own established
grammar for that weight class — a user who has learned "two steps means re-key is happening" would
be trained wrong by seeing it here. Giving it *no* confirmation at all would understate it — a
revoked recipient genuinely loses ongoing access, and the row disappearing from an owner's own
Sharing overview with no confirmation risks an accidental click silently cutting someone off. The
single-step tier is the honest middle: real friction, real honesty copy (`share.revokeBody`), no
false re-key ceremony.

## Phase-Specific Notes

### 1. No extension surface for revoke (B-3) — stated so it is not mistaken for an omission

Per 28-CONTEXT.md B-3, SHARE-06's revoke affordance is **web only**. EXT-06's no-in-popup-forms
doctrine and Phase 27's own precedent (every sharing-management action stayed in the web app) both
hold. This UI-SPEC does not design an extension revoke surface because one must not exist, not
because it was overlooked.

### 2. WINDOWS #13 (add-to-existing-collection) — excluded, not deferred silently

28-RESEARCH.md's own cost assessment (§A) found this is not cheap alongside revoke: it needs a
picker UI, a genuinely new "unwrap the caller's own Collection Key, reseal to a new recipient"
crypto composition that does not exist anywhere in the client today, and the `add_member`
confused-deputy precondition surfaced honestly. This UI-SPEC does not design it, consistent with
28-CONTEXT.md leaving it a judgment call that research resolved as "leave it out."

### 3. Component inventory (new + extended)

- **Web:** `SharingOverviewPanel.tsx` (extended — row action + optimistic local-state update on both
  tabs). A new small confirmation dialog (naming left to plan-time — e.g. `RevokeShareDialog.tsx`,
  or inline dialog state within `SharingOverviewPanel.tsx` itself) reusing `DeleteConfirmDialog.tsx`'s
  exact shell. `web/src/lib/vault/api.ts` (extended — two new DELETE wrappers, no visual surface of
  their own).
- **Extension:** `extension/lib/autofill/save-update-toast.ts` (extended — two new render branches
  inside its existing state machine, no new file). `extension/entrypoints/background/capture-handler.ts`
  (extended — the classification that decides which toast state opens; no visual surface of its own).

### 4. What "suppressed, not failed" means operationally, restated for the planner

For both extension blocked-write states, the classification that decides "this is a blocked write"
must happen **before** the toast ever offers an Update button — not as a confirm-time failure of an
offer that looked real. The `ReadOnlyAccessError`/new direct-share error class stay as the data-layer
backstop (mirroring web's own `canEditItem` proactive-suppression + `DirectShareNotEditableError`
reactive-backstop two-layer precedent, 28-RESEARCH.md §B) — but the UI-visible contract in this
document is about what renders on the FIRST render of the toast for these two cases, not about a
button that appears clickable and then errors on click.
