<objective>
Close v0.4 audit Blocker 3: the 404 that proves the server severed a member's shared access is the same
404 both clients read as "this account has no family," latching the shared-sync poll off for the
session and silently preventing the purge that would drop cached plaintext. A removed member keeps
autofilling shared credentials until lock; suspension's direct-share bucket gets no signal at all.

**Correction 28-RESEARCH.md made to the audit's own framing (do not re-derive from the audit alone):**
suspension's COLLECTIONS half already self-heals via existing Phase 27 code (the empty-array response
already drives the existing per-collection purge, `vault-store.ts:809-819`/`store.ts:1120`) —
untouched by this plan. Only the DIRECT-share half of suspension is genuinely broken (a missing
`shared_direct_revision` bump), and removal's client purge never runs at all because the latch fires
before it. Per B-7 (28-CONTEXT.md, resolved by 28-RESEARCH.md's "the open design question"): the fix
is client-side — a session-scoped "has this ever succeeded" flag distinguishes "no family" from
"removed mid-session" using information the client already legitimately holds, no server change, no
schema change. Per B-8: suspension's fix is a 2-line `shared_direct_revision` bump on BOTH
`suspend_member` and `reinstate_member` (Pitfall 3: both directions need it, not just suspend).

**FAM-09's "immediately" is honestly bounded, not silently redefined** (per this phase's own explicit
instruction): the discovery path is the alarm-backed poll, clamped by `chrome.alarms` to >= 1 minute.
"Immediately" can only truthfully mean "on the next completed sync cycle, without requiring
lock/unlock" — this plan states that bound explicitly (see `must_haves.truths`) and proves it, rather
than letting the requirement's word go unexamined.

Purpose: "removal severs access" must be true of BOTH clients, not just the server — this is the
milestone's headline security promise (FAM-07/08/09) and its cleanest closed defect (KEY-06: the purge
must never over-reach into the member's own personal vault, which would be a worse bug than the one
being fixed).
Output: a 2-line server fix in `families.rs`; a byte-identical-shape client fix in both
`sync-client.ts`/`sync.ts` and `vault-store.ts`/`store.ts`; live proof on both clients for removal and
for suspension's direct-bucket signal.
</objective>
