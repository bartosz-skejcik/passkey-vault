# Phase 12 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **Scope note:** this is the first UI-SPEC written for the `extension/` surface (Phases 8–11 haven't produced their own UI-SPEC yet at time of writing). This document therefore (a) carries forward `docs/UI-DESIGN.md` §3's extension tokens/geometry as the baseline design system for the whole extension — so later Phase 9/10/11 UI-SPECs don't have to re-derive them — and (b) scopes its actual *contract* narrowly to Phase 12's own new surface: **the passkey-ceremony consent UI** (PROV-01..05). It does not redesign the popup's unlock/browse/search/item-detail screens (Phase 9's job), the in-page autofill dropdown (Phase 10's job), or the save/capture prompts (Phase 11's job) — it only assumes those exist as a shell the ceremony view is mounted into, and cross-references them where the ceremony flow touches them (e.g., "if locked, show the existing unlock screen first").

## Design System

| Property | Value |
|----------|-------|

| Preset | not applicable |

React is the popup's UI framework (`@wxt-dev/module-react`, per 12-RESEARCH.md's inherited Phase 8 stack choice), so the same component vocabulary (`btn btn-primary`/`btn btn-accent`/`btn-ghost`, `modal`-shape overlays, `divider`) transfers directly — this phase reuses that vocabulary, it does not invent a parallel one. New component classes this phase: none beyond what Phase 2–4's `btn-accent` (teal) and `btn-ghost` usages already established on the web side. |
| Icon library | `lucide-react` (same package as `web/`, no new dependency). Reused meanings, not reinvented: `KeyRound` (passkey/PRF meaning — Phase 2/3's locked reservation), `Fingerprint` (in-progress ceremony / "confirm on your device" — Phase 3/4's locked reservation, paired with `Loader2` for the busy spin), `Globe` (new this phase — neutral fallback glyph for a site with no fetchable favicon, see Color/Phase-Specific Notes for why favicons aren't fetched at all this phase). `AlertTriangle` is available but **deliberately not used** in the ceremony screens — genuine failures stay plain `text-error` text, matching Phase 4's restraint on this exact security-critical-surface question. |
| Font | Unchanged: `DM Sans` for all extension UI text. `Fuzzy Bubbles`/emoji are **never** used anywhere in this phase's surfaces — the passkey ceremony is, if anything, a more security-critical moment than the vault-unlock screen (it grants a third-party site a working credential), so it inherits the same "never playful" list Phase 2–4 already built (unlock overlay, delete-confirm, enrollment ceremony, PRF fallback tiers). `ui-monospace` is not needed this phase — no raw key/secret value is ever rendered in this UI (see Color's zero-knowledge note). |

## Spacing Scale

Declared values (must be multiples of 4) — unchanged from the web app's scale, carried to the extension:

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon-to-label gaps (favicon/`Globe` glyph to hostname text) |
| sm | 8px | Compact spacing; gap between stacked credential-choice rows in the multi-match list |
| md | 16px | Default element spacing — vertical rhythm between ceremony header, body copy, and action row |
| lg | 24px | Ceremony view's outer padding (all four sides of the popup canvas while the ceremony view is mounted) |
| xl | 32px | Unused this phase — the popup canvas is too small to need a layout-region-level gap this large |
| 2xl / 3xl | 48px / 64px | Unused this phase |

**Fixed layout dimensions this phase (all multiples of 4/8, justified below where new):**

| Element | Value |
|---|---|
| **Popup canonical width** | **360px** — literal value from `docs/UI-DESIGN.md` §3.7 ("szerokość ~360px"). Not re-opened as a discretion question; this phase's ceremony view is a simple vertical stack that fits comfortably at 360px (no wide table/grid content like Phase 6's import wizard needed), so there is no justification to claim the 400px upper bound the phase brief allows. |
| **Popup max height** | **600px**, content scrolls internally past that. This is a Chrome MV3 platform ceiling for `default_popup`, not a design choice — declared here so the ceremony view's multi-match credential list knows its scroll boundary. |
| RP/credential icon slot | 32px — reuses the exact `ItemRow`-style neutral icon-in-slot convention from the web app (Phase 2/3/6), not a bespoke size. |
| **Credential-choice row height (multi-match list only)** | **56px — new, phase-specific exception**, denser than the web app's 64px vault-list row. Justified: the popup's 360px canvas and ≤600px height have far less room than the web app's full-width list; a 56px row (32px icon slot + 8px vertical padding top/bottom + single-line username text) keeps 3–4 matching credentials visible without forcing scroll on the common case. |
| Icon-only touch target (if any icon-only control appears, e.g. a settings gear in the popup's normal chrome) | 40px hit area — reuses Phase 2's pre-approved exception verbatim. **Not needed inside the ceremony view itself** — every control in this phase's ceremony screens carries a visible text label (see Copywriting Contract), so no new icon-only exception is opened here. |

## Typography

Unchanged from the web app — 4 sizes, 2 weights, carried forward, not re-opened:

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Label | 14px | 400 | 1.4 |
| Body | 16px | 400 | 1.5 |
| Heading | 20px | 700 | 1.2 |
| Display | 28px | 700 | 1.15 |

- Label → RP hostname/origin line, credential-choice row username text, PRF-note/fallback explainer copy, footer fine print.
- Body → the ceremony's one-line explanation of what's about to happen ("{site} wants to save a new passkey to your vault" / "{site} is asking you to sign in with a passkey").
- Heading → ceremony view's short title if one is used above the body line (e.g. "New passkey" / "Sign in with a passkey") — optional per screen, see Phase-Specific Notes; when present it's Heading, never Display.
- **Display is unused this phase** — there is no "hero number" (security score, item count) in a passkey ceremony; do not invent one. Carried in the table only for consistency with every other phase's declared typography contract.

## Color

Unchanged 60/30/10 split and OKLCH/hex values from `docs/UI-DESIGN.md` §2 (`vault-dark` default, full `vault-light` parity) — this phase does not introduce a new hue, it extends an existing one (teal) into a new surface (a full-width primary confirm button on a *third-party-facing* consent screen, one level more consequential than Phase 4's vault-unlock button).

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#1F1F1F` base-300 dark (light: web app's fixed `base-300` equivalent) | Popup canvas behind the ceremony view |
| Secondary (30%) | `#262626` base-100 / `#212121` base-200 | Credential-choice row background (base-200, hover → base-100), any settled surface behind the ceremony's action row |
| Accent (10%, coral `#E16540`) | primary | **Not used anywhere in the ceremony view.** This is a deliberate, phase-specific departure from Phase 4's "two equal accent-weight paths" pattern (teal PRF button *and* coral password button side by side): the passkey-provider ceremony has no password alternative to offer — its second path is "use something else" (native/other-extension fallback), which is semantically a *ghost/neutral* exit, not a competing brand-weighted action. Coral stays reserved for the popup's ordinary browse-mode chrome (e.g. a "+ New item" button, Phase 9's concern) — it never appears inside this phase's ceremony screens. |
| Destructive | `#FF5861` error | Genuine mid-ceremony failure text only (e.g. background couldn't sign/save the new passkey, or a sync round-trip failed) — plain `text-error` paragraph, no icon, matching Phase 4 Tier-3's exact treatment. **Never** used for user decline/cancellation (see below) and never for the zero-match auto-fallthrough (that's not a failure, it's expected routing). |

**Teal (`#00CDB7`, DaisyUI `accent` token) — this phase's single confirm-action color, reusing the existing "passkey = teal" domain rule, not opening a new one:**
- The ceremony's one primary confirm button — `btn btn-accent`, full width — for both ceremony kinds: "Create passkey" (registration) and "Sign in with passkey" (authentication).
- `KeyRound` icon inside the confirm button and inside each credential-choice row (multi-match list) — same icon, same meaning, as every other passkey-adjacent surface in the app.
- The small PRF-capable indicator line's icon slot, when shown (see Copywriting Contract) — text stays neutral (`base-content/70`), only the accompanying `KeyRound` glyph, if one is used, takes teal.
- **Teal is not used for the fallback button.** "Use something else" is `btn btn-ghost` — no fill color, no icon — matching Phase 4's plain-text-cancel convention (a decline is a legitimate, expected, non-alarming choice, not a downgrade to punish visually).

**Neutral (`base-content/70`) — the PRF-related explainer lines, both directions:**
- The PRF-capable note ("this passkey will also unlock your vault") and the PRF-unavailable-for-this-request fallback message (PROV-04) are both rendered in the same neutral, non-alarming tone — reusing Phase 4's "no fake success, no hard failure" doctrine verbatim. Neither is warning-yellow or error-red: one is a bonus-capability confirmation, the other is an honest capability gap, and neither is a problem the user needs to react to.

**Zero-knowledge note (not a new color rule, a boundary reminder for the checker/executor):** nothing rendered by this UI ever needs `ui-monospace` or a raw-value display, because nothing in this screen is a secret — RP name/origin, username, and credential nickname are the only values shown, and they are already known to the third-party page itself. This view must never attempt to display a private key, PRF output, or the User Key in any form (that would be a Color/Copywriting-dimension violation *and* a PROV-05 security-review failure).

**No destructive action in this phase's UI.** Creating or using a passkey is not a delete/revoke/irreversible action from this screen's point of view (revoking an enrolled passkey is Phase 3's Settings-panel concern, unchanged). The template's "Destructive Confirmation" row is not applicable here.

**No empty state in this phase's UI.** A zero-match `get()` does not render an empty-state screen — it silently falls through to the native authenticator (PROV-03) with, at most, the transient `provider.noMatchTransient` line if the popup was already visible. This is a deliberate design choice, not an oversight — see Phase-Specific Notes.

## Phase-Specific Notes

### Where the ceremony consent UI lives (discretion area, now resolved with a default)

**Decision: the ceremony consent screen is always rendered inside the extension's own popup surface (or, if the popup can't be programmatically opened, a dedicated small `chrome.windows.create` popup-type window at the same route) — never injected into the third-party page itself.**

Rationale: an in-page overlay would be rendered inside a DOM the page's own CSS/JS can cover, resize, or attempt to spoof — the opposite of the trust boundary D-02/D-05 establish for everything else in this phase. The extension's own popup is a browser-chrome-owned surface a page cannot draw over or read from, which is exactly the property a consent UI for "should this site get a working credential" needs. This also matches `docs/UI-DESIGN.md` §3.7's own framing of the "passkey capture dialog" as a popup-hosted card, not an in-page one, and is consistent with how the two production extensions this space is modeled on (Bitwarden, 1Password) surface their own equivalent prompts.

Mechanism:
1. Background attempts `browser.action.openPopup()` (or the WXT-typed equivalent) to bring the existing popup to the front.
2. If that call is unavailable or rejected (older Chrome, or a user-gesture requirement not met at call time), fall back to `browser.windows.create({ type: 'popup', width: 360, url: 'popup.html#/provider-ceremony' })` — a small dedicated window, same 360px width, same view.
3. Either way, the popup's router immediately takeover-mounts the ceremony view (`ProviderCeremonyView`), replacing whatever the user was looking at (list/search/settings) — a pending ceremony always wins focus, since the page's `create()`/`get()` promise is actively waiting. When the ceremony resolves (confirm, decline, or error), the popup either closes (if it was opened solely for this) or returns to the view the user was on before (if it was already open).

### Zero-match `get()` never shows a screen (PROV-03, resolved default)

If the background finds no vault credential matching the RP, this phase's UI does **not** show an empty-state screen, a "no matches" card, or any confirm/decline choice — it silently and immediately signals fallthrough to the native authenticator (or whatever else is registered). If the popup happened to already be open (the user was mid-browse when the page's ceremony fired), a single transient `provider.noMatchTransient` line (Label, neutral, `base-content/70`) appears for ~1.5s in the popup's existing view before it returns to what it was showing — a light-touch transparency gesture (per CONTEXT.md's "Specific Ideas" note about clarifying which provider handled a given ceremony), not a blocking dialog. If the popup was never opened for this ceremony, nothing renders at all — the fallthrough is instant and invisible, exactly matching what a user with no password-manager extension installed would already experience.

### Popup dismissal = implicit decline (D-11, resolved default)

If the user closes the popup/window without clicking either the confirm or "Use something else" button (click-away, `Esc`, browser chrome close), the background must treat this identically to an explicit decline and trigger fallthrough to the native authenticator — never leave the page's promise hanging. This is the concrete mechanism that satisfies D-11's "never dead-end the ceremony" for the one interaction path (accidental/ambiguous dismissal) that isn't already an explicit button.

### Single-path ceremony, not Phase 4's dual-path pattern (Color section, cross-referenced)

Phase 4's unlock screen deliberately shows two equally-weighted accent buttons (teal PRF, coral password) because both are genuine, parallel ways to unlock the *user's own* vault. This phase's ceremony is structurally different: there is exactly one thing Passkey Vault can offer (the vault-backed passkey, teal), and exactly one alternative (defer to whatever else the browser/OS/another extension offers, ghost-neutral) — not two competing brand-weighted actions. Do not add a second coral button here by analogy to Phase 4; it would misrepresent "use something else" as an equally-promoted path when it's actually an escape hatch.

### PRF handling in this screen is about the *site's* PRF request, not vault-unlock (clarifying a possible confusion with Phase 3/4)

The PRF notes in this Copywriting Contract are **not** about whether this new passkey can later unlock the user's own Passkey Vault session (that's Phase 3/4's PRF-vault-unlock feature, a separate concern) — they're about whether the *third-party RP's own* `create()`/`get()` request included the WebAuthn `prf` extension (some RPs use PRF output for their own client-side encryption features, independent of Passkey Vault). `provider.prfCapableNote`/`provider.prfUnavailableNote` only render when the RP's request actually included the `prf` extension — most ceremonies won't show either line. This is a genuinely new interpretation this document is making explicit (12-RESEARCH.md doesn't spell out the UI angle) — flagged in Review Notes.

### Favicon strategy: none, by default (discretion area, resolved conservatively)

This phase's ceremony header shows the RP's hostname as plain Label text next to a neutral `Globe` icon — **it does not fetch the site's favicon** (neither directly nor via an icon-proxy service). Rationale: a direct cross-origin favicon fetch from the extension would be a new network call this phase doesn't otherwise need, and a proxy-fetched favicon (the common alternative, e.g. Bitwarden's icon service) means routing every RP hostname the user authenticates against through a third party — a privacy trade-off this self-hosted, zero-knowledge-postured product shouldn't take on by default. Hostname text plus a neutral icon is sufficient to identify the RP (the same information the browser's own native WebAuthn dialog shows). If a future phase wants favicons, that's an additive, low-risk follow-up — not blocking this phase.

### Multi-match credential list (PROV-02)

When more than one vault-stored passkey matches the RP, the ceremony view renders a vertically stacked list of 56px credential-choice rows (see Spacing Scale) — each row: 32px `KeyRound` icon slot (teal) + account/username text (Label) + a selection affordance (radio-style, single-select). The primary confirm button (`provider.signinCta`) stays disabled until a row is selected if there's more than one; with exactly one match, that credential is pre-selected and the body copy uses `provider.signinBodySingle` instead of the list-plus-picker layout — no list is rendered at all for the single-match case, matching the "don't force an extra click when there's only one sensible choice" principle already used elsewhere in the app (e.g. Phase 6's auto-advance on successful import-format detection).

### Busy and error states (reuses Phase 3/4's established grammar, not a new one)

- **Busy:** confirm button becomes disabled, its label swaps to `provider.createBusy`/`provider.signinBusy`, and the button's leading icon becomes `Fingerprint` + `Loader2` (`animate-spin`, same `-right-2 -top-2` offset composition as `EnrollPasskeyDialog.tsx`/`PasskeyUnlockButton`) — identical visual grammar to every other in-progress passkey ceremony in the app, not a new pattern.
- **Error (genuine failure, not decline):** `provider.failed` renders as a plain `text-sm text-error` line directly below the button, exactly like Phase 4 Tier-3's mid-ceremony failure text — no icon, no banner. The button returns to idle/enabled so the user can retry or fall back.
- **Cancellation:** if the *page itself* aborts the ceremony (e.g., `AbortSignal`) while the popup is showing this view, the popup silently closes/returns to its prior view — no error text, matching Phase 4's "cancellation earns no color, no copy" rule.

### Explicit non-goal: no in-page indicator this phase

Per 12-CONTEXT.md's Deferred Ideas ("icon-in-field indicator polish… out of this milestone's core scope"), this phase's contract does **not** include any visual marker injected into the page (no icon-in-field badge, no context-menu entry) to signal "Passkey Vault is available here." The only user-visible surface for this entire feature is the popup-hosted ceremony view described above. Do not let this phase's plan quietly reuse Phase 10/11's in-page dropdown/prompt pattern for the passkey ceremony — they are intentionally different surfaces for the reason given in "Where the ceremony consent UI lives" above.

### Accessibility

| Control | PL `aria-label` | EN `aria-label` |
|---|---|---|
| Popup/window close while a ceremony is pending (treated as decline, per D-11) | `Zamknij i użyj innej metody` | `Close and use something else` |
| Credential-choice row (multi-match list), when the row itself is the interactive element | Composed from the row's own visible username text — no separate `aria-label` needed, per the existing "visible text label = accessible name" rule this app already follows | (same) |

`KeyRound`/`Fingerprint`/`Globe`/`Loader2` are all `aria-hidden="true"` wherever they sit inside a control that already carries a visible text label (every control in this phase does) — no new icon-only exception is introduced. If the multi-match list grows past what fits in the 600px popup height, it must scroll with a normal focus-order-preserving native scroll container — no custom virtualization/keyboard-trap component for this phase's list sizes (a personal/family vault won't realistically have dozens of passkeys for one RP).

## Review Notes

Discretionary calls this document made where 12-CONTEXT.md left the choice open ("Discretion Areas") or where this document had to interpret a requirement's UI angle that 12-RESEARCH.md didn't spell out. None of these affect the security/trust-boundary model (D-01–D-15 are followed as locked, not relitigated) — all are presentation-layer defaults, reversible without touching the ceremony/routing logic.

1. **Ceremony consent UI surfaces exclusively via the extension's own popup (or a dedicated small window), never in-page.** This is the single most consequential UI decision in this document and is treated as load-bearing for PROV-05's trust boundary, not just a taste call — flagging it prominently rather than burying it as a minor detail.
2. **Zero-match `get()` shows no screen at all (silent instant fallthrough), with only an optional 1.5s transient line if the popup was already open.** An alternative is always showing a brief "no passkey here" card even when the popup wasn't previously open, at the cost of an extra popup-open flash on every miss — rejected as more disruptive than informative for what should be the common case (most sites won't have a vault-stored passkey yet).
3. **No favicon fetch — hostname + neutral `Globe` icon only.** A conservative, privacy-preserving default; revisit if product wants richer RP branding later.
4. **No coral button anywhere in the ceremony view** (single-path teal-confirm + ghost-fallback, not Phase 4's dual-path teal+coral). Flag if you'd rather visually equalize "use something else" as a stronger secondary action.
5. **PRF notes in this screen are scoped to the RP's own `prf` extension request, not to Phase 3/4's vault-unlock PRF feature** — a genuinely new interpretation of PROV-04's UI angle, since 12-RESEARCH.md's Assumption A1 flags the exact PRF wiring call sites as unverified against the pinned crate source. If implementation reveals PRF is actually being used here for something closer to vault-unlock semantics, this copy will need to change.
6. **Extension i18n mechanism assumed to mirror `web/src/lib/i18n/dictionary.ts` (shared or copied), not newly invented** — flagged as a planner-level question, not a UI decision this document can resolve on its own.
