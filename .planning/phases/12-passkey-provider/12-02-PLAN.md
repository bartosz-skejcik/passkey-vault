<objective>
Implement the background service worker's provider-ceremony orchestration: dispatch `credentials.create`/`credentials.get` messages (arriving on the content-frame channel from `content-relay.content.ts`) to handlers that check/await vault unlock (D-09), re-check session state fresh on every call (D-10), call Plan 12-01's WASM bindings, report PRF capability honestly from the real passkey-rs ceremony signal (D-16/D-14), and decide fallthrough vs. respond (D-11/PROV-03) — never throwing uncaught.

Purpose: This is the "server" tier of the extension's passkey provider — the sole place passkey-rs/pv-wasm are invoked (D-05) and the sole place the unlocked User Key is read from `chrome.storage.session`.
Output: `provider-ceremony.ts`, `credential-store.ts`, extended `ext-protocol.ts` message shapes, and an extended `router.ts` with full Vitest coverage of the decision logic (locked/unlocked, match/no-match, PRF capable/not, genuine failure).

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| ISOLATED content script <-> background (runtime.sendMessage) | Any content script (this extension's own, or in principle a compromised one) can send a `runtime.sendMessage` — background must verify sender, not trust payload |
| background <-> chrome.storage.session | Only the background reads/writes the unlocked User Key handle; must always re-check freshness after a possible idle-kill |
| background <-> pv-wasm (Plan 12-01) | Background is the sole caller of the WASM bindings that touch key material (D-05) |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-12-05 | Spoofing | router.ts message dispatch | high | mitigate | Origin/frameId taken from browser-verified `sender` object, never the payload's self-reported fields — tested explicitly in Task 3 |
| T-12-06 | Information Disclosure | provider-ceremony.ts session handling | high | mitigate | D-10 fresh re-check of `chrome.storage.session` on every handler invocation, tested explicitly in Task 2 |
| T-12-07 | Denial of Service (of ceremony) | provider-ceremony.ts | medium | mitigate | Top-level try/catch in every handler converts any failure to an explicit `{failed: true}` response, never a hang — tested in Task 2 |
| T-12-08 | Tampering | chrome.storage.session `pendingProviderItems` | low | accept | Storage is extension-internal (not page-reachable); contents are already ciphertext (the `EncryptedItem` under the User Key), so tampering only causes a decrypt failure on resume, never disclosure |

</threat_model>
