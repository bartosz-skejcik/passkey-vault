## From Plan 12-05 (IN-01, 12-REVIEW.md): D-20(a) non-configurable-accessor ↔ D-12 coexistence tension — accepted trade-off

**Files:** `extension/entrypoints/page-bridge.content.ts`, `extension/entrypoints/page-bridge-firefox.ts` (`installPatch()`)

**The tension:** D-20(a) mandates installing `navigator.credentials.create`/`get` via `Object.defineProperty` with `configurable: false, writable: false` — this is a deliberate defense against a racing PAGE script re-defining/restoring the patch mid-ceremony (Chromium bug 634381: `world:'MAIN'` + `document_start` does not guarantee running before the page's own inline scripts). D-12 separately requires this extension to coexist with a SECOND password-manager extension "from the first version."

These two requirements are in direct, inherent conflict: whichever extension's content script patches `navigator.credentials.create`/`get` FIRST, on a given page load, permanently wins that property for the rest of the page's lifetime — a non-configurable descriptor cannot be redefined by anyone, including a second legitimate password manager racing to install its own patch a few milliseconds later. `installPatch()`'s `try/catch` around the `Object.defineProperty` calls only protects THIS extension when it loses that race (fails safe: leaves the environment untouched, native WebAuthn keeps working, this provider simply doesn't broker that page) — it cannot un-break the OTHER extension's own patch attempt when this extension wins the race instead. Most real password-manager extensions (Bitwarden, 1Password, etc.) also install their `navigator.credentials` patch as non-configurable for the exact same anti-tamper reason, so the practical, empirically-likely outcome across the ecosystem is "whichever extension's content script runs first, for a given page load, wins that page's WebAuthn provider role for its entire lifetime" — not a graceful hand-off, not a merge, not both extensions serving the same page.

**Why no code fix exists (and won't, while D-20a stands):** the ONLY way to make the property re-patchable by a second extension is to drop `configurable: false`, which reopens the exact page-script tampering window D-20(a) was written to close. There is no known technique that gets both properties (tamper-resistant AND multiply-patchable) on the same `Object.defineProperty`-based approach — the two are structurally exclusive on this API surface. This is therefore an ACCEPTED, DOCUMENTED trade-off, not an open bug: D-20(a)'s security property is judged more important than seamless multi-PM coexistence on the SAME page load, and D-12's "coexist" requirement is satisfied in the weaker, still-meaningful sense that the extension that loses the race fails SAFE (no crash, no broken native WebAuthn, no silent double-broker) rather than in the stronger sense of "both providers usable on the same page."

**Action for `/gsd-secure-phase` (D-15):** add an explicit two-password-manager install-order UAT case to the security-phase checklist:
1. Install this extension AND a second real password-manager extension (e.g. Bitwarden) simultaneously in the same browser profile.
2. Visit a WebAuthn-capable third-party site and trigger `credentials.create()`/`get()` twice, once with each extension's own content-script load ORDER swapped (achievable via extension load/reload order, or by disabling/re-enabling one extension between the two test runs).
3. Confirm: (a) exactly ONE extension brokers the ceremony each time — whichever one's content script ran first for that page load; (b) the OTHER extension's own `Object.defineProperty` attempt throws internally but is caught (`installPatch()`'s `try/catch`) and produces NO user-visible error, NO broken native WebAuthn fallback, and NO console-visible unhandled exception; (c) native WebAuthn (e.g. an OS-level passkey/security key) still works end-to-end through whichever extension won the race, exactly as it would with only one PM extension installed.
