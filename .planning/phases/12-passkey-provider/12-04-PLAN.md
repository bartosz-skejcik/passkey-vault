<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| third-party page <-> popup (browser-chrome-owned surface) | The popup is intentionally the ONLY place this consent UI renders, since a page cannot draw over or read from browser chrome (unlike an in-page overlay) |
| popup <-> background | Confirm/decline/selection messages must reach background reliably, including on ambiguous dismissal |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-12-14 | Spoofing | third-party page attempting to fake a "Passkey Vault" consent UI in-page to phish confirm clicks | high | mitigate | Structural: the ceremony consent screen never renders in-page, only in the browser-chrome-owned popup a page cannot draw over or read from (12-UI-SPEC.md Review Note #1) — no additional code-level mitigation needed in this plan since the architecture already prevents the vector |
| T-12-15 | Information Disclosure | ProviderCeremonyView rendering | critical | mitigate | 12-UI-SPEC.md's zero-knowledge note: no `ui-monospace`, no raw-value display anywhere in this screen — enforced by this plan's task-level review, no secret-shaped prop is ever passed to this component |
| T-12-16 | Denial of Service (of ceremony) | user closes popup without an explicit decision | medium | mitigate | Dismissal-as-decline wiring (Task 2) — page's promise always resolves via an explicit fallthrough signal, never hangs |
