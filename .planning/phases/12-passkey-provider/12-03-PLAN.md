<objective>
Build the phase's most security-critical surface: the MAIN-world `navigator.credentials` patch that is a dependency-free, key-free RPC shim (D-01, D-02, D-04), the ISOLATED-world content-relay that validates and forwards messages (D-03), and the automated grep-audit script that makes PROV-05's zero-knowledge boundary machine-checkable — on both Chrome (declarative) and Firefox (manual injection, per Research Pattern 3).

Purpose: This plan's files are exactly what `/gsd-secure-phase` (D-15, Plan 12-05) reviews. Getting the dependency-free property right here is the single highest-severity risk in this milestone (12-RESEARCH.md Pitfall 5).
Output: `page-bridge.content.ts` (Chrome), `page-bridge.ts` (Firefox unlisted asset), extended `content-relay.content.ts`, extended `page-protocol.ts`, `scripts/audit-mainworld-boundary.sh`.

**Explicit cross-browser decision (Research Architecture Pattern 3):** WXT's declarative `world: 'MAIN'` content-script field is Chrome-only; Firefox has no equivalent and needs `injectScript()`-based manual injection. This plan implements the Firefox variant NOW (not deferred to Phase 13), because ROADMAP's Phase 12 success criteria describe the extension as "a full passkey provider" without a Chrome-only qualifier, and PROV-04 already requires Firefox-specific behavior this phase. Do not let this default silently to "declarative `world:'MAIN'` works everywhere" — it does not.
</objective>

  <action>
    Define a WXT entrypoint with `matches: ['<all_urls>']`, `world: 'MAIN'`, `runAt: 'document_start'` (D-04). At module load, BEFORE any patching: `const originalCreate = navigator.credentials.create.bind(navigator.credentials); const originalGet = navigator.credentials.get.bind(navigator.credentials);` — capturing native refs first is what makes fallthrough and multi-extension coexistence (D-12) possible.

    Patch both `navigator.credentials.create`/`.get` with an async wrapper that: generates a per-call nonce (`crypto.randomUUID()`); posts `window.postMessage({source: 'pv-page-bridge', nonce, kind: 'credentials.create'|'credentials.get', origin: location.origin, publicKey: options.publicKey}, location.origin)` — target origin is ALWAYS `location.origin`, never `'*'` (D-03); listens for a single matching-nonce `message` event from `content-relay.content.ts` with a bounded timeout (choose and document 5000ms as the default — long enough for a popup-unlock round trip per D-09, short enough not to visibly stall the page; this resolves CONTEXT.md's open discretion item on the popup-await timeout). On a `credential` response: return a plain object shaped to satisfy `PublicKeyCredential`'s enumerable contract (`id`, `rawId`, `type: 'public-key'`, `response`, `getClientExtensionResults()`, `toJSON()`) — document in a comment that `PublicKeyCredential` cannot be constructed directly by page script (no public constructor), so a spec-shaped plain object is the same approach Bitwarden/1Password's extensions use, not an oversight. On a `fallthrough` signal, a relay-side error, OR the timeout firing: invoke the captured `originalCreate`/`originalGet` and return/reject with ITS real result — never let the wrapped function throw an error type the page didn't already trigger itself (D-11).

    Wrap the ENTIRE wrapper body in try/catch; any exception inside the wrapper (not from the original call) falls through to the original call too, never propagating a new/different error to the page.

    Extend `extension/lib/messaging/page-protocol.ts` with `CredentialsCreateEnvelope`/`CredentialsGetEnvelope` types: typed `unknown` for `publicKey`/`credential` fields at this boundary (12-PATTERNS.md's "thin wire-client, typed unknown" discipline) — interpretation of WebAuthn JSON shapes happens one layer up in background's `provider-ceremony.ts` (Plan 12-02), never in this file.

    HARD CONSTRAINT (D-02, grep-audited by Task 3): this file imports nothing beyond the typed envelope interfaces from `lib/messaging/page-protocol.ts` (data shapes, zero runtime crypto code) — no WASM bindings, no soft-authenticator crate bindings, no crypto or vault modules of any kind. See 12-CONTEXT.md's D-02 for the exact forbidden-import list used by Task 3's audit script. Do NOT restate that forbidden-import list as an in-file comment here or in Task 2's twin file — the audit script's grep pattern matches on the literal package/module names wherever they appear, including inside a comment, so a comment naming them would itself trip the audit as a false positive. If an explanatory comment is useful, describe the constraint by concept ("this file stays dependency-free per the zero-knowledge boundary, see D-02") rather than naming the specific forbidden imports.
  </action>
