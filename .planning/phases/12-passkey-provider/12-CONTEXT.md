# Phase 12: Passkey Provider - Context

**Gathered:** 2026-07-14
**Status:** Ready for planning

<domain>
## Phase Boundary

**In scope:** On third-party sites, the extension intercepts `navigator.credentials.create()` and `navigator.credentials.get()` and acts as a full WebAuthn passkey provider backed by the user's vault:
- Registration (`create()`): a new ES256 passkey is generated by an in-extension soft authenticator (`passkey-rs`) and saved to the vault as a new credential item.
- Authentication (`get()`): the extension signs an assertion with a vault-stored passkey matching the relying party.
- Clean fall-through to the native OS/platform authenticator (or another installed password-manager extension) whenever the user declines or the vault has no matching credential — the page's ceremony must never dead-end.
- PRF used where the browser/authenticator combination supports it (Chromium-first); an honest, specific fallback message everywhere else (Firefox, Safari/iOS-roaming-key combos, etc.).
- The MAIN-world `navigator.credentials` patch is a thin, key-free RPC shim; all WebAuthn/PRF ceremony logic, passkey-rs, and key material stay in the background service worker. Gated by an explicit `/gsd-secure-phase` security review before this phase is considered done (PROV-05, ROADMAP SC #5).

**Explicitly OUT of scope for this phase** (cross-ref neighbouring phases):
- Vault unlock/session/popup browse — already delivered by Phase 9 (this phase *consumes* the unlocked User Key via the existing session core; it does not re-implement it).
- Login/TOTP/card/identity DOM autofill — Phase 10. This phase reuses the ISOLATED content-relay messaging pattern Phase 10 establishes, but the *passkey* provider flow is a separate ceremony from filling form fields.
- Generated-password suggestion / save-new-login / password-change detection — Phase 11 (CAP-01/02/03). Not part of this phase, even though a passkey "registration" is conceptually adjacent to "saving a new login."
- Firefox/Chrome dual-browser hardening pass and final parity sign-off — Phase 13. This phase must implement the Firefox PRF-unavailable fallback message (PROV-04), but the dedicated cross-browser verification pass belongs to Phase 13.
- Mobile/Windows credential providers, `chrome.webAuthenticationProxy`-based provider path, FIDO CXF import/export — out of milestone entirely per REQUIREMENTS.md "Future Requirements"/"Out of Scope".
- Server-side changes: none expected. The passkey provider is entirely a client-side (extension) concern; `pv-server`'s existing CORS allowlist (established in Phase 9) and vault CRUD/sync contracts are reused unchanged for storing the new passkey credential item.

</domain>

<decisions>
## Locked Decisions

Each decision below is already fixed by the ROADMAP success criteria, the non-negotiable invariants, or the v0.2 research recommendations — not new product/UX choices made in this session.

### Architecture / trust boundary
- **D-01:** Three-context bridge is mandatory: MAIN-world page-bridge (key-free RPC shim, captures native `navigator.credentials` refs) → ISOLATED-world content-relay (validates/shapes `postMessage`, forwards via `browser.runtime.sendMessage`/`Port`) → background service worker (sole owner of passkey-rs, WASM, unlocked User Key, ceremony logic). Source: ARCHITECTURE.md Pattern 1; ROADMAP goal statement; PROV-05.
- **D-02:** The MAIN-world file must be dependency-free and never import `pv-wasm`/`passkey-rs` or touch raw key bytes, PRF output, or the unwrapped User Key — even transiently. This is the grep-auditable line PROV-05 requires and the security review checks. Source: PITFALLS.md Pitfall 5 (rated "single most severe possible mistake in this milestone"); INVARIANTS.
- **D-03:** `window.postMessage` payloads between MAIN and ISOLATED worlds carry only opaque WebAuthn ceremony data (challenge, credential ID, signed assertion, RP/user info) — never secrets — because the channel is page-readable by any script (`targeting '*'`). Source: PITFALLS.md Pitfall 5; ARCHITECTURE.md Pattern 1 example envelope.
- **D-04:** Injection timing uses MV3's native `world: 'MAIN'` content-script field at `document_start` (not the older `<script>`-tag injection workaround). Source: PITFALLS.md Pitfall 1.
- **D-05:** The background service worker is the only place passkey-rs/pv-wasm are imported/instantiated (reuse of Phase 8's WASM-in-background pattern and Phase 9's session core) — never in popup or content scripts. Source: ARCHITECTURE.md "Structure Rationale," Pattern 3.

### Crypto / authenticator
- **D-06:** `passkey-authenticator`/`passkey-client`/`passkey-types` (passkey-rs, 1Password's open-sourced crates, pinned together at the same version) is the soft ES256 WebAuthn authenticator — do not hand-roll a WebAuthn authenticator. Source: STACK.md/SUMMARY.md recommendation; PROJECT.md invariant "Add passkey-rs... for the ES256 soft authenticator in phase 12."
- **D-07:** New passkeys created via `create()` are stored as vault credential items using the existing `pv-core` wrap/AEAD primitives (Argon2id/XChaCha20-Poly1305/HKDF-SHA256) — no second, divergent crypto implementation. Source: CLAUDE.md conventions; REQUIREMENTS.md "Out of Scope: a second, divergent crypto implementation in JS."
- **D-08:** All HKDF domain-separation constants used by the provider ceremony (e.g., any new `pv:passkey-provider:vN`-style constant) must be versioned byte strings, distinct from existing `pv:pw-unlock:v1` / `pv:prf-unlock:v1` contexts — never reused across contexts. Source: INVARIANTS; CLAUDE.md "Domain Separation" conventions.

### Session / key lifecycle
- **D-09:** The provider ceremony consumes the already-unlocked User Key from `chrome.storage.session` (Phase 9's session core) — it never re-derives or re-stores key material outside that established envelope. If the vault is locked when a ceremony is invoked, the background opens the popup for an unlock prompt before proceeding (per ARCHITECTURE.md's data-flow diagram) rather than failing the ceremony outright. Source: ARCHITECTURE.md Data Flow ("needs unlocked UK? checks storage.session... if locked, opens popup for unlock prompt, awaits response"); EXT-02/EXT-03 (Phase 9).
- **D-10:** Every message handler in the background treats itself as possibly just-woken (re-check `storage.session`, don't assume in-memory state survived) — same discipline established in Phase 8/9, applied here to ceremony handlers. Source: PITFALLS.md Pitfall 3.

### Fallback / coexistence
- **D-11:** Fall-through to the native OS authenticator (or another installed password-manager extension) is required whenever the user declines the vault's prompt or no matching credential exists in the vault — the patched functions must never throw uncaught or dead-end the page's promise. Source: ROADMAP SC #3; PROV-03; PITFALLS.md Integration Gotchas ("feature-detect conflicts, fail open... never throw uncaught").
- **D-12:** The extension must not assume exclusive ownership of `navigator.credentials` — design for coexistence with another installed password-manager extension from the first version, verified in UAT with a second extension installed simultaneously (per ROADMAP SC #3's explicit verification instruction). Source: PITFALLS.md Pitfall 1.

### PRF / cross-browser
- **D-13:** PRF is attempted where the browser/authenticator combination supports it (Chromium-first, feature-detected via `clientExtensionResults.prf.enabled` at ceremony time, not assumed from browser/OS alone); wherever unavailable (Firefox, Safari/iOS-roaming-key combinations, etc.) the flow must degrade with an honest, specific message — never a silent failure or generic error. Source: PROV-04; PITFALLS.md Pitfall 2; ROADMAP SC #4.
- **D-14:** Password/session-based access must remain the universal fallback path everywhere in this phase's UX — PRF is never a hard requirement to complete a provider ceremony. Source: PITFALLS.md Pitfall 2; v0.1 multi-recipient wrap design (already established).

### Security review gate
- **D-15:** This phase is not complete until `/gsd-secure-phase` confirms (via grep-audit) that no User Key, PRF output, or plaintext crosses into MAIN-world JS — this is a named ROADMAP success criterion (#5), not an optional nice-to-have. Source: ROADMAP SC #5; PROV-05; INVARIANTS "Security-review gated."

### Discretion Areas
The following are left to the planner/executor to decide during plan-phase, since neither ROADMAP nor research locks a single choice:
- Exact WASM module boundary: whether passkey-rs is compiled into the same WASM binary as `pv-wasm` or a sibling module loaded alongside it in the background (ARCHITECTURE.md notes both as viable — "likely compiled into the same or a sibling WASM module").
- Exact UX/UI of the in-popup ceremony prompt (which passkey to use when multiple match an RP, decline button copy, PRF-unavailable message wording) — no specific copy or layout has been dictated; this phase has `UI hint: yes` in ROADMAP, so a UI-researcher/ui-phase pass is appropriate.
- Whether the "if locked, open popup and await unlock" flow (D-09) blocks the ceremony with a timeout, and what that timeout is — research flags this as an implementation detail, not a locked value.
- Exact mechanism for storing the newly-created passkey private key material in `chrome.storage.session` between ceremony and vault-save persistence (i.e., the precise envelope shape) — Pattern 2 in ARCHITECTURE.md describes the general shape (short-TTL, in-memory-only, deliberate exception to "keys never leave WASM") but leaves exact structure to implementation.
- Whether/how the extension surfaces "Passkey Vault will handle this" vs. "using your device" messaging (research suggests it as a differentiator, doesn't mandate exact wording).

</decisions>

<specifics>
## Specific Ideas

No specific UI mockups or exact wording were dictated for this phase. The research explicitly recommends (as a differentiator, not a hard requirement) making fall-through/coexistence *transparent* to the user — e.g., messaging that clarifies whether Passkey Vault or the native/OS authenticator is handling a given ceremony — since this is a known area of user confusion when multiple credential providers coexist.

</specifics>

<code_context>
## Existing Code Insights

### Reusable Assets (once Phases 8-11 land)
- `crates/pv-core` wrap/AEAD primitives (Argon2id, XChaCha20-Poly1305, HKDF-SHA256) — reused unchanged for wrapping the new passkey credential's private key material into a vault item.
- `pv-wasm` build/bindgen pipeline (existing pin: `wasm-bindgen=0.2.126`, `getrandom 0.2 js`) — the passkey-rs authenticator should be compiled through the same pipeline, not a divergent WASM toolchain.
- Phase 9's background service-worker skeleton, `chrome.storage.session` envelope, and sync client — this phase's `provider-ceremony.ts` is a new module alongside `vault-session.ts`/`sync-client.ts` in `entrypoints/background/`, not a replacement.
- Phase 10's ISOLATED content-relay and typed messaging contracts (`lib/messaging/page-protocol.ts`, `ext-protocol.ts`) — the passkey provider's `page-bridge.content.ts`/`content-relay.content.ts` extend this same messaging layer with new message kinds (`credentials.create`, `credentials.get`), not a parallel one.

### Established Patterns
- Zero-knowledge choke-point pattern from v0.1 (`web/src/lib/crypto/`) relocates to `entrypoints/background/` for the extension — this phase must preserve that single-grep-auditable-boundary property, now with the additional MAIN-world hostile-context constraint layered on top.
- v0.1's multi-recipient key wrapping (User Key wrapped independently by password and each enrolled passkey) is the existing pattern a new vault-stored passkey credential item should follow for storage shape.

### Integration Points
- Background `router.ts` (Phase 9/10) gains new `onMessage` cases for `credentials.create`/`credentials.get`, dispatching to a new `provider-ceremony.ts` module.
- `pv-server` vault CRUD/sync endpoints (unchanged) persist the new passkey credential item exactly like any other vault item — no new server routes anticipated for this phase.
- `pv-server` CORS allowlist for `chrome-extension://`/`moz-extension://` origins (established Phase 9, SC #5) must already be in place; this phase does not need to touch it again but should verify it still covers the sync calls triggered by saving a new passkey item.
