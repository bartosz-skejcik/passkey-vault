<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| WS frame (untrusted network payload) → `pullOnce()` trigger | The frame's bytes never cross into any code path that treats them as data — carried over unchanged from v0.1 (D-07) |
| Background's decrypted item cache (`vault-store.ts`) ↔ lock state | The one place plaintext vault data is held in this extension outside `pv-wasm`'s own memory — must be provably empty whenever the vault is locked |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-09-12 | Tampering | `sync-client.ts`'s WS message handler | high | mitigate | `socket.onmessage` never reads `.data` — any frame, regardless of content, only triggers `pullOnce()`'s authenticated REST fetch; carried over unchanged from v0.1's SYNC-02/D-07 boundary, re-verified by Task 2's ported test suite |
| T-09-18 | Information Disclosure | `vault-store.ts`'s decrypted item cache surviving a lock event | high | mitigate | Task 3's Test 3/4 assert `stopSync()` runs before the array-clear and that `getItems()`/`getFolders()` are empty immediately after a lock event — the exact Pitfall 4 failure mode this plan is written to prevent |
| T-09-19 | Race Condition (Information Disclosure) | A snapshot fetch in flight when a lock event fires, applied after the fact | medium | mitigate | `applySyncSnapshot` re-checks `getUnlockedUserKey() !== null` immediately before decrypting (Task 3 Test 2) — a snapshot arriving after a lock is silently dropped, never decrypted into the now-supposed-to-be-empty cache |

</threat_model>
