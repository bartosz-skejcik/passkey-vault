## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| popup ↔ background (runtime.sendMessage) | Both are extension-privileged contexts (same trust tier) — no content script or page exists yet this phase |
| background ↔ chrome.storage.session | Platform-enforced `TRUSTED_CONTEXTS` access level — the only persistence layer for the unlocked key envelope |
| background ↔ chrome.alarms | Platform primitive, not attacker-influenceable directly, but its silent-failure mode is a security-relevant availability concern |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-09-05 | Information Disclosure | session-storage.ts's `chrome.storage.session` access level | high | mitigate | Never call `setAccessLevel(TRUSTED_AND_UNTRUSTED_CONTEXTS)` — documented as a standing anti-pattern directly above the storage functions so a future content-script phase (10+) doesn't "fix" this by widening it |
| T-09-06 | Information Disclosure | Exported User Key bytes lingering in a JS `Uint8Array` after `writeEnvelope()` | high | mitigate | `setUnlockedUserKey`'s `finally` block zeroizes the transient buffer regardless of write success/failure, mirroring `deriveAuthMaterial`'s discipline |
| T-09-07 | Denial of Service (of the security control) | Auto-lock alarm silently failing to fire (e.g., after a browser update resets scheduled alarms) | medium | mitigate | `background/index.ts`'s startup/`onInstalled` handler defensively re-arms the alarm whenever `ensureHydrated()` finds the vault still logically unlocked; `noteActivity()` also re-arms on every message, so a single missed alarm-creation call is not fatal |
| T-09-08 | Tampering | A corrupted/tampered `idleTimeoutMinutes` value in the stored envelope | low | accept | `autolock.ts`'s whitelist validation (`AUTOLOCK_OPTIONS`) is applied wherever the value is READ for arming — an out-of-whitelist value falls back to `DEFAULT_AUTOLOCK_MINUTES`, matching v0.1's `readAutolockMinutes()` precedent; low severity since the worst case is a longer-than-intended (not indefinite) unlock window |
