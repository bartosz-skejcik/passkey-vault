## Spacing Scale

Declared values (must be multiples of 4) — same numeric scale as the web app and `13-UI-SPEC.md`, with the same one popup-specific exception `13-UI-SPEC.md` already established:

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon-to-label gaps, badge inline padding, item-detail field-row internal gaps |
| sm | 8px | Compact row spacing (item-list rows), `Loader2`/spinner offsets, copy-toast micro-spacing |
| md | 16px | **Popup container horizontal padding** (not 24px — see exception below), default vertical rhythm between popup sections (search bar → list, list → footer auto-lock control) |
| lg | 24px | Vertical section padding within the popup body (unlock card's own internal padding, item-detail panel's internal padding) |
| xl | 32px | Unused in the popup this phase — no surface needs it at 360-400px width |
| 2xl / 3xl | 48px / 64px | Unused this phase |

**Exception — popup horizontal padding is 16px, not the web app's usual 24px** (inherited verbatim from `13-UI-SPEC.md`'s reasoning): at 360-400px viewport width, 24px per side eats too much into row content (favicon + two text lines + trailing affordance). Still an 8-point value (`md` instead of `lg`), not an arbitrary number. Vertical padding keeps the standard `lg`/24px rhythm.

**Touch-target exception:** icon-only controls (copy-to-clipboard buttons, back-chevron, password-reveal toggle) get a 40px hit area even where the visible glyph is 16-20px — same rule as `02`/`03`-UI-SPEC.md's accessibility contract, unchanged.

## Phase-Specific Notes

### Popup shell (authoritative this phase — supersedes `13-UI-SPEC.md`'s placeholder sketch with the same numbers)

- **Viewport:** fixed width 360-400px (browser-imposed popup constraint), variable height up to ~600px before the browser clips/scrolls — no popup screen this phase assumes more vertical room than that.
- **Top-level states, one visible at a time (popup is single-view, no tabs):**
  1. **Loading** — shown for the brief window between popup mount and the background responding to the first `session.status`/`vault.list` message. Centered `loading loading-spinner` + `Ładowanie sejfu…`/`Loading your vault…` (Body role, `base-content/70`).
  2. **Sign-in / Unlock** (see below) — shown whenever the background reports the vault is locked (no valid session envelope), regardless of *why* (fresh install, auto-lock fired, browser restart).
  3. **Item List + Search** — shown once unlocked and the background's `vault-store.ts` cache is populated.
  4. **Item Detail** — an in-popup panel swap (not a new window, not a side-by-side split — there's no room beside it at 360px), replacing the list view with a `ChevronLeft`-led back affordance at the top.
- **Row height:** 48px minimum for item-list rows (reused verbatim from `13-UI-SPEC.md` — tighter than the web app's 64px rows since popup real estate is scarcer and rows carry less per-row content this phase: favicon/type-icon + two text lines, no trailing action button yet).

### Popup header + delegated-management affordances (BINDING — Bartek 2026-07-15, NordPass reference screenshots)

Bartek supplied NordPass popup screenshots as the interaction reference: even a mature product implements **neither settings nor item creation inside the popup** — both redirect to the fullscreen web vault. That is exactly our EXT-06 doctrine; the popup gains the affordances but they are PURE REDIRECTS via the configured server URL (`config.get` → `browser.tabs.create`), never in-popup forms:

- **Slim header row** (above the search bar, list view only): `Settings` lucide gear icon-button on the left (aria-label PL `Ustawienia` / EN `Settings`; opens `${baseUrl}/?panel=settings` in a new tab), the existing "open full vault" control on the right as a compact `btn btn-ghost btn-sm` labeled PL `Pełny widok` / EN `Full screen` with the `ExternalLink` icon (relocated from the footer per the NordPass layout).
- **"+" new-item button**: `Plus` lucide icon-button, bottom-right of the list view (small FAB-style, `btn btn-primary btn-circle btn-sm`, aria-label PL `Nowy element` / EN `New item`; opens `${baseUrl}/?action=new-item` in a new tab). NO in-popup create form, NO type-picker menu in the popup this phase — the web app's own new-item flow handles type selection.
- **Footer row** keeps the auto-lock `select` only.
- **Web-app side (small, same phase):** the SPA at `/` reads `panel=settings` / `action=new-item` query params on mount and — after the vault is unlocked — opens the Settings panel / new-item dialog respectively, then strips the param from the URL (history.replaceState) so refresh doesn't re-trigger. If locked, the param survives until unlock completes, then applies once.
- All three redirect URLs derive EXCLUSIVELY from `config.get` (EXT-06's no-hard-coded-URL invariant applies — the grep gate in 09-06 covers these new controls too).

### Unlock / Sign-in view

Two sub-variants of one screen, distinguished only by whether an email field is present — mirrors `04-UI-SPEC.md`'s `LoginForm`-vs-`UnlockOverlay` split, relocated into the popup's single-column layout:

**Sign-in variant** (no valid bearer session token in `chrome.storage.session` — first popup open, or after a very long absence):
1. Email field (`input input-bordered`, required, pre-filled from any previously-stored email if the background has one cached, always editable).
2. PRF unlock button (`unlock.passkeyLoginCta` copy) — or the Tier-1 explainer line in its place, exact same absent-vs-disabled rule as `04-UI-SPEC.md` (button doesn't render at all when `window.PublicKeyCredential === undefined`; a plain explainer line takes its slot).
3. Tier-2 / cross-browser-gap / Tier-3 explainer line, only when applicable (see Copywriting Contract).
4. `divider` ("lub"/"or").
5. Password field (`font-mono`).
6. Coral `btn btn-primary` submit (`unlock.submit`).

**Unlock-only variant** (valid session token exists, only the User Key envelope is missing/expired — the common case: auto-lock fired, or SW woke from a browser restart):
1. Session-locked notice line (Label, `base-content/70`) — only shown when the lock was auto-lock-triggered (background can distinguish "never logged in" from "was unlocked, now locked" and passes that flag along); omitted on true first-open.
2. PRF unlock button (`unlock.passkeyCta` copy, shorter unlock-only wording) — or Tier-1 explainer.
3. Tier-2 / cross-browser-gap / Tier-3 line, as above.
4. `divider`.
5. Password field + coral submit — no email field, the account is already known from the stored session token.

Both variants share the exact card vocabulary already established (`AuthCard`/`UnlockOverlay`'s 16px radius, 1px border, 24px internal padding), simply narrowed to the popup's 360-400px width — which, per `04-UI-SPEC.md`'s own dimensions (a 400px card), needed **no adaptation at all**: the existing unlock card was already popup-width-compatible before this phase started.

### Item List + Search view

- Top: `input input-bordered` search bar, `Search` icon leading, sticky top, instant-filter on every keystroke (no debounce — `search.ts`'s `searchItems`/`filterItems` is a synchronous pure function over an already-in-memory decrypted list per `vault-store.ts`, so there is no network-call-per-keystroke cost to debounce against; this matches CONTEXT.md's Discretion Area's default of mirroring the web app's existing behavior).
- Below: item rows (48px min height) — item-type icon (20-24px: `KeyRound` teal/muted, `CreditCard`, `IdCard`, `StickyNote`) → item name (Body) + username/subtext (Label, muted) stacked → no trailing action button this phase (reserved slot for Phase 10's "Fill" button — this phase's row affordance is the row itself: tap/click opens Item Detail).
- Empty states: zero items in vault → the "vault empty so far" copy (Copywriting Contract); zero search matches → the reused `Brak wyników dla „{query}"` line, same neutral tone, no icon, no color.
- Sync-driven updates (an edit landing from another synced client) re-render the list in place, no toast/notification needed this phase — `05-UI-SPEC.md`'s live-edit-conflict banner (`AlertCircle`, informational not alarming) is **out of scope here** since this phase has no open-for-edit state to conflict with (read-only browse); if Phase 10/11 later opens an editable surface in the popup, that banner pattern is the one to reuse, not reinvent.

### Item Detail view (minimal, per CONTEXT.md's Discretion Area — picker-only depth, not full CRUD)

- Header: `ChevronLeft` back button (40px hit area) + item name (Heading) + item-type badge.
- Body: field rows only for fields that exist on this item type — label (Label role) + value (Body role, or `font-mono` for password/TOTP/card-number-shaped values) + trailing `Copy`/`Check` icon button (40px hit area, flash-confirm on click, reused verbatim from `02-UI-SPEC.md`).
- Password fields default **masked** with an `Eye`/`EyeOff` reveal toggle (reused convention) — never rendered in plaintext by default, matching the web app's item-detail security posture.
- No edit, no delete, no "open in web app" deep-link this phase (all deferred — CONTEXT.md's Deferred Ideas list explicitly keeps CRUD out of this phase's scope). If the item type is a passkey-managed credential, its RP ID / "last used" metadata (from `03-UI-SPEC.md`'s passkey-detail convention) **MUST render read-only whenever present in the synced item payload — RESOLVED by Bartek 2026-07-15 (Review Question 4): guaranteed this phase, not executor discretion.** Fields absent from the payload render as a muted "—" placeholder row, never silently omitted, so the surface is ready when Phase 12's provider starts writing these fields.

### Auto-lock control (EXT-03, resolves CONTEXT.md's Discretion Area)

- Default idle timeout: **15 minutes** — matches the web app's own `AUTH-08` default (`02-UI-SPEC.md`: "1/5/15/30/60 min, default 15") and 09-RESEARCH.md's own recommendation, so the extension and web app read as one consistent product rather than picking a divergent number.
- Surfaced as a single `select select-bordered select-sm` control (options: 5/15/30/60 min, same set as the web app) in a lightweight footer row below the item list — **not** a dedicated settings screen (CONTEXT.md's Deferred Ideas explicitly excludes a broader settings surface; this is the one control EXT-03's "configurable" wording requires, kept to a single row, not a new view).
- Changing the value re-arms the `chrome.alarms` timer immediately (background responsibility, not a UI concern) — the control itself is a plain, unstyled-beyond-`select-sm` DaisyUI form element, no confirm dialog (non-destructive, reversible instantly).

### Accessibility

- `Fingerprint`/`Loader2` inside the PRF button, `Search` inside the search bar, `ChevronLeft`/`Copy`/`Eye`/`EyeOff` in item detail are all `aria-hidden="true"` — each control's visible text label or accessible name (via `aria-label` for icon-only buttons) carries the semantics, per the standing "decorative icon inside a labeled control" rule from `01`-`03`-UI-SPEC.md.
- Icon-only controls (back button, copy buttons, reveal toggle) get explicit `aria-label`s (`"Wróć do listy"`/`"Back to list"`, `"Kopiuj hasło"`/`"Copy password"`, `"Pokaż hasło"`/`"Show password"`) — same convention as `02-UI-SPEC.md`'s icon-only accessibility contract, not a new pattern.
- Search-result-count changes are not wrapped in an `aria-live` region this phase (consistent with `04-UI-SPEC.md`'s precedent of not adding one for the fallback-tier lines) — flagged as a reasonable follow-up hardening, not blocking.
