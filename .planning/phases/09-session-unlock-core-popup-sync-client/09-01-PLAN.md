  ```rust
  // SANCTIONED EXCEPTION (CONTEXT.md D-02): the MV3 extension's service
  // worker destroys its WASM instance (and every opaque handle in its linear
  // memory) on idle-kill, so the extension MUST be able to serialize a
  // WasmUserKey's raw bytes into chrome.storage.session and reconstruct it
  // on wake. This is the ONLY place raw User Key bytes cross the WASM
  // boundary as a Vec<u8> in the whole codebase — web/ NEVER calls these two
  // functions; only extension/entrypoints/background/vault-session.ts may.
  // Callers MUST zeroize the JS-side byte buffer immediately after writing
  // it to chrome.storage.session (Phase 9 Wave 2's responsibility).
  #[wasm_bindgen(js_name = exportUserKeyForSession)]
  pub fn export_user_key_for_session(uk: &WasmUserKey) -> Vec<u8> {
      uk.0.expose().to_vec()
  }

  /// Inverse of `exportUserKeyForSession` — reconstructs a `WasmUserKey` from
  /// its raw exported bytes. `bytes` is zeroized (WASM-side, and via
  /// wasm-bindgen's mutable-slice copy-back, the JS-side view too)
  /// regardless of success or failure, mirroring `from_password`'s/
  /// `from_prf`'s zeroize-regardless-of-outcome discipline.
  #[wasm_bindgen(js_name = importUserKeyFromSession)]
  pub fn import_user_key_from_session(bytes: &mut [u8]) -> Result<WasmUserKey, JsValue> {
      if bytes.len() != KEY_LEN {
          bytes.zeroize();
          return Err(to_js_str_err("expected 32 bytes"));
      }
      let mut arr = [0u8; KEY_LEN];
      arr.copy_from_slice(bytes);
      bytes.zeroize();
      Ok(WasmUserKey(UserKey::from_bytes(arr)))
  }
  ```

  Add three tests inside the existing `#[cfg(test)] mod tests` block (same file), following the exact style of `full_roundtrip`/`from_prf_rejects_short_input`:

  ```rust
  fn cors_layer() -> CorsLayer {
      let dev_cors_enabled = std::env::var("PV_DEV_CORS")
          .map(|v| v == "1" || v.eq_ignore_ascii_case("true"))
          .unwrap_or(false);
      let extension_origins_csv = std::env::var("PV_EXTENSION_ORIGINS").unwrap_or_default();
      build_cors_layer(dev_cors_enabled, &extension_origins_csv)
  }

  /// Pure, env-free core of `cors_layer()` — split out so it is unit-testable
  /// against a real HTTP request/response (see `mod tests` below) without
  /// mutating process-global env vars, which would be flaky under parallel
  /// `cargo test` execution. `extension_origins_csv` is a comma-separated
  /// list of allowed origins, e.g. "chrome-extension://<id>,moz-extension://<id>"
  /// (CONTEXT.md D-08 — additive to, never replacing, PV_DEV_CORS).
  fn build_cors_layer(dev_cors_enabled: bool, extension_origins_csv: &str) -> CorsLayer {
      if dev_cors_enabled {
          return CorsLayer::permissive();
      }
      let origins: Vec<_> = extension_origins_csv
          .split(',')
          .map(str::trim)
          .filter(|s| !s.is_empty())
          .filter_map(|s| s.parse().ok())
          .collect();
      if origins.is_empty() {
          CorsLayer::new() // unchanged existing behavior when unset
      } else {
          CorsLayer::new()
              .allow_origin(AllowOrigin::list(origins))
              .allow_methods(Any)
              .allow_headers(Any)
      }
  }
  ```

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| pv-server ↔ extension origin (network) | `chrome-extension://<id>` / `moz-extension://<id>` cross-origin fetch()/WS calls, authenticated via Bearer token in header or WS query param — no cookies/credentials mode involved |
| pv-wasm export boundary | `exportUserKeyForSession` deliberately lets raw User Key bytes leave the opaque WASM handle as a `Vec<u8>` — the one sanctioned crack in the "opaque handle only" invariant |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-09-01 | Spoofing | `build_cors_layer`'s origin allowlist | high | mitigate | `AllowOrigin::list` with exact, explicit origin strings (never a wildcard scheme predicate like "any chrome-extension://*"); each origin string is parsed via `HeaderValue`'s own strict parser, invalid entries silently dropped rather than defaulting to permissive |
| T-09-02 | Information Disclosure | `exportUserKeyForSession` (pv-wasm) | high | mitigate | Extension-only, grep-auditable name (`grep -r exportUserKeyForSession` should only ever match `vault-session.ts` once Phase 9 Wave 2 lands); doc comment explicitly states web/ must never call it; caller-side zeroize-after-write discipline is Wave 2's responsibility (documented here so it is not lost across the wave boundary) |
| T-09-03 | Tampering | `PV_EXTENSION_ORIGINS` misconfiguration | medium | mitigate | Malformed/empty entries are dropped by the `HeaderValue` parse rather than silently widening access; an entirely empty/unset value degrades to today's existing no-CORS behavior (fail-closed), never to permissive |
| T-09-04 | Denial of Service | `import_user_key_from_session` wrong-length input | low | accept | Returns a typed `Err` rather than panicking; length mismatch is the only validated failure mode and is exercised by a test — no un-panicked path exists for malformed session-storage data |

</threat_model>
