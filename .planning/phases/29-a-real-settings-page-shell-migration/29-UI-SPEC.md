# Phase 29 — UI Design Contract

> Visual and interaction contract for the `/settings` route shell + migration. Generated by
> gsd-ui-researcher, verified by gsd-ui-checker. This phase moves a container and fixes one
> honesty defect (DEBT-02); it does **not** redesign Family & Sharing (SET-03 — Phase 33).

---

## Design System

| Property | Value |
|----------|-------|
| Tool | none — shadcn was never adopted (`components.json` absent, confirmed) and is **not** introduced by this phase. The project has its own mature design system. |
| Preset | not applicable |
| Component library | DaisyUI 5 primitives (`btn`, `tabs`, `alert`, `dropdown`, `join`, `badge`, `card`-adjacent `rounded-box border` row treatment) + `packages/pv-ui` (i18n engine `t`/`interpolate`, `ItemIconTile`, fingerprint display) |
| Icon library | `lucide-react` (already the sole icon source in `web/src/components/shell/Sidebar.tsx`, `SettingsPanel.tsx`, all `*Tab.tsx`) |
| Font | DM Sans (`--font-sans`) for all page chrome, headings and body. **Fuzzy Bubbles and emoji are explicitly forbidden anywhere on `/settings`** — UI-DESIGN.md's "security UI zawsze czytelne" rule already excludes them from settings-adjacent dialogs; this phase extends that exclusion to the whole page now that settings is a first-class surface, not just a panel. |

Reuse discipline: this phase must not invent new OKLCH values, radii, or component primitives.
Every token below is either an existing `packages/pv-ui/tokens.css` value or an existing
in-codebase Tailwind utility pattern (cited by file:line where one exists).

## Spacing Scale

Declared values (must be multiples of 4), reused from the project's existing informal 4px scale
(`gap-1`…`gap-16`, `p-4`/`p-6` throughout `web/src/components/shell/Sidebar.tsx`/`SettingsPanel.tsx`):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon-to-label gaps (back-link icon, jump-nav pill icon if any) |
| sm | 8px | Compact row spacing inside migrated tab content (unchanged, e.g. `gap-2` list rows) |
| md | 16px | Group heading → description → content gap; page horizontal padding on mobile (`px-4`) |
| lg | 24px | Page horizontal padding on desktop (`px-6`); jump-nav rail ↔ content gap |
| xl | 32px | Header ↔ first group gap |
| 2xl | 48px | Group-to-group gap on mobile (`<768px`); page horizontal padding at the widest desktop breakpoint (`px-12`) |
| 3xl | 64px | Group-to-group gap on desktop (`≥768px`) — deliberately larger than the 2xl default to make SET-04's "predict where a setting lives" test read clearly on a full page, where the old 400px panel had no room to breathe between tabs |

Exceptions:
- Mobile jump-nav pills use a `min-h-11` (44px) tap target even though their visual content is
  smaller — icon-only/short-label touch-target floor, matching the template's own standard
  exception class.
- Group-to-group gap is 3xl (64px) desktop / 2xl (48px) mobile, not a single fixed value — see
  table above.

## Typography

Four roles: two reused, two new. `Body` (16px) and `Label` (14px) reuse the codebase's existing
`text-base`/`text-sm` usage throughout `SettingsPanel.tsx`/`*Tab.tsx`. `Display` (28px) and
`Heading` (24px) are both **new** — neither exists in shipped code today; the closest existing
size is the 20px dialog/sub-heading tier (`SettingsPanel.tsx:40`, `ExportDialog.tsx:45` =
`text-[20px] font-bold leading-[1.2]`), which this phase does not reuse for either role (see the
hierarchy note below for why, and for where that 20px tier ends up instead).

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Display (page `<h1>`) | 28px | 700 (bold) | 1.2 |
| Heading (group `<h2>`) | 24px | 700 (bold) | 1.2 |
| Body | 16px | 400 (regular) | 1.5 |
| Label (secondary/meta text) | 14px | 400 (regular) | 1.5 |

Only two weights in the whole contract: 400 and 700 — the codebase has never used 600/semibold
(`font-bold` is the only non-regular weight found across `SettingsPanel.tsx`, `ExportDialog.tsx`,
`FamilyTab.tsx`), so this phase does not introduce a third.

**Deliberate hierarchy note (locks an ambiguity the migration would otherwise trip on):** existing
internal sub-headings — `ConfirmDialog.tsx:79`, `DeleteAccountDialog.tsx`, `EnrollPasskeyDialog.tsx:61`,
`RemoveMemberDialog.tsx`, `FamilyTab.tsx` (multiple), and `SecurityTab.tsx:131`'s
`account.deleteSectionHeading` — are all `text-[20px] font-bold leading-[1.2]`, the **same size**
this phase would otherwise have reused for the new group `<h2>`. Reusing 20px for the group
heading would make a group heading visually indistinguishable from a dialog title or an existing
internal `<h3>`, defeating SC3's "a reviewer can point at the heading that owns any given
setting" test. Resolution: the new group `<h2>` is **24px**, one size above every pre-existing
heading in this design system. Every existing 20px heading (dialog titles, `FamilyTab`'s internal
`<h2>`/`<h3>`s, `SecurityTab`'s `account.deleteSectionHeading`) stays **exactly as shipped, unchanged**
— they now sit correctly *between* the new 24px group heading and 16px body text in the page's
hierarchy (`28 h1 > 24 h2(group) > 20 h3(pre-existing internal) > 16 body`). This is a purely
additive typographic decision — it requires zero edits to `FamilyTab.tsx` (whose content is
carried across verbatim, protecting the Phase 33 boundary) and exactly one edit to
`SecurityTab.tsx` (see Migration Mapping — its delete-account sub-heading moves to a different
group, not a different size).

**This 20px tier is inherited, not declared.** It is not one of this phase's four typography
roles and is not part of its size budget — it survives on the page purely because 29-CONTEXT.md
locks the migrated components (`FamilyTab.tsx` especially) as verbatim carry-across, and this
phase has no mandate to touch their internal headings. A later reader of this contract should not
count `28 / 24 / 20 / 16` as "four declared sizes plus a stray fifth" — it is `28 / 24 / 16 / 14`
declared (Display / Heading / Body / Label), with a pre-existing, out-of-budget 20px tier
inherited from carried-across content and positioned correctly underneath the new Heading role.

| Accent (10%) | `primary` (koral `#E16540`) | Reserved for: the active state of the jump-nav's current-in-view link (background `bg-primary/[0.08]` + `text-primary`, the identical `navItemClass` pattern already in `web/src/components/shell/Sidebar.tsx:67-73` — reused verbatim, not reinvented); primary-action buttons already inside migrated content (`Zaimportuj hasła` / `Eksportuj vault` CTAs, `settings-import-cta`/`settings-export-cta`, unchanged); focus rings |

light per `packages/pv-ui/tokens.css:42,60`) and a single hex annotation would misrepresent
whichever theme it wasn't computed from. `primary`/`error` above keep their hex annotations
because those are theme-invariant per UI-DESIGN.md's Color section (same OKLCH hue/chroma in both
themes, confirmed by `tokens.css`'s own comment that non-`base-*` tokens are declared once on
`:root` and never overridden per-theme).

Accent is explicitly **not** used for: group headings, jump-nav inactive items, back-to-vault
link, or any icon that isn't inside an active/primary state. Passkey-teal (`#00CDB7`) inside the
Konto group's passkeys list is pre-existing domain color (per UI-DESIGN.md's "Passkey = teal"
rule) and is unchanged — it is not part of this phase's 10% accent budget, it is a separate,
already-settled domain-semantic color.

Export's existing `alert-warning` banner (`#FFBE00`) is unchanged — see DEBT-02 Export Disclosure
below for why the new disclosure sentence does **not** get its own color treatment.

## Page Layout Contract

**Visual focal point.** The `<h1>` + header bar is the page's primary visual anchor — it is the
largest text on the page (Display, 28px/700), sits fixed at the top on every scroll position
(`sticky top-0`), and is the first thing rendered. The jump-nav's active pill/link is the **only**
other accent-bearing (`primary`-colored) element ever in view at once — with the header
established as the anchor and the jump-nav's single active item as the sole secondary point of
color, an executor does not have to infer where the eye should land first.

**Route & chrome.** `/settings` is a full-width standalone page: the vault `Sidebar` is not
rendered on this route (own layout branch, not `Sidebar` conditionally hidden via CSS — a hidden-
but-mounted sidebar would still cost a render and contradicts "you have left the vault"). The page
supplies its own `<header>`.

**Header** (`sticky top-0 z-10 border-b border-base-300 bg-base-100`):
1. Back-to-vault link, `<a href="/" data-testid="settings-back-to-vault">`: `ArrowLeft` (lucide,
   16px) + `settings.backToVault` label, `text-sm text-base-content/70`, hover
   `text-base-content` — same understated treatment as `web/src/components/shell/Sidebar.tsx`'s dropdown items, deliberately
   not accent-colored (it is navigation, not a primary action).
2. `<h1>` `settings.title`, Display role (28px/700/1.2), directly below the back-link.
Mobile (`<768px`): back-link and `<h1>` stack in a `flex-col`; header never truncates or wraps
awkwardly at 375px — verified, not assumed.

**Jump-nav.** A `<nav aria-label={t("settings.jumpNavLabel")}>` landmark listing the four group
names as in-page anchor links (`#konto`, `#bezpieczenstwo`, `#dane`, `#rodzina` — ASCII slugs,
fragment-safe).
- **Desktop (`≥768px`):** a slim vertical rail, `sticky top-[header height]`, fixed width ~200px,
  positioned left of the content column inside a `grid grid-cols-[200px_1fr] gap-6 max-w-5xl
  mx-auto` page grid. Active item (the group currently in viewport, via `IntersectionObserver`
  scroll-spy) uses the **exact** `navItemClass` active pattern already shipped in
  `web/src/components/shell/Sidebar.tsx:67-73` (`bg-primary/[0.08] text-primary`) — reused, not reinvented.
- **Mobile (`<768px`):** the vertical rail does **not** survive a 375px viewport (explicitly
  called out as a risk — this is the concrete resolution). It becomes a horizontal,
  `overflow-x-auto`, `sticky top-[header height]` row of pill-shaped links (`rounded-selector`,
  `1.9rem` radius per UI-DESIGN.md's badge-pill geometry), each `min-h-11` (44px tap target).
  Active state: same `bg-primary/[0.08] text-primary` treatment, applied to the pill.

**Content column.** `max-w-2xl` (672px), regardless of the page's own width. This is a
**deliberate reflow-prevention decision**, not cosmetic: `FamilyTab.tsx`'s markup (and to a
lesser extent `SessionsTab`/`PasskeysTab`'s row lists) was built and visually tuned for a 400px
drawer. Letting it stretch to fill a 1000px+ page column before Phase 33's redesign would make it
look sparse or broken — exactly the "shipping a lift-and-shift as if it satisfied SET-03" failure
mode SC5 warns against, at the visual level. The page's extra width is spent on margin and the
jump-nav rail, **never** on stretching migrated content wider than it was designed for.

**Section anatomy** (each of the 4 groups): `<section id="{slug}" aria-labelledby="{slug}-heading"
data-testid="settings-section-{slug}" className="scroll-mt-[header+jumpnav height] flex flex-col
gap-4">`
1. `<h2 id="{slug}-heading">` — Heading role (24px/700/1.2), the group name.
2. Optional description `<p>` — Label role (14px/400), `text-base-content/70`, one line, from the
   table above.
3. Content — the migrated component(s), unmodified internally except where Migration Mapping
   below requires a relocation. No outer card/border wraps the whole section; existing
   `rounded-box border border-base-300` row treatments inside the migrated components are kept
   as-is.
4. `border-t border-base-300` divider before the *next* group (not after the last).

`scroll-mt-*` on every `<section>` and every `<h2>` is required so a jump-nav click lands the
heading below the sticky header+nav, not underneath it.

## DEBT-02 Export Disclosure

**Resolution (locked by 29-CONTEXT.md): disclose at export time, never mask.** The export dialog
states plainly that the file contains passwords for items shared to the user at `hidden_password`
access level, quantified by count.

**Placement — must not compete with the existing warning banner.** `ExportDialog.tsx:67-69`
already renders one `alert alert-warning` box (`data-testid="export-warning-banner"`) containing
`export.warningBody`. The DEBT-02 sentence is a **second `<p>` inside that same alert box**, not a
new colored alert, not a second `alert-warning`/`alert-info` element:

```
<div className="alert alert-warning" data-testid="export-warning-banner">
  <div className="flex flex-col gap-1">
    <span>{t("export.warningBody")}</span>
    {hiddenPasswordCount > 0 ? (
      <p data-testid="export-hidden-password-disclosure">
        {interpolate(t("export.hiddenPasswordDisclosure"), { n: hiddenPasswordCount })}
      </p>
    ) : null}
  </div>
</div>
```

- **Count source:** `getItems().filter(isPasswordHidden).length` — `isPasswordHidden` already
  exists at `web/src/lib/vault/itemCapabilities.ts:32` and is the single established predicate for
  this exact access level; no new predicate should be introduced.
- **Zero-count behaviour:** at `hiddenPasswordCount === 0`, the `<p>` does not render at all — no
  placeholder, no "0 items" sentence.
- **JSON and CSV parity:** the disclosure sentence and the count it reports are computed once in
  `ExportDialog.tsx` (format-agnostic — the dialog, not the exporter, owns the statement) and
  apply identically regardless of which format tab (`export-format-json`/`export-format-csv`) is
  selected. Neither `toCsv.ts` nor `toJson.ts` gains any new masking logic — DEBT-02's resolution
  is explicitly *not* to change what the exporters emit, only to state honestly what they already
  emit.
- **No per-export checkbox** — one stated behaviour, no opt-in/opt-out control (locked decision).
- **Verification bar (SC4):** the bytes of a real generated export file must contain the
  `password` field for every `hidden_password`-level item, matching what the dialog states. This
  is a live-run/file-byte assertion, not a unit-test-only claim (Non-Negotiable #2).

## Accessibility Contract

- **Heading order:** exactly one `<h1>` (`settings.title`) → four `<h2>` (group headings, in
  document order matching the locked sequence Konto → Bezpieczeństwo → Dane → Rodzina i
  udostępnianie) → any pre-existing `<h3>`/20px headings inside migrated content, unchanged. No
  heading level is skipped.
- **Jump-nav landmark:** `<nav aria-label={t("settings.jumpNavLabel")}>` — a real landmark, not a
  generic `<div>`. Links are real `<a href="#slug">` elements, not buttons with `onClick` scroll
  handlers, so they remain keyboard- and screen-reader-navigable via the browser's native anchor
  behavior even if the scroll-spy JS fails to load.
- **Focus management on jump-nav activation:** each group `<h2>` gets `tabIndex={-1}`. On a
  jump-nav link click, after the browser's native anchor scroll, the corresponding `<h2>` receives
  `.focus()` — so a screen-reader user lands on the heading that owns the destination content, not
  merely at an unannounced scroll position. This is a required behavior, not a nice-to-have: it is
  the direct replacement for the tab semantics being retired (see below).
- **`role="tablist"` retirement — must not be left half-migrated.** `SettingsPanel.tsx:52-102`'s
  `<div className="tabs tabs-bordered" role="tablist">` with five `role="tab"` buttons is fully
  removed, not hidden or left dormant. The new page has **zero** occurrences of `role="tablist"`,
  `role="tab"`, `aria-selected`, or the DaisyUI `tabs`/`tab`/`tab-active` classes anywhere on
  `/settings`. The replacement semantics are: `<nav>` (jump-nav) + `<section
  aria-labelledby="...">` (each group) — a navigation-and-landmark model, not a
  selection/disclosure (tab) model, because content is never hidden behind a tab click on this
  page (SC3's literal requirement).
- **Sidebar gear → link:** `web/src/components/shell/Sidebar.tsx:576-583`'s `sidebar-open-settings` element changes from
  `<button onClick={() => onOpenSettings?.()}>` to `<a href="/settings"
  data-testid="sidebar-open-settings">`, keeping its existing `aria-label={t("aria.openSettings")}`
  and icon. Tests asserting `getByRole("button", ...)` on this element must change to
  `getByRole("link", ...)` — call this out explicitly to whoever migrates `Sidebar.test.tsx`, since
  it is exactly the kind of one-line assertion change that is easy to miss and easy to mistake for
  "weakening" a test when it is in fact required by SET-01 itself (real link semantics).
