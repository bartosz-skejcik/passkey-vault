<objective>
Harden the extension's cross-browser manifest/CSP configuration and install the tooling needed to prove it: pin Firefox's `browser_specific_settings.gecko` (D-04) and a strict, identical CSP declaration (D-09) in `wxt.config.ts` — re-confirming (not re-deciding) Phase 8's actual MV2-vs-MV3 Firefox target (D-07) — then verify the packaged Firefox build passes `web-ext lint` (D-02) and actually instantiates WASM at runtime, not just in dev mode.

Purpose: D-02/D-04/D-07/D-09 are the phase's configuration-correctness bar (ROADMAP Phase 13 SC #2 and #4). Without a deliberately-pinned Firefox extension ID, `chrome.storage.session` state churns across dev sessions (breaking D-05's invariant test in later plans); without a verified CSP, `pv-wasm` silently fails to instantiate only in the packaged build (Pitfall 2/4).
Output: A hardened `extension/wxt.config.ts` + `extension/package.json` (web-ext scripts), a clean `web-ext lint` pass on the packaged Firefox build, Firefox installed on the dev machine for this and later plans' manual/self-driven verification.
</objective>

    For the Firefox branch only, set `browser_specific_settings.gecko.id` to a real, permanent
    extension identifier (e.g. `passkey-vault@paczesny.pl`, matching the project's real domain from

    sessions and would invalidate any `chrome.storage.session`-scoped secret keyed to extension
    identity). Set `browser_specific_settings.gecko.strict_min_version` to a deliberately-chosen
    floor, not an arbitrarily low one — per Pitfall 3, `web-ext lint`'s version-gated API-availability
    checks only activate when this field is set; choose a version that reliably supports whichever MV
    target Phase 8 pinned (MV3: Firefox 109+ is the practical floor for stable MV3 support; MV2: a much
    older floor is defensible, e.g. Firefox 91 ESR — pick based on Phase 8's actual pin, and record
    the chosen floor + rationale in this plan's SUMMARY).

    reads host patterns from there), keeping `optional_host_permissions` for the Chrome/MV3 branch.

| Boundary | Description |

| Extension build config → packaged browser runtime | `wxt.config.ts`'s declared manifest/CSP is the only thing standing between the packaged extension and a browser that might silently relax or reject it |
| npm registry → dev machine | Installing `web-ext` as a new devDependency pulls third-party code onto the build machine |

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |

| T-13-01 | Tampering | `content_security_policy.extension_pages` in `wxt.config.ts` | high | mitigate | Explicit identical CSP string on both browsers (D-09); `web-ext lint` catches syntax regressions; manual runtime smoke test (Task 3) catches functional regressions lint alone can't see |
