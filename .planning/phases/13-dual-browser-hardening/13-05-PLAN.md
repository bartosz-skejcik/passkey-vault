<objective>
Close the still-open moz-extension half of Phase 9's SC#6 (EXT-05) and the matching remnant of this phase's own requirement (XBR-01): give `pv-server` a deliberate, scheme-scoped way to accept Firefox's per-install `moz-extension://<uuid>` origin in `PV_EXTENSION_ORIGINS` without ever loosening the bare-`*` rejection (WR-07), and give the extension's `ServerConfigView` an honest way to tell a Firefox self-hoster "the server is up but hasn't allowlisted this origin yet" instead of the generic "unreachable" message that currently swallows every `/healthz` failure indistinguishably (D-11).

Bartek's decision (13-CONTEXT.md ADDENDUM D-10, overriding the freshness audit's concrete-origins-only recommendation): `pv-server` gains FIRST-CLASS support for the literal entry `moz-extension://*` — a dedicated wildcard PATTERN implemented via a real mechanism (`AllowOrigin::predicate`), matching any well-formed `moz-extension://<uuid>` origin, never by weakening the existing bare-`*` fatal-at-startup guard. This is explicitly flagged as tech-debt Bartek accepted knowingly ("oflaguj to jako do zmiany później") because CORS is not this API's auth boundary (every state-changing route still requires a bearer token) and Firefox's per-profile UUID churn makes concrete-origin-only configuration hostile UX today.

Purpose: without this, Firefox self-hosters cannot get past `ServerConfigView`'s first-run gate at all — the `/healthz` probe is rejected by CORS before any host-permission grant runs (13-01's fix is a different, client-side half of a different problem), and the generic "unreachable" copy gives them no path forward. This plan is the missing server + docs + UX half; 13-01 already does the client `optional_permissions` half.

Output: `crates/pv-server` accepts `moz-extension://*` as a scheme-scoped wildcard pattern (tech-debt logged + recorded), `docs/SELF-HOSTING.md`/`.env.example` document the whole `PV_EXTENSION_ORIGINS` story for both browsers, and the extension's `ServerConfigView` gives a Firefox operator an actionable, copyable-origin CORS-blocked message instead of a dead-end "unreachable".
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Browser extension origin → pv-server CORS layer | `PV_EXTENSION_ORIGINS` (and now its `moz-extension://*` pattern carve-out) is the only thing standing between an arbitrary web/extension origin and a same-origin-policy-bypassing fetch to the API |
| pv-server API → bearer-token auth boundary | CORS decides which origins get an `Access-Control-Allow-Origin` echo; it is NOT the authentication boundary — every state-changing route still requires a valid session/bearer token regardless of CORS outcome (this is the load-bearing assumption D-10's risk acceptance rests on) |

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|------------------|
| T-13-11 | Elevation of Privilege | `is_well_formed_moz_extension_origin` predicate | medium | mitigate | Strict scheme + 36-byte UUID-shape check (exact hyphen positions, hex-only remainder) — rejects any origin that isn't syntactically `moz-extension://<uuid>`; covered by explicit malformed-origin regression tests (Task 1) |
| T-13-12 | Spoofing | Widened CORS predicate vs. hostile web content | low | accept (D-10, Bartek-approved) | A hostile page cannot forge a browser's `Origin` header, so it cannot spoof `moz-extension://<uuid>` to exploit the wildcard — only a REAL Firefox extension process can send that origin.
