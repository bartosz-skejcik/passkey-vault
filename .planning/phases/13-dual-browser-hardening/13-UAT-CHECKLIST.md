## Deviations / findings from the Firefox pass (13-04, this plan)

**No product-code divergences were found.** Every genuine issue encountered while building this session's from-scratch selenium-webdriver harness was a **test-harness technique bug**, corrected before the result recorded above; none required touching `extension/` or `crates/` source:

1. **[Test-harness] WebDriver's `switchTo().window()` genuinely changes Firefox's OS-level "active tab"** — confirmed empirically (a small isolated probe) that, unlike Playwright/CDP (which can address a background target's JS without stealing tab focus), classic WebDriver's window-switch is specified to actually select that tab. This makes the popup's own `autofill.match`/`autofill.fill` message pair (which resolves "the current tab" via `browser.tabs.query({active:true, currentWindow:true})`) undriveable the same way 13-03's Chrome harness drives it — switching to the popup to send the message makes the POPUP itself "the active tab" by the time the background handler runs. **Resolution:** every autofill fill test (P10-SC1 through SC5) was driven instead via Surface B/A (`autofill.matchFrame`/`fillFrame`, `content-relay.content.ts`'s own sender-derived-origin channel, entirely independent of "active tab" semantics) — the exact same underlying `fillValues()`/`content.fill` product code path, just reached via a different, real, in-page UI surface instead of the popup's picker.
2. **[Test-harness] Firefox does not expose CDP**, so the Chrome harness's `DOM.getDocument({pierce:true})` technique for reading/clicking inside this project's closed shadow roots (Phase 11's generator popover, Surface A/B's autofill panels, the save/update toast) has no equivalent — confirmed additionally that `document.elementFromPoint()` also does NOT pierce closed shadow roots on Firefox (a grid-search probe against a known-visible trigger icon returned nothing). **Resolution:** every closed-shadow-root interaction was driven via coordinate clicks computed either (a) directly from the product's own CSS/JS positioning formulas (`inpage-overlay.ts`'s exact `top/right/width` + row-height constants for Surface A/B; `generate-popover.ts`'s own `positionTrigger()`/`positionPopover()` functions for the generator), or (b) via a small, purpose-built script (`find_color.py`, Python + Pillow) that locates the brand-orange primary-action button by scanning a real screenshot for that exact RGB value and clustering matches — never by visual guessing. This is real, falsifiable coordinate-based automation, not a narrated pass.
3. **[Test-harness] `sendKeys('\n')` does not reliably dispatch a real Enter keypress/submit event on Firefox/geckodriver** — the literal-newline string was silently swallowed (the test page's own `submit` listener never fired), which produced two false FAILs (P11-SC2, P11-SC4) on the first attempt before being root-caused and fixed to `sendKeys(Key.RETURN)` (selenium-webdriver's proper synthetic key event).
4. **[Test-harness] This shared UAT account has accumulated many historical items across dozens of prior sessions/plans**, which surfaced two further test-only issues, both corrected:
   - TOTP items match by issuer-vs-hostname only (`issuerMatchesHost`, ignoring port) — many prior TOTP items share the issuer `"localhost"`, so a fixed "click row 0" assumption sometimes landed on an unrelated historical TOTP/login item instead of this run's own. Fixed by iterating rows until the expected result appears (P10-SC2), confirmed via an isolated diagnostic probe that row 2's click produced a live, real 6-digit code while rows 0/1 (other real, valid items) did not populate the OTP field being checked.
   - Card and identity items are NOT origin-scoped by design (`itemMatchesOrigin()` returns `true` unconditionally for both — a real product behavior, not a bug: "a stored card/identity is not origin-bound data"), so row 0 on a mixed card+identity list reliably resolved to an (unrelated) real card, not the freshly-created identity item under test (P10-SC4). Because a *successful* fill of ANY kind dismisses the whole panel (`handlePick`'s `overlay?.dismiss()`), the fix was to reload the page fresh before each row attempt (each fresh mount re-renders the same list from scratch) rather than assume the list persists across a wrong-kind fill.
5. **[Test-harness] Two false FAILs from over-broad selectors, both corrected:** P9-SC7's fullscreen-button click initially targeted a non-clickable ancestor `<div>` sharing the button's text instead of the actual `<button>` element; P11-SC4's cross-origin-isolation check initially queried `[data-pv-mount-host], [data-pv-autofill-host]` together on the top page, which wrongly flagged Surface B's own legitimate, unrelated login-autofill suggestion for Origin A's real form as if it were the (correctly frame-scoped, correctly absent) mismatch panel.
