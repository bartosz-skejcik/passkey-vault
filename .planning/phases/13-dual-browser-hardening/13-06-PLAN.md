<objective>
Give Firefox users a real passkey unlock for the extension by running the WebAuthn+PRF ceremony where Firefox allows it — on the user's OWN configured pv-server origin (a plain https/localhost page, PRF supported since FF135) — and relaying the result to the extension background over the phase-12-hardened content-relay channel. This is the researched, spec-aligned answer (13-FF-WEBAUTHN-RESEARCH.md option 1) to the permanent impossibility of rpId=extension-id on Firefox: reuse the v0.1 server-rpId PRF passkeys and the v0.1 `passkeyUnlock()` ceremony code, with the extension background as the sole unwrap/trust anchor.

Purpose: closes the last genuine Firefox capability gap of v0.2 with a working feature instead of a degradation (XBR-01's "parity OR explicit degradation" — this upgrades the ext-unlock row from degradation to parity for users with server passkeys). Bartek-mandated before the phase-13 seal.
Output: a working "Unlock with passkey (via your server)" path on Firefox (functional on Chrome too, offered only when the ext-scoped path is unusable), with the ceremony window lifecycle, validated relay, background unwrap, honest empty-state, and full test coverage.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Server page JS ↔ extension background | PRF output + wrapped blob transit the configured server's own page and content-relay; equal trust to v0.1's web unlock (the server already serves the vault frontend) — NOT a widening beyond v0.1, but a widening vs the Chrome ext-scoped path; documented, accepted (13-FF-WEBAUTHN-RESEARCH.md) |
| Page ↔ content-relay postMessage | Hostile page scripts on OTHER origins must never reach the listener (origin pin to configured server), and replay must be impossible (single-use background-issued nonce) |
