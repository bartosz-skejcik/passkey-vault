# Phase 13 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **Scope note:** Phases 8–12 (the extension's actual feature-build phases) have not yet been executed and have no UI-SPEC of their own. Phase 13 is a *hardening/verification* pass, not a build phase (13-CONTEXT.md is explicit: no new user-facing feature is built here). But since no prior extension UI-SPEC exists, this document serves double duty: (a) it is the single design-contract source of truth the dual-browser re-verification pass (D-01) checks visual/interaction consistency against across every extension surface, and (b) it specifies, in full, the one genuinely new piece of UI this phase adds — the explicit Firefox-capability-degradation contract (D-03). Where a surface is described below but owned by an earlier phase (popup unlock, autofill dropdown, capture prompts, passkey-provider ceremony), that phase's eventual executor/UI-SPEC is expected to converge on these tokens, not diverge — this is written to be forward-compatible, reusing every locked pattern from the v0.1 web app (`01`–`06`-UI-SPEC.md) verbatim wherever the surface is equivalent.

No Radix, no new JS-primitive dependency, no CSS framework beyond what `web/` already ships. |

This is a **narrower rule than the web app** (which allows Fuzzy Bubbles in onboarding/empty-states) and is called out as a review question below, not silently assumed. `ui-monospace` — passwords, TOTP codes, recovery-adjacent text, unchanged from web app convention. |

## Spacing Scale

Declared values (must be multiples of 4) — identical numeric scale to the web app, with one extension-specific exception:

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon-to-label gaps, badge inline padding, dropdown-row internal gaps |
| sm | 8px | Compact row spacing (popup item rows, autofill dropdown entries), `Loader2` spin offset |
| md | 16px | Default element spacing — popup container **horizontal** padding (see exception below), vertical rhythm between popup sections |
| lg | 24px | Popup card vertical section padding, ceremony-consent card padding (card is wider than the popup — see Phase-Specific Notes) |
| xl | 32px | Unused in the popup itself; reserved for the (wider) passkey-provider ceremony card and in-page save/capture toast if it needs more breathing room than the 360px popup allows |
| 2xl | 48px | Unused this phase |
| 3xl | 64px | Unused this phase |

**Exception — popup horizontal padding:** the web app's card/section convention uses 24px (`p-6`) as its default horizontal padding (per `01`–`04`-UI-SPEC.md). At the popup's 360–400px viewport width, 24px on both sides (48px total) meaningfully eats into content width, especially for item rows that need room for a favicon + two lines of text + a trailing action button. **The popup container uses 16px horizontal padding, not 24px** — still an 8-point value, not a new arbitrary number, just the `md` token instead of `lg` for this one dimension. Vertical padding and all other spacing keeps the standard `lg`/24px card rhythm unchanged.

## Typography

Same 4 roles, same sizes/weights/line-heights as the web app (`01`-UI-SPEC.md, unchanged since) — **not reopened**, reused verbatim so the extension never reads as a visually distinct product from the web app it's a companion to:

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Label | 14px | 400 | 1.4 |
| Body | 16px | 400 | 1.5 |
| Heading | 20px | 700 | 1.2 |
| Display | 28px | 700 | 1.15 |

- Label → item-row secondary text (username, "last used" relative time), dropdown entry subtext, badge text, ceremony RP-name/account-picker secondary lines.
- Body → default running text, item-row primary text (item name), banner/degradation-notice copy, capture-prompt body copy.
- Heading → popup section titles ("Twoje sejfy" / section headers, if any), ceremony-consent card title ("Zaloguj się passkeyem" / rendered RP name context line).
- Display → **not used anywhere in the extension this phase.** The popup has no hero-score/dashboard context (that's the web app's Security Health screen, out of scope here); at 360–400px width a 28px Display-role string risks wrapping awkwardly. If a later phase (9's item-count empty state, say) wants a Display-sized number, it inherits this same role unchanged — Phase 13 simply has no surface that needs it.

## Color

Unchanged 60/30/10 split and exact hex/OKLCH values from `docs/UI-DESIGN.md` and every v0.1 UI-SPEC (`vault-dark` default, full `vault-light` parity) — the extension is a **second surface for the same theme tokens**, not a new palette:

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#1F1F1F` base-300 dark / `#FCFBFA` base-200 light | Popup page canvas, ceremony-card scrim backdrop (on the host page, behind the injected consent card) |
| Secondary (30%) | `#262626` base-100 dark / `#FFFFFF` base-100 light, `#212121` base-200 dark | Popup item-list surface, autofill dropdown surface, ceremony-consent card surface, capture/save-prompt toast surface |
| Accent (10%, coral `#E16540`) | primary | Popup unlock-form password submit button (`btn-primary`, unchanged meaning from web app), capture-prompt primary "Save" action, generate-password suggestion CTA — i.e. the *generic* primary-action token, exactly as reserved in every prior phase |
| Destructive | `#FF5861` error | Origin-mismatch warning banner in capture prompts (`alert alert-error` or `alert-warning` per severity — see below), tier-3 mid-ceremony genuine-failure text (reused exactly from `04-UI-SPEC.md`'s tier model). (Item deletion is NOT a popup surface in v0.2 — EXT-06 delegates it to the web app; stale in-popup delete reference removed 2026-07-15.) |

**Teal (`#00CDB7`, `accent` token) — reserved for passkey-meaning only, unchanged carve-out from Phase 2–4:**
- Popup unlock screen's `PasskeyUnlockButton` (`btn btn-accent`, `Fingerprint` icon) — the *exact same component* from `04-UI-SPEC.md`, reused unchanged in the extension popup context, not reinvented.
- Passkey-provider ceremony's confirm button (`docs/UI-DESIGN.md` §3: "teal przycisk potwierdzenia") — same token, same meaning (a passkey-capable action), on a new surface.
- **Never** used for the capability-degradation banner (see below) — that state is deliberately neutral, not passkey-branded, per the established "no fake success, no hard failure" rule.

**Accent reserved for:** the popup password-submit button, capture/save-prompt primary CTA, and the password/passphrase-generator suggestion CTA only — never for item-type badges, dropdown-entry icons, or the degradation banner.

**Semantic-severity split for warning content (new distinction this phase makes explicit, not a new color):**
- **Neutral/muted** (`text-base-content/70`, no icon, no colored box — exact reuse of `04-UI-SPEC.md`'s Tier 2 treatment): the Firefox PRF-capability-gap message. Nothing is wrong; the password fallback fully works. This is an *honest, calm* state, not a warning.
- **Warning** (`alert alert-warning`, `AlertTriangle` icon): capture/save-prompt origin-mismatch notice ("this form is embedded from a different domain") — a real, actionable heads-up, not a failure, but genuinely worth a beat of attention before the user saves.
- **Error/destructive** (`alert alert-error` / `text-error`, `AlertTriangle` where a box is used): item-delete confirmation, genuine mid-ceremony passkey failure (network/hardware fault, not cancellation or PRF-absence).

## Phase-Specific Notes

### The capability-degradation contract (D-03 core deliverable)

A single presentational pattern, reused verbatim across every surface where PRF may be absent — **not a new component per surface**, one shared treatment:

```
Visual: plain text row, `text-sm text-base-content/70`, no icon, no colored box,
        no `alert` wrapper — identical composition to 04-UI-SPEC.md's Tier 2 line.
Placement: directly below the passkey-action button/CTA it qualifies (popup unlock:
        between the PasskeyUnlockButton and the password field, exact same slot
        04-UI-SPEC.md already defines; provider ceremony: directly below the
        ceremony's account-picker row, above the confirm button).
Trigger: read at ceremony-attempt time via `clientExtensionResults.prf.enabled`
        (13-RESEARCH.md Pattern 2) — never inferred from `navigator.userAgent` or
        a hardcoded "Firefox = no PRF" branch, since PRF support is per-credential/
        per-OS, not purely per-browser (Chromium-first is the *expectation*, not
        a hard rule the UI should bake in as fact).
Button state: the passkey-action button stays visible and clickable in every case
        (mirrors 04-UI-SPEC.md's Tier 2 rule exactly) — the password/native
        fallback path is offered *alongside*, never by hiding/disabling the
        passkey affordance, since a different enrolled passkey might still work.
```

This is the one piece of genuinely new UI code this phase owns (`PrfUnavailableBanner`-equivalent inline text, per `13-RESEARCH.md`'s Recommended Project Structure) — everything else in this document describes surfaces Phases 9–12 build, reused/confirmed here for hardening-pass consistency.

### Popup shell (Phase 9's surface — 09-UI-SPEC.md is AUTHORITATIVE; superseded sketch note 2026-07-15)

> This section was written BEFORE Phase 9's own UI-SPEC existed and before Bartek's NordPass-reference
> direction (2026-07-15). `09-UI-SPEC.md` ("Popup shell" + "Popup header + delegated-management
> affordances") is the single source of truth for the popup — this phase RE-VERIFIES that shell on both
> browsers, it does not redefine it. Corrected outline for cross-reference only:

- **Viewport:** fixed width 360–400px, variable height up to ~600px (unchanged).
- **Structure, top to bottom (per 09-UI-SPEC + NordPass reference):** slim header row (`Settings` gear icon-button left → opens `${baseUrl}/?panel=settings` in a new tab; "Full screen" `btn btn-ghost btn-sm` + `ExternalLink` right → opens the configured web app) → sticky search bar → item list (48px-min rows; Phase 10 adds the trailing `Wypełnij`/`Fill` affordance) → `Plus` FAB bottom-right (→ `${baseUrl}/?action=new-item` in a new tab — NO in-popup create) → footer row with the auto-lock `select` ONLY. Item detail is an in-popup panel swap with `ChevronLeft` back (unchanged), **read-only**: NO edit, NO delete, NO management actions in the popup — EXT-06 delegates all management to the web app (deletion happens there).
- **Row height:** 48px minimum (unchanged).

### In-page autofill dropdown (Phase 10's surface)

- **Isolation:** rendered inside a Shadow DOM host (or an isolated iframe) so host-page CSS never leaks in — this is an implementation requirement with a direct visual consequence: the dropdown must look identical regardless of the host page's own styles, on both browsers.
- **Geometry:** 8px radius (the **input/button** radius token, not the 16px card/modal token) — this is a compact anchored menu, not a modal, and should read as an extension of the form field it's attached to, not a floating app window.
- **Entry row:** favicon/item-type icon (16–20px) + item name (Body) + username (Label, muted) — `Wypełnij`/`Fill` is implicit on click of the row itself, no separate button needed at this density.
- **Gesture gate (FILL-05 invariant, re-verified not re-decided this phase):** the dropdown only opens on an explicit user gesture (field focus/click) — never auto-opens on page load, never repositions/reopens without a fresh gesture. This is a hardening-pass check item, not new UI, but is stated here so the contract is checkable cross-browser.

### Save/capture prompt (Phase 11's surface)

- **Placement:** a toast-like card anchored top-right of the host page viewport (standard extension-prompt convention, e.g. 1Password/Bitwarden's own save-prompt placement) — same Shadow-DOM isolation as the autofill dropdown.
- **Geometry:** 16px radius (this **is** card-class content — domain name, two action buttons, dismiss), `xl`/32px width budget if the popup's 360px constraint doesn't apply (it's on the host page, not inside the browser popup chrome, so it can be a little wider — a fixed 320–360px card is a reasonable default, not a hard requirement).
- **Content, top to bottom:** originating domain (Body, bold-weight not available per 2-weight limit — use Heading role at reduced size if emphasis is needed, or plain Body with the domain name itself doing the emphasis work), origin-mismatch warning row (only when applicable — `alert alert-warning`, see Color), primary "Save"/"Update" button (coral `btn-primary`), secondary dismiss ("Nie teraz" / "Not now", plain text link, no icon).

### Passkey-provider ceremony consent card (Phase 12's surface)

- **Placement:** center-anchored overlay on the host page (this is the single most important UX moment per `docs/UI-DESIGN.md` §3: "nasz najważniejszy moment UX"), Shadow-DOM isolated, with a dimmed scrim behind it (`base-300`-tinted, matching the web app's existing unlock-overlay scrim treatment).
- **Content, top to bottom:** requesting site's favicon + RP name (Heading), account picker (when the vault has multiple matching passkeys — item rows same vocabulary as the popup list), the D-03 capability-gap line (only when PRF is unavailable for the selected credential — see above), teal `btn-accent` confirm button (`Fingerprint` icon, `Potwierdź passkeyem`/`Confirm with passkey`), and the **always-visible** native-fallback secondary action ("Użyj innego menedżera"/"Use another authenticator") — PROV-03's "never dead-ends the ceremony" invariant made visually concrete: this link is never hidden, never disabled, regardless of which tier the PRF state is in.

### Toolbar icon / lock-state indicator (open review question, not blocking)

Neither `docs/UI-DESIGN.md` nor any CONTEXT/RESEARCH artifact locks whether the extension's browser-toolbar icon changes appearance (badge dot, icon swap) between locked/unlocked states. A minimal, non-blocking default: a small teal dot badge when unlocked, no badge when locked — reusing the existing teal-for-passkey/vault-access semantic, not a new color meaning. Flagged here as a genuine open product choice for Bartek or the executor, not resolved as a hard requirement, since no phase's success criteria mention the toolbar icon.

### Fuzzy Bubbles narrowing (review question)

This document declares **zero** Fuzzy Bubbles usage anywhere in the extension (narrower than the web app's onboarding/empty-state allowance). Rationale: every extension surface either handles credentials directly or is a compact 360px utility view with no natural annotation moment. If a future phase wants a lighter touch for, say, the "nothing saved for this site yet" empty state (which is genuinely low-stakes, non-security content), that's a one-line addition to this contract, not a violation of it — flagged here so it isn't silently foreclosed.
