<objective>
Give Firefox's PRF gap (and any other authenticator that can't do PRF for the extension-scoped unlock passkey) an explicit, legible, honest UI state wherever the POPUP offers this passkey fast-path: the unlock screen (UnlockView.tsx) and the post-unlock enrollment offer (EnrollExtPasskeyPrompt.tsx). Both are real WebAuthn ceremonies against `rpId = browser.runtime.id`, so detection reads the actual ceremony's outcome — `create()`/`get()` throwing, or the PRF extension result being absent — never user-agent sniffing (D-06 invariant: PRF must never become a hard requirement).

**This plan does NOT touch the passkey-provider ceremony (ProviderCeremonyView.tsx).** That surface already ships its own honest-degradation line (`provider.prfUnavailableNote`), driven by the background's real passkey-rs `prfCapable` capability signal (D-16) — a WASM computation that is browser-independent by design. Reusing this plan's browser-framed copy there would reintroduce exactly the "this browser doesn't support PRF" framing that WR-02 (12-05 review) deliberately removed, because the provider computes PRF in WASM regardless of browser. The provider surface is already-satisfied; nothing here should reference it.

Two concrete gaps exist on the popup surface today, per the freshness audit's ground-truth read of the shipped code:
1. `UnlockView.tsx`'s `navigator.credentials.get()` catch block (~line 153) silently `return`s on ANY throw — including genuine ceremony failures, not just user-cancel — so a real Firefox PRF-unusable case dead-ends with zero feedback.
2. `UnlockView.tsx`'s `extractPrfBytes(assertion) === undefined` path (~line 161) renders `unlock.passkeyFailed` in alarming `text-error` styling — the wrong tone for an honest capability gap (should be the calm, neutral D-03 line), and the wrong copy (generic "couldn't use passkey" instead of "not available on this browser").
3. `EnrollExtPasskeyPrompt.tsx`'s `create()` catch block (~line 65) silently resets to `"idle"` on ANY throw, same silent-dead-end shape as #1.

`EnrollExtPasskeyPrompt.tsx`'s existing `capability.prf?.enabled` check (line 72-73, AFTER a successful `create()`) is already an honest degradation — it renders `extPasskey.enrollNoPrf` and never calls `enroll.finish`. That check is NOT broken; this plan only DRYs its inline shape into a shared, unit-tested helper (Task 1) because the same two-case-collapse logic belongs in one tested place, not duplicated ad hoc.

D-12 (Bartek override, supersedes the "keep the button always-enabled, never disabled" framing found elsewhere): once THIS popup session has observed one genuine (non-cancel) PRF-ceremony failure on either surface, the passkey affordance flips to **visible-but-disabled** with the inline D-13-canon explainer sitting alongside it — never hidden. Before that first genuine failure (support unknown), the button stays fully enabled and clickable, because a first attempt must always be possible (a different enrolled credential, or a Firefox update, might work). The password path (Unlock) / skip-and-keep-password path (Enroll) is always available regardless of this state.

D-13 (Bartek override, copy canon): the popup unlock/enroll surface's fallback copy is the exact 13-UI-SPEC wording (browser-framed, since this IS a real browser WebAuthn ceremony on this surface): PL "Szybkie odblokowanie passkeyem nie jest dostępne w tej przeglądarce — użyj hasła." / EN "Fast unlock isn't available for this passkey on this browser — use your password." This replaces the dictionary's existing `unlock.passkeyUnsupported` wording (currently used only for the "WebAuthn API entirely absent" Tier-1 case) so there is ONE canonical string reused for every "can't do it here" case on this surface, instead of three near-duplicate messages.

Purpose: ROADMAP Phase 13 SC #3 — "wherever Firefox lacks a capability... the UI communicates it explicitly instead of silently failing or degrading," scoped correctly to the surface that actually reads a browser-level signal.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Popup UI ↔ WebAuthn ceremony (`navigator.credentials.create()`/`get()`) | The PRF availability/failure signal crosses from the browser's own WebAuthn implementation into the popup's render state |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|------------------|
| T-13-04 | Information Disclosure | `prf-capability.ts`'s reading of `clientExtensionResults` | low | accept | Detection reads only a boolean-like `enabled` flag and returns only `boolean` — raw PRF bytes never cross this module's return boundary (they never enter it either: `extractPrfBytes` in `prf.ts`, unchanged, is the only reader of `prf.results.first`, and that stays untouched by this plan) |
| T-13-05 | Denial of Service (silent dead-end on genuine ceremony failure) | `UnlockView.tsx`'s `get()` catch, `EnrollExtPasskeyPrompt.tsx`'s `create()` catch | medium | mitigate | Task 2's explicit cancel-vs-fail split ensures every non-`NotAllowedError` throw surfaces the neutral D-03/D-13 banner and flips the affordance to visible-but-disabled (D-12) rather than resetting to idle/busy with zero feedback; the password (Unlock) / skip (Enroll) path stays fully functional throughout (D-06) |
| T-13-06 | Denial of Service (passkey affordance wrongly disabled before it's proven unusable) | Button-disable logic in both components | low | mitigate | The disabled state is gated exclusively on an OBSERVED failure this popup session (`prfUnusableThisSession`/`phase === "unusable"`), never on browser detection or a pre-emptive guess — the first attempt in any popup session is always possible, satisfying D-12's explicit "support unknown ⇒ clickable" rule |

**Out of scope, explicitly:** the passkey-provider ceremony's own capability signal (`prfCapable`, passkey-rs/WASM-derived, D-16) is a different trust boundary (background↔WASM, not popup↔browser-WebAuthn) and is not touched by this plan.
</threat_model>
