Verifies and CORRECTS 13-04's headline finding. Key corrections: (1) since Firefox 150 (bug 1956484 RESOLVED) extensions CAN run WebAuthn for WEB-domain rpIds they hold host_permissions for — only rpId=extension-id is permanently impossible (spec origin rules, moz-extension is not a registrable domain); (2) bug 2026687 (open, design-decision-approved) closes the action popup on the OS prompt, so any extension-run ceremony needs a tab/window; (3) PRF works on regular pages since FF135/139 — so a SERVER-ORIGIN PRF ceremony (rpId = server domain, reusing v0.1 passkeyUnlock()) relayed via content-relay is a viable Firefox unlock path TODAY. # Firefox extension WebAuthn / PRF-unlock: research findings\n\n## Bottom line up front\n\nThe empirical finding in `13-04-SUMMARY.md` is **correct for the two rpIds it tested, but the blanket conclusion it draws is now out of date.** As of **Firefox 150** (shipped ~Q2 2026; you tested on 152), Firefox *does* let an extension run `navigator.credentials.create()/get()` — but only with an rpId of a **web domain the extension holds `host_permissions` for**, never the extension's own id, and **not from the action popup** (a separate open bug closes the popup when the OS prompt appears). Both of your probes (`rpId=extension-id` and `rpId=\"localhost\"`) were destined to fail regardless of Firefox version, so the `~2ms SecurityError` is consistent with the new model, not contradicted by it. This materially changes the workaround landscape and the recommendation.\n\n---\n\n## Q1 — Confirming the limitation (with the FF150 correction)\n\n**Verified facts:**\n\n1. **Extension WebAuthn IS supported since Firefox 150 / Chrome 122 — for host-permitted web domains only.** Bug [1956484](https://bugzilla.mozilla.org/show_bug.cgi?id=1956484) (\"Allow web extensions to assert WebAuthn relying party identifiers of a web domain they have host permissions for\") is **RESOLVED FIXED in Firefox 150**. Per [MDN's \"Use the web authn api\"](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/Use_the_web_authn_api): *\"a web extension can call these APIs and specify an RP ID for any domain covered by its host permissions… enabling extensions to act as WebAuthn clients on behalf of web services.\"* This is exactly the \"password-manager as WebAuthn client for someone else's domain\" model — and is a different mechanism from your Phase-12 provider bridge.\n\n2. **The extension's own id as rpId is NOT supported on Firefox.** MDN and bug 1956484 only ever describe *web-domain* rpIds. `moz-extension://…` is not a registrable domain, so `rpId = browser.runtime.id` fails origin validation → `SecurityError: \"The operation is insecure.\"` This is the Chrome-specific special-casing that Firefox never adopted. So your Bitwarden-style extension-scoped passkey (rpId = extension id) is genuinely Firefox-incompatible, permanently, by design.\n\n3. **Your `rpId=\"localhost\"` control also fails for a mundane reason:** unless the extension declares `host_permissions` covering `localhost`, FF150 rejects that rpId too. So \"both probes returned identical SecurityError\" is *expected* under the new rules — it does **not** prove \"Firefox rejects WebAuthn from any moz-extension page regardless of rpId.\" The untested case — **rpId = a real server domain the extension has host permission for** — is precisely the one FF150 enables.\n\n4. **BUT: WebAuthn from the action popup is separately broken.** Bug [2026687](https://bugzilla.mozilla.org/show_bug.cgi?id=2026687) (\"WebAuthn prompt closes extension popup\") is **open (NEW), status `[design-decision-approved]`, ~4 votes, targeted informally at Firefox 150+ but unassigned.** Rob Wu notes it's not WebAuthn-specific (color picker etc. also close the popup); Mozilla is *\"in favor of addressing this issue if feasible.\"* MDN documents the workaround explicitly: *\"the flow does not work as the popup closes when the prompt for credentials appears. A workaround is to open the page in a new tab.\"* Chromium and Safari do not have this bug. So even the host-permitted-domain path can't run inside your popup today — it needs a tab/window or a background-page ceremony.\n\n5. **moz-extension origin format for RPs:** FF150 emits a stable `moz-extension://<hash>` origin in `clientDataJSON` (SHA-256 of the extension id, byte+97 → chars a–p), so servers can allowlist it. Relevant only if you ever verify an extension-run ceremony server-side (you don't — the PRF output is your secret).\n\n6. **PRF on regular pages is solid on Firefox now.** Meta-bug [1863819](https://bugzilla.mozilla.org/show_bug.cgi?id=1863819) is **RESOLVED FIXED**: PRF shipped **FF135** (desktop, security keys via authenticator-rs), **FF139** (macOS platform authenticator), Android following. Caveat: when an authenticator lacks PRF, Firefox returns empty `{}` rather than Chrome's `enabled:false` — your `extractPrfBytes()` already treats `undefined` as a Tier-1 gap, so you're covered. **Windows Hello / macOS native authenticator PRF-at-OS-level was still lagging** as of these releases — worth remembering for UX expectations.\n\n**Signal on Mozilla changing the popup behavior:** Yes — bug 2026687 is approved-for-fix in principle, so in-popup WebAuthn *may* eventually work on Firefox. There is **no** signal Mozilla will ever allow `rpId = extension-id` (that path is closed by spec origin rules, not a Firefox choice).\n\n**Uncertainty:** Whether the FF150 extension-domain path also surfaces PRF results is **not documented** (MDN's extension page omits PRF entirely). PRF is origin-orthogonal in the spec, so it *should* flow, but treat this as **inference, not verified** — it would need a live probe.\n\n---\n\n## Q2 — How competitors do \"unlock the extension\" on Firefox (2025–2026)\n\nVerified pattern: **none of the majors use a `moz-extension` WebAuthn ceremony for unlock.** They split into \"native-messaging to a desktop app\" vs \"not offered on Firefox.\"\n\n| PM | Firefox unlock mechanism | WebAuthn/moz-ext? | Status on Firefox |\n|---|---|---|---|\n| **Bitwarden** | Biometric/\"unlock with biometrics\" = **native messaging to the Bitwarden desktop app**, which performs the OS biometric. It sidesteps *both* Firefox extension limitations: no extension-id rpId, no popup-close bug (it runs in a tab, not the action popup). **No dependency on FF150 at all.**\n- **You already have the flow:** `web/src/lib/passkeys/login.ts` `passkeyUnlock()` runs the exact server-rpId PRF ceremony; the background already has HKDF/unwrap paths (`ext-passkey.ts`).\n- **Security posture — honest caveat:** the PRF output is computed inside **server-delivered JS** on the server-origin page. That is the *same* trust boundary as v0.1's own web unlock (a compromised/malicious server could serve exfiltrating JS) — acceptable for a self-hosted vault where the server is the user's own. But note it is **strictly weaker than the ext-scoped passkey**, where PRF only ever touches extension-controlled code: relaying via the server page reintroduces \"trust the server's JS\" that the extension trust-anchor was meant to reduce. Mitigation is limited (you can't move the ceremony onto extension-controlled static HTML without an extension-origin rpId, which Firefox forbids). Recommend the relay pass PRF straight to the background and derive/unwrap there (as today) — never let it linger in page scope — and document the boundary as equal-to-v0.1-web-unlock.\n- **UX:** tab/window flash vs the current in-popup Touch ID. A small popup `window` (or a focused tab that auto-closes on completion) is the least jarring. This is the tradeoff.\n- **Could also serve Chrome (unification):** Yes — a server-origin ceremony works identically on Chrome, so you *could* drop the ext-scoped passkey entirely and have one code path. Embedding doesn't change the container.\n- **Plus** a `moz-extension://` top-level delegating `publickey-credentials-get` to a cross-origin child is uncharted (permissions-policy from an extension embedder is not a tested/spec'd path) — **inference**, but moot given the popup-close blocker. **Verdict: don't pursue.**\n\n### (c) Other real options\n\n- **FF150 extension-asserts-domain-rpId (bug 1956484):** Real, but for *your* case it collapses into option (a): you'd still (i) need `host_permissions` for the server domain, (ii) be blocked from the popup by 2026687 → run it in a tab/window anyway, and (iii) it's FF150+ only and PRF-in-extension is unverified. It gives no advantage over running the ceremony on the actual server page, and adds a server-side `moz-extension://<hash>` origin-allowlist concern. **Skip in favour of (a).**\n- **Native messaging to an OS authenticator helper:** This is what Bitwarden/1Password/Proton do — but it requires a companion desktop app, which **violates your single-container/no-desktop-app positioning.** Not an option.\n- **`browser.webauthn` API:** No such WebExtensions API exists. No signal of one.\n- **WECG/spec direction:** [w3c/webauthn #1766](https://github.com/w3c/webauthn/issues/1766) (filed by Dashlane, 2022, now **closed**) drove exactly the host-permission-domain-rpId model that FF150/Chrome122 shipped — plus servers allowlisting the deterministic extension origin. The spec direction is \"extensions act as clients for *web domains*,\" never \"extensions get their own rpId namespace.\" So the long-term platform answer aligns with option (a), not with your Chrome-only extension-id trick.\n\n---\n\n## Q4 — Ranked recommendation\n\nTrust rule respected throughout: PRF must never reach an *untrusted third-party* page; the server-origin page is the user's own trusted vault frontend (same trust as v0.1 web unlock), and the extension background stays the unwrap anchor.\n\n**Classification: v0.2.x backlog — NOT a fix-now blocker for Phase 13.** Phase 13's job was honest dual-browser degradation, and password unlock (D-06) is a fully-functional universal fallback that ships correctly today.
