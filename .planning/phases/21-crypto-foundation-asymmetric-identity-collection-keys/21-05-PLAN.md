<objective>
Expose the two new pv-core primitives (identity keypair from Plan 21-02/21-04, collection-scoped
item encryption from Plan 21-03) through `pv-wasm`'s existing opaque-handle bridge pattern, so
downstream phases (22+) consume a finished bridge rather than each re-doing this bridge work.

private-key-byte-returning method, generate/wrap/unwrap/seal/unseal as thin pass-throughs to
pv-core with JSON-blob (de)serialization at the boundary.

new primitives, so downstream phases consume a finished bridge rather than each re-doing bridge
work" — this is that deliverable, consolidated into one plan since every addition here touches
the same single file (`crates/pv-wasm/src/lib.rs`) and all of pv-core's primitives this phase
introduces (Plans 21-02, 21-03, 21-04) must already exist before this plan can run.

Output: `crates/pv-wasm/src/lib.rs` gains `WasmIdentityKey`, `WasmCollectionKey`, and six new
`#[wasm_bindgen]` functions, with native `cargo test -p pv-wasm` coverage (no browser required,
matching this file's existing test-without-a-host pattern).

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| WASM linear memory <-> JS host (browser/extension) | The one boundary this entire file exists to police — no raw secret-key byte may cross it as a bare `Vec<u8>`/`&[u8]` return value |
| Untrusted JSON blobs from JS (wrapped_json/sealed_json/item_json) <-> pv-core deserialization | JS-supplied strings are attacker-influenced input in a compromised-extension or malicious-page scenario; malformed input must fail cleanly, never panic |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-21-05-01 | Information Disclosure | `WasmIdentityKey`/`WasmCollectionKey` (raw secret bytes crossing the WASM/JS boundary) | critical | mitigate | Opaque-handle pattern identical to `WasmUserKey`/`WasmWrappingKey`; Task 1's acceptance criteria explicitly checks no new method returns private key material; `publicKeyBytes` is the sole, deliberate, non-secret exception |
| T-21-05-02 | Tampering | `unwrapIdentitySecretKey`/`unsealCollectionKey`/`decryptItemForCollection` (malformed JS-supplied JSON) | medium | mitigate | Existing `serde_json::from_str` + `to_js_str_err` error-propagation pattern (matching `unwrapUserKey`/`decryptItem`'s established handling) turns malformed input into a clean `Err`, never a panic; `unsealCollectionKey`'s length check on the unsealed payload follows `importUserKeyFromSession`'s existing reject-don't-truncate discipline |
| T-21-05-03 | Denial of Service | Malformed/oversized JSON deserialization | low | accept | Same residual risk profile as every other existing `serde_json::from_str` call site in this file (e.g. `unwrapUserKey`, `decryptItem`) — no new exposure introduced, not re-mitigated here |
