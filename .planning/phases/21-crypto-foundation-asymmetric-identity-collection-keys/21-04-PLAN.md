<objective>
Add the hand-written, anonymous-sender sealed-box wrapper on top of Task 1's identity keypair
primitive: a fresh ephemeral `crypto_box::SecretKey` generated per seal, `ChaChaBox` for the
ECDH+AEAD composition, and immediate zeroization of the ephemeral secret — never stored, never
reused across seals. This is the ONE piece of composition pv-core owns (crypto_box has no
built-in seal for ChaChaBox, only for the rejected SalsaBox-hardcoded `seal` feature); keep it
minimal and heavily commented per the CONTEXT.md instruction.

Purpose: KEY-02 requires a shared collection's Collection Key to be sealed independently to
each member's public key, so that adding/removing a member only rewraps keys — item ciphertext
is never touched. This plan delivers the pure-crypto seal/unseal primitive that later phases
(22, 25) build the actual multi-recipient collection membership logic on top of; this phase
delivers only the primitive and its tests, not any collection/membership orchestration.

Output: `crates/pv-core/src/identity.rs` gains `SealedKey` and `seal`/`unseal`, plus the
`lib.rs` hierarchy diagram's sealing branch is confirmed accurate against the real
implementation (Plan 21-02 already added the diagram text; this plan makes it true).
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Ephemeral sender identity (seal-time) <-> long-lived recipient identity | Every seal uses a throwaway keypair that exists only for the duration of one `seal()` call; the recipient's long-lived `IdentitySecretKey` is the only durable secret on either side |
| Server-relayed `SealedKey` blobs <-> client unseal | The server stores and relays `SealedKey` rows between clients without ever holding a key that can open them (zero-knowledge boundary) |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-21-04-01 | Tampering | `seal`'s ephemeral secret key (reuse risk) | high | mitigate | A fresh `crypto_box::SecretKey::generate(&mut OsRng)` is drawn per `seal()` call as a function-local variable, never stored/cached/returned — structurally impossible to reuse across two calls; Task 1's acceptance criteria explicitly checks for this |
| T-21-04-02 | Information Disclosure | `seal`'s nonce (reuse risk) | high | mitigate | `ChaChaBox::generate_nonce(&mut OsRng)` drawn fresh per call, never derived deterministically or cached, matching `aead_seal`'s existing discipline elsewhere in this codebase |
| T-21-04-03 | Information Disclosure | Ephemeral `crypto_box::SecretKey`'s transient bytes (Zeroize gap, ephemeral variant) | low | accept | Same documented residual gap as T-21-02-02, applied to the ephemeral key this time; the ephemeral key exists for a single function call and its `Drop` still zeroizes its internal scalar, narrowing the exposure window further than the long-lived `IdentitySecretKey` case |
| T-21-04-04 | Tampering | Server-side `SealedKey` blob substitution (no AAD at this layer) | medium | mitigate | `ChaChaBox` cryptographically rejects non-empty AAD (Test 1, Task 1) so this layer cannot bind `(collection_id, recipient)` directly; the compensating control is Plan 21-03's item-layer scope-bound AAD one layer down — a swapped `SealedKey` either fails AEAD outright or, in the vanishing case it doesn't, yields 32 bytes of garbage that then fails to decrypt any real item since item AAD is bound to the real `collection_id` — documented in this task's code comments per 21-RESEARCH.md's "AAD Binding — Where It Actually Lives" |
</threat_model>
