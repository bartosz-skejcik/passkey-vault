<objective>
The phase's tracer: wire the recipient-side shared-item READ path end-to-end through every background layer this phase touches — WASM crypto (27-03) -> collections/identity stores (27-03) -> vault-store's decrypt dispatch -> sync-client's shared-revision pull -> the popup's `vault.list` message — and prove it live with two real extension instances, member A sharing a collection+item with member B via direct pv-server API calls, member B's extension observing the correctly-decrypted result. This is the single most valuable assertion in the phase (27-CONTEXT.md's own framing): a recipient-side read is exactly the class of bug that shipped twice in Phase 26.

This plan implements A-1 (port web's shared-read model rather than invent a new one — the three-source merge, decrypt dispatch, and merge orchestration below are ported shape, not re-derived), A-2 (EXT-11: identity/Collection Key material lives in service-worker memory only, never `chrome.storage.session`), A-3 (the new key caches are cleared inside the EXISTING `subscribeSessionLockState` handler, after `stopSync()`, never a second listener), and A-4 (the KEY-01 extension trigger mirrors Phase 26's idempotent-publish design, wired at this extension's own single unlock choke point).

Purpose: every other plan in this phase (TOTP, provider ceremony, write routing, popup UI) is a horizontal expansion that depends on `getItems()` returning correctly-tagged, correctly-decrypted shared items. Proving that here, live, in Wave 2 — not the final wave — is this phase's direct application of the inherited Phase 26 lesson (STATE.md blocker) that a live proof deferred to the end only audits a broken feature instead of steering it. Re-execution note: Task 1 alone touches 8 of this plan's 11 files and is the phase's single highest re-execution-risk task — the executor should budget context accordingly (read every `<read_first>` source fully before writing, since a partial re-read mid-task is the expensive failure mode here, not a cheap one).
Output: vault-store.ts's full shared-read port, sync-client.ts's shared buckets, the KEY-01 extension trigger wired, and a green live two-extension recipient-side proof.
</objective>
