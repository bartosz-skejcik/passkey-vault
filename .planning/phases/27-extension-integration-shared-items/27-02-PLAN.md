<assumption_delta_decision>
**Detector finding:** `kind: pluralization`, term "multiple", from "a passkey shared across multiple members' concurrently active extensions" (27-CONTEXT.md/ROADMAP SC 3). The generalization: a provider passkey credential was implicitly modeled as exercised by ONE authenticator instance; it is now genuinely exercised by N concurrent member extensions.

**Decision: `promote`.** The generalized model ("a credential may be exercised by N concurrent members") becomes primary; the single-member case is a degenerate variant (N=1) of it. Rationale, established by this phase's own research and confirmed empirically by Task 1 below: `pv-provider` sets no signature counter at all (`ceremony.rs:87,155` construct `Authenticator::new(...)` with no `.make_credentials_with_signature_counter(true)` call), so promotion is realized by NOT introducing per-device counter state — the anti-goal named in 27-CONTEXT.md §A-8. A per-item monotonic counter would make two members' extensions race on a revision-guarded row and manufacture precisely the counter regression EXT-10 exists to prevent. There is no code path in this decision that distinguishes "one member" from "N members" — that IS the promotion: the concurrent-member case requires zero special-casing because the degenerate single-member case already receives the same (absent) counter treatment.

**Companion invariant test (Task 2):** an assertion produced by ANY member's extension for a shared passkey reports `signCount` 0 — added as a permanent Rust regression test so a future phase that reintroduces per-device counter tracking trips it immediately.
</assumption_delta_decision>
