<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| chrome.storage.session <-> service-worker memory | The only persistence boundary this plan's two new modules touch at all — and per EXT-11, they must NEVER write to it |
| Server-published identity public key <-> local unwrap | The wrapped identity secret key blob crosses from server storage into this client, but only ever as an opaque, User-Key-wrapped blob the server never unwraps (zero-knowledge invariant, unchanged) |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-27-05 | Information Disclosure | Collection Key / identity secret key leaking into `chrome.storage.session` | high | mitigate | Both modules hold their caches (`collectionKeys` Map, `cachedIdentityKey`) as bare module-level variables, never passed to any `chrome.storage.*` call anywhere in either file — Task 2/Task 3's own acceptance criteria assert the modules compile and pass without any such call; grep-verified in the executor's own verification pass (`grep -c 'storage\.' collections-store.ts identity-store.ts` should show zero matches touching the new key material) |
| T-27-06 | Tampering | A stale, revoked Collection Key handed out after membership removal | high | mitigate | The WR-02 eviction loop (ported verbatim in Task 2) frees and removes any cached key for a collection the server no longer returns — closes the post-revocation-staleness threat once 27-04 wires `refreshCollectionsNow()` into the periodic shared-revisions tick, not only the one-time unlock call |
| T-27-07 | Repudiation | Two devices (web + extension) racing to publish an identity keypair | medium | mitigate | `ensureOwnIdentityKeypair`'s `adopted_existing` branch (ported verbatim) — the race loser discards its own locally-generated key and adopts the server's canonical published one, never overwriting it |

</threat_model>
