<objective>
Migrate the last two DS-01 modules -- `search.ts` (domain/search helpers) and `sort.ts` (the sort
comparator) -- into `packages/pv-ui/vault/`. Both import `VaultItem`/`ItemFields`/`VaultFilter`
from their local `./types` module, which is why this plan depends on Plan 16-02: the pv-ui copies
of `search.ts` and `sort.ts` need `packages/pv-ui/vault/types.ts` to already exist so their own
sibling `./types` import resolves.

`search.ts` is a pure `export *` candidate (byte-identical logic, comment-only diff, already
verified at planning time). `sort.ts` is the phase's one split-shim: the comparator
(`SortOption`/`DEFAULT_SORT`/`sortItems`) is byte-identical on both sides and moves to pv-ui, but
`readSortPreference()`/`writeSortPreference()` are genuinely platform-specific (sync `localStorage`
on web vs async `browser.storage.local` on the extension, different storage keys) and stay local
by CONTEXT.md's own locked decision.

This plan also closes a specific security_enforcement concern: `search.ts`'s `domainFromUrl()`
feeds only the loose, fail-OPEN search-matching path -- the actual access-control gate
(`itemMatchesOrigin()`) lives in a separate file this plan never touches and does not import from
`search.ts` at all, so this move cannot drift that boundary. This plan verifies that claim
directly rather than assuming it.

Purpose: close the final two DS-01 duplication-inventory entries.
Output: `packages/pv-ui/vault/search.ts`, `packages/pv-ui/vault/sort.ts`; all 4 consumer copies
converted (2 pure shims, 2 split-shims); the origin-matching security boundary proven untouched.
</objective>
