  1. Owner creates a personal login item with a known password. Owner creates a shared destination folder co-managed with a SECOND real edit-holder (`memberA`, granted `"edit"` via `shareExistingFolderWithMember`) — the second edit-holder is what makes the later revoke observable without tripping the last-key-holder guard (memberA remains sole edit-holder after revoking the owner).

  4. From memberA's own session/token, `DELETE /api/vault/collections/{destinationId}/access/{ownerUserId}` — the deliberately-driven TOCTOU window, between the owner's destination-selection (step 2) and their submit (step 5).

  7. Byte-identical check: re-read the item via the OWNER'S OWN token and assert `enc_key`/`enc_data`/`revision` are IDENTICAL to the step-3 baseline.   <action>
  Mirrors this file's existing `"the sixth proof obligation..."` test (~line 1263-1362) and F-1's demotion test (~line 1376-1480) in shape — positive-then-negative anchor, next-completed-sync bound, no reload/lock-unlock on the negative side — but drives a MOVE-OUT via the item editor instead of a revoke or demotion, and is deliberately constructed so the member holds NO direct `item_shares` grant on this item at any point (Non-negotiable scoping: "loses access" must prove the FOLDER-derived grant is gone, without asserting anything false about a direct share — the cleanest way to make that claim true by construction is to never create a direct share on this item in the first place).

  1. Owner creates a personal item; owner creates a personal folder, shares it with a member at `"read"` (`shareExistingFolderWithMember`) — this member's ONLY relationship to the eventual item is folder membership, never a direct `item_shares` row.

  3. Member's session: `reloadAndUnlock` (brand-new membership pickup, this file's own established convention), then positive anchor — `assertRecipientDecrypts` (or its local equivalent from 32-01) reads the real decrypted password, panel left OPEN (no `detail-panel-close`).
  4. Owner reopens the SAME item in edit mode and moves it back OUT (`item-folder-select` set to `""`, "Bez folderu") and saves.
  5. **B-4 (32-PLAN-CHECK.md): the negative anchor must be the SAME read as the positive anchor, not merely a list-membership count.** ORG-04's own wording is "that member's own client reads the content before the move, and the SAME READ fails after" — a bare `item-row` count of 0 does not prove that; the panel from step 3 is deliberately left OPEN with the plaintext already rendered, and if `mergeCollectionSnapshot` drops the cached item while the MOUNTED `DetailPanel` keeps rendering its stale props, that list-only assertion would go green while the member is still looking at the real password. Two assertions, on the member's SAME still-open session (no reload, no lock/unlock, no re-navigation):
     - First, `item-row-${itemId}` `toHaveCount(0, { timeout: 60000 })` — the next-completed-sync SIGNAL (`mergeCollectionSnapshot`'s wholesale-replace-per-collection contract, `store.ts:760-763`, already dropping an item absent from the collection's fresh item list; `move_item`'s pre-existing `bump_collection_revision`(source) + `Collection`-typed `SyncEvent`, `vault.rs:1209-1212`/`:1243-1253` — both unmodified by this phase, confirmed by 32-RESEARCH.md Pitfall 3 to already be correct, unlike Phase 31's F-1, a DIFFERENT handler bumping the wrong counter). This step establishes WHEN the sync landed; it is not itself the access-loss proof.
     - Second, the actual negative READ — the exact inverse of step 3's positive anchor locator: `await expect(member.page.getByText(itemPassword, { exact: true }), "the same read must fail after the move-out -- not merely absent from the list").toHaveCount(0)` (no additional timeout needed; the prior assertion already waited for the sync). Whether the still-open `DetailPanel` unmounted (parent no longer finds the item), re-rendered into an empty/fallback state, or anything else — this assertion is agnostic to WHY and asserts the one thing that actually matters: the plaintext password is no longer anywhere in the document.
