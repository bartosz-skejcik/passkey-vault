# Phase 2 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

---

## Design System

| Property | Value |
|----------|-------|
| Tool | none — carried forward unchanged from Phase 1. `docs/UI-DESIGN.md` §5 locks shadcn to "only if Radix primitives turn out to be needed." Every new Phase 2 surface (delete-confirm dialog, copy toast, generator popover, locale/settings menu) is buildable on DaisyUI's native `<dialog>`-backed `modal`, `toast`, and `dropdown` classes — no focus-trap/portal primitive gap exists that would justify initializing shadcn. `components.json` confirmed absent. **Not re-asked of the user — this is a standing project decision, not a per-phase choice.** |
| Preset | not applicable |
| Component library | DaisyUI 5. New component classes entering the app this phase: `modal` (native `<dialog>`, delete confirmation), `toast` (copy feedback), `dropdown` (password-generator popover, sidebar settings/locale menu), `alert` (irrecoverable-master-password warning, revision-conflict banner), `range`/`input[type=range]` (generator length slider), `radio`/segmented buttons (generator mode toggle), `tabs` or plain link toggle (Login ↔ Register). No Radix, no new JS-primitive dependency. |
| Icon library | `lucide-react` (carried forward). New icons this phase: `Eye`/`EyeOff` (password visibility), `Copy`/`Check` (copy-to-clipboard + confirm flash), `X` (dialog/toast dismiss), `AlertTriangle` (destructive + irrecoverable-password warnings), `RefreshCw` (generator regenerate), `Globe` (favicon fallback + language switcher), `KeyRound` (passkey placeholder section, teal), `Lock`/`Unlock` (lock overlay, manual lock-now action), `Languages` (locale switcher), `Pencil` (edit item), `Trash2` (delete item), `Plus` (new item / new folder), `CreditCard`, `IdCard`, `StickyNote` (item-type icons for card/identity/note — `Vault`/`KeyRound` already cover login), `ChevronDown` (dropdown affordance). |
| Font | Unchanged: `DM Sans` (`--font-sans`, 400/700) for all UI text; `Fuzzy Bubbles` (`--font-hand`) strictly confined to the vault empty-state (per UI-DESIGN.md §1: "nigdy w treści itemów, dialogach potwierdzeń, modalu odblokowania" — never in item content, confirmation dialogs, or the unlock modal). This phase is the first to actually build all three excluded surfaces (item forms, delete dialog, unlock overlay) — the rule is now load-bearing, not theoretical: **plain DM Sans only** in auth forms, item create/edit forms, the unlock overlay, the delete-confirm dialog, and the copy toast. `ui-monospace` extends from "self-test technical detail" (Phase 1) to: password fields (login items, generator output), card numbers, and any other secret/key-shaped value. |

## Spacing Scale

Declared values (must be multiples of 4) — unchanged from Phase 1, extended with this phase's fixed layout dimensions:

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon-to-label gaps, badge inline padding, health-dot diameter |
| sm | 8px | Compact spacing within form rows, list-row internal gaps |
| md | 16px | Default element spacing, form field vertical rhythm, list-row horizontal padding |
| lg | 24px | Section padding within cards/panels, dialog internal padding |
| xl | 32px | Desktop main-column padding, layout gaps between shell regions |
| 2xl | 48px | Major section breaks |
| 3xl | 64px | Page-level spacing (auth screens: gap above/below the centered card) |

**Fixed layout dimensions this phase (all multiples of 4/8, not new tokens — same discipline as Phase 1's 256px sidebar / 64px top bar):**

| Element | Value |
|---|---|
| Vault list row height | 64px (matches TopBar height) |
| Row favicon/type-icon size | 32px, 8px radius |
| Health-dot diameter | 8px (= `xs` token; static/muted placeholder, see Color section) |
| Detail panel width (desktop) | 400px fixed, full-width overlay below `md` breakpoint (mirrors Sidebar's `md:` pattern) |
| Delete-confirmation dialog width | 400px |
| Copy toast width | 320px |
| Password-generator popover width | 320px |
| Auth screen centered card width | 400px (matches detail panel — one card width vocabulary across the app) |

**Exception — icon-only touch targets:** interactive icon buttons that appear only on hover/focus in dense contexts (row-level copy/delete affordances, detail-panel field copy buttons, toast dismiss) use a 40px hit area (padding around a 16–18px icon) even though 40 sits between the `sm`(8) and `md`(16) multiples used elsewhere — this is the same category of exception Phase 1 pre-approved for touch targets, applied concretely here. The icon-only buttons audited as off-scale in the Phase 1 review (`px-3`/`gap-3` = 12px) must be snapped to `sm`(8) or `md`(16) when touched in this phase's shell work — no new 12px usage is introduced.

## Typography

Unchanged from Phase 1 — 4 sizes, 2 weights. Carried forward, not re-opened:

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Label | 14px | 400 | 1.4 |
| Body | 16px | 400 | 1.5 |
| Heading | 20px | 700 | 1.2 |
| Display | 28px | 700 | 1.15 |

**Autonomous call — the Phase 1 "weight 500 deferred to Phase 2 for active vault-list rows" note is resolved by *not* introducing a third weight.** The design contract caps weights at exactly 2; adding 500 would also contradict Phase 1's already-approved/implemented heading weight (700) if reused loosely for emphasis. Active/selected vault-list rows and selected sidebar folders/tags get their emphasis from **background + left accent bar + icon color**, not a new font weight (see Color section). This keeps typography identical across phases — nothing for the checker to re-litigate.

- Label → form field labels, list-row username/subtext, badge text, detail-panel field labels, toast body, generator control labels, timestamps ("ostatnio użyty").
- Body → running text, form helper text, empty-state description (non-hand-font portion), dialog body copy.
- Heading → section titles ("Zaloguj się", "Nowy item", dialog titles, detail-panel item name when in view mode).
- Display → page title ("Vault") — unchanged usage from Phase 1.
- `ui-monospace` (not a sized role — rides at Body/Label size) → passwords (item field + generator output), card numbers.

## Color

Unchanged 60/30/10 split and hex/OKLCH values from Phase 1 (`vault-dark` default, full `vault-light` parity). This phase is the first to put several previously-unused semantic tokens into real UI — documented below.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#1F1F1F` base-300 dark / see **Light theme fix** below | Page background, main-column canvas, blurred-shell scrim |
| Secondary (30%) | `#262626` base-100 (cards, detail panel, dialogs) + `#212121` base-200 (sidebar, top bar) | Cards, panels, sidebar, top bar |
| Accent (10%) | `#E16540` primary coral | "+ Nowy item" CTA (now live), primary submit buttons (Zaloguj się / Załóż konto / Zapisz item), active/selected sidebar nav + folder/tag indicator, focus rings, "Odblokuj" button on the unlock overlay's password path |
| Destructive | `#FF5861` error | Delete-item confirm button, delete-confirm warning icon, form validation error text/borders, revision-conflict (409) banner, self-test fail (carried) |

Accent reserved for: the elements listed above only. **Never** used for item-type badges, health-dot, or decorative fills — those stay neutral (see below).

**Newly-activated semantic tokens this phase:**
- **Teal accent `#00CDB7` (DaisyUI `accent`)** — locked to passkey meaning only, per project instruction. In Phase 2 it appears in exactly **one** place: the `KeyRound` icon inside the login-item detail panel's passkey placeholder section. It does **not** appear on list-row type badges (no login item can have an enrolled passkey until Phase 3 ships enrollment — the section is a display placeholder, so nothing in the list view should visually claim a passkey exists yet).
- **Success `#00A96E`** → generator strength meter "strong" segment, brief save-confirmation flash on the item Save button (checkmark, ~1.5s, non-blocking).
- **Warning `#FFBE00`** → the irrecoverable-master-password notice on Register (`alert alert-warning`), generator strength meter "medium" segment.
- **Secondary `#8DCDFF`** → inline text links only: the Login↔Register toggle link. Matches UI-DESIGN.md's own reservation ("linki") — do not use it for anything else this phase.
- **Info `#00B5FF`** → still unused this phase (forward-compat only, same as Phase 1's treatment of teal).

**Item-type badges are intentionally neutral, not color-coded:** `badge` pill on `base-200`/`base-300` fill with `base-content/70` text, differentiated by icon (`Vault`=login, `CreditCard`=card, `IdCard`=identity, `StickyNote`=note) + label, never by hue. This avoids a second accent system competing with the 10% coral and keeps teal's passkey-only meaning unambiguous.

**Health-dot is a static, non-semantic placeholder this phase:** VAULT-01/UI-03 call for a "health-dot placeholder" in the row — real password-health scoring is HEALTH-01 (v0.3, out of scope). Render an 8px muted-gray dot (`bg-base-content/20`), non-interactive, no success/warning/error coloring yet. A native `title="Password Health — wkrótce"` tooltip is a cheap, optional nicety; not required.

**Light theme fix (folds in Phase 1 UI-REVIEW Priority Fix #1 — WARNING, not optional):**
`vault-light`'s `--color-base-300` currently duplicates `--color-base-200` (`oklch(98.86% 0.0017 67.80)`), so every `border-base-300` divider (TopBar bottom border, card borders, future list-row dividers, dialog borders) is invisible against `bg-base-200` in light mode. Fix: give light theme's `base-300` a **third, distinct step** reserved for borders/dividers — `oklch(93% 0.004 67.80)` (a warm light-gray, visibly darker than both the cream page background at 98.86% and white cards at 100%, same ~67° warm hue as the rest of the palette per UI-DESIGN.md's "nothing cold" rule). This is a one-line `globals.css` change; every component already references `border-base-300` correctly — only the token value was wrong.

## Phase-Specific Notes

### Auth screens — login vs. register vs. unlock (AUTH-01/02, "visibly distinct states")

- **Register** and **Login** are two states of one centered auth card (400px wide, `base-100` surface, 16px radius, 1px `base-300` border, 24px padding, vertically centered on a `base-300` page — no shell chrome, since the user isn't authenticated yet). Toggle via the Secondary-blue text link, not tabs — keeps one primary CTA per screen.
  - Register fields: email, master password, confirm master password, inline strength meter (reuses generator's strength logic — success/warning/error segments), the irrecoverable-password `alert alert-warning` shown persistently (not dismissible) above the submit button.
  - Login fields: email, master password. On success: session token stored, user is authenticated but **vault is not yet unlocked** — this is the architectural split from AUTH-02. Route immediately to the shell with the **unlock overlay active** (see next).
- **Unlock overlay** is visually and structurally distinct from both: it renders **on top of** the real (blurred) shell — sidebar/top bar/main-column chrome visible-but-blurred behind a scrim, never a plain centered card on a blank page like Login. This is the single strongest visual signal that "logged in" ≠ "unlocked."
  - Overlay treatment: `backdrop-blur-md` (12px) applied to the shell layer, `bg-base-300/70` scrim, unlock card (same 400px/16px-radius/24px-padding vocabulary as the auth card) floating centered above it, `z-50`.
  - **Hard requirement, not cosmetic-only:** the blur is decorative. The vault list/detail panel component tree must actually be unmounted (or rendered with no decrypted item data in props/state) whenever locked — a DOM inspector on the blurred background must show no plaintext item names/usernames/passwords, blurred or not. This applies equally to the idle-triggered auto-lock (AUTH-08) and a fresh page load with a valid session but a freed/never-created WASM UK handle.
  - Unlock overlay is playfulness-free per UI-DESIGN.md's explicit "modalu odblokowania" exclusion — plain DM Sans, no Fuzzy Bubbles, no emoji, same rule as the delete dialog.

### Vault list + detail panel (UI-03, VAULT-01/03/04)

- **List rows** (64px height, 16px horizontal padding, 8px internal gap): 32px favicon/type-icon → name (Body/400) + username (Label/400, `base-content/60`) stacked → neutral type badge (icon + label, `badge-sm`) → 8px static health-dot → row-hover reveals copy/delete icon buttons (40px hit area) at the row's trailing edge. Row hover = `base-content/6%` background wash (per UI-DESIGN.md's stated hover treatment, unchanged from the existing datafa.st reference).
- Selected/active row: `bg-primary/8%` fill + 2px coral left border (the "500-weight" emphasis substitute described in Typography) — not a font-weight change.
- **Detail panel** (400px fixed, `base-100` surface, same border/radius vocabulary as cards) replaces — does not modally cover — part of the main column when an item is selected or "+ Nowy item" is clicked; list stays visible/scrollable alongside it on desktop, panel becomes a full-width overlay below `md`.
  - View mode: item name as Heading, fields below as Label (field name) + value (Body, `ui-monospace` for password/card-number), each field row with a trailing 40px copy icon button. Header row: `Pencil` edit button + `Trash2` delete button (opens the delete-confirm dialog).
  - Create mode (from "+ Nowy item"): first shows a 4-tile **type picker** (login/card/identity/note, icon + label per tile, no color-coding — same neutral treatment as list badges), then the type-specific form.
  - Edit/Create form fields, plain DM Sans, no emoji:
    - **Login**: name, username, password (mono, `Eye`/`EyeOff` toggle, trailing generator-popover trigger), URL, notes, folder select, tag multi-select, then the **passkey placeholder section** (bordered sub-panel, `KeyRound` icon in teal, "Brak passkeyów — enrollment dostępny wkrótce" — inert, no add-passkey action this phase).
    - **Card**: name, cardholder name, number (mono, masked with reveal toggle), expiry (MM/YY), CVV (mono, masked), notes.
    - **Identity**: name, first/last name, email, phone, address fields, notes.
    - **Note**: name, body (plain multi-line textarea — **not** mono; secure notes are prose, mono is reserved for password/key-shaped secrets only).
  - Folders/tags live as their own sidebar sections (below the existing Vault/Foldery/Tagi nav placeholders, now functional): flat list, `Plus` affordance to create, selecting one filters the list. Same neutral-icon-plus-label treatment as item-type badges — no per-folder/tag color coding.
- **Search** (TopBar, now live): same input, instant client-side filter as-you-type across name/username/domain; empty-results state uses the copy row above, plain DM Sans (not the Fuzzy Bubbles empty-vault state — those are different conditions: zero items ever created vs. zero matches).

### Password generator (VAULT-05)

- Trigger: small icon button trailing the password field (login/card CVV+number don't get a generator — only the login password field does).
- Surface: `dropdown` popover, 320px wide, anchored below the field.
- Contents top-to-bottom: mode segmented toggle (Znaki / Passphrase — length-first framing per CONTEXT), generated preview (mono, Body size), length control (`range` input, default 20, 8–64 for character mode / 3–10 words for passphrase mode), character-set checkboxes (uppercase/lowercase/digits/symbols — character mode only), strength meter (success/warning/error segments, reused by the Register form), `RefreshCw` regenerate + coral "Użyj tego hasła" apply button.

### Copy toast & clipboard auto-clear (VAULT-06)

- DaisyUI `toast toast-end toast-bottom`, 320px, `base-100` surface, 1px border, 8px radius (field/button radius, not card radius — toast reads as a transient control, not a surface).
- Persists for the **entire** clipboard-clear duration (default 40s, configurable 30–60s per settings — not a typical 3-second toast), showing a live per-second countdown in the copy string. At 0: flips to the "cleared" copy for ~1.5s then fades. Manual `X` dismiss hides the toast early but never cancels the underlying clipboard-clear timer — the timer is a security guarantee, independent of whether the toast is visible.
- Only one toast active at a time; copying a new field while one is showing replaces it and resets the timer (matches the single system clipboard's actual behavior).

### Delete confirmation dialog (VAULT-01, destructive)

- Native `<dialog>`-backed DaisyUI `modal`, 400px, centered, `base-100` surface, `AlertTriangle` icon in error color, plain DM Sans throughout (per UI-DESIGN.md's explicit "nigdy... w dialogach potwierdzeń" exclusion — same rule as the unlock overlay). Confirm button is `btn-error` (destructive red), Cancel is `btn-ghost`/neutral. No trash/soft-delete this phase — the copy says "na stałe"/"permanently" because it is.

### Auto-lock & settings surface (AUTH-08)

- No dedicated Settings screen yet (UI-05 is Phase 3). Auto-lock idle timeout, clipboard-clear duration, language switcher, and a manual "Lock now" (`Lock` icon) action live in a lightweight `dropdown` menu opened from the existing Sidebar account block (extends, doesn't replace, the Phase 1 avatar+name+theme-toggle row). Idle timeout options: 1/5/15/30/60 min, default 15 (per AUTH-08's "np. 15 min").
- Language switcher: icon-only button (`Languages`) beside the existing theme toggle, same interaction pattern (click cycles PL↔EN, persists to `localStorage['pv-locale']`, updates `<html lang>`), same FOUC-avoidance approach as the theme's inline pre-hydration script — no flash of wrong-language text on load.

### Icon-only controls — accessibility contract

Every icon-only interactive control MUST carry an `aria-label` (localized through the same i18n dictionary as visible copy — not hardcoded), following the pattern Phase 1 established with the theme toggle's `aria-label="Przełącz motyw"`:

| Control | PL `aria-label` | EN `aria-label` |
|---|---|---|
| Row-hover copy button | `Kopiuj {field}` | `Copy {field}` |
| Row-hover delete button | `Usuń „{name}"` | `Delete "{name}"` |
| Detail-panel field copy button | `Kopiuj {field}` | `Copy {field}` |
| Password visibility toggle | `Pokaż hasło` / `Ukryj hasło` | `Show password` / `Hide password` |
| Toast dismiss X | `Zamknij powiadomienie` | `Dismiss notification` |
| Generator popover trigger | `Generuj hasło` | `Generate password` |
| Generator regenerate (if icon-only) | `Losuj ponownie` | `Regenerate` |
| Locale switcher | `Zmień język` | `Change language` |
| "Lock now" action | `Zablokuj teraz` | `Lock now` |
| Detail-panel edit button (if icon-only) | `Edytuj item` | `Edit item` |
| Sidebar "+" (new folder/tag) | `Nowy folder` / `Nowy tag` | `New folder` / `New tag` |

A visible `title` tooltip may accompany the `aria-label` but never replaces it. Decorative icons inside labeled controls stay `aria-hidden="true"` (Phase 1 pattern, carried forward).

### Carried-forward fixes from Phase 1 UI-REVIEW (folded into this phase's shell touches)

1. **Light theme `base-300` fix** — see Color section above (WARNING priority, done here since Phase 2 is the next time light-mode surfaces are touched).
2. **Self-test fatal-branch retry** — wherever the self-test lands after this phase's shell rework (dev route or diagnostic panel — planner's call per CONTEXT), its fatal branch must render the "Uruchom ponownie" button and call `run()`, matching the results branch. Do not leave the fatal branch without a recovery affordance.
3. **"patrz błąd poniżej" copy fix** — reword to `"{n}/5 kroków przeszło — patrz błąd przy kroku powyżej"` (EN: `"...see the error at the step above"`) wherever this string is carried into the i18n dictionary.
4. *(Optional, non-blocking, pick up opportunistically per CONTEXT):* 14px→16–20px status icon sizing, remaining off-scale 12px spacing, `aria-disabled` on non-interactive nav `<div>`s.
