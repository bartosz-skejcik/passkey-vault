<objective>
Build the real password-authentication API: `prelogin` (now a real DB lookup with anti-enumeration dummy salts), `register`, `login`, `logout`, and `me`, backed by a `SessionUser` axum extractor that validates opaque bearer tokens hashed at rest. This delivers AUTH-01/AUTH-02 at the API layer — a client (curl, a test, or Plan 02-04's future UI) can create an account and log in, receiving a session token and the caller's `pw_wrapped_uk`, with the server never touching a password or a wrapping key.

This plan also performs a one-time structural fix required for testability: `pv-server` currently has no `src/lib.rs`, so nothing under `tests/` can import its router — Wave 0's "no integration test directory exists yet" gap (flagged in RESEARCH.md/VALIDATION.md) cannot be closed without this. Splitting into a thin `main.rs` + real `lib.rs` is a one-time necessity, not scope creep.

Purpose: Deliver AUTH-01 (register with hash-po-KDF, server never sees the password) and AUTH-02 (login issues a session; unlock is a separate client-side step this plan does not touch) at the server boundary, independent of and parallel to Plan 02-01's crypto extension (the server never runs pv-core crypto — it only stores/verifies bytes the client already derived).
Output: A working, integration-tested auth API (`/api/auth/{prelogin,register,login,logout,me}`) any HTTP client can exercise today.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Client (untrusted) → `/api/auth/*` | All request bodies are attacker-controlled; email/salt/auth_hash length and format must be validated |
| Bearer token (client-held) → `sessions` table | The only artifact standing between an anonymous request and an authenticated one |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-04 | Spoofing | `login` handler | high | mitigate | `constant_time_eq` comparison of `server_rehash` output; identical `ApiError::Unauthorized` for both wrong-password and unknown-email cases so a timing/response-shape oracle can't distinguish them |
| T-02-05 | Information Disclosure | `prelogin` (account enumeration) | medium | mitigate | Deterministic-per-email dummy KDF/salt response for unknown accounts, shape-identical to a real account's response; residual risk of unsalted precomputation accepted as low severity for a self-hosted, low-account-count product |
| T-02-06 | Information Disclosure | `users.auth_hash` at rest (DB leak) | high | mitigate | Server never stores the client-computed `auth_hash` verbatim — `server_rehash` (fresh per-user salt, distinct from the KDF salt) is stored instead, per RESEARCH.md's explicit anti-pattern warning |
| T-02-07 | Elevation of Privilege | Session token reuse after logout | medium | mitigate | `logout` deletes the `sessions` row by `token_hash`; a follow-up `/me` call with the same token returns 401 (covered by an integration test) |
| T-02-08 | Tampering | CORS `permissive()` in dev | low | accept | Production (Phase 7) serves API + static export from one origin in a single container — no cross-origin surface to protect once packaged; permissive CORS is a dev-only convenience documented inline |
| T-02-09 | Information Disclosure | `tower-http` `TraceLayer` logging request/response bodies | high | mitigate | `TraceLayer::new_for_http()`'s defaults log method/URI/status/latency only, never bodies — no custom `on_request`/`on_response` closure is added that would log auth request bodies (containing `auth_hash`) or any future vault ciphertext |

</threat_model>
