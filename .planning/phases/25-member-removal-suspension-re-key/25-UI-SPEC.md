# Phase 25 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **Scope note.** This phase introduces four new visual surfaces, all inside already-existing
> containers — no new page, route, or drawer: (1) a **member list** inside `FamilyTab.tsx`
> (currently absent — `FamilyTab` only renders the bootstrap/invite panels; `GET
> /api/families/members` has been readable by every member since Phase 22 but nothing has ever
> rendered it), gaining per-row Suspend/Reinstate/Remove actions for the owner; (2) a **suspend
> confirmation** (single-step, warning-severity); (3) a **two-step remove confirmation** with an
> honest "what they could see" disclosure (UX-04); and (4) a **"Delete account" section** inside
> `SecurityTab.tsx` (also currently absent — no account-deletion UI exists anywhere in this
> codebase per `25-CONTEXT.md`), reusing the same two-step pattern with owner-vs-member branching.
> A fifth, smaller surface — the **suspended-member banner** a suspended member sees in their own
> `FamilyTab` — closes `25-CONTEXT.md`'s "not a silent loss of data" decision. No new visual
> language: every token, class, and component below is reused verbatim from `docs/UI-DESIGN.md`,
> `packages/pv-ui/tokens.css`, and the existing `ConfirmDialog`/`DeleteConfirmDialog`/
> `PasskeyDeleteConfirmDialog`/`FamilyTab`/`SecurityTab`/`SessionsTab` components. `components.json`
> is absent and shadcn is not part of this project's stack (DaisyUI 5 + `packages/pv-ui`, per
> `CLAUDE.md`/`docs/UI-DESIGN.md`, unchanged across every prior UI-SPEC) — the shadcn init gate is
> not applicable and was not re-asked.
>
> **This phase is entirely security UI** (suspend/remove/delete-account confirmations) — per
> `docs/UI-DESIGN.md`'s "security UI zawsze czytelne, playfulness nigdy w dialogach bezpieczeństwa"
> rule, nothing in this spec uses Fuzzy Bubbles, emoji, or founder-voice copy. Plain DM Sans, calm
> tone, throughout.

## Spacing Scale

Declared values (must be multiples of 4) — identical numeric scale to every prior phase, **no new exception**:

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon-to-label gaps (badge internal padding, row action icon spacing) |
| sm | 8px | Compact inline gaps (role badge to status badge, busy spinner to button label, row action button pair `gap-2`) |
| md | 16px | Member-row internal padding (`px-4`), form/list vertical rhythm |
| lg | 24px | Dialog/card internal padding (`p-6`, matching every existing modal in this codebase) |
| xl | 32px | Vertical gap between the Members section and the "Invite someone" section below it in `FamilyTab` |
| 2xl / 3xl | 48px / 64px | Unused this phase |

**Exception — 12px (`gap-3` / `py-3`):** the member-row shell (§1) uses `gap-3`/`px-4 py-3`, an
explicit deviation from the 8/16 scale. This is not a new invention — it is the **exact, already-
shipped row shell** both `SessionsTab.tsx` (`session-row-*`) and `PasskeysTab.tsx` (`passkey-row-*`)
use today in this same `SettingsPanel` drawer (`flex min-h-16 items-center gap-3 rounded-box border
border-base-300 px-4 py-3`). Matching that exact value keeps the three row types in the same drawer
visually identical in density; picking `gap-2`/`py-2` or `gap-4`/`py-4` instead would make the new
member rows the only visually-inconsistent row type in the panel. No other new 12px usage exists in
this phase — this is the sole exception.

## Color

Unchanged 60/30/10 split and exact OKLCH/hex values from `docs/UI-DESIGN.md` / `packages/pv-ui/tokens.css` — **no new palette, no new hue**. The one new *semantic* pattern this phase introduces is deliberate and load-bearing (SC 1's "reversible-vs-permanent must be legible" requirement):

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | base-300 — `#1F1F1F` dark / light-theme equivalent from `tokens.css` | Page canvas behind the settings drawer (unchanged, this phase adds no new page-level surface) |
| Secondary (30%) | `#262626` base-100 dark / `#FFFFFF` base-100 light | The `SettingsPanel` drawer surface, the member-row card border/background, every dialog's card surface — all reused verbatim |
| Accent (10%, coral `#E16540`) | primary | The "Reinstate" action's icon/text color only (`text-primary` — restoring access is a constructive, brand-adjacent action, not a warning or a destructive one) and the two-step dialogs' first-step "Continue" button (`btn btn-primary`, matches every other neutral-progression CTA in this codebase, e.g. Phase 24's `invite.generateCta`) |
| Warning (new use this phase, `#FFBE00`) | `btn-warning` / `text-warning` / `badge-warning badge-outline` / `alert-warning` | **Reserved exclusively for reversible states**: the Suspend action's confirmation dialog (icon + `btn btn-warning` confirm button, replacing `AlertTriangle`'s usual `text-error` with `text-warning`), the "Suspended" status badge, and the suspended-member's own persistent banner. This is the phase's core color decision: amber, not red, for anything the owner can undo. |
| Destructive (`#FF5861` error) | `btn-error` / `text-error` | **Reserved exclusively for irreversible states**: both steps of the Remove-member dialog, both steps of the Delete-account dialog, and the "Delete account" section's trigger button (`btn btn-ghost` normally, escalating to the dialog's `btn-error` only on the confirm step — the trigger button itself stays neutral, per the row-action precedent below) |

**Row-action neutrality — explicit deviation from a naive "color the destructive icon red" instinct, stated so it isn't mistaken for an oversight:** every row-level action trigger (Suspend/Reinstate/Remove icon buttons in the member list, the "Delete account" section's trigger button) uses the SAME neutral `btn btn-ghost btn-square btn-sm` with no icon color override — exactly matching `DetailPanel.tsx`'s `Trash2` delete-item trigger and `PasskeysTab.tsx`'s rename/delete pair, neither of which colors its icon red at the row level either. Severity is communicated **only inside the confirmation dialog** (warning-amber for suspend, error-red for remove/delete), never by making an entire settings row look alarming. This is a direct consequence of `docs/UI-DESIGN.md`'s "communicate security through calm and clarity, not black/padlocks" principle, and mirrors the precedent Phase 24 already established for its own `alert-warning`-not-`alert-error` failure state.

**Accent reserved for:** the Reinstate action and the two-step dialogs' non-final "Continue" button, both named above. Nothing else in this phase's scope competes for the accent budget — teal (identity/passkey semantic) is not used anywhere in this phase.

**Copywriting honesty constraints (hard requirements of this phase, re-stated here for the checker):**

1. `member.removeHonestyWarning` must never be omitted, softened, or placed anywhere but directly beneath the access list on Remove step 1 — it is the phase's single most safety-critical string (`25-CONTEXT.md`: "not negotiable copy").
2. `account.deleteOwnerWarning` must render for the owner and must interpolate the real family name and a real member count — never a generic "this affects other people" without specifics. A non-owner deleting their own account never sees this string.
3. No copy anywhere in this phase implies suspension protects past exposure — suspension's honesty burden is smaller (it does not claim to undo anything; it only claims to pause future access), but `member.suspendConfirmBody`'s "reversible" framing must not bleed into remove/delete copy, and vice versa — the two must stay visually and textually distinct (see Color's warning-vs-error split).
4. The removed/suspended member receives no notification copy anywhere in this phase — `25-CONTEXT.md` explicitly declines this. `family.suspendedBannerTitle`/`Body` are read only by the affected member themselves, on their own next visit to `FamilyTab` — never pushed to them as a toast/notification at the moment of suspension.

### E1 — Member list (`FamilyTab.tsx`, new "Members" section)

| Category | Status | Resolution |
|----------|--------|------------|

| error | ✅ covered | `account.deleteFailed`, inline, dialog stays open (never a silent close on failure — matches `PasskeyDeleteConfirmDialog`'s precedent). |
| branch — no family | ✅ covered | `account.deleteStep1Body` alone; `account.deleteOwnerWarning` never renders. |
| branch — plain member | ✅ covered | `account.deleteStep1Body` alone (already covers "if you belong to a family, you'll lose access…" generically); `account.deleteOwnerWarning` never renders — only the owner sees the family-name/member-count specific warning. |

  with a `severity?: "error" | "warning"` prop (default `"error"`, zero behavior change for

  (title/body/confirmLabel/onConfirm/onClose) is otherwise identical to `ConfirmDialog`'s existing
  contract. `severity="warning"` swaps `AlertTriangle`'s `text-error` for `text-warning` and the

### 1. Member row layout (E1)

Row shell: `flex min-h-16 items-center gap-3 rounded-box border border-base-300 px-4 py-3` —
**identical** to `SessionsTab.tsx`'s existing session-row shell (same min-height, same border/radius,
same internal padding), so the member list reads as visually continuous with the rest of the
Settings drawer rather than introducing a new row idiom:

```
[Users-icon-less row — no per-row icon, unlike sessions' DeviceIcon]
  email (truncate+title, Label role)  [role badge]  [status badge if suspended]
  family.joinedLabel (Label role, text-base-content/60)
                                                    [PauseCircle/PlayCircle btn]  [UserMinus btn]
```

Both action icons are `btn btn-ghost btn-square btn-sm` (E1's action-visibility row, Color's
row-neutrality decision) with `aria-label`s from `member.suspendAria`/`reinstateAria`/`removeAria`,
each interpolating the row's own email — mirroring `SessionsTab.tsx`'s exact
`aria.revokeSessionLabel` pattern (interpolated device name).

### 2. Remove dialog — access list rendering (E4)

Fetches `GET /api/families/members/{user_id}/access` (already shipped, Phase 22 —
`MemberAccessResponse { collections: [{ id, access_level }], item_shares: [{ item_id, access_level
}] }`). The list groups by the two response arrays exactly:

```
member.removeAccessListHeading

  [if collections.length > 0]
  member.removeAccessFolderLabel × N        (folder name + access-level badge)
    → nested item names inside that folder, OR
      member.removeAccessItemsUnresolvedNote (count-only fallback — see §4)

  [if item_shares.length > 0]
  (item name + access-level badge) × N — individually-shared items, flat list

  [if both empty]
  member.removeAccessListEmpty
```

Access-level badges use `badge badge-ghost` with the mapped copy from `access.readOnly` /
`access.fullEdit` / `access.hiddenPassword` (see Copywriting Contract) — never the raw
`access_level` enum string (`read`/`edit`/`hidden_password`) from the API response. This is
user-facing security copy inside a destructive-confirm dialog, not a debug value. Phase 26 owns the
richer sharing-UI visual language (badge color-coding, iconography) for these same three levels when
it ships the actual share-creation flow; this phase's badge is display-only (it never sets an access
level) and may be superseded by Phase 26's styling later, but the **copy itself** is this phase's own
contract, not a placeholder.

### 3. Two-step dialog shell (E4, E6)

Both `RemoveMemberDialog` and `DeleteAccountDialog` use the **same 400px modal shell** as every
other dialog in this codebase (`fixed inset-0 z-50 flex items-center justify-center bg-base-300/70
p-4` outer, `w-full max-w-[400px] flex-col gap-4 rounded-box border border-base-300 bg-base-100
p-6` card) with **one internal state machine, not two stacked dialogs** — step 2 replaces step 1's
content inside the same card, matching `InviteLandingView`'s established "one component, multiple
states" idiom rather than opening a second overlay. Cancel at step 2 returns to step 1 (not a full
close) **except** the access-list fetch itself is not re-run — the already-fetched list stays in
memory for the duration of the dialog's lifetime, only being cleared on full dialog close.

### 4. Cross-phase gap this UI-SPEC surfaces (flag for the plan, not silently assumed)

`25-CONTEXT.md`'s UX-04 decision is explicit and non-negotiable: the disclosure list must show
**actual item names**, not counts. Resolving a folder's contents into item names requires
unwrapping that folder's Collection Key and decrypting each item's name field — the crypto
primitives for this shipped in Phase 21 (`CollectionKey` unseal + collection-scope item decrypt,
`crates/pv-core`/`crates/pv-wasm`), but per `.planning/STATE.md`'s Phase 24 note, **no client-side
capability to list or decrypt a `collections` resource exists anywhere in `web/src` yet** — that
capability is Phase 26's headline deliverable.

This phase's owner is, by construction, a member of every collection it might need to resolve
(family owners retain full access per `25-CONTEXT.md`/Phase 24's `invite.honestVisibilityNote`
precedent) — so the *crypto* is possible with what Phase 21 already shipped. What's missing is the
**plumbing**: an endpoint to list a collection's items and a client call site to unwrap+decrypt
them, scoped narrowly to this one dialog's need (not the full collections browser Phase 26 builds).

**Requirement for the plan — not optional, not a rendering branch to authorize:** the plan must
build the minimal fetch-and-decrypt path needed for this one disclosure list, reusing Phase 21's
already-shipped WASM primitives (`CollectionKey` unseal + collection-scope item decrypt) directly —
not waiting on Phase 26. `25-CONTEXT.md`'s UX-04 decision is locked: "the confirmation lists the
actual item names... a count cannot answer that." This phase owes real item names in the normal
case, full stop.

`member.removeAccessItemsUnresolvedNote` is scoped **exclusively to genuine runtime resolution
failure** — a network error mid-fetch, or a collection deleted between the access-list fetch and the
name-resolution call. It is not an authorized substitute for building the resolution path, and it
must never be reached because the resolution path was never implemented. A plan that ships
count-only disclosure for every folder — or that treats "not yet built" as an instance of this
fallback — does not conform to this UI-SPEC. At verification time, the resolved-names path must be
shown reachable in the shipped code (e.g. a test that asserts real item names render for a populated
folder), not merely that the fallback copy exists somewhere.

### 5. Non-visual notes carried from CONTEXT.md (traceability only)

- FAM-09's immediacy ("suspended/removed member's session loses access on the very next request")
  is a server/authorization property, not a UI token — this UI-SPEC's only obligation toward it is
  E5's suspended-banner surface, which communicates the *consequence* of that immediacy honestly
  rather than implementing it.
- The WR-07 inherited debt ("revoked access moves no counter the revoked member can observe") is
  a sync-layer fix, not a UI concern — not re-specified here.
