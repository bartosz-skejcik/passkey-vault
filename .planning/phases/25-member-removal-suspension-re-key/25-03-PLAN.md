<objective>
Build the flagship deliverable of Phase 25: a member can be atomically, provably-scoped removed from
the family, with every collection they could reach re-keyed in one transaction, every direct share they
held severed, their own next request denied, and every item's payload ciphertext left byte-for-byte
untouched. This is the tracer that proves the whole re-key architecture end-to-end at the server layer
before any client UI exists to drive it — the batch is constructed directly from `pv-core` in this
plan's own integration test, exactly the way a real browser tab will construct it in Plan 25-07.

Purpose: FAM-08, KEY-02(SC 6), KEY-06, KEY-07, and FAM-09's remove-side all become real, callable,
tested server behavior in this one transaction. Every later Phase 25 plan (hardening tests, account
deletion, client orchestration, UI) builds on the shape this plan fixes.
Output: `collection_items`, `remove_member`, the shared `apply_member_removal_rekey` helper, both
routes wired into `mod.rs`, and a green `tests/family_removal.rs` proving the full happy path plus the
zero-collection degenerate case.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| family owner (authenticated, FamilyMembership<RequireEdit>) → remove_member's client-supplied batch | the batch's SHAPE (which collections, which item ids, which recipient ids) is untrusted input the server must re-verify; the batch's CONTENT (sealed keys, wrapped keys) is opaque and inherently trusted by zero-knowledge design — the server cannot validate it cryptographically, only structurally |
| removed member's already-issued session token → any Membership/FamilyMembership-gated route | must lose all resource authorization on the very next request, independent of token validity |
