<objective>
Lay the two pieces of groundwork every later Phase 25 plan depends on: an additive suspension-state
column on `family_members`, wired into the SAME fresh-per-request access-resolution queries every
other authorization decision in this codebase already uses (so FAM-09's "next request loses access"
property falls out of existing infrastructure rather than a new caching mechanism); and a direct,
empirical proof that SQLite foreign-key enforcement is genuinely ON in the real connection pool — the
precondition Plan 25-06's account-deletion delete-ordering logic depends on being true, not assumed.

Purpose: every downstream Phase 25 plan (suspend/reinstate handlers, the removal transaction, account
deletion) is unsound if either of these two facts is wrong; this plan makes both facts true and proven.
Output: migration 0018, an extended `membership.rs` with the suspension join and regression tests, and
a new `lib.rs` test closing RESEARCH.md's Assumption A1.
</objective>

## Artifacts this phase produces

- `crates/pv-server/migrations/0018_member_suspension.sql` (new) — `family_members.status` column,

  `Item::resolve_access`'s RECIPIENT-side `family_members` joins gain `AND fm.status = 'active'`; four
  new unit tests.

  `.foreign_keys(true)` fix to `build_pool`'s `SqliteConnectOptions` chain if the empirical assertion
  fails on first run.
