# Phase 15 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **Scope note.** This phase is REMOVAL + re-layout of three existing popup auth surfaces (signed-out hero, locked unlock card, server-change confirmation) plus deletion of the entire ext-scoped-PRF surface (`EnrollExtPasskeyPrompt.tsx` and its `extPasskey.*` copy). It introduces **zero new visual language** — every token, color, and component class below is reused verbatim from `09-UI-SPEC.md` (popup shell) and `13-UI-SPEC.md` (extension-wide tokens), which remain authoritative for every surface this phase doesn't touch (item list, item detail, autofill, provider ceremony). The four grey areas Bartek resolved today (`15-CONTEXT.md`) are treated as locked inputs, not reopened.

## Typography

Same 4 roles, same sizes/weights/line-heights as every prior phase — **not reopened**:

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Label | 14px | 400 | 1.4 |
| Body | 16px | 400 | 1.5 |
| Heading | 20px | 700 | 1.2 |
| Display | 28px | 700 | 1.15 |

- **Heading → the signed-out hero's wordmark** ("Passkey Vault", `app.title` — the popup's "logo": no image/SVG mark exists anywhere in this codebase, confirmed this session, so the wordmark itself, DM Sans 700, IS the logo). **Explicit decision: Heading (20px), not Display (28px)**, even though this is the one moment the popup gets a hero-feeling screen. Rationale: `09`/`13`-UI-SPEC.md already flagged Display as wrap-risky at the popup's 360–400px width, and "Passkey Vault" (12 characters + space) has no numeric/hero-metric reason to earn the escalation a security-score or item-count would justify. Staying at Heading keeps this phase from reopening a settled typography question for a one-line wordmark that doesn't need it.
- Body → password-field label text's sibling copy (session-locked notice, busy/failure inline lines), confirm-dialog body copy.
- Label → field label ("Hasło główne"), gear icon-button's accessible name (not visually rendered, but same role/weight family as every other label-role string in this component tree).
- Display → still **not used anywhere in the popup**, unchanged.

## Color

Unchanged 60/30/10 split and exact hex/OKLCH values from `docs/UI-DESIGN.md` — **no new palette, no new hue**:

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#1F1F1F` base-300 dark / `#FCFBFA` base-200 light | Popup canvas behind all three surfaces this phase touches |
| Secondary (30%) | `#262626` base-100 dark / `#FFFFFF` base-100 light | Confirm-dialog card surface (reuses the standing card vocabulary — 16px radius, 1px border, `lg`/24px padding) |
| Accent (10%, coral `#E16540`) | primary | Signed-out hero's "Zaloguj się" button, locked view's "Odblokuj" password submit, confirm-dialog's "Zmień serwer" button |
| Destructive | `#FF5861` error | Wrong-password inline text only. **Explicitly NOT used for the server-change confirmation dialog** (see below) |

**Teal (`#00CDB7`, `accent` token) — reserved for passkey meaning only, unchanged carve-out, one consolidation this phase:**
- The locked view's "Odblokuj passkeyem" button (`btn btn-accent`, `Fingerprint` icon, `unlock.passkeyCta` copy) is **promoted** from its current `btn-outline` treatment (where it was a secondary, D-12-gated fallback behind the dying ext-scoped teal button) to the primary teal treatment — it is now the ONE passkey-unlock affordance on both browsers, so it inherits the teal carve-out every prior phase reserved for "the" passkey action, exactly as `04`/`09`/`13`-UI-SPEC.md always intended once a single ceremony existed.
- The signed-out hero's "Zaloguj się" button is deliberately **coral, not teal** — it opens the ceremony window, which may itself resolve via password or passkey (out-of-scope-visually per the phase boundary), so the popup-side button is an honest generic "continue to sign in" action, not a passkey-specific commitment.

**Server-change confirmation dialog — WARNING tier, not destructive/error tier (explicit deviation from the codebase's usual delete-confirm convention, stated here so it isn't mistaken for an oversight):** a server-URL change that signs the user out is **reversible** (they can sign back in) — categorically different from an irreversible data-loss action (item delete), which is the only class of confirm-dialog this codebase has used the `AlertTriangle` + `btn-error` combination for so far (`02-UI-SPEC.md`). This dialog uses `AlertTriangle` (icon only, neutral/warning color — `text-warning`, not `text-error`) + `btn btn-primary` confirm (not `btn-error`) + `btn btn-ghost` cancel. This mirrors `13-UI-SPEC.md`'s own "Semantic-severity split for warning content" doctrine (a real, actionable heads-up is `alert-warning`, not automatically `alert-error`).

**Accent reserved for:** the three primary-action buttons named above (hero CTA, password submit, dialog confirm) plus the one teal passkey button. Nothing else in this phase's scope competes for either budget.

## Phase-Specific Notes

### Signed-out popup hero (AUTH-01 — REPLACES UnlockView's current Sign-in variant entirely)

Bartek's decision, verbatim: "Rób wszystko przez okno, jedyne co w popup to odblokowanie jeśli chodzi o auth i url servera." The `status.kind === "no-session"` branch of the popup's auth view becomes a genuinely minimal hero, not a form:

- **Top-right corner:** `Server` icon-button (40px hit area per the standing touch-target exception), `aria-label` = `config.changeServer` — opens `ServerConfigView` in reconfigure mode. This is the SAME position and SAME component used in the locked view below (one consistent server-config affordance across both signed-out and locked states — see next section), not a separate treatment per state.
- **Centered vertical stack**, generous breathing room (`xl`/32px gaps, first legitimate popup use of that token — see Spacing):
  1. Wordmark ("Passkey Vault", `app.title`, Heading role, `text-center`) — the popup's logo, since no image mark exists.
  2. "Zaloguj się" button (`auth.loginSubmit`, `btn btn-primary`, coral, no icon — see Color's rationale for why this is coral not teal). Dispatches `unlock.serverCeremony.start` with `mode: "signin"` (existing infra, `unlock.serverCeremonyInFlight`/`unlock.serverCeremonySigninFailed` reused verbatim for busy/failure — see Copywriting Contract's flagged stale-clause note on the failure copy).
- **No email field, no password field, ever, in this view.** This is the literal AUTH-01 success criterion — the popup itself never renders a password sign-in form.
- **No `hasServerConfig` gate needed on this button** (simplification vs. the current code): `App.tsx`'s `refreshFromScratch()` already routes to the first-run `server-config` gate BEFORE this view can ever render, so a server is guaranteed configured by the time the hero shows. Remove the now-redundant conditional.
- **Out of scope, explicitly:** the ceremony window's own sign-in UI (`web/src/components/auth/ExtUnlockBridge.tsx`, `mode="signin"`) is NOT redesigned by this phase. If plan-phase decides that window needs a password fallback added (per `15-CONTEXT.md`'s Claude's Discretion note on whether `auth.signIn.password` survives as an internal-only ceremony-window path), any such addition must stay strictly within this document's existing token vocabulary (`input input-bordered`, `btn btn-primary`, DM Sans, no Fuzzy Bubbles — security-critical surface) rather than inventing new visual language there.

### Locked popup unlock card (AUTH-02 — password-first, promoted passkey button)

Bartek accepted the recommendation: password-first with autofocus, "Odblokuj" (Enter submits), a secondary "Odblokuj passkeyem" button below it. Layout, top to bottom:

1. Same `Server` icon-button, same top-right position, same `config.changeServer` aria-label as the signed-out hero — **replaces** the current bottom `btn-link` "Zmień serwer" text link entirely. One consistent server-config affordance across the whole unlock-only auth surface (not two redundant ones), matching Bartek's "auth w popupie = TYLKO odblokowanie i URL serwera" framing.
2. Session-locked notice (`unlock.sessionLockedNotice`, Body role, muted) — only when `wasAutoLocked`, unchanged from current behavior.
3. Password field: label `auth.passwordLabel`, `input input-bordered w-full font-mono`, **`autoFocus` — new, must be added** (current code has no autofocus; this is the one concrete behavioral change Bartek's decision requires beyond reordering).
4. Wrong-password error line (`auth.loginFailed`, `text-error`) — unchanged.
5. Primary submit: "Odblokuj" (`unlock.submit`, `btn btn-primary w-full`) — Enter key already submits via the existing `<form onSubmit>` wrapper, no new wiring needed.
6. Divider (`unlock.orDivider`).
7. Secondary button: "Odblokuj passkeyem" (`unlock.passkeyCta`, `btn btn-accent w-full`, `Fingerprint` icon) — dispatches `unlock.serverCeremony.start` with `mode: "unlock"` (existing infra, reused). **Always visible whenever a server is configured** (which, per the unlock view's own precondition, it always is) — no more D-12 "unusable"/Firefox-known-impossible gating logic; that entire branch (`extScopedUnusable`, `showServerCeremonyButton`'s conditional) is dead code once ext-scoped PRF is removed, since there is exactly one ceremony and it behaves identically on both browsers.
8. Busy/failure inline lines (`unlock.serverCeremonyInFlight` / `unlock.serverCeremonyFailed`) — reused verbatim; button re-enables after failure, no permanent disabled state (see UI Considerations).

**State variables this view sheds entirely:** `email`, `prfBusy`, `prfNotice`, `prfOrphanedThisSession`, `prfUnusableThisSession`, `extPasskeyEnrolled`/`showPrfButton`/`showTier1Explainer`/`extScopedUnusable`/`showServerCeremonyButton` (the last one collapses to an unconditional render), `randomChallengeB64()` and its whole ext-scoped `navigator.credentials.get()` call path. What remains: `submitting`, `passwordError`, `serverCeremonyBusy`, `serverCeremonyFailed`, `hasServerConfig` (now only gates showing the `Server` icon-button, trivially always true here too since this view also can't render without a configured server — arguably removable, executor's call).

### Server-change confirmation dialog (AUTH-04)

Reached from `ServerConfigView`'s submit handler when a session or host-permission exists for the CURRENTLY configured (about-to-be-replaced) server. **Order matters:** validate + probe the NEW url FIRST using `ServerConfigView`'s existing `invalid-url`/`unreachable`/`cors-blocked` error states (unchanged, blocks early exactly as today) — only once the new server is confirmed reachable does this dialog appear, so the user is never asked to confirm a switch that would fail anyway.

- Modal overlay: reuses the codebase's standing `fixed inset-0 z-50` scrim + centered card pattern (`02-UI-SPEC.md`'s delete-confirm convention, `ExtUnlockBridge.tsx`'s own overlay for structural precedent), card = the standing 16px-radius/1px-border/`lg`-24px-padding vocabulary.
- `AlertTriangle` icon (warning-tier color — see Color's explicit deviation from the destructive/error convention).
- Body: `config.changeServerConfirmBody`, interpolated `{host}` = hostname only (see UI Considerations' long-text row).
- Two buttons: "Potwierdź" (`btn btn-primary`) and "Anuluj" (`config.cancel`, `btn btn-ghost`).
- On confirm: busy state (`loading loading-spinner loading-sm` on the confirm button, both buttons disabled) while the full sign-out + old-origin revoke + new-origin grant sequence runs (`15-CONTEXT.md`'s Claude's Discretion: exact grant-then-revoke vs. revoke-then-grant ordering is the planner's call — "pick the order that can't strand the user with zero working origins" is the one hard constraint this document inherits, not resolves).
- On failure mid-migration: `config.changeServerMigrationFailed` inline error line (`alert alert-error`), dialog stays open, both buttons re-enabled for retry — the user must never be left signed out of the old server without being signed into the new one (AUTH-04's own success criterion).
- On success: dialog closes, the popup's own view state resets to the signed-out hero (fresh sign-in against the new server) — no stale item-list/detail view survives a full sign-out, mirroring the existing `session.locked` handling already in `App.tsx`.

### Ext-scoped PRF removal (AUTH-03 — no new UI, pure deletion)

`EnrollExtPasskeyPrompt.tsx` and its render slot (`App.tsx`'s `showEnrollPrompt`/item-list "top slot") are deleted outright — no replacement banner, no one-time notice, per Bartek's explicit "wycofaj to i zrób jednolite" mandate. `extension/lib/passkeys/prf.ts` (ext-scoped helpers), `extension/lib/passkeys/ext-prf.ts` (`buildExtGetOptions`), and the `unlock.extPrf.*` message kinds/background handlers are removed with no UI-facing trace. Server-side `prf_wrapped_uk` blobs from prior ext-scoped enrollments are a data-cleanup question (Claude's Discretion per CONTEXT.md), not a UI-SPEC concern — no popup surface references them either way.
