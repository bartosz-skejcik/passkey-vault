    concurrent_redemption_exactly_one_wins()`. Build one family via an owner account, then loop 5
    times: create a fresh family-only invite, register two brand-new users (`racer-a-{i}@example.com`,
    `racer-b-{i}@example.com`), clone the router (`axum::Router` is cheap to `.clone()` — both clones
    share the same underlying `AppState`/`SqlitePool`), and launch both `accept` requests via
    `tokio::join!(app_a.clone().oneshot(accept_request_a), app_b.clone().oneshot(accept_request_b))`.
    Assert exactly one of the two responses is `StatusCode::OK` and the other is `StatusCode::NOT_FOUND`
    (or `CONFLICT` — whichever the losing branch's guarded-UPDATE-then-bump path returns; assert
    against whatever `accept`'s actual losing-path status is, not an assumed one). After each
    iteration, `SELECT user_id FROM family_members WHERE family_id = ?` and assert the result set's
    length grew by exactly 1 (one of the two racers, not both, not neither) — the strongest possible
    assertion, since it fails even if per-response status parsing were somehow fooled.
