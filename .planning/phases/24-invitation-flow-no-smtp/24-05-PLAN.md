<objective>
Give the web app the two client-side libraries every UI plan in this phase (24-06, 24-07) will import
from: a widened `lib/crypto` choke-point exposing Phase 21/22/24's identity/collection/invite WASM
bindings, and a new `lib/invite/` orchestration layer (API client + crypto glue) plus the
`ensureOwnIdentityKeypair` helper that is this phase's actual FIRST real caller of `PUT
/api/identity/keypair` (Phase 22 built the endpoint; nothing has called it until now). Also lands every
new i18n string this phase's two UI plans need, in one place, so neither later plan touches
`dictionary.ts` and the two UI plans can execute in parallel without a shared-file conflict.

Purpose: isolates all new crypto/network wiring behind small, independently-testable modules before any
component is built on top of them — including 24-CONTEXT.md's Amendment 2 proof-of-possession leg,
which touches both the create-time and redemption-time call sites.
Output: `lib/identity/{api,ensure}.ts`, `lib/invite/{api,crypto}.ts`, widened `lib/crypto/index.ts`,
every new `dictionary.ts` key.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| lib/crypto/index.ts ↔ rest of web/src | the only sanctioned crossing point for raw WASM bindings — a second import site would let key material leak into a component's own scope unaudited |
| invite URL fragment ↔ invite URL path | both derived from the same secret; a mismatch means either a tampered link or a copy/paste error — must be caught client-side before any network call |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-24-12 | Information Disclosure | web/src/lib/invite/crypto.ts | medium | mitigate | `secretBytes` is captured into `secretForUrl` (a value, not a live buffer reference) before `WasmInviteChannel.fromSecret` zeroizes it; the raw secret is never written to `localStorage`/`sessionStorage` anywhere in this module (React state ownership lands in Plan 24-06) |
| T-24-13 | Tampering | web/src/lib/invite/crypto.ts (fetchInviteMetadataFlow / redeemInviteFlow) | medium | mitigate | the fragment-vs-path invite_id self-consistency check runs BEFORE any network call in BOTH orchestration functions independently, so a corrupted/mismatched link fails closed client-side rather than producing a confusing server round trip |
| T-24-14 | Elevation of Privilege | web/src/lib/identity/ensure.ts | medium | mitigate | the race-loser path always adopts the SERVER's canonical published key (never trusts its own locally-generated one once `adopted_existing: true` comes back), matching `identity.rs`'s own documented idempotent-upsert contract |
| T-24-24 | Tampering | web/src/lib/invite/crypto.ts (proof hash vs raw proof) | high | mitigate | `generateInviteLink` sends ONLY `channel.proofHashForCreation()`'s output as `proof_hash`; `fetchInviteMetadataFlow`/`redeemInviteFlow` send ONLY `channel.proofForRedemption()`'s output as `invite_proof` — the two client functions are never called for the other's purpose, and the new Vitest test explicitly asserts they produce different byte sequences from the same channel (Amendment 2's server-side comparison depends entirely on the client never swapping these) |
