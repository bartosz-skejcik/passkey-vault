<objective>
Wire `webauthn-rs` (already a pinned, unused workspace dependency) into a real, persisted-state WebAuthn ceremony pipeline: replace the schema-incompatible `webauthn_credentials` table, add the `webauthn_states`/`sessions` schema this phase needs, and implement the AUTH-03 two-ceremony passkey enrollment endpoints (`register/start`, `register/finish`, `:id/prf-wrap`) per 03-CONTEXT.md's locked flow and 03-RESEARCH.md's Architectural Responsibility Map (ceremony verification and no-stranding enforcement are backend-tier; PRF evaluation itself never touches this crate).

This is the load-bearing crypto-protocol plan of the phase — everything else (passkey management, sessions, the enrollment UI) builds on the endpoint contracts and schema this plan establishes.

Purpose: A logged-in user can enroll a PRF-capable passkey and have the server durably record BOTH the credential and a passkey-wrapped copy of the User Key, added alongside (never replacing) the password wrap — the foundation of AUTH-03 and, transitively, AUTH-05's structural recovery invariant.
Output: `passkeys`/`webauthn_states` tables, `PV_RP_ID`/`PV_ORIGIN`-driven `Webauthn` instance on `AppState`, three working ceremony endpoints verified end-to-end by a software-authenticator-driven integration test (no browser required).
</objective>

`Passkey` (from `webauthn-rs-0.5.5/src/interface.rs` — always `Serialize + Deserialize`, no feature flag needed):
```rust

    pub fn cred_id(&self) -> &CredentialID;         // CredentialID derefs to Vec<u8>, impls AsRef<[u8]>

```

`PasskeyRegistration`/`PasskeyAuthentication` (the ceremony state that MUST be persisted, per
03-CONTEXT.md's `webauthn_states` decision) are `Serialize + Deserialize` ONLY when the crate
feature `danger-allow-state-serialisation` is enabled — this is NOT currently on in
`crates/pv-server/Cargo.toml` (`webauthn-rs = "0.5"`, no features). This is a genuine, verified
gap in 03-RESEARCH.md (which says "no new crates needed" — true, but a feature flag IS needed).
The crate's own doc explicitly calls serialising-to-a-database the *safe* case this feature exists
for (as opposed to a client-side cookie, which would allow replay).

`CreationChallengeResponse`/`RequestChallengeResponse` shape (from `webauthn-rs-proto-0.5.5`):
```rust
#[serde(rename_all = "camelCase")]
pub struct CreationChallengeResponse { pub public_key: PublicKeyCredentialCreationOptions }
#[serde(rename_all = "camelCase")]
pub struct RequestChallengeResponse { pub public_key: PublicKeyCredentialRequestOptions, ... }
```
Emit these structs as opaque fields of your own response DTOs (`#[derive(Serialize)]`) — never
construct or destructure `PublicKeyCredentialCreationOptions`/`...RequestOptions` by hand.

All WebAuthn wire fields (`challenge`, `id`/`rawId`, `attestationObject`, `clientDataJSON`,
`signature`) serialize as base64url-no-padding (RFC 4648 §5, via `Base64UrlSafeData`) — this is
DIFFERENT from the rest of this codebase's standard-base64 convention (`STANDARD.encode`, used for
`kdf_salt`/`auth_hash`/session tokens). Do not run these fields through the app's existing
standard-base64 helpers. `prf_salt` (an app-invented value, not part of the WebAuthn wire format)
correctly uses standard base64 (`STANDARD.encode`/`STANDARD.decode`), matching every other salt in
this codebase.
