<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Bearer session → passkey/session row ownership | Every list/rename/delete/revoke query must resolve strictly to the caller's own `user_id` |
| Client → recovery-invariant delete guard | A client (or a compromised/buggy frontend) must not be able to strand the vault by deleting the last recovery-capable credential |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|------------------|
| T-03-02 | Elevation of Privilege | `passkeys.rs::rename/delete_passkey`, `sessions.rs::revoke` | high | mitigate | Every query is `WHERE id = ? AND user_id = ?` bound to `session.user_id`; cross-user access returns 404, proven by `passkeys_ownership_rejects_cross_user_access`/`sessions_revoke_ownership_check` |
| T-03-03 | Denial of Service (self-inflicted, must be structurally prevented) | `passkeys.rs::delete_passkey` | critical | mitigate | Runtime 409 defense-in-depth check reads `users.pw_wrapped_uk` before any DELETE, layered on top of the schema-level `NOT NULL` constraint already in place since Phase 2; proven by `delete_passkey_blocked_without_password_wrap` against a DB-manipulated otherwise-unreachable state |
| T-03-06 | Denial of Service (availability, self-host) | `auth.rs::me` last_used_at update | low | mitigate | Throttled (5-minute) conditional UPDATE instead of unconditional per-request writes, avoiding SQLite single-writer contention under normal use |

</threat_model>
