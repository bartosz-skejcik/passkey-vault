From Plan 03-01/03-02 (backend, already on disk): `GET /api/passkeys` returns
`{ id, name, prf_capable: boolean, created_at: string, last_used_at: string | null }[]`.
`PATCH /api/passkeys/:id` takes `{ name: string }`, `204` on success, `400` on empty/too-long name,
`404` cross-user. `DELETE /api/passkeys/:id` returns `204` normally, `409` (with a JSON `{ error }`
body per this codebase's `ApiError` shape) when it would strand the vault.
`GET /api/sessions` returns `{ id, user_agent: string | null, created_at: string, last_used_at: string | null, current: boolean }[]`.
`DELETE /api/sessions/:id` returns `204`, `404` cross-user.

`registerStart`/`registerFinish`/`prfWrap` and the `apiJson<T>` wrapper pattern — this plan ADDS
`listPasskeys`, `renamePasskey`, `deletePasskey` to that SAME file (extend, do not create a second
API-client file for passkeys).

`formatRelativeTime(updatedAt: string | undefined, t, locale, now?): string | null` (from
`@/lib/format/relativeTime`) — pass `row.last_used_at ?? undefined`, fall back to
`t("passkeys.neverUsed")`/`t("sessions.unknownDevice")`-equivalent copy when it returns `null`.
