# Phase 3 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **Generated overnight in fully autonomous mode** (Bartek asleep, explicit authorization — see 03-CONTEXT.md header). Every visual-taste call this agent had to make without a human in the loop is called out in **Morning review notes** at the end of this document. | Icon library | `lucide-react` (carried forward). New icons this phase: `Fingerprint` (enrollment ceremony steps — the one new icon concept this phase introduces, standard WebAuthn/passkey visual shorthand, teal when a step succeeds), `Loader2` (spin animation, ceremony step in-progress — paired with, not replacing, DaisyUI's `loading-spinner` class where a plain CSS spinner suffices), `Check` (ceremony step success — already in the Phase 2 icon set, reused), `AlertTriangle` (already in Phase 2 icon set — reused for delete-passkey dialog and the 409 blocked-delete banner, never a new meaning), `Monitor` (session row device icon — see Morning review notes on why this is a single generic icon, not per-device-type detection), `LogOut` (already in Phase 2 icon set — reused for both the per-session revoke row action and the "Wyloguj pozostałe" bulk action, keeping one icon = one meaning across the app), `ShieldCheck` (Bezpieczeństwo tab icon in the Settings tab bar), `KeyRound` (already in Phase 2 icon set, teal — reused for the Passkeys tab icon and PRF-capable badge; rendered **muted/neutral**, not teal, for `prf_capable: false` passkeys — see Color section), `Pencil`/`X` (already in Phase 2 icon set — inline rename trigger/cancel, reused verbatim). No new icon-library dependency; every icon above ships in the `lucide-react` version already installed. |
| Font | Unchanged: `DM Sans` for all UI text; `Fuzzy Bubbles` stays confined to the vault empty-state per UI-DESIGN.md §1. This phase adds two more surfaces to the explicit "never Fuzzy Bubbles, never emoji" list (extending Phase 2's rule, which already covered the unlock overlay and delete-confirm dialog): the **passkey-delete confirmation dialog** and the **enrollment ceremony dialog** are both security-adjacent flows and stay plain DM Sans throughout, matching this phase's IMPORTANT instruction that passkey-delete/session-revoke UI must be sober and legible, never playful. `ui-monospace` is **not** needed this phase — no new secret-shaped value is displayed (credential IDs/PRF salts are never rendered to the user, per the zero-knowledge/least-disclosure default). |

## Color

Unchanged 60/30/10 split and hex/OKLCH values from Phase 1/2 (`vault-dark` default, full `vault-light` parity). This phase extends two previously-narrow semantic tokens (teal, error) into real new UI and introduces no new hue.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#1F1F1F` base-300 dark (light: see Phase 2's `base-300` fix) | Settings panel scrim, page canvas behind the drawer |
| Secondary (30%) | `#262626` base-100 (panels, dialogs, rows) + `#212121` base-200 (row hover/muted fills) | Settings panel surface, passkey/session row background, ceremony dialog surface |
| Accent (10%, coral `#E16540`) | primary | "+ Dodaj passkey" CTA, active Settings tab indicator, "Zapisz" (inline-rename confirm) icon-button accent, ceremony step icon while a step is genuinely in-progress-and-about-to-succeed is **not** coral (see teal below) — coral stays reserved for CTA/submit/active-nav meaning exactly as Phase 2 defined it, not repurposed for ceremony progress |
| Destructive | `#FF5861` error | Passkey delete-confirm button (`btn-error`), delete-dialog `AlertTriangle` icon, ceremony-failure icon/text ("Nie udało się dodać passkeya"), 409 blocked-delete defense-in-depth banner (`alert alert-error`), per-session revoke icon button's hover state (matches Phase 2's row-hover-delete treatment) |

Accent (coral) reserved for: the elements listed above only — **never** used for passkey/session row badges, ceremony step icons, or decorative fills. This is a direct continuation of Phase 2's rule, not a new carve-out.

**Teal (`#00CDB7`, DaisyUI `accent` token) — locked to PRF-capability meaning, extended this phase:**
- PRF-capable passkey badge (fill/border teal, text teal-on-dark or `accent-content`), `Fingerprint` icon while an enrollment step is actively succeeding, `Check` icon (success color, see below) once a step *completes* — teal marks "this passkey can unlock the vault," not general progress.
- `KeyRound` icon in the Passkeys Settings-tab tab-bar icon and on each PRF-capable passkey row.
- **`prf_capable: false` passkeys get a muted/neutral badge, not teal, not warning-yellow.** Per 03-CONTEXT.md: "no fake success, no hard failure" — a device without PRF support is an honest, unremarkable state, not a problem needing warning-color attention. Badge: `badge-ghost` / `base-content/50` text on `base-200` fill, label "Bez PRF" / "No PRF", `KeyRound` icon rendered `text-base-content/40` (muted, not teal) on that row only.

**Success `#00A96E`** → each completed ceremony step's `Check` icon (step 1 "credential registered," step 2 "PRF enabled"), the final "Passkey dodany" success state icon. Reused exactly as Phase 2 used it for the generator strength meter — a completion signal, not a CTA color.

**Item-type-badge neutrality rule extends to passkey/session badges:** the current-device session badge ("to urządzenie") is neutral (`base-200` fill, `base-content/70` text), **not** coral or teal — it is informational, not an accent-worthy state. This mirrors Phase 2's explicit "item-type badges are intentionally neutral, not color-coded" rule, applied here to session state.

**No new warning-color (`#FFBE00`) usage this phase** — there is no "something needs your attention soon" state in this phase's scope (that's Phase 4's PRF-unavailable-at-login banner). Using warning-yellow for `prf_capable: false` was considered and rejected (see Morning review notes) — it would visually flag an ordinary, honest state as a problem, contradicting CONTEXT.md's explicit "no fake success, no hard failure" instruction.

## Phase-Specific Notes

### Settings panel entry & structure (UI-05)

- The sidebar footer "Konto" button (currently a `dropdown` trigger per Phase 2's `Sidebar.tsx`) **becomes the Settings entry point**: clicking it opens the Settings panel as a `z-40` drawer + `z-30` scrim overlay — the exact same shape as `DetailPanel`/`TypePicker` (`fixed inset-y-0 right-0 z-40 ... md:w-[400px]`, click-outside scrim at `z-30`, `bg-base-300/40`). This is a **reuse**, not a new pattern — no new CSS/interaction vocabulary is introduced.
- Panel header: "Ustawienia" (Heading, 20px/700) + close button (`X`, reusing `aria.closePanel`) at the top-right, matching `DetailPanel`'s header row exactly.
- Below the header: a `tabs tabs-bordered` row (Passkeys / Sesje i urządzenia / Bezpieczeństwo / Import-Eksport), each tab icon-labeled (`KeyRound`, `Monitor`, `ShieldCheck`, an inert import/export icon — planner's choice, not specified here since that tab is a placeholder), `tab-active` styled with the coral `border-primary`/`text-primary` DaisyUI default (no custom override needed — reuses the theme's own active-tab treatment).
- Panel opens to the **Passkeys** tab by default (this phase's primary new capability — AUTH-03/06 — gets first billing over the migrated Bezpieczeństwo controls).
- Bezpieczeństwo tab content is a **direct move**, not a redesign: the exact `autolock.label` `<select>` and `clipboard.durationLabel` `<input type="range">` controls currently in `Sidebar.tsx`'s dropdown move here verbatim (same DaisyUI classes, same i18n keys, same `localStorage` read/write logic) — only their container changes from a `dropdown-content menu` to a Settings-tab section.
- Import/Eksport tab: a single centered `Body`-sized placeholder line (see Copywriting Contract), no icon-illustration, no Fuzzy Bubbles — this is an inert future-feature notice, not an empty-state worth decorating.

### Sidebar footer — what stays, what moves (see Morning review notes #1)

- The account row (`User` icon + "Konto" text) now opens Settings directly on click — the `dropdown` wrapper is removed from this element.
- **`autolock`/`clipboard` controls move fully into Settings → Bezpieczeństwo** (per CONTEXT.md, explicit).
- **Theme toggle and language switcher stay exactly where they are** in the sidebar footer (unchanged `btn-ghost btn-square btn-sm` icon buttons next to the account row) — these are low-risk, high-frequency toggles that don't warrant a trip into a full settings panel, and CONTEXT.md doesn't ask for them to move.
- **"Zablokuj teraz" (Lock now) stays a one-click icon-adjacent action**, not buried in Settings — AUTH-08's whole value is instant, zero-friction locking. Placement: a small `Lock`-icon `btn-ghost btn-square btn-sm` button in the sidebar footer row, next to the theme toggle (same visual weight/size), replacing its former home inside the now-removed dropdown.
- **"Wyloguj" (Logout) moves into the Settings panel**, as a full-width `btn-ghost` row pinned to the bottom of the panel (below the tab content, above nothing — last element, `border-t border-base-300` separator), visible regardless of which tab is active. Rationale: logout is a state-changing, moderately consequential action; one extra click via Settings is acceptable friction and reduces the accidental-logout risk a stray dropdown-item click carried in Phase 2's implementation.

### Passkey enrollment — two-ceremony dialog (AUTH-03)

A single modal dialog (`fixed inset-0 z-50`, `bg-base-300/70` scrim, 400px centered card, same shape/border/radius vocabulary as `DeleteConfirmDialog`/`GeneratorDialog`) drives the full flow. **Not** a DaisyUI `steps` progress bar — a 2-node ceremony with live "waiting on your browser" text reads better as sequential state text + one icon than a horizontal step tracker (see Morning review notes #3).

States, top to bottom in the dialog body:

1. **Name entry** (idle, pre-ceremony): a single text input, `enroll.nameLabel`, pre-filled with a sensible default (planner's discretion — e.g. browser/OS guess or empty), coral "Dodaj passkey" submit button starts ceremony 1 on click. `Cancel` closes the dialog with no side effects.
2. **Step 1 — create()`** (`Fingerprint` icon, `Loader2` spin overlay or adjacent, `text-base-content/70`): `enroll.step1` heading + `enroll.step1Waiting` body. No user action available except an implicit browser-native cancel (which surfaces as the *cancelled* state below). On success, the icon flips to `Check` (success green) for a beat, then the dialog **auto-advances** to Step 2 — no user click required between ceremonies (per CONTEXT.md's "immediate follow-up").
3. **Step 2 — get() + PRF eval`** (same `Fingerprint`/spin treatment): `enroll.step2` heading + `enroll.step2Waiting` body.
4. **Done — success (PRF)**: `Check` icon (success green), `enroll.success`/PRF-body copy, teal `PRF` badge preview next to the passkey's name, `Gotowe` button closes the dialog and refreshes the Passkeys list.
5. **Done — success (no PRF)**: same `Check`/success treatment (this **is** a success — the credential is enrolled and usable for future login — not a partial-failure red state), `enroll.success`/no-PRF-body copy, muted `Bez PRF` badge preview. This is the concrete UI expression of CONTEXT's "no fake success, no hard failure": both outcomes render as calm, honest completions, differentiated only by badge color/copy, never by using error styling for the no-PRF case.
6. **Cancelled** (user dismissed a native browser/authenticator prompt): `AlertTriangle`-free, neutral `text-base-content/70` icon-less state, `enroll.cancelled` copy, `Spróbuj ponownie` (restarts from Name entry) + `Anuluj` (closes) buttons.
7. **Failed** (network/server error, not user cancellation): `AlertTriangle` (error color), `enroll.failed` copy, same `Spróbuj ponownie`/`Anuluj` buttons as Cancelled.

The dialog is **not** dismissible via click-outside or `Esc` while a ceremony (state 2 or 3) is actively in-flight — the browser's own native WebAuthn UI is already modal at the OS level; an app-level accidental-dismiss during that window would desync app state from an in-flight browser ceremony. Dismissible in every other state (1, 4, 5, 6, 7).

### Passkey row (AUTH-06)

Row shape (min-height 64px, 16px horizontal padding, matches vault-list row vocabulary): `KeyRound` icon (32px circle, teal if `prf_capable: true` else muted `text-base-content/40`) → name (Body, inline-rename target) + created/last-used (Label, `base-content/60`, stacked below name) → PRF badge (`PRF` teal or `Bez PRF` muted-ghost, per Color section) → trailing icon-button pair (`Pencil` rename, `Trash2` delete, 40px hit area each, row-hover-revealed on desktop / always-visible on touch — same responsive-reveal convention as Phase 2's list-row copy/delete buttons).

**Inline rename** (reuses Sidebar's existing inline-new-folder-input interaction, not a new pattern): clicking `Pencil` swaps the name `Body` text for an `input input-bordered input-xs flex-1` pre-filled with the current name, with `Check`(save)/`X`(cancel) icon buttons trailing it. `Enter` saves, `Escape` cancels, blur-without-Enter saves (matches normal inline-edit expectations — CONTEXT.md doesn't specify blur behavior, this is a reasonable default). Rename is immediate (`PATCH /api/passkeys/:id`), no separate confirmation dialog — renaming is fully reversible and non-destructive, unlike delete.

**Delete** (`Trash2` icon, 40px hit area) opens the sober confirmation dialog described next.

### Passkey delete confirmation dialog (AUTH-05, AUTH-06 — destructive, security-critical)

Same 400px centered-modal shape as Phase 2's `DeleteConfirmDialog.tsx` — literally the closest reusable component in the codebase; the planner/executor should model this dialog directly on that file's structure (`AlertTriangle` in error color + `Heading` title + `Body` copy + `btn-ghost` Cancel / `btn-error` Confirm). **Plain DM Sans throughout, no Fuzzy Bubbles, no emoji** — this is explicitly named as security-critical UI in this phase's instructions, held to the same sober standard as Phase 2's item-delete dialog and unlock overlay.

- Body copy explicitly reassures the user that the master password unlock path is untouched (`passkeys.deleteBody` — "Hasło główne zawsze pozostaje działającym sposobem odblokowania vaulta") — this is the concrete UI expression of AUTH-05's recovery invariant, making the server-enforced guarantee *visible*, not just true.
- **409 defense-in-depth path**: if the server ever rejects the delete (would-strand-the-vault guard, per 03-CONTEXT.md's `pw_wrapped_uk`-missing check — structurally near-impossible in v0.1 since registration always creates the password wrap, but the API contract requires the guard to exist and be testable), the dialog does **not** silently close — it replaces the Confirm/Cancel row with an `alert alert-error` showing `passkeys.deleteBlockedError` and a single `Zamknij`/`Close`-equivalent button (reuse `delete.cancel`'s copy for the dismiss action, since "Anuluj" reads correctly here too — no new key needed for that specific button label).

### Sessions & devices (AUTH-07)
