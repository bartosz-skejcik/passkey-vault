<objective>
Close the multi-recipient fan-out mechanism at its source: a new additive migration gives every
collection its own revision counter, and `vault.rs`'s three `TODO(phase-23, WR-09)` blocks get
closed so that editing, deleting, or moving a shared item bumps the right revision counter(s) AND
notifies every current recipient — collection_keys holders, item_shares holders, and the item's own
owner — inside the SAME transaction as the mutation, per SYNC-04's per-collection model and
SYNC-05's emit-time-fresh membership resolution (CONTEXT.md locked decisions, Pitfalls 14/17).

Per D-01 (`SYNC-04`): the revision counter is per-collection, not per-user or global.
Per D-02 (`SYNC-05`): membership is resolved fresh, inside the mutation's own transaction, never
cached — this is the property Phase 25's member-removal work inherits for free.

Purpose: this is the phase's tracer — the thinnest end-to-end path (migration → mutation-transaction
→ WS fan-out → a real live-socket proof) through every layer the phase touches, proven before the
read-side endpoints (Plan 23-02), attribution UX (Plans 23-03/23-05), and standing test harness
(Plans 23-04/23-06) expand outward from it.
Output: `collections.revision` + `vault_items.last_editor_user_id` columns; `EntityType::Collection`;
`SyncHub::publish_to_recipients`; closed `update()`/`delete()`/`move_item()` TODOs; a new
`tests/sync_shared.rs` with the first live 2-session, 1-real-WS proof.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| authenticated caller -> shared mutation | An authenticated `Membership<Item, RequireEdit>`-gated caller triggers a fan-out that touches OTHER users' `vault_revision` rows and OTHER users' live WS channels |
| mutation transaction -> WS publish | The fan-out publish must only ever fire with a resolved recipient set computed AFTER the mutation's own transaction commits successfully |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-23-01 | Information Disclosure | `resolve_recipients` | high | mitigate | Recipients are resolved ONLY from `collection_keys`/`item_shares` rows for the item's own `collection_id`/`item_id` — never a caller-supplied recipient list; a non-recipient can never be added to the fan-out target set by request manipulation. |
| T-23-02 | Tampering | `bump_recipients_vault_revision` | medium | mitigate | Single batched `UPDATE ... WHERE id IN (...)` built from server-resolved ids only, never from request body content — no SQL injection surface (parameterized placeholders per recipient). |
| T-23-03 | Denial of Service | multi-recipient fan-out | low | accept | A pathological collection with thousands of recipients could make one mutation's fan-out loop expensive; out of scope for this milestone's family-scale (2-6 person) target per REQUIREMENTS.md's Out of Scope table (seat limits / enterprise scale explicitly excluded). |
| T-23-04 | Information Disclosure | `SyncEvent` Collection variant | high | mitigate | `SyncEvent` gains no new field (CONTEXT.md hard constraint 4); the collection id rides the existing `id` field and is delivered only via `publish_to_recipients`'s freshly-resolved set, never a broadcast-to-all. |
</threat_model>
