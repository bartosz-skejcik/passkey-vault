# Phase 30 — UI Design Contract

> Visual and interaction contract for FSH-01…05/FAM-10 (family-wide sharing as a living group).
> Generated by gsd-ui-researcher, verified by gsd-ui-checker. This phase renders the family-wide
> target **plainly** inside the existing `ShareDialog`/`SharingOverviewPanel`/`ItemRow` surfaces —
> it does not redesign any of them. The share dialog's final per-person layout is Phase 31
> (MOD-01/02/03); the redesigned family surface is Phase 33; the full "what am I exposing"
> inventory is Phase 34. Nothing below asks those phases' questions.

---

## Design System

| Property | Value |
|----------|-------|
| Tool | none — shadcn was never adopted (`components.json` absent) and is not introduced here. |
| Preset | not applicable |
| Component library | DaisyUI 5 primitives (`checkbox`, `radio`, `badge`, `alert`, `toast`, `rounded-box`/`rounded-field` row treatments) + `packages/pv-ui` (i18n `t`/`interpolate`, fingerprint helpers — unused by this phase but present) |
| Icon library | `lucide-react` — reuses `Users` (already imported in `FamilyTab.tsx` for the Members heading), `Clock` (new to this phase, no prior use found), `Folder`/`Share2`/`X` (already used identically in `SharingOverviewPanel.tsx`/`CopyToast.tsx`) |
| Font | DM Sans (`--font-sans`). Fuzzy Bubbles/emoji are **not** used anywhere in this phase — every surface touched (`ShareDialog`, `SharingOverviewPanel`, `ItemRow`, `DetailPanel`) is security-adjacent per UI-DESIGN.md's "security UI zawsze czytelne" rule. |

Reuse discipline: this phase invents no new OKLCH values, radii, or component primitives. Every
token below is an existing `packages/pv-ui/tokens.css` value or an existing in-codebase Tailwind
utility pattern, cited by file:line where one exists.

## Typography

Three sizes, two weights — no new size is introduced beyond what the codebase already uses.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Display (inherited dialog/panel title tier) | 20px | 700 | 1.2 |
| Heading (new bold row/section labels) | 14px | 700 | 1.5 |
| Body (explanatory paragraphs) | 16px | 400 | 1.5 |
| Label (meta/secondary text) | 14px | 400 | 1.5 |

- **Display (20px/700/1.2)** is not new — it is the existing `text-[20px] font-bold leading-[1.2]`
  dialog/panel-title tier already on `ShareDialog.tsx`'s `<h2>` and `SharingOverviewPanel.tsx`'s
  `<h2>`. This phase adds no new page and no new title, so this row exists only as ambient
  context for where the new content below nests — it is inherited, not declared, mirroring
  29-UI-SPEC.md's own treatment of its inherited 20px tier.
- **Heading and Label are the SAME 14px size, differing only by weight** — this is the codebase's
  own established pattern, not a new convention (`ShareDialog.tsx:729` `"text-sm font-bold"` for
  "Komu udostępnić" next to `ShareDialog.tsx:749` `"text-sm"` for a recipient's plain email). The
  new "Cała rodzina" row label uses Heading (14/700); the new member-count and timing-caveat text
  use Label (14/400).
- **Body (16px/400/1.5)** is used exactly once, newly, for the pending-newcomer **item row's**
  placeholder primary text (`item-row-pending-family-key`'s `"truncate text-base
  text-base-content/70"` span — see Pending-Newcomer Item-Row State below), matching
  `ItemRow.tsx`'s own existing `text-base` convention for a row's primary line (e.g. `primaryText`
  at `ItemRow.tsx:131`). This is genuinely exercised, 16px, in this phase — not a placeholder row
  kept only to fill the template.

  **Correction, scoped to the DetailPanel note only** (an earlier draft of this table
  over-generalized this correction to the whole phase — it applies to exactly one element).
  Verified against the actual precedent the pending-newcomer **detail-panel** note copies
  (`item-shared-with-you-note`, `DetailPanel.tsx:462`): that note renders at `text-sm`, not
  `text-base`. The pending-newcomer DETAIL-PANEL note (see Pending-Newcomer Detail-Panel State
  below) reuses that exact shape, so it is **14px (Label)**, not 16px (Body). This correction does
  **not** extend to the pending-newcomer ITEM-ROW's primary text described in the Body bullet
  above — the row and the detail note intentionally use two different sizes because each reuses a
  different existing precedent (`ItemRow`'s own `text-base` primary-line convention vs
  `DetailPanel`'s own `text-sm` note convention), and Body (16px) remains a genuinely-exercised
  role in this contract.

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `base-100`/`base-300` (unchanged) | Existing dialog/panel/row backgrounds — this phase adds no new page and no new background treatment |
| Secondary (30%) | `base-300` border, `base-200` (unchanged) | Row/section borders (`border-base-300`), the new "Cała rodzina" row's boxed treatment (`rounded-field border border-base-300`, distinguishing it from the borderless plain-`<label>` person rows below it) |
| Accent (10%) | `secondary` (`#8DCDFF`, **not** `primary`/koral) | Reserved for: the family badge's `Users` icon in the item list; the "Cała rodzina" row's `Users` icon in `ShareDialog`; the pinned family-wide block's `Users` icon in `SharingOverviewPanel`. This reuses the SAME `text-secondary` role `AvatarStack`'s icon variant and `ItemRow`'s `sharedToMe` marker already use for "this row is about sharing" — the marker's **icon shape** (`Users` vs `Share2`) is what distinguishes "family-wide" from "person-to-person," not a new color. `primary` (koral) is explicitly **not** used anywhere in this phase's new elements — per UI-DESIGN.md, koral is reserved for CTAs/brand/active state, and none of this phase's new elements are a primary action. |
| Destructive | `error` (`#FF5861`) | Not introduced by this phase. No new destructive action exists here (re-key is a system consequence of the existing remove/leave/delete-account flows, whose confirmations are unchanged). |

Accent is explicitly **not** used for: the pending-newcomer state (deliberately neutral, see
below — a pending key is not a warning), the re-key notice (deliberately quiet, not a `warning`-
or `error`-styled `alert`), or the member-count/caveat text (plain `base-content/60`–`/70`, same
as every other secondary-text line in these two files).

**Pending-newcomer state is deliberately colorless (`base-content/40`–`/70`, no semantic hue).**
This is a considered choice, not an omission: `warning` (#FFBE00) is UI-DESIGN.md's own reserved
color for "hasło stare/powtórzone" (aged/reused password) — reusing it here would borrow that
"needs attention" association for a state that is normal and expected (CONTEXT.md: "never a
silently absent item," not "never a calm item"). It mirrors the existing
`identity.fingerprintUnavailable` treatment (`FamilyTab.tsx:743`, plain `text-base-content/70`,
explicitly NOT styled as a warning) for the same reason: a benign, expected "not yet" state gets
the same calm treatment this codebase already established for one.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA | Unchanged — `share.ctaFolder`/`share.ctaItem` ("Udostępnij folder"/"Udostępnij item") serve both individual and family-wide submissions; no new CTA copy is introduced. |
| "Cała rodzina" row label | **NEW** `share.familyWideOptionLabel`: pl "Cała rodzina", en "Whole family" |
| Timing caveat (FSH-05 — shown in BOTH the dialog at creation time and the overview's family-wide block, same key, same string, so the two required locations can never drift) | **NEW** `share.familyWideTimingCaveat`: pl "Nowi członkowie rodziny zobaczą to od razu, jeśli dołączą przez świeże zaproszenie. Jeśli ktoś korzysta z linku wysłanego wcześniej, dostęp pojawi się przy najbliższym otwarciu aplikacji przez Ciebie lub innego członka rodziny.", en "New family members see this right away if they join through a fresh invite. If someone is using a link that was sent earlier, access arrives the next time you or another family member opens the app." A single compound sentence naming both mechanism paths (invite-carried = instant; outstanding pre-existing invite = lazy-reseal bound). **Re-derived post-research** (the FSH-02 decision record confirmed the hybrid survives, with a refinement this string must reflect): the lazy-reseal trigger fires on **any key-holder's next app open, including the sharer themselves** — the sharer always already holds the Collection Key, so "you or another family member" is the correct actor set, not "another family member" alone, which named the wrong actor and overstated the wait. The PL clause is deliberately nominalized ("przy najbliższym otwarciu aplikacji przez Ciebie lub innego członka rodziny") rather than conjugated for two different grammatical persons ("Ty ... otworzysz" + "on/ona ... otworzy" cannot share one verb) — this sidesteps the agreement problem entirely rather than getting it wrong. The EN clause uses ordinary proximity agreement ("you or another family member opens" — the verb agrees with the nearer subject), which is standard English usage. This copy is **derived from the FSH-02 decision record, not asserted as permanently evergreen** — SC5's bar is "checked against the measurement, not against the intent," so if a future mechanism change alters who/what completes the fallback grant, this string must be re-derived again, not assumed to still hold. |
| Member count — populated (n≥2) | **NEW** `share.familyWideMemberCount` (interpolated `{count}`): pl "Liczba osób w rodzinie: {count} — plus każdy, kto dołączy później.", en "People in the family right now: {count} — plus anyone who joins later." `{count}` trails as a standalone number after the noun already appears ("osób"/"family") — never governs a declined noun, correct at every `n` with zero plural-selection machinery, following 29-UI-SPEC.md's own DEBT-02 resolution pattern exactly. |
| Member count — solo owner (n=1, just the sharer) | **NEW** `share.familyWideMemberCountSoloOwner`: pl "Na razie w rodzinie jesteś tylko Ty — to udostępnienie zobaczy każdy, kto dołączy.", en "It's just you in the family for now — anyone who joins will see this." Distinct copy, not `familyWideMemberCount` interpolated with `1` — at n=1 the number itself is uninformative ("1" doesn't communicate "nobody else can see this yet"); this sentence states the actually-relevant fact plainly. |
| Member count — loading | **NEW** `share.familyWideMemberCountLoading`: pl "Ładowanie liczby osób w rodzinie…", en "Loading family member count…" Rendered while the count is unresolved — never a flash of "0" or of the solo-owner copy, both of which would be false claims about family size. |
| Member count — error | **NEW** `share.familyWideMemberCountError`: pl "Nie udało się wczytać liczby osób w rodzinie.", en "Couldn't load the family member count." | Pending-newcomer detail-panel note (mirrors `share.sharedWithYouNote`'s exact two-line shape at `DetailPanel.tsx:462`) | **NEW** `share.pendingFamilyKeyNote`: pl "To jest udostępnione całej rodzinie, ale Twój klucz jeszcze nie dotarł.", en "This is shared with the whole family, but your key hasn't arrived yet." |

## Share Dialog — "Cała rodzina" Row Contract (FSH-01)

**Anatomy**, inserted into `ShareDialog.tsx` immediately above the existing
`share-recipient-list` block, in **both** the item and folder variants (`scope.kind` is
irrelevant to this row — FSH-01 covers both):

```
<label
  data-testid="share-recipient-family-wide"
  className="flex items-center gap-2 rounded-field border border-base-300 px-2 py-2"
>
  <input type="checkbox" className="checkbox checkbox-sm" ... aria-describedby="share-family-wide-caveat" />
  <Users size={14} className="shrink-0 text-secondary" aria-hidden="true" />
  <span className="flex min-w-0 flex-1 flex-col">
    <span className="text-sm font-bold">{t("share.familyWideOptionLabel")}</span>
    <span data-testid="share-family-wide-member-count" className="text-sm text-base-content/60">
      {memberCountText}
    </span>
  </span>
</label>
<p id="share-family-wide-caveat" data-testid="share-family-wide-timing-caveat" className="text-sm text-base-content/60">
  {t("share.familyWideTimingCaveat")}
</p>
<div className="border-t border-base-300" />
{/* existing share-recipient-list block, unchanged, follows below */}
```

- **Pinned above, boxed treatment.** The row gets `rounded-field border border-base-300` — a
  treatment **no individual person row has** (those are plain `<label className="flex items-center
  gap-2">` with no border). This is the row's primary visual distinction from a person row,
  independent of its icon/copy — satisfying the locked "reads as one [recipient], pinned above"
  requirement structurally, not just by position.
- **Mutual exclusivity (locks FSH-01's "no per-person overrides" for this phase).** Checking
  "Cała rodzina" clears and disables every individual person checkbox below it (native `disabled`
  attribute, matching how every other control in this dialog already disables during `sharing`
  state — no custom disabled styling introduced). Checking any individual person checkbox
  similarly clears and disables the family-wide checkbox. The two modes are mutually exclusive
  within one dialog session — there is no UI state where both are simultaneously checked.
- **Access level: the SAME existing single radio group, no new control.** The dialog's existing
  `share.accessLevelLabel` radio group (`read`/`edit`/`hidden_password`) governs whichever mode is
  active. This is the literal mechanism by which "access level is chosen for the family-wide share
  like any other recipient" (locked decision) is satisfied — reusing the identical control both
  modes already share, not inventing a second one.
- **Member count text** (`share-family-wide-member-count`, inside the row): one of
  `familyWideMemberCount` (n≥2, interpolated) / `familyWideMemberCountSoloOwner` (n=1) /
  `familyWideMemberCountLoading` (unresolved) / `familyWideMemberCountError` (fetch failed) — see
  Copywriting Contract. `n` is the current family member count **excluding** the caller
  themselves is deliberately **wrong** here — CONTEXT.md's "a live current-member count" is the
  count of everyone who would gain access, and the sharer is already implicitly included by virtue
  of being the owner; the count shown is every family member INCLUDING the sharer (mirrors how
  `family.membersHeading`'s own list in `FamilyTab.tsx` includes the caller's own row). On fetch
  failure, `familyWideMemberCountError` renders with no retry control — see the Copywriting
  Contract's "Member count — error" row for the stated no-action behavior (re-resolves on remount).
- **Timing caveat** (`share-family-wide-timing-caveat`, below the row, `aria-describedby`-linked to
  the checkbox): renders unconditionally whenever the family-wide row is visible — **not** only
  after it is checked. This mirrors the hidden-password inline note's own discipline
  (`ShareDialog.tsx`'s honesty constraint 2: "on EVERY occasion, not only after a recipient is
  picked") — the caveat is a property of the FEATURE, not of the current selection.

## Sharing Overview — Family-Wide Block Contract (FSH-05, "the family-wide row")

**A single pinned block, not a third tab, not a per-share row set.** CONTEXT.md's wording is
singular ("the family-wide row in the sharing overview") and the caveat/count are properties of
the **family**, not of any one share — repeating them once per family-wide share would be
redundant and would risk drifting out of sync. Positioned **above** the existing
`sharing-overview-tabs` switcher (same "primary content before secondary nav" precedent as
29-UI-SPEC.md's own focal-point rule), rendered **only** when the caller has ≥1 family-wide share.

```
<div data-testid="sharing-overview-family-wide" className="flex flex-col gap-2 rounded-box border border-base-300 px-4 py-3">
  <div className="flex items-center gap-2">
    <Users size={16} className="shrink-0 text-secondary" aria-hidden="true" />
    <span className="text-sm font-bold">{t("share.familyWideOptionLabel")}</span>
  </div>
  <p data-testid="sharing-overview-family-wide-count" className="text-sm text-base-content/70">
    {memberCountText}
  </p>
  <p data-testid="sharing-overview-family-wide-caveat" className="text-sm text-base-content/60">
    {t("share.familyWideTimingCaveat")}
  </p>
  <ul data-testid="sharing-overview-family-wide-list" className="flex flex-col gap-1 pl-6">
    {familyWideShares.map((share) => (
      <li key={share.id} className="flex items-center gap-2">
        {share.kind === "folder"
          ? <Folder size={14} className="shrink-0 text-base-content/60" aria-hidden="true" />
          : <Share2 size={14} className="shrink-0 text-secondary" aria-hidden="true" />}
        <span className="min-w-0 flex-1 truncate text-sm" title={share.name}>{share.name}</span>
      </li>
    ))}
  </ul>
</div>
```

- **Why a dedicated block, not the existing "By folder" tab.** The "By folder" tab only lists
  collections the caller has `edit`-level access to (`SharingOverviewPanel.tsx`'s own
  `editableIds` filter) and has no representation for a directly-shared **item** at all (that gap
  is VIS-03, Phase 34's). If family-wide is ever applied to an item (FSH-01 covers both folder and
  item), forcing it into the folder-only tab would either misrepresent it as a folder or have
  nowhere to go. A dedicated block, keyed by "this is a family-wide share" rather than by
  folder-vs-item, sidesteps that gap without this phase reaching into VIS-03's territory.
- **No expand/collapse, unlike folder/person rows.** This block already shows everything at once
  (count, caveat, the flat list of what's shared) — there is no per-recipient breakdown to
  progressively disclose (there is no "recipient list" for a family-wide share; the audience IS
  the family, described once by the count line above).
- **No revoke action.** Deliberately absent (no `UserMinus` button anywhere in this block) — a
  per-person revoke on a family-wide share is exactly the "per-person override" this phase defers
  (locked decision). The only way to change who can read a family-wide share in this phase is
  through the existing leave/remove/delete-account paths, which already exist elsewhere and are
  unchanged.
- **Sort order.** Stable, by `share.name` — the block itself, not its individual list rows, is
  what is "pinned above"; the list inside it has no further precedence rule to state.
- **Member count failure.** Same behavior as `ShareDialog`'s row (see Copywriting Contract's
  "Member count — error"): `sharing-overview-family-wide-count` renders
  `familyWideMemberCountError` with no retry control; it re-resolves the next time
  `SharingOverviewPanel` remounts.

## Item List & Detail — Family Badge and Pending-Newcomer Contract (FSH-01 badge, FSH-05 pending state)

**Scope boundary (do not over-build):** this phase owns exactly two new item-level states — the
OWNER-side family badge, and the RECIPIENT-side pending-newcomer state. It does **not** touch
`item.sharedToMe`'s existing generic "shared with you" marker for a family-wide item whose key has
already arrived — distinguishing "shared with me by the whole family" from "shared with me by one
person" is VIS-02 (Phase 34's). After a newcomer's key arrives, their experience of a family-wide
item is identical to any other shared-with-me item today. Do not add a "family" variant to that
marker in this phase.

### Family badge (owner-side, replaces `AvatarStack` for a family-wide item)

A **new, standalone component** (not a new `AvatarStack` variant) — `AvatarStack`'s own recipient
data flow (`useShareRecipients`) is exactly what CONTEXT.md instructs this phase NOT to depend on
("design the family badge so it does not depend on a resolved recipient list at all," working
around `AvatarStack.tsx:100`'s known VIS-01 defect rather than inheriting it). The badge's boolean
input must be **synchronously available from the item's own already-loaded metadata** (whatever
field the data-model decision — Claude's discretion per 30-CONTEXT.md — produces on `VaultItem`),
never from an async recipient fetch.

```
<span
  data-testid="item-row-family-badge"
  role="img"
  aria-label={t("vault.familyBadgeAria")}
  title={t("vault.familyBadgeAria")}
  className="inline-flex shrink-0 items-center text-secondary"
>
  <Users size={14} aria-hidden="true" />
</span>
```

- Rendered in `ItemRow.tsx`'s existing marker slot (the same conditional block that today chooses
  between `sharedToMe`'s `Share2` marker and `AvatarStack`) **in place of** `AvatarStack` whenever
  the item is a family-wide share and the caller is its owner — never alongside `AvatarStack`
  (a family-wide item never also renders N individual avatars, per the locked "not N avatars"
  decision).
- Distinguishing shape, reused color: `Users` vs `AvatarStack`'s overlapping-circles-with-initials
  or `Share2` — the glyph is what differs; the color (`text-secondary`) intentionally matches
  every other "this row is about sharing" marker already in this codebase (`AvatarStack`'s own
  icon variant, `ItemRow`'s `sharedToMe` marker), keeping the color vocabulary "sharing = secondary
  blue" consistent while the icon shape carries the "which kind of share" distinction — exactly the
  same shape-carries-meaning principle `AvatarStack`'s doc comment already states for its own two
  variants ("circles" vs "icon").
- Independent of recipient resolution **by construction**: the badge never calls
  `useShareRecipients`, so it renders correctly (or is correctly absent) before, during, and after
  any recipient-list fetch — there is no loading/error state for this element at all, because it
  has no fetch to begin with.

### Pending-newcomer item-row state (recipient-side, before the key arrives)

**Cannot reuse the item's real name/subtitle** — the item's `fields.name`/`fields.username`/type
live inside `enc_data`, which is by definition still undecryptable for a pending newcomer. The row
renders a fully generic, placeholder-content variant instead of its normal content:

```
<div data-testid="item-row-pending-family-key" className="flex min-w-0 flex-1 items-center gap-2">
  <div className="flex h-8 w-8 shrink-0 items-center justify-center rounded-field bg-base-200 text-base-content/40">
    <Clock size={16} aria-hidden="true" />
  </div>
  <span className="flex min-w-0 flex-1 flex-col items-start">
    <span className="truncate text-base text-base-content/70">{t("vault.pendingFamilyKeyItemName")}</span>
    <span className="truncate text-sm text-base-content/60">{t("vault.pendingFamilyKeyRow")}</span>
  </span>
</div>
```

- Replaces `ItemIconTile` (which also cannot determine a type-specific icon for undecryptable
  fields) with a generic, neutral tile — same footprint (`h-8 w-8 rounded-field`), no domain color.
- The sharing-marker slot (family badge / `AvatarStack` / `sharedToMe`) is **suppressed** for a
  pending row — the pending treatment already fully communicates the state; a second marker would
  be redundant, not additive.
- **Corrected against the actual authorization model (post-research):** a pending newcomer cannot
  reach the normal item/collection listing at all — `Collection`/`Item::resolve_access`
  (`crates/pv-server/src/routes/membership.rs`) 404s anyone without a `collection_keys`/
  `item_shares` row, regardless of family membership, and that 404 is deliberately not widened
  (doing so would break the revocation guarantee it exists to enforce). Closing this needs a
  narrow, **ids-only** discovery endpoint — this contract does not design that endpoint, but its
  row anatomy must not assume any field richer than an id. Concretely: **the trailing metadata slot
  (normally relative time or the TOTP ring) is omitted entirely for a pending row**, not populated
  and not left rendering a stale/fake value — an ids-only discovery path carries no `updated_at`
  (or any other metadata) to show there. Row height stays `h-16` (no layout shift versus a normal
  row), but nothing occupies that slot. The row's only content is the generic icon + the two
  placeholder text lines above, both static translator strings requiring no server data at all.
- **Distinct from `item.undecryptable` (existing) — do not reuse or overload that flag.**
  `item.undecryptable` means "a prior successful decrypt exists; the latest sync merge failed,
  showing a retained stale copy" (`DetailPanel.tsx:441-453`'s own comment). Pending-family-key
  means "never successfully decrypted — there is no stale copy to fall back to." These are
  different situations needing different UI and must be two independently-checked conditions, not
  one flag with two meanings. Check the pending-family-key condition **before** any
  decrypt-dependent rendering (including before checking `undecryptable`), since a pending item has
  no historical decrypt result to reason about at all.
- **Detection must be narrow — the single most important honesty risk in this contract.** The
  pending copy may render **only** when the client can positively identify "this specific grant's
  key has not yet been delivered" (however the FSH-02 mechanism signals that — Claude's/planner's
  discretion). It must **never** be the catch-all for an unexplained decrypt exception on real
  ciphertext — that is a genuine failure and must continue to render through the EXISTING failure
  path, unchanged. Recreating the reassuring pending copy as a blanket catch for any decrypt error
  would be the exact inverse dishonesty from DEBT-03 (hiding a real problem behind calm words,
  instead of DEBT-03's hiding a stale phantom behind silence) — CONTEXT.md's own framing ("the
  inverse of DEBT-03's phantom-row defect and must not recreate it") cuts both ways.

### Pending-newcomer detail-panel state

Mirrors `DetailPanel.tsx:462`'s existing `item-shared-with-you-note` shape exactly (two plain
`text-sm text-base-content/70` lines, no bold heading — this phase does not invent a new detail-
note shape where an identical existing one already fits):

```
<div data-testid="pending-family-key-detail" role="status" aria-live="polite" className="flex flex-col gap-1 text-sm text-base-content/70">
  <span>{t("share.pendingFamilyKeyNote")}</span>
  <span data-testid="pending-family-key-detail-explanation">{t("share.pendingFamilyKeyNoteDetail")}</span>
</div>
```

- `role="status" aria-live="polite"` — **not** `role="alert"`. Every genuine error banner in this
  codebase (`undecryptable-item-banner`, `revision-conflict-banner`, `live-edit-conflict-banner`)
  uses `alert`/`role="alert"` semantics; this note deliberately does not, so a screen-reader user
  gets the same non-alarming signal a sighted user gets from the absence of warning/error color.
- Once the key resolves, the item simply renders normally on the next sync/re-render — no
  transition animation, no confirming toast. This matches the deliberately low-fanfare tone the
  re-key notice below also uses (quiet arrival, quiet departure).

## Re-Key Notice Contract (FSH-04, FAM-10 — "the sharer is told, quietly")

**Surface: a toast, reusing `CopyToast.tsx`'s exact visual shell** (`toast toast-end toast-bottom`,
320px, `rounded-field border border-base-300 bg-base-100 p-3 text-sm`) — **not** a `DaisyUI
alert`, and **not** `warning`/`error`-colored. This is the literal meaning of "quiet": the same
understated, non-urgent chrome the app already uses for a routine copy confirmation, not the
heavier `alert-warning`/`alert-error` treatment reserved for things that need the user's active
attention (a suspended-family banner, a revision conflict).

```
<div data-testid="family-rekey-notice" role="status" aria-live="polite" className="toast toast-end toast-bottom z-50">
  <div className="flex w-[320px] items-center justify-between gap-3 rounded-field border border-base-300 bg-base-100 p-3 text-sm">
    <span>{t("share.familyRekeyNotice")}</span>
    <button
      type="button"
      data-testid="family-rekey-notice-dismiss"
      aria-label={t("aria.dismissToast")}
      className="btn btn-ghost btn-square btn-xs"
      onClick={...}
    >
      <X size={14} aria-hidden="true" />
    </button>
  </div>
</div>
```

- **No auto-hide timer.** Unlike `CopyToast` (which auto-clears because it tracks a real,
  time-bounded clipboard guarantee), a re-key event has no natural expiry — it persists until the
  sharer manually dismisses it (`family-rekey-notice-dismiss`, reusing `aria.dismissToast`
  verbatim rather than introducing a new aria-label key).
- **Singleton, replace-not-stack** — mirrors `copyToast.ts`'s own documented behavior exactly ("a
  new toast REPLACES any currently-showing toast's state rather than stacking a second one"). A
  second re-key event arriving while the first notice is still showing replaces its content; it
  never produces two stacked toasts.
- **Generic content, no item names** (see Copywriting Contract) — a re-key batch can touch several
  items at once; naming one would misrepresent the batch's scope.

## Accessibility Contract

- **"Cała rodzina" row semantics.** A real `<label>` wrapping a real `<input type="checkbox">` —
  identical native association to every sibling person row, so it is keyboard- and
  screen-reader-navigable with zero custom ARIA on the control itself. The checkbox carries
  `aria-describedby="share-family-wide-caveat"`, pointing at the timing-caveat `<p id=...>` below
  it, so a screen-reader user checking the box also hears the caveat associated with that specific
  action — not merely present somewhere later in reading order.
- **Pending state is `role="status" aria-live="polite"`, never `role="alert"`.** See Pending-
  Newcomer Detail-Panel State above — this is the accessible expression of "expected, not
  alarming," matching the visual (colorless, no warning/error hue) treatment exactly.
- **Family badge accessible name.** `role="img" aria-label={t("vault.familyBadgeAria")}` — mirrors
  `AvatarStack`'s own `role="img"` + single-summarizing-label pattern (never one label per visual
  element), but its content self-describes "the whole family" rather than naming N individuals,
  since there is no per-person breakdown a family badge could enumerate.
- **Re-key notice.** `role="status" aria-live="polite"` (routine, non-blocking announcement — never
  `role="alert"`, which would imply urgency this quiet notice deliberately does not carry).
- **Sharing-overview family-wide block.** Plain content inside the existing `<aside>` landmark —
  no new landmark role is introduced; it participates in the panel's existing reading order,
  positioned before the `tablist` in both DOM order and visual order (so tab order and reading
  order agree).
