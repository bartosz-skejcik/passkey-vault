<objective>
Give the server two additive capabilities the rest of the phase depends on: (1) a collection can be
minted as family-wide (`family_wide_kind`), exposed on every existing read so clients can tell it
apart from an ordinary shared folder; (2) a brand-new, deliberately narrow discovery endpoint that
answers "what family-wide grants exist that I (the caller) don't hold a key for" and, inverted, "who
among active family members lacks a key I could grant them" -- without ever widening the
`Collection`/`Item::resolve_access` enforcement boundary those two functions exist to guarantee.

Purpose: this is the authorization-shaped half of FSH-02's mechanism -- the piece every client-side
reseal/pending-UI plan in this phase reads from.
Output: `family_wide_kind` on collection create/get/list; `GET /api/families/family-wide-pending`.
</objective>

<task type="checkpoint:decision" gate="blocking">
  <name>Task 1: confirm the discovery-endpoint authorization shape before building it</name>
  <decision>
    The newcomer-discovery surface: should FSH-02's "does the caller lack a key for a family-wide
    grant" question be answered by (a) a brand-new, narrow, ids-only endpoint gated by
    `ActiveFamilyMembership&lt;RequireRead&gt;` with no per-resource check at all, or (b) widening
    `Collection`/`Item::resolve_access` to also grant read visibility on bare family membership?
  </decision>
  <context>
    `Collection`/`Item::resolve_access` (`membership.rs`) are this codebase's sole, heavily-tested
    (14+ unit tests, including 5 explicit suspended-member regressions) enforcement point for every
    revocation guarantee this project has shipped since Phase 22/25. RESEARCH.md's own Anti-Patterns
    section names widening them as the single highest-severity mistake this phase could make: it
    would let a suspended or removed member regain implicit "pending" visibility into every
    family-wide collection through the widened branch, silently breaking the "revocation enforced on
    the very next request" guarantee Phase 22 SC4 and Phase 25 SC4 already proved. Recommendation
    (research, high confidence): option (a) -- a genuinely new, additive read surface that answers a
    DIFFERENT question ("does a pending grant exist") from what `resolve_access` answers ("can I
    decrypt this resource right now"), returning ids/kind only, never ciphertext or key material.
  </context>
  <options>
    <option id="narrow-discovery-endpoint">
      <name>New GET /api/families/family-wide-pending, ids/kind only, ActiveFamilyMembership-gated</name>
      <pros>Zero change to the proven resolve_access enforcement boundary; response shape structurally cannot leak more than "an id exists and its kind"; matches this codebase's existing "one canonical query, multiple callers" discipline.</pros>
      <cons>A second authorization concept to reason about alongside resolve_access (though a strictly narrower one).</cons>
    </option>
    <option id="widen-resolve-access">
      <name>Widen Collection/Item::resolve_access to grant a "pending" read on bare family membership</name>
      <pros>One fewer endpoint.</pros>
      <cons>Breaks the revocation-on-next-request guarantee for every family-wide collection, for every suspended/removed member, silently; touches the single most safety-critical function in the codebase for a feature that does not need to.</cons>
    </option>
  </options>
  <resume-signal>Select: narrow-discovery-endpoint (recommended) or widen-resolve-access</resume-signal>
</task>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Family member -> discovery endpoint | An authenticated, active family member queries a cross-cutting view of family-wide grant state that no single-resource authorization check like `resolve_access` was designed to answer. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-30-03 | Elevation of Privilege | `family_wide_pending` | high | mitigate | Gated by `ActiveFamilyMembership&lt;RequireRead&gt;` (status-active-only) -- a suspended/removed caller gets 403 before either query runs, exactly like every other family-scoped read; resolved by Task 1's checkpoint. |
| T-30-04 | Information Disclosure | `family_wide_pending` response shape | high | mitigate | `PendingGrant`/`ResealableGrant` carry only ids/kind -- no `enc_name`, `sealed_key`, or any ciphertext field exists on either type to leak. |
| T-30-05 | Information Disclosure | Cross-family leakage via the two new queries | medium | mitigate | Both queries bind `c.family_id = ?` to the CALLER's own resolved `family_id` -- never a client-supplied value -- matching `member_access`'s existing WR-03 discipline. |
| T-30-06 | Tampering | `family_wide_kind` closed-set validation | low | mitigate | `validate_family_wide_kind` rejects anything outside `{folder, item_bucket}` before any DB work, mirroring `validate_collection_id_shape`'s existing discipline; the DB-level CHECK constraint (0019) is defense in depth. |
