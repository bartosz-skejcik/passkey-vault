**Why the proactive live-edit banner reuses `error` instead of introducing `warning`:** considered and rejected — see Morning review notes #2. ## Phase-Specific Notes

### Sync status indicator (SYNC-01/02/03, "minimal, unobtrusive presence indicator")

- **Placement:** a small corner-badge dot on the existing account-avatar circle in the sidebar footer (`Sidebar.tsx`'s `h-9 w-9 rounded-full bg-base-300` `User`-icon circle — the account row currently at the bottom of the sidebar). If Phase 3's Settings-panel restructure has already shipped by the time this phase executes, the same avatar circle carries over unchanged per `03-UI-SPEC.md` — attach the dot there instead; this is a positioning choice, not a dependency on Phase 3's completion (05-CONTEXT.md is explicit that this phase depends only on Phase 2).
- **Two visual states only** — deliberately not three. `connected` and `offline`/`not-running` (vault locked, sync never started) render **nothing at all**: no dot, no color, no DOM node beyond an empty `role="status"` container. `reconnecting` renders an 8px `bg-warning` dot with a slow `animate-pulse`, positioned `absolute bottom-0 right-0 rounded-full ring-2 ring-base-200` (the ring cuts the dot out from the avatar background, standard presence-indicator technique — no new CSS utility, Tailwind's built-in `ring-*`).
- **Why "reconnecting" is the only visible state, not "connected":** CONTEXT.md's own language — "a small dot/pulse... rather than a chatty banner or toast-per-change" — reads as "mostly quiet, becomes visible only when something's happening." A permanently-on ambient dot for the nominal case would be the one thing datafa.st's understated aesthetic explicitly argues against. Silence *is* the "everything's fine" signal.
- **Why "offline" collapses into "nothing," not a third alarming state:** per `web/src/lib/vault/sync.ts`'s own reference implementation (05-RESEARCH.md Pattern 4), `setSyncStatus("offline")` is called by `stopSync()` — i.e. it means "sync isn't running" (vault locked), not "sync failed while unlocked." There is no persistent-failure state that isn't already covered by `reconnecting` (WS backoff caps at ~30s and keeps retrying indefinitely; the poll timer runs the whole time regardless) — so a separate "offline-while-unlocked" visual would never actually be reachable in normal operation and would only add a state the checker/executor has to reason about for no user benefit.
- **Accessibility:** the dot's container carries `role="status"` + `aria-live="polite"` + the reconnecting tooltip copy above as `aria-label` (screen readers get a single polite announcement on state change, not a running commentary — matches CONTEXT's explicit "not chatty" instruction applied to assistive tech too). Not a button, not focusable — pure status, no click affordance (no requirement drives "click dot to force-reconnect").

### Live-edit-conflict banner (SYNC-03, extends an existing component)

- **This is not a new component.** `DetailPanel.tsx` already renders a `data-testid="revision-conflict-banner"` `alert alert-error text-sm` div in edit mode, currently triggered only by a failed save (`RevisionConflictError` from a 409). This phase adds a **second trigger path** to the exact same visual slot: a `SyncEvent`/poll-tick revealing `entity_type === "item" && id === item.id && revision !== item.revision` while `mode === "edit"` shows the same-shaped banner *before* the user attempts to save.
- **Visual difference between the two triggers:** copy differs (see Copywriting Contract), and only the **proactive** variant gets a trailing action row — a `RefreshCw`-icon `Odśwież`/`Refresh` button (`btn btn-error btn-outline btn-sm`, matching the banner's error family, outlined rather than filled so it doesn't read as a second destructive CTA) plus a smaller `text-xs opacity-70` consequence line underneath the main sentence: "Odświeżenie zastąpi Twoje niezapisane zmiany." The **reactive** (save-time, existing) variant is unchanged — no button, exactly as it ships today, since the user's save already failed and the form's own retry-the-save flow is the recovery path, not a refresh.
- **What "Refresh" does (behavioral contract, not a new visual):** discards the in-progress form's unsaved field values, repopulates `ItemForm` from the freshly-merged store item (already decrypted client-side via the silent background-merge flow — no extra fetch needed, the merge already happened), and updates the form's `currentRevision` baseline to the new value. This is the only path in this phase that can discard user-typed input — hence the consequence line is a hard requirement, not optional polish.
- **Gating (functional contract, drives the vitest case already listed in 05-RESEARCH.md's validation map):** the banner must fire only when the changed item's id matches the currently-open-for-edit item — a `SyncEvent` for a different item must never surface this banner. This mirrors the exact same revision-comparison the reactive 409 path already performs; no second "is this item stale" mechanism.

### Remote-delete-while-viewing (SYNC-03)

- **View mode, not edit mode:** if the item open in `DetailPanel` (in `view` mode) is absent from an incoming snapshot, the panel closes (`onClose()`, existing prop) and a toast appears. If the item is open in **edit** mode when this happens, the live-edit-conflict banner above already covers "something changed" — but a delete is a stronger case than an edit (there's nothing left to refresh into). Treat a remote delete identically regardless of view/edit mode: close the panel, show the toast. Don't build a separate "your edits are gone because it was deleted" banner variant — the toast plus panel-close is sufficient and matches CONTEXT's literal instruction ("the panel closes and a toast explains it was deleted on another device").
- **Toast mechanism — extends `ErrorToast.tsx`, does not introduce a new toast component.** Add an optional `variant?: "error" | "info"` field to `ErrorToastState` (`errorToast.ts`) and a corresponding class swap in `ErrorToast.tsx` (`alert-error` default, `alert-info` when `variant === "info"`). `showErrorToast(message, { variant: "info" })` (or an equivalent second export, e.g. `showInfoToast(message)` — planner's call, keep the module's existing single-state-slot/single-toast-at-a-time behavior unchanged) is called with the remote-delete copy. Same top-end position, same 320px width, same 4s auto-dismiss, same manual `X` dismiss — zero new layout, only a color/semantic swap. This is the first real use of the `info` (`#00B5FF`) token in the app (see Color section).

### Background list refresh (SYNC-01/03) — no new UI

- A WS push or poll tick revealing a changed `vault_revision` re-pulls, re-decrypts, and merges into `items`/`folders` silently. The list view (`ItemRow`, `Sidebar` folder/tag counts) already re-renders from the same `useSyncExternalStore`-backed store Phase 2 built — no new component, no flash/highlight/animation on updated rows. CONTEXT is explicit this must feel "ambient," not "chatty" — a per-row "updated!" badge or flash was considered and rejected (see Morning review notes #4).

## Morning review notes

Taste calls this agent made autonomously overnight (05-CONTEXT.md's decisions were binding and are **not** relitigated here — only genuinely open visual/UX choices CONTEXT explicitly left to "Claude's discretion" or the planner). None of these affect data model, API shape, or the zero-knowledge/no-ciphertext-in-WS-frames invariant — they're all presentation-layer and reversible in a follow-up pass.

1. **Sync dot is invisible except while reconnecting** (not a permanently-visible muted "connected" dot). I read CONTEXT's "small dot/pulse... rather than chatty" as arguing for near-total silence in the nominal case, but an always-on subtle dot (e.g. `bg-base-content/20`, matching Phase 2's static health-dot precedent exactly) is a legitimate alternative if you want a permanent "yes, sync is live" ambient cue rather than a purely reactive one. One-line change (render the dot in a muted color for `connected` instead of `null`).
2. **Live-edit banner stays `alert-error` for both the proactive and reactive trigger**, rather than splitting proactive into `alert-warning` to signal "lower stakes, nothing's broken yet." I chose consistency (same fact, same color, regardless of when the user learns it) over severity-tiering, reading CONTEXT's "matching tone" instruction as the stronger signal. If you'd rather visually distinguish "heads up" from "your save just failed," swap the proactive variant to `alert-warning` + `text-warning` — everything else (copy, button, gating logic) is unaffected.
3. **`RefreshCw` reused for "refresh the item," not just "regenerate a password."** Lucide's own icon name/shape reads as generic-refresh already; I didn't feel this needed a new icon. Flag if you'd rather keep one-icon-one-meaning strictly and introduce a dedicated refresh glyph.
4. **No per-row "updated elsewhere" flash/highlight on background list merges.** Considered (a brief `bg-primary/5` fade on rows whose revision just changed, similar to the copy-button's 1.5s checkmark flash) and rejected — SYNC-03's requirement is "live update," not "draw attention to what changed," and CONTEXT's specifics section explicitly wants sync to feel ambient, not chatty. A subtle flash is cheap to add later if real usage shows users can't tell why a row just moved/changed.
