<objective>
Build SYNC-02's server-side push channel on top of Plan 05-01's revision plumbing: an in-process per-user `tokio::sync::broadcast`-backed `SyncHub`, a `GET /api/sync/ws` upgrade handler authenticated via the same session-token hash lookup every REST endpoint already uses, and metadata-only `SyncEvent` publishes wired into every vault/folder mutation handler.

Purpose: an already-open second device is notified the instant a first device changes something, without the notification ever carrying anything more than "something changed, go pull" — the WS channel is the newest surface where this project's zero-knowledge/no-plaintext-to-server invariant must hold, and this plan proves it at the raw frame level, not just by code inspection.
Output: `SyncHub`/`SyncEvent` types, a working `GET /api/sync/ws`, publish-wiring in every mutation handler, and a real-socket integration test harness (`tests/common::test_server`) since this crate's existing `oneshot()` harness cannot exercise a WebSocket upgrade at all.
</objective>

`axum::extract::ws` (feature = "ws", already documented in 05-RESEARCH.md's Pattern 3 / Code Examples — read that section now, it is the exact reference implementation this plan follows):
`WebSocketUpgrade::on_upgrade(self, callback) -> axum::response::Response` — `callback: impl FnOnce(WebSocket) -> Fut + Send + 'static`.
`WebSocket::recv(&mut self) -> Option<Result<Message, axum::Error>>`, `WebSocket::send(&mut self, msg: Message) -> Result<(), axum::Error>`.
`Message::Text(...)` (constructed from a `String`/`&str` via `.into()`), `Message::Close(...)`.

`tokio::sync::broadcast` (already a dependency via `tokio`, no Cargo.toml change needed for this part):
`channel::<T>(capacity: usize) -> (Sender<T>, Receiver<T>)`.
`Sender<T>::send(&self, value: T) -> Result<usize, SendError<T>>` — `Err` ONLY when there are currently zero receivers; the returned value is the un-sent event, safe to drop.
`Sender<T>::subscribe(&self) -> Receiver<T>`, `Sender<T>::receiver_count(&self) -> usize`.
`Receiver<T>::recv(&mut self) -> Result<T, RecvError>` where `RecvError` is `Lagged(u64)` or `Closed`.

`tokio_tungstenite` (NEW `[dev-dependencies]` entry this plan adds, tests only — already Package-Legitimacy-audited OK in 05-RESEARCH.md, no additional human checkpoint needed):
`connect_async(url: &str) -> Result<(WebSocketStream<...>, http::Response<...>), tungstenite::Error>`. The returned stream implements `futures_util::{Stream, Sink}` — call `.next().await` (via `use futures_util::StreamExt;`) to get `Option<Result<tungstenite::Message, tungstenite::Error>>`; match `tungstenite::Message::Text(text)` and read it as a string (`text.as_str()` or `text.to_string()`) — this is tungstenite's OWN `Message` type, distinct from axum's `axum::extract::ws::Message` used server-side; do not conflate them across the client/server boundary in the test file.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Browser → `GET /api/sync/ws?token=` | Untrusted query-param token crosses here; must validate identically to the REST `Authorization` header path |
| `sync_hub` (in-process broadcast) → WS connections | Must never deliver user A's event to user B's socket |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|------------------|
| T-05-04 | Information Disclosure | `sync.rs::SyncEvent` / `handle_socket` | high | mitigate | `SyncEvent` carries only `entity_type`/`id`/`revision`/`change_type` — no field capable of holding ciphertext; `ws_event_contains_no_ciphertext` asserts the exact wire key set on a real mutation's frame |
| T-05-05 | Spoofing / Elevation of Privilege | `sync.rs::ws_handler` / `SyncHub` | critical | mitigate | `sync_hub` is keyed strictly by the server-validated `user_id` from `validate_token()` — never a client-supplied value; `ws_cross_user_isolation` proves a connection only ever receives its own user's events |
| T-05-06 | Information Disclosure | `ws_handler`'s `?token=` query param | medium | accept | session tokens are already short-TTL, revocable (`DELETE /api/sessions/{id}`), bearer-capability credentials per Phase 2/3 — landing in server/proxy access logs is an accepted, documented risk (05-CONTEXT.md), flagged pre-v1.0 hardening (first-message auth instead of query string) |
| T-05-07 | Elevation of Privilege | `ws_handler` (token validated only at upgrade, not per-message) | medium | accept | a session revoked via `DELETE /api/sessions/{id}` does not proactively close an already-open WS connection — matches this project's existing long-lived-connection posture, flagged as a pre-v1.0 stretch goal (proactive close-on-revoke), not blocking for SYNC-02 |
| T-05-08 | Denial of Service | `SyncHub` (unbounded connections per user) | low | accept | no requirement drives a per-user connection cap at this project's self-hosted/personal-vault scale |
| T-05-SC | Tampering (supply chain) | `tokio-tungstenite` dev-dependency | n/a | accept | already OK-verdict audited in 05-RESEARCH.md's Package Legitimacy Audit table (9-year-old crate, 4.1M weekly downloads, `snapview`/kanidm-adjacent maintainer); dev-dependency only, never shipped in the production binary — no additional checkpoint required |
