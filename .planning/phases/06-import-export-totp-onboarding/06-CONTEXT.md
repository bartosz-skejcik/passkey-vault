# Phase 6: Import/Export, TOTP & Onboarding - Context

**Gathered:** 2026-07-14
**Status:** Ready for planning
**Mode:** Smart discuss, auto-accepted (autonomous overnight run — Bartek asleep, explicit standing authorization to decide; UX-taste items flagged for morning review)

<domain>
## Phase Boundary

A new user can bring their existing passwords in during a 3-step onboarding flow (import offered first), see live TOTP codes on vault items generated locally from a stored secret, and export the whole vault back out to JSON/CSV with a plaintext warning. Deliverables: TOTP as a fifth first-class `ItemType` (own badge, own crypto path through pv-core/pv-wasm, live counting-down code in the detail panel and list), a fully client-side import pipeline (Bitwarden JSON+CSV, NordPass/1Password/LastPass/KeePass CSV, generic CSV/JSON with manual column mapping — no plaintext ever sent to the server), a client-side export pipeline (generic JSON + flat CSV, plaintext-warning confirmation), and a new onboarding wizard that appears after registration with import as step 1. Depends only on Phase 2 (vault CRUD + item model); does not depend on Phase 3/4/5 (passkeys/PRF/sync) — import/export/TOTP work identically regardless of unlock method or sync state. FIDO CXF import/export is explicitly deferred (CXF-01, v0.4+ per REQUIREMENTS.md) even though `docs/UI-DESIGN.md`'s onboarding line mentions it — that doc predates the roadmap's v1-requirements split and is superseded here for this phase.

</domain>

<decisions>
## Implementation Decisions

### Area 1: TOTP as a first-class item type & crypto path (auto-accepted)

- **TOTP is its own `ItemType`, not a field bolted onto `login`** — locked directly by ROADMAP.md's Phase 6 success criterion #5 ("Vault items of type TOTP show a live, counting-down code") and `docs/UI-DESIGN.md`'s vault-list badge enumeration ("Hasło / Passkey teal / Karta / Notatka / **TOTP**"). `web/src/lib/vault/types.ts`'s `ItemType` union grows a fifth member: `"totp"`. Fields: `{ type: "totp", name, secret (base32), issuer?, algorithm?, digits?, period?, folderId, tags }` with RFC 6238 defaults (SHA1, 6 digits, 30s period) applied when a source format doesn't specify them — matches every major password manager's own default and keeps manual-add UI to a single required field (secret) in the common case.
- **TOTP code computation goes through pv-core → pv-wasm, not a standalone JS library** — continues the established "no new crypto paths outside pv-core" convention (Phase 2 decision, reaffirmed every phase since). Add `totp-rs` to `pv-core` with `default-features = false` and only the `otpauth` feature enabled (parses `otpauth://totp/...` URIs — needed for Area 2's import mapping when a source format embeds one) — explicitly **not** the `qr`/`gen_secret`/`steam` features (no QR camera scanning or QR generation in this phase's scope; nothing in VAULT-07/IMPEX-* asks for it). `pv-wasm` exposes a pure, stateless `totp_now(secret, algorithm, digits, period, unix_time_seconds) -> { code, seconds_remaining }` — takes the current time as an explicit parameter (from `Date.now()` on the JS side) rather than reading the clock inside WASM, keeping the binding pure/testable. This is a read path only (no key material persists across the boundary) — lighter zero-knowledge bar than `WasmUserKey`, but the same choke-point discipline (only `lib/crypto/` imports the wasm package) still applies.
- **Live countdown ticks client-side via `setInterval` (~1s), recomputing through the WASM export each tick** — no server involvement, no push channel; matches Phase 5's established "sync only concerns ciphertext/metadata, never plaintext" boundary (TOTP codes never touch the network). Detail-panel ring color is **coral** (`--color-primary`, `#E16540`) per `docs/UI-DESIGN.md` §3.3 literal spec ("TOTP z odliczającym pierścieniem w kolorze koralowym") — not teal (teal is reserved for passkey/passwordless accents per the same doc's color-role table).
- **A TOTP item is a standalone item, never implicitly linked to a login item** — the data model has no foreign keys between items (Phase 2 decision: folder membership and all relations live inside each item's own encrypted payload). When an imported source row bundles a TOTP secret onto a login record (Bitwarden's `login.totp` field is the common case), the importer (Area 2) creates a *second*, separate TOTP item named after the same login (e.g. `"GitHub"` login → `"GitHub"` TOTP item), same folder/tags copied across — discoverable side-by-side in the list by name, not by a hidden relation. A manually-added TOTP item works the same way: added via the existing `TypePicker` tile grid, independent of any login item.

### Area 2: Import pipeline — parsing, mapping, execution (auto-accepted)

- **CSV parsing uses a small dedicated library (`papaparse`), not a hand-rolled parser** — RFC 4180 edge cases (quoted commas, embedded newlines/quotes, BOM, CRLF vs LF) are exactly the kind of correctness surface where a hand-rolled parser silently mis-imports a user's real passwords; `papaparse` is well-established, has no runtime dependencies, and bundles fine into a static export. First new npm dependency this phase — deliberate exception to keeping `web/package.json` minimal, justified by import-correctness stakes.
- **One shared `ImportWizard` component, invoked from two call sites** — Settings → Import/Export tab (Phase 3's existing "wkrótce" placeholder gets filled in) and Onboarding step 1 (Area 4) both render the same underlying flow: (1) file drop/select, (2) auto-detect source format from file extension + header/shape sniffing (Bitwarden `.json` has a distinctive `{"items": [...], "folders": [...]}` shape; Bitwarden/NordPass/1Password/LastPass CSVs are distinguished by their known column-header sets), (3) preview table of parsed rows mapped to our item fields, with a manual column-mapping UI surfaced whenever auto-detection doesn't recognize the header set (this *is* IMPEX-03's generic-CSV path — same UI, not a separate screen), (4) sequential per-item `encryptItem` + `POST /api/vault/items` with a progress bar (`N / total imported`), matching the zero-knowledge model exactly like every other write path (each row is encrypted client-side before it ever reaches `fetch`). No new server endpoint — the existing single-item `POST /api/vault/items` (Plan 02-03) is reused in a loop; a bulk-insert endpoint would be a meaningful complexity add (transactional semantics, partial-failure reporting) for a one-time, already-fast-enough client-side loop at solo-indie/self-host scale.
- **Per-tool CSV column mappers are static lookup tables, not a generic heuristic engine** — one small mapper module per source (`bitwardenCsv.ts`, `nordpassCsv.ts`, `onePasswordCsv.ts`, `lastpassCsv.ts`, `keepassCsv.ts`) each exporting a fixed `{ ourField: sourceColumnName }` table plus a `detect(headers): boolean`. KeePass's *native* export is `.kdbx` (encrypted binary, out of scope) or XML; **KeePass CSV export** (File → Export → "CSV File", a documented KeePass feature) is the supported IMPEX-02 path — consistent with IMPEX-02's literal "ich formaty eksportu CSV" wording naming CSV specifically for all four tools, not KeePass's other export options.
- **Row-level fault tolerance, not all-or-nothing** — a malformed/unparseable row is skipped and counted, not fatal to the whole import; the wizard's final screen reports `"Imported 42 of 45 — 3 skipped"` with a expandable reason list (missing required field, decrypt-unsupported row type, etc.), never a silent partial success. **No dedup against existing vault items in v0.1** — re-running an import (or importing overlapping exports from two tools) creates duplicate items; flagged as a known, acceptable v0.1 limitation (dedup-by-fuzzy-match is a real feature with real false-positive risk, not a quick add) rather than silently or aggressively merging.

### Area 3: Export pipeline (auto-accepted)

- **Export format is our own generic schema, not Bitwarden-compatible** — consistent with PROJECT.md's Decision A1 (greenfield, explicitly rejecting API/format compatibility as a design constraint). JSON export: `{ "exportedAt": ISO8601, "items": [ { type, name, ...type-specific fields }, ... ], "folders": [...] }` — same shape as the decrypted in-memory `VaultItem[]`/`Folder[]` the store already holds, serialized directly (no format translation layer to invent or maintain).
- **CSV export is a single flat file with a `type` column, blank cells for inapplicable fields** — one row per item, superset of columns across all 5 types (`name, type, username, password, urls, cardholderName, number, expiry, cvv, firstName, lastName, email, phone, address, secret, notes, folder, tags`), consistent with how Bitwarden/1Password's own CSV exports work and therefore familiar to the exact audience (self-hosters migrating *between* tools) this feature serves. Rejected: one CSV per item type / a zip of files — more moving parts for a one-time convenience export, no requirement asks for it.
- **Passkey sub-records are never exported** — a passkey's private key lives inside the authenticator hardware, never in the vault's own ciphertext; only its placeholder metadata (name, RP) exists client-side at all, and that metadata isn't portable/reimportable as a credential anywhere. Export silently omits passkey items entirely rather than emitting a misleading partial row — the plaintext-warning dialog copy notes this explicitly ("passkeys nie są eksportowane — nie da się ich przenieść") so it doesn't read as a bug.
- **Plaintext warning is a confirmation dialog before the download fires**, reusing `DeleteConfirmDialog`'s sober security-UI treatment (no Fuzzy Bubbles/emoji — locked by `docs/UI-DESIGN.md`'s "security UI zawsze czytelne" principle) — copy states the file will contain every password/secret in readable plaintext and the user is responsible for deleting it securely afterward. Download itself is a client-side `Blob` + `<a download>` (no server round-trip — matches the static-export/no-SSR constraint that already rules out any server-side file generation).

### Area 4: Onboarding wizard (UI-04) (auto-accepted; VISUAL/UX TASTE FLAGGED FOR MORNING REVIEW)

- **Three concrete steps**, filling the previously-unspecified content of UI-04's "3 kroki": **Step 1 — Import** (the `ImportWizard` from Area 2, with a prominent "Skip for now" — import is never mandatory, mirrors the recovery-invariant philosophy of never blocking a user from reaching their vault); **Step 2 — "Poznaj swój vault"/"Meet your vault"** a short static highlight of the two things unique to this product (PRF passkey unlock — teaser linking to Settings → Passkeys built in Phase 3, and the auto-lock/clipboard-clear behavior already active by default) — no new functionality, just orientation copy over the existing shell; **Step 3 — Finish**, a calm confirmation screen ("Gotowe — Twój vault czeka" / "All set — your vault is ready") that dismisses into the normal app, satisfying the onboarding/empty-state Fuzzy-Bubbles-and-emoji allowance from `docs/UI-DESIGN.md` §1/§4 one last time before the rest of the app returns to sober security-UI tone.
- **Triggers once, immediately after registration succeeds; never forced on returning users** — a `localStorage` flag (`pv-onboarding-complete`) set on wizard dismissal (via finish OR explicit skip-to-end) gates it; a user who logs in on a new browser/device does **not** see onboarding again (the flag is per-browser, not server-tracked — consistent with onboarding being pure UX orientation, not an account-state migration with security implications). Re-accessible later only indirectly: the import step's content is separately reachable anytime via Settings → Import/Export (Area 2's shared-component decision), so nothing is permanently lost by skipping.
- **Rendered as a distinct full-screen modal wizard, not the existing z-40 drawer+scrim pattern** — the drawer pattern (DetailPanel/Settings) is reserved for "working inside the vault" contexts; onboarding is a first-run, celebratory, higher-chrome moment (Fuzzy Bubbles annotations, step dots/progress) that competing products (Proton Pass, Bitwarden) also treat as a takeover, not an inline panel — a deliberate visual distinction from Settings so the two never feel like the same surface. **Flagged for morning review**: exact modal chrome/step-indicator styling is Claude's taste call, drafted here as full-screen-takeover-over-blurred-shell (echoing `UnlockOverlay`'s existing blur treatment for visual-language consistency) but not pixel-locked.
- **Step 1's import UI inside the wizard is the same full `ImportWizard`, not a stripped-down subset** — including the manual-column-mapping screen for unrecognized CSVs; a first-time user with a LastPass export is exactly the person onboarding exists for, and forcing them to "finish onboarding, then go find Settings" to do the real import they came for would undermine the entire "import as step 1" success criterion. The wizard's own internal step (file → preview/map → import-progress → done) nests inside onboarding's step 1 slot; "Skip" is available at the file-select screen only (once a file is loaded, the natural exit is "finish importing" or an explicit back/cancel, not an ambiguous skip mid-import).

### Claude's Discretion
- Exact `totp-rs` version pin and wasm32 build verification (mirrors Phase 1's `build-wasm.sh` audit discipline — confirm no incompatible transitive dep, e.g. anything pulling in real I/O/time-of-day system calls, before locking the dependency).
- Exact per-tool CSV column-name tables (Bitwarden/NordPass/1Password/LastPass/KeePass) — verify against each tool's actual current export format at plan/implementation time rather than trusting memory; format drift is plausible given tools update their export schemas.
- Component decomposition of `ImportWizard`/export flow, exact progress-bar/error-list UI, migration/test structure, i18n key naming — all within established codebase conventions.
- Whether TOTP's `algorithm`/`digits`/`period` are exposed as advanced fields in the manual-add form (behind a collapsed "Advanced" toggle) or fully hidden with RFC 6238 defaults and only settable via import — leaning toward the collapsed-advanced-toggle for parity with every competitor's manual-TOTP-add UX, but not load-bearing to any requirement.

## Existing Code Insights

### Reusable Assets
- `web/src/lib/vault/types.ts`: `ItemType` union (currently `"login" | "card" | "identity" | "note"`) — this phase's TOTP addition follows the exact same pattern as the other four (add to the union, add a `*Fields` interface, extend `normalizeItemFields`'s discriminated-union switch if a legacy-shape migration is ever needed).
- `web/src/components/vault/{TypePicker,ItemForm,DetailPanel,ItemRow}.tsx`: each already switches on `fields.type`/`item type` to render per-type UI (`TypePicker`'s `TILES` array, `ItemForm`'s `emptyFieldsFor` switch) — adding TOTP as a fifth case is additive, not a restructure, in every one of these files.
- `web/src/lib/vault/store.ts`: `createVaultItem`/`updateVaultItem`, `encryptItem`/`decryptItem` from `lib/crypto` — the exact per-item encrypt-then-POST primitives Area 2's import loop calls repeatedly (no new store API needed, just a driver loop around existing exports).
- `web/src/lib/vault/api.ts`: single-item `createItem(id, encKey, encData)` (Plan 02-03) — the only server write primitive import needs; no bulk endpoint exists or is being added.
- `crates/pv-server/src/routes/vault.rs` / `mod.rs`: confirms the full current route table — no vault-import/export server routes exist; none are needed (both pipelines are 100% client-side per IMPEX-01's explicit "przetwarzanie w całości klientowe").
- Phase 3's Settings drawer (`03-CONTEXT.md`): already reserves an **Import/Eksport** tab as a "wkrótce" placeholder — this phase is exactly what fills it in; the drawer/tab shell should already exist by the time Phase 6 executes (Phase 3 lands first per roadmap order).
- `web/src/lib/clipboard.ts`: countdown-timer pattern (`clampClipboardSeconds`, single-active-timer discipline) — not directly reused (TOTP's countdown is period-based, not action-triggered) but establishes the codebase's existing convention for a "visible countdown tied to a security-relevant value" UI, worth matching in tone for the TOTP ring.
- `web/src/components/vault/PasskeyPlaceholderSection.tsx`: the existing pattern for a type-specific detail-panel sub-section (passkey section on login items) — the TOTP countdown ring in the detail panel follows the same "extra section rendered conditionally on item type" shape.
- `web/src/components/auth/UnlockOverlay.tsx`: existing blurred-full-screen-overlay treatment — the visual precedent Area 4's onboarding modal chrome borrows from.
- `crates/pv-core/Cargo.toml`: current deps (`argon2`, `chacha20poly1305`, `hkdf`, `sha2`, `zeroize`, `serde`, `thiserror`, `base64`) — `totp-rs` (Area 1) is pv-core's first *new* runtime dependency since the project's crypto foundation was laid; verify its own transitive deps (likely `hmac`, `sha1`, `constant_time_eq`, optionally `base32`) don't conflict with the existing pinned versions.

### Established Patterns
- Zero-knowledge: server only ever sees ciphertext blobs — reaffirmed here for both import (client encrypts before POST) and export (client decrypts, never round-trips through the server to produce the download file).
- i18n PL+EN dictionary entries for every new string (`web/src/lib/i18n/dictionary.ts`) — established every phase since Phase 2; this phase adds the largest single batch yet (per-tool import copy, onboarding step copy, export warning copy).
- "No new crypto paths outside pv-core" (Phase 2 decision, reaffirmed Phase 3/4) — directly shapes Area 1's totp-rs-in-pv-core-not-JS decision.
- z-40 drawer+scrim pattern for in-vault panels (DetailPanel, Settings) vs full-screen overlay for pre-vault/security-critical moments (UnlockOverlay) — Area 4 explicitly classifies onboarding with the latter group.
- Sober, no-emoji security UI vs Fuzzy-Bubbles-allowed onboarding/empty-state UI — both regimes are exercised within this single phase (export's plaintext-warning dialog is the former; the onboarding wizard chrome is the latter) and must not bleed into each other.

### Integration Points
- `web/src/app/page.tsx`: currently gates on `authed` → `unlocked` (two sequential states). Onboarding is a *third* state, inserted between "just registered" and "normal vault view" — likely a new `showOnboarding` flag set true immediately after a successful `RegisterForm` submit (not after every login), read from/written to the `pv-onboarding-complete` localStorage flag.
- `web/src/components/settings/` (Phase 3): gains an `ImportExportPanel.tsx` (or similar) replacing the current placeholder tab content; this is the same component Area 4's onboarding step 1 mounts.
- `web/src/lib/i18n/dictionary.ts`: gains `import.*`, `export.*`, `totp.*`, `onboarding.*`, `itemType.totp` key namespaces.
- `crates/pv-wasm`: gains a `totp_now`-shaped export alongside the existing opaque-handle key exports (Phase 1 pattern) — this one returns plain data (code string + seconds-remaining), not a handle, since no secret key material needs to survive across calls.
- No migration needed in `crates/pv-server/migrations/` — TOTP items are just another `fields.type` value inside the existing opaque `enc_data` blob (Phase 2's "server sees ciphertext only, item type lives inside the ciphertext" model already covers a 5th type for free).

<deferred>
## Deferred Ideas

- FIDO CXF import/export (CXF-01) — v0.4+, deferred per REQUIREMENTS.md; `credential-exchange-format` crate not touched this phase.
- Dedup-on-import (fuzzy-match existing vault items against incoming rows) — real feature, real false-positive risk, explicitly deferred past v0.1 (Area 2).
- QR-code scanning to add a TOTP secret (camera capture of a third-party site's enrollment QR) — no requirement drives it; totp-rs's `qr` feature deliberately left disabled.
- Bulk/transactional server-side import endpoint — the existing single-item POST loop is judged sufficient at self-host scale; revisit only if a real user reports large-import performance pain post-v0.1.
- Server-tracked onboarding-completion state (vs. the chosen per-browser localStorage flag) — would let a user's onboarding-seen status follow them across devices, but onboarding is pure UX orientation with no security implication, so the added complexity isn't justified for v0.1.
- Password-history / attachments sections mentioned in `docs/UI-DESIGN.md`'s item-detail screen sketch — out of this phase's requirement set (VAULT-07/IMPEX-*/UI-04 don't touch either); attachments remain a v1 ATTACH-01 item, password history a v0.4+ HARD item per REQUIREMENTS.md.
