# Quick task 260812-01e: Code Review

**Reviewed:** 2026-08-12 (read-only; no builds, no `cargo test`, no `npm`, no Playwright run)
**Range:** `3219b16..fde4b1b`, source only (`crates/`, `web/`)
**Verdict:** REQUEST CHANGES — 1 Critical, 4 High, 5 Medium, 5 Low

## Summary

The mechanism is real and the two side doors the plan names are genuinely closed on the endpoints
it names. The `UPDATE` is correctly scoped to the caller's own row, cannot be driven against a
non-`item_bucket` collection, honours the documented pre-transaction pool-acquire ordering, and is
idempotent. Migration 0021 is correct. LOCKED decision 2 is honoured byte-for-byte (verified by
`git diff` greps — see "Verified clean"). The live e2e's recipient identity is **genuinely a second
real account**, so the headline proof does not collapse.

What fails is completeness and the honesty of two artifacts:

1. There is a **third propagation path** the plan never enumerated — the *explicit*
   collection-scoped invite field, which carries no declared-level bound at all. A self-escalated
   family owner can hand a brand-new invitee `edit` on a `read`-declared bucket, producing exactly
   the outcome `T-30fix-05` is marked `mitigate` for and directly falsifying
   `must_haves.truths[3]`.
2. The claim is **not atomic with the move**, so it is in fact the standalone self-promotion
   primitive that three separate doc comments and `T-30fix-01` explicitly say it is not.
3. After deviation #1's `item_bucket`-only narrowing, `LegacyUnknown`'s only remaining behavioural
   effect is to leave **legacy NULL-level item_buckets** unbounded — the one collection kind where
   the new escalation mechanism lives — and its regression guard test uses a `folder`, so it is
   vacuous and its recorded falsification cannot reproduce against the shipped code.
4. Face 2's discriminating assertion has **never been observed red** at either layer (server or
   live); both falsifications tripped one step earlier on Task 2's bound.

Deviation judgements requested in the brief are answered inline under each finding and in
"Verified clean".

## Critical

### CR-01: A third propagation path — the explicit collection-scoped invite bypasses the declared-level bound entirely

**File:** `crates/pv-server/src/routes/invitations.rs:215-227` (unbounded), vs the bounded loop at
`crates/pv-server/src/routes/invitations.rs:278-292`
**Also:** `crates/pv-server/src/routes/invitations.rs:547-571` (accept-time re-check), `:594-620`
(the grant)

Task 2 bounds exactly two propagation sites: `collections::add_member` and `invitations::create`'s
`family_wide_keys` fold-in loop. `invitations::create` has a **third** grant surface — the
top-level `collection_id` / `access_level` / `wrapped_collection_key` triple — and its only gate is
`membership::require_collection_edit(...)` at line 226. It never reads
`collections.family_wide_access_level`. At accept time, line 556-566 re-validates only that the
inviter *still holds `edit`* — which a self-escalated contributor does — and line 615 inserts the
recipient's row at the invite's own stored level.

**Concrete failure scenario**
1. Member `A` (not the family owner) creates the family's `read`-declared `item_bucket`; the family
   owner `O` is fanned out at `read` (exactly the fixture
   `task2_self_escalated_family_owner_cannot_fold_edit_into_an_invite` already builds,
   `crates/pv-server/tests/family_wide_sharing.rs:1937-1948`).
2. `O` self-escalates to `edit` on that bucket via Task 1's mechanism (two API calls).
3. `O` calls `POST /api/invitations` with `collection_id = <bucketId>`, `access_level = "edit"`,
   `wrapped_collection_key = <CK wrapped for the invite>`, and **omits** that bucket from
   `family_wide_keys` (so the bounded loop never sees it, and the accept-side duplicate-insert
   conflict at line 618 never fires).
4. The newcomer accepts. `insert_collection_key(..., "edit")` writes an `edit` row on a bucket whose
   declared level is `read`.

This is `T-30fix-05`'s outcome, reached by the same actor, on the same endpoint, one JSON field
over. It falsifies the plan's own `must_haves.truths[3]` ("cannot hand any OTHER member **or
invitee** a level higher than the bucket's own declared `family_wide_access_level`") and the
SUMMARY's claim that the side doors are closed.

**Fix**
```rust
// invitations.rs, inside `if let Some(collection_id) = &req.collection_id {`,
// after require_collection_edit:
if let membership::FamilyWideDeclaredLevel::Declared(declared) =
    membership::resolve_family_wide_declared_level(&state.db, collection_id).await?
{
    let requested = membership::parse_access_level_from_request(access_level_str)?;
    if requested != declared
        && membership::is_item_bucket_collection(&state.db, collection_id).await?
    {
        return Err(ApiError::Forbidden);
    }
}
```
Add a fourth attacker test mirroring
`task2_self_escalated_family_owner_cannot_fold_edit_into_an_invite`, but placing the bucket in the
*explicit* scope instead of `family_wide_keys`; falsify it (observe `201` pre-fix).

## High

### HI-01: The `edit` claim commits outside the move's transaction — it is a standalone self-promotion primitive, contrary to three doc comments and the threat register

**File:** `crates/pv-server/src/routes/membership.rs:669-678` (executes on `&state.db`, autocommit),
`crates/pv-server/src/routes/vault.rs:984-989` (gate), `:991-992` (validation runs *after*),
`:1010` (`tx` opens *after*)

The claim runs on a pool connection in autocommit mode, before blob validation and before the
transaction that performs the move. Every later failure path leaves the escalation permanently
committed with **no item ever landing in the bucket**:

- oversized `enc_key`/`enc_data` → `400` at `vault.rs:991`, escalation already persisted;
- `expected_revision` stale → `409` at `vault.rs:1046`, escalation already persisted;
- item deleted concurrently → `404` at `vault.rs:1018`, escalation already persisted.

**Concrete failure scenario:** a `read`-level member creates one personal item, then sends
`PUT /api/vault/items/{id}/collection` with `new_collection_id = <bucket>` and
`expected_revision: 999`. Response is `409`. Their `collection_keys` row is now `'edit'`, no junk
item exists in the bucket, and nothing in any log or UI records a "contribution". This is strictly
*worse* than the accepted `T-30fix-01` reachability, which at least leaves an artifact.

It also makes three shipped statements false:
- `membership.rs:631-634`: "atomically, on the SAME request that writes the item in — never a
  standalone endpoint a member could call without ever contributing anything";
- `vault.rs:977-979`: "a contributor's own row is atomically upgraded to `edit` on this same
  request";
- `T-30fix-01`'s "two API calls, create any owned personal item, then move it in".

**Fix (pick one, then correct the prose):** either (a) move the claim `UPDATE` inside the
transaction opened at `vault.rs:1010` — but note this collides with the documented
`max_connections(1)` constraint, so it must be executed on `&mut *tx`, not on `&state.db`, and the
gate's *read* must stay pre-tx; or (b) keep the current shape and rewrite all three comments plus
`T-30fix-01` to say plainly that the claim persists independently of whether the move succeeds.
(a) is the honest fix; (b) is the minimum.

### HI-02: `LegacyUnknown` now protects nothing and exposes exactly the wrong case; its regression guard is vacuous

**File:** `crates/pv-server/src/routes/collections.rs:571-587`,
`crates/pv-server/src/routes/invitations.rs:278-298`,
`crates/pv-server/tests/family_wide_sharing.rs:2099-2164`

The three states are structurally distinct in the resolver (`membership.rs:679-745`) and
`LegacyUnknown` does apply no equality bound — so the letter of the C-1 requirement is met. But
deviation #1 added `&& is_item_bucket_collection(...)` to the `Declared` arm's bound
(`collections.rs:576-577`, `invitations.rs:287-288`). Trace the two arms:

| collection | `Declared` arm | `LegacyUnknown` arm |
|---|---|---|
| family-wide **folder** | `may_grant` only (equality skipped: not item_bucket) | `may_grant` only |
| family-wide **item_bucket** | `may_grant` + equality | `may_grant` only |

So the two arms are **behaviourally identical for folders** and differ only on item_buckets.
Consequences:

1. C-1's stated purpose (protect a legacy `edit`-holder's invite generation on a pre-0020 row) is
   already satisfied by the `item_bucket` narrowing alone. `LegacyUnknown`'s only live effect is to
   leave a **legacy NULL-level `item_bucket`** entirely unbounded — the one kind where Task 1's
   self-escalation applies. A `read`-holder on such a bucket self-escalates, then `add_member`s any
   other member at `"edit"`: full `T-30fix-05` escalation, in the shipped code.
2. The Task 2 test 4 guard at `:2099` seeds `'folder'`, not `'item_bucket'` (line 2114). Under the
   shipped code it would pass **identically** with `LegacyUnknown` collapsed into `Declared(Read)`
   (`Edit != Read` is true, but `is_item_bucket_collection` is false → no `403`). The SUMMARY's
   Falsification 4 (`left: 403 / right: 201`) therefore cannot reproduce against the code as
   committed — it was observed against the pre-narrowing implementation from earlier in the same
   commit. The recorded evidence measures a code state that did not ship.

**Fix:** either apply the equality bound to `LegacyUnknown` **when the collection is an
item_bucket** (fail closed there; a NULL-level bucket cannot be created through the API anyway, so
nothing legitimate breaks), or backfill/refuse legacy NULL-level item_buckets. Then re-point test 4
at a `'folder'` **and** add a sibling test for a NULL-level `'item_bucket'` asserting the bound
*does* fire, each independently falsified against the shipped code.

### HI-03: The bound protects grants but not content — a self-escalated member can relocate or destroy other members' items, and launder a `read` share into an `edit` bucket

**File:** `crates/pv-server/src/routes/vault.rs:921-961` (Gate 0 covers **personal** items only),
`:975-989` (destination gate), `:715-717` (`delete` is `Membership<Item, RequireEdit>`)

Once escalated to `edit` on the bucket, `Item::resolve_access` (`membership.rs:354-386`) resolves
`Edit` for the attacker on **every item in that bucket, regardless of who owns it**. Gate 0 only
refuses re-scoping a *personal* item owned by someone else; a collection-scoped item has no owner
check at all.

**Concrete failure scenarios**
- *Destruction:* member `B` self-escalates on the `read` bucket and calls
  `DELETE /api/vault/items/{X}` for the owner's item `X`. Gone for the whole family. Task 2's
  `revoke_access` refusal stops `B` evicting the *members*; nothing stops `B` evicting the
  *content*, which is the same end state one item at a time.
- *Level laundering:* `B` self-escalates on the `read` bucket, creates a **new** `item_bucket`
  declared `"edit"` (legal after migration 0021, and `B` is its creator so holds `edit`), then
  `move_item`s every item out of the `read` bucket into it (source gate satisfied by the escalated
  row, destination gate satisfied by creator-`edit`), re-encrypting under the new CK which `B`
  holds. `B` then `add_member`s every family member at `"edit"` — which passes the new bound,
  because `"edit"` *is* the new bucket's declared level. The owner's chosen `read` declaration has
  been converted to `edit` for all content, with every bound intact.

`T-30fix-04/05`'s stated residual — "the escalated row grants edit over the BUCKET'S OWN CONTENT
only — it can neither revoke another member nor hand a third party more than the bucket's own
declared level" — is true only if "content only" is read as harmless. It is not: deletion,
relocation and re-declaration of other members' data all live inside it, and none of it is
disclosed by Task 7's note (which speaks only of "editing").

**Fix:** at minimum, record this honestly in the threat register and widen the disclosure copy. A
real bound would be to refuse `move_item` *out of* an `item_bucket`, and `delete`, for a caller who
is not the item's `user_id` — same shape as Gate 0, extended to item_bucket-scoped items.

### HI-04: The Task 7 disclosure is bypassed entirely by the ordinary folder picker, which now silently succeeds where it used to 403

**File:** `web/src/components/vault/CollectionPicker.tsx:66,111-113` (no `familyWideKind` filter),
`web/src/components/shell/Sidebar.tsx:111`, vs the disclosure at
`web/src/components/vault/ShareDialog.tsx:1312-1319`

`<select>` with no exclusion, so up to three entries literally named `family-wide-items`
(`ShareDialog.tsx:293` placeholder) appear in the ordinary "move this item to a folder" control.

**Concrete failure scenario:** a `read`-level family member picks `family-wide-items` in the folder

happened. After it, the move succeeds: the item becomes readable by everyone holding the bucket key

"never render an item_bucket as a folder" rule (30-UI-SPEC.md) is violated by the picker and the

**Fix:** filter `familyWideKind === "item_bucket"` out of `CollectionPicker`'s options and the
sidebar folder list (the same one-line exclusion Task 6 applied to `editableIds`).

### ME-02: `recipientAlreadyHoldsIntendedLevel` treats `"edit"` as satisfying an intended `"hidden_password"`

**File:** `web/src/components/vault/ShareDialog.tsx:229-234`

```ts
return entry !== undefined && (entry.access_level === intendedLevel || entry.access_level === "edit");
```

`AccessLevel`'s own doc comment (`membership.rs:68-76`) and `may_grant_access_level`'s nine arms
exist precisely because `edit` is **not** "more than" `hidden_password` along the axis the user
cares about: `hidden_password` means *cannot reveal the password*. A user who deliberately chose
`hidden_password`, hit a 409 for a recipient who already holds `edit`, is told the share succeeded
at their chosen level while that recipient can read the password.

The `|| "edit"` is load-bearing for the `read` case (past contributors legitimately hold `edit`), so
it cannot simply be deleted — but it should be scoped:

```ts
const contributorCeilingApplies = intendedLevel !== "hidden_password";
return entry !== undefined &&
  (entry.access_level === intendedLevel || (contributorCeilingApplies && entry.access_level === "edit"));
```
No test covers this combination; the two new Face-2 tests both use `intendedLevel = "edit"`.

### ME-04: `require_and_claim_item_bucket_edit` does not enforce the predicate its name promises

**File:** `crates/pv-server/src/routes/membership.rs:664-679`, call site
`crates/pv-server/src/routes/vault.rs:984-985`

The function will unconditionally promote the caller's row to `edit` on *any* collection it is
handed. The `item_bucket` predicate lives only at the single call site, separated from the claim by
an `await`. Not exploitable today (there is no endpoint that mutates `collections.family_wide_kind`
— verified: `collections.rs` exposes only `create`/`get`/`list`/`collection_items`/`add_member`/
`revoke_access`/`access_list`), but this is a privilege-granting primitive whose safety rests
entirely on one caller remembering to check. Fold the
`SELECT ... AND family_wide_kind = 'item_bucket'` predicate into the `UPDATE`'s own `WHERE` clause
(one `EXISTS` sub-select) so the guarantee is structural.

### ME-05: The e2e's "no share-error / no share-partial-error" assertions are evaluated after the dialog has detached, so they can never fail

**File:** `web/e2e/family-wide-sharing.spec.ts:1707-1717`

`await ...getByTestId("share-dialog").waitFor({ state: "detached" })` precedes both
`toHaveCount(0)` assertions. Once the dialog is detached, every descendant testid is gone, so both
counts are trivially 0. The real evidence is carried by the detach itself (the dialog only detaches
via `onShared()`), so nothing is *lost* — but the plan asked for these two assertions specifically
and as written they are dead. Assert them *before* clicking submit's completion, or replace them
with an explicit `expect(dialog).toBeHidden()`-plus-error-absence check taken while the dialog is
still mounted.

## Verified clean (checked, no finding)

- **The claim `UPDATE`** (`membership.rs:672-674`) is scoped to `collection_id = ? AND
  recipient_user_id = ?` — the caller's own row only, no wildcard, no level filter needed since
  `Collection::resolve_access` already proved a row exists *and* that the caller is an `active`
  member of the collection's family (`membership.rs:221-231`). It cannot create a row, only
  promote an existing one. Idempotent (`if level != Edit`), never an error on already-edit.
- **Pool-connection ordering at Gate 2** is respected: `is_item_bucket_collection` and
  `require_and_claim_item_bucket_edit` both run on `&state.db` (`vault.rs:984-988`), sequentially,
  each releasing its connection, and the transaction opens only at `vault.rs:1010`. No
  `max_connections(1)` self-deadlock.
- **The claim path cannot be driven at a non-`item_bucket` collection** through any shipped route:
  the branch predicate is a server-side `family_wide_kind = 'item_bucket'` read, and no endpoint
  can mutate that column after creation.
- **`revoke_access`'s refusal is correctly narrow.** `apply_member_removal_rekey`
  (`families.rs:698-743`) deletes the departing member's `collection_keys` row in its own handler
  and its own transaction, generic over every collection the target holds a row on in the family —
  including item_buckets. It never routes through `revoke_access`. **Phase 30's SC6 does not
  regress.** The refusal is also unreachable from the UI: `RevokeShareDialog` is only ever mounted
  from rows built out of `editableCollections`, which Task 6 now excludes item_buckets from.
- **Deviation #1 (scope narrowing) is defensible for folders.** There is no contributor-escalation
  path to a family-wide folder: `move_item`'s Gate 2 branches to the claim only for `item_bucket`
  (`vault.rs:984`), and every other writer of `collection_keys.access_level` is
  `collections::create`'s creator row, `add_member`, or the invite-accept insert. `T-30fix-05`'s
  premise holds. *However*, the narrowing has a second-order consequence the executor did not
  record — see HI-02.
- **`resolve_family_wide_declared_level` reads only the `collections` row** (`membership.rs:721`),
  takes only an id, and never touches anything client-supplied. Confirmed.
- **Deviation #4 (the live proof's identity) is sound — the recipient is a different real
  account.** `memberCtx` authenticates as `pv-e2e-item-bucket-member-${uniqueSuffix()}@example.test`
  via `ensureNamedFamilySession` (`web/e2e/family-wide-sharing.spec.ts:1618-1625`,
  `e2e/fixtures.ts:202-239`) — a genuinely fresh account that joins through the real invite UI. The
  owner side reuses `FAMILY_OWNER_EMAIL` on a fresh browser context, but the two decrypt steps that
  carry the claim are cross-account in both directions: the member decrypts the owner's item X
  (`:1683`) and the **owner decrypts the member's item Y** (`:1727`), each via
  `assertRecipientDecrypts` (`:443-465`), which asserts the real decrypted name in the row *and* the
  real revealed password in the detail panel. Only the *family* is reused, which is genuinely
  forced by `idx_families_singleton`. **The proof is not vacuous.**
- **Migration 0021** (`crates/pv-server/migrations/0021_item_bucket_per_level.sql`) is forward-only
  and data-preserving; `COALESCE(family_wide_access_level, '')` is the correct expression form for
  SQLite's distinct-NULLs behaviour; the partial predicate `WHERE family_wide_kind = 'item_bucket'`
  is preserved so `'folder'` stays unbounded and `collections::create`'s bare
  `ON CONFLICT DO NOTHING` still catches it; every existing family holds at most one bucket, so no
  live row can collide under the strictly wider key. Header wording is accurate (does not claim
  "additive-only").
- **LOCKED decision 2, byte-for-byte:**
  `git diff 3219b16..fde4b1b -- membership.rs | grep 'AccessLevel::X, AccessLevel::'` → no output
