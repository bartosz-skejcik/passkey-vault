# Context — Phase 30 fix: the family-wide ITEM variant

This is a **defect fix**, not new scope. It closes the single remaining gap in Phase 30's SC2
(`.planning/ROADMAP.md`, "### Phase 30", criterion 2 — FSH-01's "share a folder **or an item**").
The folder variant is finished and live-proven; the item variant is broken.

Everything below marked **LOCKED** is a decision already made. Do not revisit it, do not
re-litigate it, do not propose an alternative in the plan.

## The defect (established by probe at HEAD, not by reading)

One root cause, two user-visible faces.

Every family's family-wide item shares route through **one** singleton collection with
`family_wide_kind: 'item_bucket'`, enforced at the DB level by the partial unique index
`idx_one_item_bucket_per_family`. That singleton carries exactly **one**
`family_wide_access_level` — while `ShareDialog` offers a level control on **every** share.
The bucket's level is therefore fixed forever by whoever makes the family's *first*
family-wide item share.

**Face 1 — the bucket is write-locked to every non-creator member when it was created below
`edit`.** `submitItemFamilyWide` must call `moveItemToCollection` to put the item in the bucket,
and `vault::move_item` (`crates/pv-server/src/routes/vault.rs:976`) gates the DESTINATION with
`require_collection_edit` — an exact `AccessLevel::Edit` match (Phase 22 / SHARE-04). A member
fanned out at the bucket's declared `read` or `hidden_password` level can therefore never put an
item into it. Probed at HEAD with a control on the same fixture:

| bucket declared at | non-creator member shares their own item family-wide |
|---|---|
| `'read'` | **403 Forbidden** |
| `'edit'` (control) | **200 OK** |

The user sees `share.createFailed` — a retry that can never succeed. The bucket's *creator* is
exempt, because `collections::create` hard-codes their own `collection_keys` row to `'edit'`.
That exemption is why the defect stayed invisible.

**Face 2 — later shares silently deliver the wrong level.**
`findOrCreateFamilyItemBucket` (`web/src/components/vault/ShareDialog.tsx:424`) **ignores its
`level` argument on the existing-bucket branch**, and `grantCollectionToRecipients` swallows
`add_member`'s 409 as success. So every item share after the family's first reports success while
delivering the bucket's original level — to current members and to future joiners alike.

Invisible until now because the only coverage is mocked-crypto unit tests — precisely the
evidence class this project's standing rule rejects for a crypto claim.

## LOCKED decision 1 — one bucket per access level, sharer always gets `edit`

Chosen shape, decided by Bartek over the two alternatives (see "Rejected" below):

- **A family may hold up to three `item_bucket` collections — one per access level**
  (`read`, `edit`, `hidden_password`). A family-wide item share resolves (or lazily creates) the
  bucket **for the level the user picked on that share**, never a level-agnostic singleton.
- **Whoever contributes an item to a bucket holds an `edit` row on that bucket for themselves**,
  while every other family member holds the bucket's declared level. This is the *same asymmetry*
  `collections::create` already establishes for a collection's creator — it is being generalised
  from "the creator" to "any contributor", not invented here.
- Consequence to state plainly in the plan and honour in the code: a member who has ever
  contributed an item to a bucket can edit the other items in that same bucket. That is accepted.
  It must not be hidden — if any UI copy would now be false, fix the copy.

**Rejected, do not propose:**
- *"Family-wide item shares are always full edit"* — removes read-only family sharing, a real
  weakening of the model.
- *"Disable the item variant for now"* — withdraws a declared FSH-01 capability.

## LOCKED decision 2 — the deliberate things this fix must NOT undo

Both were investigated and settled in earlier passes. Touching them is a regression, not a fix.

1. **`collections::create` hard-coding `'edit'` for the creator's own `collection_keys` row is
   correct.** It matches `d07c2a7`'s established `read`-case precedent and has now survived two
   separate investigations. Keep it. (It is also the precedent Decision 1 generalises.)
2. **`may_grant_access_level` (`crates/pv-server/src/routes/membership.rs`) enumerates all nine
   `(caller_level, requested_level)` pairs explicitly, with no wildcard arm.** Deliberate: this
   bug class has appeared twice, each time as a missing pair in a matrix that looked complete. The
   compiler enforcing exhaustive coverage IS the fix. If this change adds a pair, add it
   explicitly. Do not collapse the match, do not add a catch-all.
   Also settled and load-bearing: `HiddenPassword -> Read` is `false` in both directions
   (`read` and `hidden_password` are different axes, not more/less), and there is no escalation
   path to `Edit`. Preserve all of that.
3. **`hidden_password` + family-wide IS a supported combination** (Bartek's recorded decision).
   Do not guard it, disable it, or narrow it in `ShareDialog`.

## LOCKED decision 3 — what counts as proof

This project's standing rule, and the reason this defect shipped: **a green mocked-crypto unit
test is NOT evidence for a crypto or access-control claim.** `web/src/**/*.test.tsx` mocks
`@/lib/crypto`; `vitest run` does not typecheck.

The fix is not done until there is **recipient-side positive proof through real crypto** that a
family-wide **item** share reaches another real account and decrypts — a live Playwright run in
`web/e2e/` or a real-WASM test, asserting on **decrypted content**, never on the presence of a
row. Today `grep -r item_bucket web/e2e/` returns nothing; that must stop being true.

Required, all of them:

- A **server integration test** covering the write-lock fix: a non-creator member contributing an
  item to a bucket declared at `read`, and at `hidden_password`. Model it on
  `b1_hidden_password_declared_family_wide_share_fans_out_invites_and_reseals` in
  `crates/pv-server/tests/family_wide_sharing.rs`.
- A test that **Face 2 cannot recur**: a second item share at a *different* level than the
  family's first must not silently land at the first level. Assert the recipient's *resolved*
  level, and stop `grantCollectionToRecipients` from swallowing a 409 as success.
- **Every new test must be falsification-proven**: revert the fix, watch the specific new test go
  red, restore, and record the observed failure in the SUMMARY. A test that was never seen to fail
  is not evidence. State in the SUMMARY *which* assertion fired and what it printed.

## LOCKED decision 4 — verify at CI width

Two of Phase 30's three blockers existed for one reason: **the acceptance command was narrower
than the CI command, so it could not fail** (`-p pv-server` instead of `--workspace`;
`vitest run`, which does not typecheck, instead of `npm run compile`).

Acceptance for this task is the literal CI set, each reported with its exit code:

```
cargo test --workspace --no-fail-fast
cd web && npm run compile
cd web && npm test
cd web && npm run build
cd web && npx playwright test e2e/<the family-wide spec> --retries=0
```

Any live run must be from a **fresh build of the current HEAD** — Phase 30's original green e2e
was produced against a stale release binary and was therefore worthless. Confirm port 8620 is
free first, use a throwaway `PV_E2E_DB_DIR`, and never touch `data/pv.db`.
