# Quick Task 260720-16k: Firefox Aux Windows Feel Like Popups (Centering, Self-Close, Scroll Cap, Autofill-Flash Race Fix) Summary

**Shared `centeredWindowPosition()` helper centers both Firefox `windows.create()` auxiliary windows over the triggering window, the consent window now self-closes and scroll-caps its candidate list, and a synchronous cross-world DOM marker closes an async postMessage race that could flash the login-autofill overlay during a passkey ceremony.**

## Performance

- **Duration:** ~15 min
- **Tasks:** 6/6 completed
- **Files modified:** 12 (2 new, 10 modified)

## Accomplishments

- New `extension/lib/window-geometry.ts` pure module (`WindowGeometry` type + `centeredWindowPosition()`) shared by both of the extension's `browser.windows.create()` call sites — one centering formula, tested once.
- `provider-ceremony.ts`'s Firefox consent fallback window now opens at 380x460 (revised from the quick task's original 420px pick, justified by the recomputed multi-match worst-case height), `focused: true`, centered over the current window when geometry is available, falling back to default placement when it isn't. Chrome's native `browser.action.openPopup()` path (`tryOpenPopup`) is byte-for-byte unmodified.
- `server-unlock.ts`'s server-origin PRF unlock/sign-in ceremony window now centers the same way, keeping its existing 480x640 size unchanged, adding `focused: true`.
- `App.tsx`'s `resolveCeremony()` now calls `window.close()` unconditionally after a successful `provider.resolveChoice` send — covering create/single-match confirm, multi-match row-click confirm, and decline alike — reusing the existing `AutofillItemRow.tsx`/`TotpFillRow.tsx` precedent. The `storage.session.onChanged` removal-while-showing-ceremony branch also now closes the window instead of falling back to `session.status`. A failed `provider.resolveChoice` send never closes the window (stays on the visible "failed" state).
- `ProviderCeremonyView.tsx`'s multi-match candidate list wrapper gained `max-h-52 overflow-y-auto` (plus `data-testid="provider-candidate-list"`) so a picker with more candidates than fit scrolls within the fixed-size consent window instead of being silently clipped.
- `page-bridge.content.ts`'s `relay()` now sets `document.documentElement.dataset.pvCeremonyInFlight = "1"` synchronously, before its `window.postMessage` call, and `content-relay.content.ts`'s Surface A (`handleFocusIn`)/Surface B (`initialMatchAndPrompt`) guards now OR that DOM marker into their existing `passkeyCeremonyInFlight` JS-flag check, closing the real async gap where a `focusin`/`DOMContentLoaded`-timed mount could race ahead of the flag (which is only set after a `postMessage` round-trip lands). `dispatchProviderCeremony` clears the marker at all 3 existing flag-clearing sites. 12-07's soft-hide/re-offer semantics are unchanged.

## Decisions Made

- Consent window height finalized at 460px (superseding this quick task's own earlier 420px pick) based on the recomputed worst-case layout: multi-match picker capped by Task 5's own `max-h-52` (208px) list, totaling ~424px including header/buttons/padding — 460 leaves ~36px headroom.
- `window.close()` called unconditionally (no Chrome/Firefox host-context branch) in App.tsx, reusing the existing, already-shipped `AutofillItemRow.tsx`/`TotpFillRow.tsx` precedent rather than inventing a new browser-detection check.
- The DOM marker (`document.documentElement.dataset.pvCeremonyInFlight`) is deliberately a plain, page-readable/writable attribute — accepted (not mitigated) as a low-severity Tampering risk in the plan's own threat model (T-quick16k-04), since it only coordinates a cosmetic UI soft-hide and never touches the actual WebAuthn consent gate.
