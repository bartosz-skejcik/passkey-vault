<objective>
Bartek's live UAT on Zen (Firefox) confirmed the passkey sign-in ceremony itself now works end-to-end. This plan closes five remaining UX rough edges from that session, none of which touch the ceremony's actual cryptographic/consent correctness:

1. **Firefox aux windows feel like stray windows, not popups** (original scope): the provider-ceremony consent fallback window and the server-origin PRF unlock/sign-in ceremony window both open with the browser's default/naive placement instead of being centered over the window that triggered them, and the consent window has no explicit height at all.
2. **Consent window never self-closes on Firefox** (new): unlike Chrome's native action popup, the `windows.create()` fallback window Firefox uses for consent stays open after the user confirms or declines, showing a stale fallback view.
3. **Consent window is too short for its own content** (new): even with this plan's own height fix, an unbounded multi-match candidate list can still exceed a fixed-size `windows.create()` window's bounds (which, unlike Chrome's auto-growing popup, never resizes to content) -- it needs its own scroll cap.
4. **Login-autofill surfaces flash on third-party pages during a passkey ceremony** (new): the 12-07 fix that soft-hides Surface A/B while a ceremony is in flight has a real async gap -- the JS flag it relies on is only set after a `postMessage` round-trip lands, and a `focusin`/`DOMContentLoaded` mount can race ahead of it.

This plan adds a shared, pure `centeredWindowPosition()` helper (`extension/lib/window-geometry.ts`) both auxiliary windows use to center themselves over the triggering window, revises the consent window's height (380x460, up from an interim 420 pick, informed by the list-cap fix below), makes the consent window close itself via `window.close()` on confirm/decline/resolved-elsewhere (reusing this popup app's own existing `AutofillItemRow.tsx` precedent), caps the multi-match candidate list at a scrollable `max-h-52` so it can never silently clip, and closes the autofill-surface race via a synchronous cross-world DOM marker (`document.documentElement.dataset.pvCeremonyInFlight`) that `page-bridge.content.ts` sets before the async postMessage hop even starts. Chrome's native action-popup consent path, and 12-07's soft-hide/re-offer semantics, are unchanged throughout.

Purpose: make Firefox's forced-window UX surfaces feel like the popups they're standing in for, and close a real (if narrow) race that flashes unrelated UI on third-party pages during a passkey ceremony -- both flagged live by Bartek.
Output: `lib/window-geometry.ts` (+test), updated `provider-ceremony.ts`/`server-unlock.ts` centering (+tests), `App.tsx` self-close wiring (+tests), `ProviderCeremonyView.tsx` scroll-capped candidate list (+tests), `page-bridge.content.ts`/`content-relay.content.ts` DOM-marker race fix (+tests), full extension/ gate green (vitest, tsc, both browser builds) as the plan's final step.
</objective>
