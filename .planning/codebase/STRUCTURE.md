## Directory Purposes

**crates/pv-core:**
- Purpose: Cryptographic operations and key hierarchy (zero I/O, WASM-compilable)
- Contains: Pure crypto functions, type-safe key abstractions, serializable data structures
- Key files: `kdf.rs` (password hashing), `keys.rs` (wrapping/unwrapping), `items.rs` (per-item encryption)
- Compilation target: Native binary (for server) + WebAssembly (for web app and extension)

**crates/pv-server:**
- Purpose: Self-hosted vault server providing REST API and database persistence
- Contains: HTTP routes (axum), database migrations (SQLx), configuration parsing
- Key files: `main.rs` (server startup and connection pooling), `routes/auth.rs` (authentication endpoints)
- Dependencies: pv-core (local), axum, tokio, sqlx, webauthn-rs, tower-http

**docs/**
- Purpose: Project-level architectural and design documentation
- Reference: Read `docs/ARCHITECTURE.md` for multi-recipient key wrapping, `docs/RESEARCH.md` for design decisions

**.planning/codebase/**
- Purpose: Generated codebase analysis for `/gsd-` commands
- Contains: Technology stack, architecture patterns, testing conventions, technical concerns
- Ownership: Generated by `/gsd-map-codebase`, consumed by `/gsd-plan-phase` and `/gsd-execute-phase`

## Key File Locations

**Entry Points:**
- `crates/pv-server/src/main.rs`: Server startup, database initialization, router setup
- `crates/pv-server/src/routes/mod.rs`: HTTP route registration (healthz, /api/auth/prelogin)
- `crates/pv-core/src/lib.rs`: Public module exports and architecture doc comments

**Configuration:**
- `crates/pv-server/src/config.rs`: Environment-based config (PV_ADDR, PV_DB_URL)
- `crates/pv-server/migrations/0001_init.sql`: Database schema (tables: users, webauthn_credentials, folders, vault_items, sessions)
- `Cargo.toml` (workspace root): Version pinning and shared dependencies

**Core Logic:**
- `crates/pv-core/src/kdf.rs`: Argon2id password hashing, HKDF wrapping key derivation
- `crates/pv-core/src/keys.rs`: User Key type, XChaCha20-Poly1305 AEAD, key wrapping primitives
- `crates/pv-core/src/prf.rs`: WebAuthn PRF output → wrapping key conversion
- `crates/pv-core/src/items.rs`: Per-item Cipher Key generation and item encryption/decryption

**Type Definitions:**
- `crates/pv-core/src/error.rs`: `CryptoError` enum (Kdf, Encrypt, Decrypt, InvalidInput)
- `crates/pv-core/src/keys.rs`: `UserKey`, `WrappedKey`, `ItemKey` types

**Testing:**
- Inline tests in each module: `#[cfg(test)] mod tests` blocks in `keys.rs`, `items.rs`, `prf.rs`
- Run via: `cargo test -p pv-core`

## Naming Conventions

**Files:**
- Snake case: `kdf.rs`, `items.rs`, `auth.rs`, `config.rs`
- Migrations: `0001_init.sql`, `0002_*.sql` (Flyway-style numbering)
- SQL tables: Plural, snake_case: `users`, `webauthn_credentials`, `vault_items`, `sessions`

**Functions:**
- Snake case: `derive_master_key()`, `wrap_user_key()`, `encrypt_item()`, `unwrap_user_key()`
- Private helpers: `aead_seal()`, `aead_open()` (prefixed with `pub(crate)` to restrict visibility)

**Variables:**
- Lowercase with underscores: `master_key`, `wrapping_key`, `prf_output`, `enc_key`, `enc_data`
- Abbreviations common in crypto: `uk` (User Key), `wk` (wrapping key), `aad` (additional authenticated data)

**Types:**
- PascalCase: `UserKey`, `WrappedKey`, `ItemKey`, `KdfParams`, `EncryptedItem`, `CryptoError`, `AppState`
- Module names: lowercase (Rust convention): `kdf`, `keys`, `prf`, `items`, `error`, `routes`, `config`

**Constants:**
- UPPERCASE: `KEY_LEN`, `NONCE_LEN`, `MASTER_KEY_LEN`, `MIN_SALT_LEN`, `PRF_OUTPUT_LEN`, `PRF_SALT_LEN`
- Domain separation: `INFO_PW_UNLOCK`, `INFO_PRF_UNLOCK`, `AAD_ITEM_KEY`, `AAD_ITEM_DATA`

**Environment Variables:**
- Prefixed `PV_`: `PV_ADDR`, `PV_DB_URL`
- Logging: Standard `RUST_LOG` (configured via tracing-subscriber)

## Where to Add New Code

**New Authentication Route:**
- File: `crates/pv-server/src/routes/auth.rs`
- Pattern: Define request/response structs, handler async function with `State` and `Json` extractors
- Example: Implement `POST /api/auth/login` alongside existing `prelogin()` handler
- Crypto logic: Reuse `pv_core::kdf::wrapping_key_from_password()` and `pv_core::keys::unwrap_user_key()`

**New Vault Operation Endpoint:**
- File: Create `crates/pv-server/src/routes/items.rs` (similar to `auth.rs`)
- Register in: `crates/pv-server/src/routes/mod.rs` via `Router::new().route(...)` and `.merge(items::router())`
- Pattern: Extract `State` with database pool, serialize/deserialize payloads, call pv-core crypto functions

**New Crypto Utility in Core:**
- File: `crates/pv-core/src/` — create new module or extend existing (e.g., `crates/pv-core/src/recovery.rs` for recovery codes)
- Export: Add to `crates/pv-core/src/lib.rs` as `pub mod recovery;`
- Pattern: No I/O, no external dependencies beyond allowed (crypto crates only)
- Tests: Add `#[cfg(test)] mod tests` block in same file

**Database Schema Change:**
- File: `crates/pv-server/migrations/0002_*.sql`
- Naming: Follow Flyway convention (sequential number + snake_case description)
- Execution: SQLx runs migrations automatically via `sqlx::migrate!("./migrations").run(&db)`

**New Configuration Parameter:**
- File: `crates/pv-server/src/config.rs`
- Add to `Config` struct, update `from_env()` with `std::env::var()` and sensible defaults
- Document in README.md under "Environment Variables"

**Testing - Unit Tests:**
- Location: Inline in module files (`keys.rs`, `items.rs`, etc.)
- Pattern: `#[test]` functions with `assert!()`, `assert_eq!()`
- Run: `cargo test -p pv-core` or `cargo test -p pv-server`

**Testing - Integration Tests:**
- Location: TODO — create `crates/pv-server/tests/` directory with integration test files
- Pattern: Spin up in-memory SQLite, call HTTP handlers, assert responses
- Example: `tests/auth_integration.rs`

## Special Directories

**crates/pv-server/migrations/:**
- Purpose: SQL schema migrations (Flyway-style)
- Generated: No (hand-written)
- Committed: Yes (required for schema versions)
- Note: `sqlx::migrate!()` macro in `main.rs` runs these at startup; do not modify existing migrations

**data/:**
- Purpose: Runtime data directory for SQLite database
- Generated: Yes (created by SQLite on first connection)
- Committed: No (in .gitignore)
- Default location: `data/pv.db` (set via `PV_DB_URL=sqlite://data/pv.db`)

**docs/:**
- Purpose: Project documentation (non-generated)
- Committed: Yes
- Reference: Read `ARCHITECTURE.md` for key hierarchy details, `RESEARCH.md` for design rationale

**.planning/codebase/:**
- Purpose: Generated codebase analysis
- Generated: Yes (by `/gsd-map-codebase`)
- Committed: Yes (cached for `/gsd-plan-phase` reference)
- Ownership: Regenerate when codebase structure changes significantly

**target/, .git/:
- Purpose: Build artifacts and version control
- Committed: No (in .gitignore)
- Note: `cargo build` creates target/; `.git` is repository metadata

## Module Visibility

**pv-core exports (public API in `lib.rs`):**
- `pub mod error;` → `CryptoError`
- `pub mod kdf;` → `KdfParams`, `derive_master_key()`, `wrapping_key_from_password()`
- `pub mod keys;` → `UserKey`, `WrappedKey`, `wrap_user_key()`, `unwrap_user_key()`
- `pub mod prf;` → `wrapping_key_from_prf()`
- `pub mod items;` → `EncryptedItem`, `encrypt_item()`, `decrypt_item()`

**pv-server structure (private to crate):**
- `mod config;` → `Config` struct
- `mod routes;` → router setup
- `pub struct AppState;` → shared state (exported for axum layers)

**Crypto primitives (implementation details, `pub(crate)`):**
- `keys::aead_seal()`, `keys::aead_open()` — internal AEAD wrapper, not part of public API
- `keys::hkdf_expand_key()` — used by both kdf and prf modules
