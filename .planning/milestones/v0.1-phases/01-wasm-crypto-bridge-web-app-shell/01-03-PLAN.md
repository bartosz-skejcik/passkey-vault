<objective>
Wire the themed app shell and a real crypto self-test together — this is the plan that actually delivers the phase's demoable capability. `lib/crypto/index.ts` becomes the sole choke-point importer of the generated WASM bindings (from plan 01-01 via plan 01-02's build wiring); the Self-Test Card drives the full derive→wrap→unwrap→encrypt→decrypt round trip against the real compiled module and renders per-step pass/fail. After this plan, a developer can load the app and watch pv-core's crypto execute for real, entirely inside the browser, with zero server involvement.

Purpose: Prove the WASM boundary end-to-end (RESEARCH.md's own "no server calls this phase" architecture) and give every later phase a trustworthy, already-audited crypto entry point.
Output: Sidebar/TopBar/MainColumn shell, SelfTestCard/StepRow, and the `lib/crypto/` facade — the phase's complete, demoable slice.
</objective>

  <action>
    Import the generated glue from `./wasm/pv_wasm.js` (produced by plan 01-01's build script into `web/src/lib/crypto/wasm/`) — default export `init`, named exports `WasmWrappingKey`, `WasmUserKey`, `wrapUserKey`, `unwrapUserKey`, `encryptItem`, `decryptItem`, `defaultKdfParamsJson`, `randomSalt` (verify exact names against `crates/pv-wasm/src/lib.rs`'s `js_name` attributes before writing the import list — do not assume).

    Implement `export function initCrypto(): Promise<void>` exactly per RESEARCH.md Pattern 1: a module-level `let ready: Promise<void> | null = null;`, and `initCrypto()` sets `ready = init('/wasm/pv_wasm_bg.wasm').then(() => undefined)` only if `ready` is currently null, then returns `ready`. The explicit string path (not the zero-argument default) is required — Turbopack cannot trace the zero-arg default's internal `new URL(..., import.meta.url)` resolution.

    Define a `StepResult` type: `{ name: string; ok: boolean; detail?: string; error?: string }`.

    Implement `export async function runSelfTest(): Promise<StepResult[]>` that awaits `initCrypto()` then executes, in order, wrapped in individual try/catch blocks so one step's failure doesn't abort later steps: (1) "Derive User Key" — `WasmWrappingKey.fromPassword('pv-self-test-password', new Uint8Array(randomSalt(16)), defaultKdfParamsJson())` plus `WasmUserKey.generate()`; (2) "Wrap" — `wrapUserKey(wrappingKey, userKey)`, storing the returned JSON string; (3) "Unwrap" — `unwrapUserKey(wrappingKey, wrappedJson)`, and use THIS unwrapped key (not the original `userKey` handle) for steps 4-5, so a broken unwrap surfaces as a downstream decrypt failure rather than a silently-ignored discrepancy; (4) "Encrypt item" — `encryptItem(unwrappedKey, '{"type":"note","body":"self-test fixture"}')`; (5) "Decrypt item" — `decryptItem(unwrappedKey, encryptedItemJson)`, asserting the returned string equals the original fixture plaintext exactly (mismatch is a failed step, not a thrown exception escaping the function). For the optional `detail` field, use a short truncated prefix (first ~16 characters) of the step's JSON/ciphertext output — never a key handle's contents, since no code path here ever has raw key bytes to display.

    This file must remain the ONLY file under `web/src` that imports from `./wasm/` or `./index` — no shell/self-test component talks to the WASM bindings directly.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Browser JS ↔ WASM linear memory, via `lib/crypto/` | The intended sole crossing point for all cryptography this app will ever do |
| Self-test UI rendering ↔ crypto operation results | Where a careless render call could leak secret material into the DOM/console |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-------------------|
| T-03-01 | Information Disclosure | Any future file importing wasm bindings outside `lib/crypto/` | high | mitigate | Task 1's acceptance-criteria grep-audit (`grep -rl "from ['\"]\./wasm" web/src` limited to `lib/crypto/index.ts`) is re-runnable as a standing check; this phase's own success criterion (UI-01) depends on it |
| T-03-02 | Information Disclosure | `SelfTestCard`/`StepRow` rendering of step `detail`/`error` text | medium | mitigate | `runSelfTest()` (Task 1) only ever produces non-secret ciphertext/JSON prefixes or error strings for the `detail`/`error` fields — no code path passes a `WasmUserKey`/`WasmWrappingKey` handle into a string/template/console call; verified by Task 1's acceptance criteria |
| T-03-03 | Denial of Service (self, UX-only) | `SelfTestCard` mount lifecycle | low | mitigate | Every `runSelfTest()` step is wrapped in try/catch (Task 1); `initCrypto()` failure is caught and rendered as the UI-SPEC.md-defined error state, never a silent infinite-loading spinner |

</threat_model>
