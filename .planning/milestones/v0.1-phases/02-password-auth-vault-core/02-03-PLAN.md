<objective>
Give the vault a real server-side storage layer: items and folders as opaque encrypted blobs, with optimistic-concurrency revision bookkeeping and zero plaintext metadata columns — the literal VAULT-01/VAULT-02/VAULT-03 server-side contract. This closes the last structural gap RESEARCH.md flagged: the existing `vault_items` migration (0001) contradicts the locked data model (plaintext `type` CHECK column, plaintext `folder_id` FK) and must be rebuilt, not altered in place.

Purpose: Every later UI plan (02-05, 02-06) needs a real, authenticated, revision-aware REST surface to call — this plan is that surface's entire server side.
Output: `/api/vault/items` (GET/POST) and `/api/vault/items/{id}` (PUT/DELETE) and `/api/vault/folders` (GET/POST) and `/api/vault/folders/{id}` (DELETE), all session-scoped, integration-tested.
</objective>

  <behavior>
    - Creating an item via `POST /api/vault/items` with `{id, enc_key, enc_data}` (client-supplied `id`; both `enc_key`/`enc_data` opaque JSON strings matching pv-core's `WrappedKey` serde shape) returns 201 with `{id, revision: 1}`.

    - `GET /api/vault/items` for the authenticated user returns only that user's items (a second registered user's items, created in the same test, never appear).
    - `PUT /api/vault/items/{id}` with the CORRECT current `expected_revision` succeeds, increments `revision`, returns 200 with the new revision.
    - `PUT /api/vault/items/{id}` with a STALE `expected_revision` (one less than current) returns 409, and the stored blob is unchanged (verified by a follow-up GET).
    - `DELETE /api/vault/items/{id}` removes the item; a follow-up GET/PUT on that id returns 404.
    - `PUT`/`DELETE` on another user's item id (from a second registered user) returns 404, not 403 (do not confirm the id's existence to a non-owner).
  </behavior>
  <action>
    Following Plan 02-02's documented decision, this plan's handlers also use runtime-checked `sqlx::query`/`query_as` throughout (never `query!`/`query_as!`) — see 02-02 Task 1's `SessionUser` extractor note for the full CLAUDE.md-convention-deviation rationale and the `.sqlx`-offline-cache follow-up idea; not re-litigated here.

    Create `crates/pv-server/migrations/0003_vault_items_rebuild.sql`: since no production data exists yet (Phase 1 shipped no write path) and SQLite cannot `ALTER TABLE ... DROP COLUMN` a column participating in a `CHECK` constraint, use `DROP TABLE vault_items;` followed by a `CREATE TABLE vault_items (id TEXT PRIMARY KEY, user_id TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE, enc_key TEXT NOT NULL, enc_data TEXT NOT NULL, revision INTEGER NOT NULL DEFAULT 1, max_blob_bytes constraint via application code not SQL, created_at TEXT NOT NULL DEFAULT (datetime('now')), updated_at TEXT NOT NULL DEFAULT (datetime('now')))` — no `type`, no `folder_id`, no `deleted_at` (this phase does permanent delete only, per CONTEXT.md's locked decision — deferred trash/soft-delete is out of scope). Recreate `CREATE INDEX idx_vault_items_user ON vault_items(user_id, revision);` preserving the existing index-naming convention.

    In `crates/pv-server/src/routes/vault.rs`, define `const MAX_ITEM_BLOB_BYTES: usize = 64 * 1024;` (64 KiB — RESEARCH.md flagged item payload size as an unbounded-storage-abuse gap with no explicit CONTEXT.md limit; 64 KiB comfortably fits any of the four item types' encrypted JSON payload with generous headroom, decided here as this plan's discretionary call).

    `CreateItemRequest { id: String, enc_key: String, enc_data: String }` — **the client supplies `id`, not the server**: the client must know the item's id BEFORE encrypting it, since pv-core's AD binds ciphertext to `item_id` (Plan 02-01) — the server cannot generate the id first and hand it back, because the ciphertext the client sends was already sealed against a specific id by the time this request arrives. Validate `id` is a well-formed UUID string (reject malformed ids with `ApiError::BadRequest`) and that both `enc_key`/`enc_data` (opaque `WrappedKey`-shaped JSON strings, produced client-side — server never parses their contents) do not exceed `MAX_ITEM_BLOB_BYTES`. `create` (extractor: `SessionUser`): `INSERT INTO vault_items (id, user_id, enc_key, enc_data, revision) VALUES (?, ?, ?, ?, 1) ON CONFLICT(id) DO NOTHING` (id collisions are astronomically unlikely for client-generated UUIDv4s, but the `ON CONFLICT` guard keeps creation atomic and race-free rather than trusting client-side uniqueness alone); `rows_affected() == 0` → `ApiError::Conflict("item id already exists".into())`. Return 201 `{id, revision: 1}`.

    `list` (extractor: `SessionUser`): `SELECT id, enc_key, enc_data, revision FROM vault_items WHERE user_id = ?` bound to `session_user.user_id` — never trust a client-supplied user id anywhere in this file.

    `UpdateItemRequest { enc_key: String, enc_data: String, expected_revision: i64 }`. `update` (extractor: `SessionUser`, path: `Path(id): Path<String>`): single-statement `UPDATE vault_items SET enc_key = ?, enc_data = ?, revision = revision + 1, updated_at = datetime('now') WHERE id = ? AND user_id = ? AND revision = ?` binding `expected_revision` last — per RESEARCH.md Pattern 3, this is atomic (no separate SELECT-then-UPDATE race window). If `rows_affected() == 0`: run a follow-up `SELECT 1 FROM vault_items WHERE id = ? AND user_id = ?` to distinguish "doesn't exist / not yours" (→ `ApiError::NotFound`) from "exists but revision mismatched" (→ `ApiError::Conflict`). Return 200 `{revision: expected_revision + 1}` on success.

    `delete` (extractor: `SessionUser`, path: `Path(id): Path<String>`): `DELETE FROM vault_items WHERE id = ? AND user_id = ?`; `rows_affected() == 0` → `ApiError::NotFound`; else `StatusCode::NO_CONTENT`.

    Register in `crates/pv-server/src/routes/mod.rs` (axum 0.8 `{id}` path-param syntax): `.route("/api/vault/items", get(vault::list).post(vault::create))`, `.route("/api/vault/items/{id}", put(vault::update).delete(vault::delete))`. Add `pub mod vault;` to the module tree.

    Extend `crates/pv-server/tests/common/mod.rs` with a `pub async fn register_and_login(app: &Router, email: &str) -> String` helper that POSTs a fixture register+login pair (deterministic fixture `auth_hash`/`salt`/`kdf`/`pw_wrapped_uk` values — the vault route tests don't need real client-side-derived crypto, just a valid session token) and returns the bearer token string, so `tests/vault.rs` doesn't duplicate this boilerplate per test.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Authenticated client → `/api/vault/*` | Every query must be scoped by the session's `user_id`, never a client-supplied one |
| Item ciphertext at rest | The server stores and forwards opaque blobs it can never decrypt — its only job is not to corrupt or misattribute them |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-10 | Elevation of Privilege | `vault.rs`/`folders.rs` update/delete handlers | critical | mitigate | Every `UPDATE`/`DELETE` includes `AND user_id = ?` bound to the session's own id — an item/folder id belonging to another user is indistinguishable from a nonexistent one (404), never a 403 that would confirm existence; covered by cross-user integration tests |
| T-02-11 | Tampering | Concurrent edits to the same item | high | mitigate | Single-statement `UPDATE ... WHERE revision = ?` + `rows_affected()` check (RESEARCH.md Pattern 3) — no TOCTOU window; stale writes rejected with 409, proven by an integration test that the stored blob is unchanged after a rejected write |
| T-02-12 | Denial of Service | Unbounded item blob size | medium | mitigate | `MAX_ITEM_BLOB_BYTES` (64 KiB) rejects oversized `enc_key`/`enc_data` payloads with 400 before they reach the database |
| T-02-13 | Information Disclosure | `tower-http` `TraceLayer` logging vault ciphertext bodies | high | mitigate | Same mitigation as T-02-09 (Plan 02-02) — default `TraceLayer::new_for_http()` never logs bodies; no handler in `vault.rs`/`folders.rs` logs `enc_key`/`enc_data` contents via `tracing::debug!`/`info!` or similar |

</threat_model>
