<objective>
Extend the shared crypto core (`pv-core` → `pv-wasm` → the `lib/crypto/` choke-point) with the two crypto primitives every later slice in this phase depends on: AD-bound item encryption (the literal VAULT-02 mechanism) and combined auth-hash/wrapping-key derivation from a single Argon2id pass (the mechanism AUTH-01/02's hash-po-KDF login model needs). This is a justified shared-foundation exception to MVP vertical-slicing — exactly as Phase 1's own WASM bridge was a dedicated foundation phase — because both the "register & log in" slice (Plan 02-02/02-04) and the "vault item CRUD" slice (Plan 02-03/02-05) require these primitives to exist and be tested before either can be built; there is no way to demo "register" or "create an item" without this layer.

Purpose: Deliver VAULT-02's signature security guarantee (AD-mutation rejection) and the auth-hash derivation AUTH-01/02 need, without ever running Argon2id twice per login (RESEARCH.md's explicit efficiency finding), and without breaking Phase 1's already-shipped self-test.
Output: `pv-core`'s items.rs/kdf.rs/keys.rs extended and tested; `pv-wasm`'s exported surface widened; `lib/crypto/index.ts` established as the full crypto facade contract for every later plan in this phase.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| WASM linear memory ↔ JS heap (`pv-wasm` public API) | Every export is a crossing point; `auth_hash` is now an INTENTIONAL crossing (it must leave to be POSTed to the server) unlike the User Key, which must never cross |
| Item ciphertext ↔ its declared identity (item_id/revision) | Where a malicious or buggy server could splice blobs between items/revisions if the AD binding were absent or wrong |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-01 | Tampering | `pv_core::items::encrypt_item`/`decrypt_item` | critical | mitigate | `build_item_aad` binds ciphertext to `item_id ‖ revision`; `aad_mutation_rejected` test asserts `Err(CryptoError::Decrypt)` on any mismatch (Task 1) — this is VAULT-02's literal, phase-defining security guarantee |
| T-02-02 | Information Disclosure | `deriveAuthMaterial`'s `auth_hash` crossing the WASM boundary as `Vec<u8>` | medium | mitigate | This is a 256-bit uniformly-random HKDF output, not the password itself (already established server-rehash rationale from RESEARCH.md Pitfall 3); its intended destination is the server over HTTPS, so this is a designed crossing at the correct boundary, not a leak — never logged, never displayed, zeroized in the WASM-side struct via `ZeroizeOnDrop` once taken |
| T-02-03 | Information Disclosure | `derive_auth_material`'s password buffer not zeroized on error path | high | mitigate | Follows the existing `from_password` ordering exactly: `password.zeroize()` runs unconditionally between computing the `Result` and propagating it with `?`, so the caller's buffer is wiped on both Ok and Err paths |

</threat_model>
