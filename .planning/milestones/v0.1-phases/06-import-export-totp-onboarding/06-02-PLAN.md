<objective>
Build the pure, framework-free import mapping layer: format detection, one small static-lookup-table mapper module per source tool (Bitwarden JSON+CSV, NordPass/1Password/LastPass/KeePass CSV), and the generic manual-column-mapping fallback — all producing a common `MappedItemDraft` intermediate shape that Plan 06-03's `ImportWizard` consumes.

Per 06-CONTEXT.md Area 2 (locked): CSV parsing uses `papaparse` (this phase's first new npm dependency — the automated Package Legitimacy check mis-flags it `[SUS]`/"too-new" because it reads the *latest release* date, not first-publish date; 06-RESEARCH.md's Package Legitimacy Audit documents this as a verified false positive and still requires a human-verify checkpoint before install, per protocol). Per-tool mappers are static lookup tables plus a `detect(headers): boolean`, never a generic heuristic engine. Row-level fault tolerance is structural, not a UI afterthought: every mapper function returns a result type that can carry a skip reason instead of throwing.

This plan is intentionally UI-free and has zero dependency on Plan 06-01's `TotpFields`/`ItemType` changes — `MappedItemDraft` is this plan's own self-contained intermediate shape (folder as a raw name string, not a resolved `folderId`; a `"totp"` variant with its own field list), so it can run in the same wave as Plan 06-01 with no shared-file conflict and no content dependency.

Purpose: IMPEX-01/02/03 — a user can import Bitwarden JSON/CSV, NordPass/1Password/LastPass/KeePass CSV, or a generic CSV/JSON via manual column mapping, entirely client-side.
Output: `web/src/lib/vault/importers/*.ts`, a pure-function mapping layer with full unit-test coverage, ready to be driven by Plan 06-03's `ImportWizard`.
</objective>

**Bitwarden JSON** (root shape, HIGH/MEDIUM confidence):
```
{ "folders": [{ "id": "...", "name": "..." }],
  "items": [{
    "id": "...", "folderId": "...", "type": 1, "name": "...", "notes": "...",
    "login": { "username": "...", "password": "...", "totp": "...", "uris": [{ "uri": "..." }] },
    "card": { "cardholderName": "...", "number": "...", "expMonth": "...", "expYear": "...", "code": "..." },
    "identity": { "firstName": "...", "lastName": "...", "email": "...", "phone": "...", "address1": "..." },
    "secureNote": { "type": 0 }
  }] }
```
`type`: `1`=Login, `2`=SecureNote, `3`=Card, `4`=Identity. Detect via
`typeof parsed === "object" && Array.isArray(parsed.items)` (no file-extension
dependency needed — this format is JSON-shape-detected, not header-detected).

**Bitwarden CSV** (MEDIUM confidence): header includes
`folder,favorite,type,name,notes,fields,reprompt,login_uri,login_username,login_password,login_totp`
(card/identity exports may add `card_*`/`identity_*` columns — read defensively,
not required for `detect()`). `detect()` requires only
`["type","name","login_username","login_password"]`.

**NordPass CSV** (MEDIUM-HIGH confidence, web-verified this session): header
`name,url,username,password,note,folder` — no TOTP/type column. `detect()`
requires exactly this set: `["name","url","username","password","note","folder"]`.
Every row maps to `type: "login"` UNLESS `username`, `password`, AND `url` are
all empty and `note` is non-empty, in which case map to `type: "note"` (body =
`note`) — NordPass exports secure notes as rows with only name/note populated.

**1Password CSV** (LOW-MEDIUM confidence, partially web-verified): assume
lowercase header `title,url,username,password,otp,tags,notes` (best-available
guess — the literal casing/exact key for "One-time password" was not
confirmable this session). `detect()` requires ONLY `["title","username","password"]`
(the two least likely to have drifted) — read `url`/`otp`/`tags`/`notes`
defensively via `row[col] ?? ""`, never required for a match.

**LastPass CSV** (MEDIUM confidence, per 06-RESEARCH.md's own verified example):
header `url,username,password,totp,extra,name,grouping,fav`. `detect()` requires
`["url","username","password","extra","name","grouping"]` (deliberately dropping
`fav` from the required set — a boolean flag column is the least central to
identifying the format, and requiring it needlessly increases false-negative
risk if LastPass ever drops/renames it).

**KeePass / KeePassXC CSV** (HIGH confidence for the shared subset, per
06-RESEARCH.md's own verified finding): header always includes
`Group,Title,Username,Password,URL,Notes` (case-insensitive match — KeePass
capitalizes columns). `detect()` requires exactly this 6-column set,
case-insensitively. KeePassXC's export additionally has a `TOTP` column (and
`Icon`/`Last Modified`/`Created`, ignored) — read `row["TOTP"] ?? ""`
defensively; a stock-KeePass row with no such column simply never produces a
totp draft (06-RESEARCH.md Pitfall 3 — this MUST degrade gracefully, not treat
the missing column as a parse error).
