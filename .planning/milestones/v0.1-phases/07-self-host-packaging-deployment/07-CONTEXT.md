# Phase 7: Self-Host Packaging & Deployment - Context

**Gathered:** 2026-07-14
**Status:** Ready for planning
**Mode:** Smart discuss, auto-accepted (packaging/infra phase — all decisions Claude's discretion per standing user preference; no UX/user-story questions arise in a packaging phase, so nothing was routed to Bartek)

<domain>
## Phase Boundary

A solo self-hoster can `docker run` (or `docker compose up`) a single built image and get a working Passkey Vault: the axum binary serves the REST API, the sync WebSocket, and the static Next.js export all on one port; SQLite lives on a mounted volume and survives container restarts; pending migrations run automatically on every boot before the server starts accepting traffic. If the operator points a non-localhost deployment at the container without setting `PV_RP_ID`/`PV_ORIGIN` correctly, the process refuses to start and prints exactly what's wrong and how to fix it — never a vague 500 or a WebAuthn `SecurityError` discovered by an end user mid-registration. A documented, tested reference reverse-proxy config (both nginx and Caddy, since self-hosters split roughly evenly between them) proves passkey ceremonies and the sync WebSocket survive being fronted by a real proxy, including the WS upgrade headers and the query-string session token that Phase 5's `make_span` redaction already flagged as a proxy-access-log risk. Depends on Phases 1-6 being feature-complete (there is nothing new to build in pv-core/pv-server/web business logic this phase — it is exclusively build, config-validation, and ops surface). Registry publishing (pushing a built image to GHCR/Docker Hub) is explicitly out of scope for v0.1 — a `Dockerfile` + `docker-compose.yml` that any self-hoster can `docker build` themselves satisfies DEPLOY-01/02 and matches the "build-it-yourself" norm of the Vaultwarden/homelab audience this project targets.

</domain>

<decisions>
## Implementation Decisions

### Area 1: Base image & multi-stage build strategy (auto-accepted)

- **Three-stage build: Rust builder → Node builder → slim runtime**, not two stages and not a single fat image. Stage 1 (`rust:1-slim` or the pinned toolchain from `rust-toolchain.toml`) builds `pv-server` in release mode, including the `wasm32-unknown-unknown` target build of `pv-core`/`pv-wasm` needed by stage 2's `npm run build` (the web app imports the wasm package from `lib/crypto/` at build time, not runtime, since `output: "export"` is a static build). Stage 2 (`node:20-slim` or later LTS) runs `npm ci && npm run build`, producing `web/out/` (the static Next.js export). Stage 3 (`debian:bookworm-slim` or `gcr.io/distroless/cc` — leaning `debian:bookworm-slim` for the shipping-day norm of needing a shell for the entrypoint's config-validation error path, not distroless) copies only the compiled `pv-server` binary and the static `out/` directory — no Rust toolchain, no Node/npm, no source tree survive into the runtime image. Rationale: keeps the shipped image small (single Rust binary + static HTML/JS/CSS, no interpreter needed for either half at runtime) and keeps the attack surface minimal for a security-sensitive self-hosted service — directly serves the "1 kontener, lekki" market positioning in PROJECT.md.
- **`wasm-pack`/`wasm-bindgen-cli` version pin lives in the builder stage exactly matching Phase 1's `build-wasm.sh` pin** — no new pin decision here, just carrying the existing one into the Dockerfile's builder stage so a container build reproduces the exact same wasm artifact a local dev build produces. `cargo build --release` for `pv-server` and the `wasm-pack build` step run in the same builder stage (both need the same Rust toolchain) but are logically separate build commands, allowing Docker layer caching to skip the wasm rebuild when only server-only Rust files change (and vice versa) via careful `COPY` ordering (copy `crates/pv-core` + `crates/pv-wasm` + wasm build script first, build wasm, then copy `crates/pv-server` and build the binary — so an edit to `pv-server`'s route handlers doesn't invalidate the wasm-build cache layer).
- **Single published `Dockerfile` at repo root**, no per-arch variants and no separate `docker/` directory of Dockerfile fragments — solo-indie pragmatism; a self-hoster clones the repo and runs `docker build .`. ARM64 (Raspberry Pi/Apple Silicon homelab boxes) is explicitly deferred (see `<deferred>`) — the same `Dockerfile` will *build* on ARM hosts via Docker's native multi-arch base images (no ARM-specific Dockerfile changes needed), but multi-arch published/tested images are not a v0.1 commitment.

### Area 2: Static file serving from axum (auto-accepted)

- **`tower-http`'s `ServeDir` + `ServeFile` SPA fallback serves the Next.js static export from the same axum `Router` and the same port as the API**, directly satisfying DEPLOY-01's "one port" requirement — no separate static file server (nginx-in-container, Caddy-in-container) inside the image, which would reintroduce the multi-process-in-one-container anti-pattern this project's "1 kontener" positioning exists to avoid. `pv-server/Cargo.toml`'s `tower-http` dependency gains the `fs` feature (currently only `trace`/`cors` are enabled). The router nests: `/api/*` and `/healthz` routes exactly as they exist today, then a fallback service serving `ServeDir::new(static_dir).not_found_service(ServeFile::new(static_dir.join("index.html")))` for everything else — the SPA-fallback pattern needed because `output: "export"` produces route-based HTML files (`out/settings.html`, etc. depending on Next.js's export routing mode) but any client-side route the Next.js router itself handles (hash-based state, not-yet-exported dynamic segments) must still resolve to *some* HTML shell rather than a bare 404.
- **Static directory path is configurable via `PV_STATIC_DIR` env var, defaulting to a fixed in-image path** (e.g. `/app/static`) — the Dockerfile's stage-3 `COPY --from=web-builder /web/out /app/static` writes to that same default, so the common case (running the packaged image) needs zero config, while local `cargo run` dev/test still works by pointing `PV_STATIC_DIR` at `web/out` (or being skipped entirely in `cargo test` contexts where no static dir exists — the fallback service is only mounted if the configured directory exists, logging a warning and serving API-only if not, rather than panicking, since integration tests build `AppState`/`router()` directly without ever running a real `web/out` build).
- **No server-side rendering, no Next.js Node runtime ships in the image** — this was already locked by `next.config.ts`'s `output: "export"` before this phase; Phase 7 only consumes that existing constraint, doesn't reopen it.

### Area 3: Config validation surface — fail-fast RP_ID/PUBLIC_URL rules (auto-accepted)

- **`Config::from_env()` gains an explicit validation pass, called from `main.rs` before any listener binds or `AppState` is built**, returning a descriptive `anyhow::Error` (not a panic, not a generic webauthn-rs error) that `main` prints and exits `std::process::exit(1)` on — matching this crate's existing `anyhow::Context`-chained error convention (`.context("invalid PV_DB_URL")` precedent already in `build_pool`). This directly satisfies DEPLOY-02's literal "fails immediately at startup with a specific, actionable error."
- **The localhost exception, precisely scoped**: validation is skipped (defaults are trusted as-is) only when `rp_id` is exactly `"localhost"` **or** `rp_origin`'s host is `localhost`/`127.0.0.1`/`::1` — i.e., the existing zero-config defaults (`PV_RP_ID` unset → `"localhost"`, `PV_ORIGIN` unset → `"http://localhost:3000"`) continue to work with no env vars set at all for local dev/testing, exactly as today. The moment either var is explicitly set to something else (a real deployment), full validation engages:
  1. `rp_origin` must parse as an absolute URL with a scheme (`http`/`https`) and a host — a bare domain string (`example.com` instead of `https://example.com`) is a common self-hoster mistake and gets its own error message naming the specific problem, not a generic parse failure.
  2. `rp_origin`'s scheme must be `https` unless its host is a localhost variant — WebAuthn's spec-level requirement (a non-localhost `http://` origin is rejected by every real browser's WebAuthn implementation at ceremony time; catching it at startup instead of "works in curl, silently fails when a user tries to register a passkey" is the entire point of DEPLOY-02).
  3. `rp_id` must equal `rp_origin`'s host, **or** be a registrable parent domain of it (the existing WebAuthn `rp_id`-is-origin-or-parent-domain rule, already documented in `config.rs`'s `rp_id` field doc comment) — a mismatch (e.g. `PV_RP_ID=vault.example.com` with `PV_ORIGIN=https://app.example.org`) fails with an error naming both configured values and the exact relationship required, not a downstream `webauthn-rs` `SecurityError` a user hits at registration time.
  4. `rp_id` must not itself be an IP address (the existing WebAuthn spec constraint webauthn-rs already enforces internally, but re-checking here produces a startup-time message instead of a runtime one) — flagged as **Claude's discretion whether to duplicate this check or trust webauthn-rs's own internal validation and just improve the error surfaced from `build_webauthn`'s existing `?` propagation**, since duplicating every rule `webauthn-rs::WebauthnBuilder` already enforces risks drift between two copies of the same validation logic; the concrete implementation call is deferred to plan time after re-reading `build_webauthn`'s current body.
- **A `PV_PUBLIC_URL` alias is *not* introduced** — the existing `PV_ORIGIN` env var already is the "public URL" the roadmap's success-criteria wording refers to (`RP_ID`/`PUBLIC_URL` is ROADMAP.md's plain-English framing of the same two concrete env vars this codebase already has: `PV_RP_ID` and `PV_ORIGIN`); introducing a second differently-named env var for the same concept would only create a self-hoster-facing ambiguity ("which one do I set?") with zero functional benefit. The reference `docker-compose.yml`/README env-var table uses `PV_RP_ID`/`PV_ORIGIN` as the canonical names throughout.

### Area 4: Migration-on-boot behavior (auto-accepted)

- **No new mechanism needed** — `build_pool()` already calls `sqlx::migrate!("./migrations").run(&db).await` unconditionally on every startup (existing code, confirmed in `crates/pv-server/src/lib.rs`), which already satisfies DEPLOY-01's "migracje na starcie" clause exactly as specified. Phase 7's only work here is verifying this survives being invoked from inside the packaged container (the `migrations/` directory must be embedded via `sqlx::migrate!`'s compile-time macro — already true, since the macro embeds migration SQL into the binary at compile time, not read from disk at runtime — so no `COPY` of the `migrations/` directory into the runtime image stage is needed at all; this is a meaningful simplification worth calling out explicitly since it's easy to assume otherwise).
- **SQLite pragmas: WAL mode + a `busy_timeout` are added to `build_pool`'s connect options**, since neither is currently set (confirmed — no `PRAGMA` anywhere in the codebase yet) and their absence is a real self-host correctness gap: a single-container deployment with the sync WebSocket's fan-out hub and multiple concurrent HTTP requests hitting one SQLite file is exactly the concurrency profile WAL mode + a busy timeout exist to make safe (avoiding `SQLITE_BUSY` errors under any concurrent write contention) — `SqliteConnectOptions::journal_mode(SqliteJournalMode::Wal)` and `.busy_timeout(Duration::from_secs(5))` (or similar) added alongside the existing `.create_if_missing(true)`. This is a small, targeted addition to existing code, not a new module.
- **Migration failure at boot is fatal, not logged-and-continued** — `build_pool`'s existing `.context("migrations")?` already propagates as a startup error via `main`'s `?`, matching DEPLOY-02's "fail loudly" philosophy applied consistently to DB state as well as config.

### Area 5: Volume & database path convention (auto-accepted)

- **Single mounted volume at `/data` inside the container**, with `PV_DB_URL` defaulting inside the image to `sqlite:///data/pv.db` (an image-specific default baked into the reference `docker-compose.yml`'s environment block, not a change to `config.rs`'s existing bare default of `sqlite://data/pv.db` — the code's own fallback stays relative/dev-friendly for `cargo run`, while the shipped compose file explicitly sets the absolute `/data` path to pair with its own volume mount). One named Docker volume (`pv_data:/data`) in the reference compose file — matches PROJECT.md's "SQLite na wolumenie" constraint exactly, and keeps backup/restore for a self-hoster reducible to "copy one file" (`/data/pv.db` plus its `-wal`/`-shm` siblings once WAL mode is on, documented explicitly in the README since a WAL-mode SQLite backup that skips the `-wal` file *will* lose recent writes).
- **No separate volume for the static web assets** — those are baked into the image at build time (Area 1/2), not runtime-mounted; only the database needs to persist across container recreation/image upgrades.

### Area 6: Reverse-proxy reference configs — nginx AND Caddy (auto-accepted)

- **Both nginx and Caddy reference configs are written and tested**, not just one — self-hosters split across both (Caddy for its auto-HTTPS simplicity, nginx for its ubiquity/existing-homelab-stack familiarity), and ROADMAP.md's phase success-criterion literally names both by example ("nginx/Caddy"). Both configs live at `deploy/nginx.conf.example` and `deploy/Caddyfile.example` (a new `deploy/` directory alongside the root `Dockerfile`/`docker-compose.yml`), each documented inline with comments explaining every non-obvious directive rather than assuming the self-hoster already knows why.
- **WebSocket upgrade headers are the load-bearing detail in both configs**: nginx needs the classic `proxy_set_header Upgrade $http_upgrade; proxy_set_header Connection "upgrade";` pair plus `proxy_http_version 1.1;` explicitly called out (nginx's `map $http_upgrade $connection_upgrade` idiom, or the simpler always-upgrade form since this proxy only ever fronts one backend); Caddy handles WS upgrades automatically via its `reverse_proxy` directive (no special config needed) but the Caddyfile still gets a comment noting this explicitly, so a self-hoster diffing the two configs doesn't wonder why nginx has extra lines Caddy doesn't.
- **Access-log token stripping for `/api/sync/ws?token=...` is documented as a required hardening step in both reference configs**, directly closing the gap Phase 5's `make_span` doc comment (WR-02) explicitly deferred to Phase 7: nginx's config includes a commented-out `map` snippet + custom `log_format` example that strips the query string for that one path (nginx has no simple per-location "redact this query param" primitive, so the documented approach is either a custom log format that omits `$request` in favor of `$uri` for that location block, or an explicit note to route access logs through a query-stripping `log_format` globally); Caddy's config uses its `log` directive's per-matcher scoping to the same effect, with an inline comment cross-referencing the same rationale (session tokens must never land in a reverse proxy's own persistent access-log files, mirroring pv-server's own already-shipped span redaction).
- **Both reference configs assume TLS termination is the reverse proxy's job, not the container's** — pv-server itself never terminates TLS (no cert/key config surface added to `Config`); Caddy's example shows its automatic-HTTPS one-liner, nginx's example assumes an existing cert (Let's Encrypt via certbot or similar) is already provisioned by the operator, since a from-scratch certbot walkthrough is out of this project's scope and well-trodden ground elsewhere.

### Area 7: Healthcheck (auto-accepted)

- **The existing `GET /healthz` route is reused as-is for both Docker's `HEALTHCHECK` instruction and the reference compose file's `healthcheck:` block** — no new endpoint needed (`{"status": "ok"}` already exists and requires no auth, no DB round-trip currently, which is *fine* for a liveness check but is called out explicitly as a known limitation: it currently proves the axum process is alive and routing, not that the SQLite pool is reachable). **Deferred, not added this phase**: upgrading `/healthz` to also ping the DB pool (`SELECT 1`) — flagged as a nice-to-have that would turn liveness into a real readiness check, but the current shape already satisfies "does `docker run` produce a container Docker/orchestrators can healthcheck," which is what DEPLOY-01 actually asks for; adding DB-touching logic to a currently-trivial, unauthenticated route is a deliberate small scope decision to revisit only if a real self-hoster hits a "container reports healthy but DB is wedged" case.
- Dockerfile's `HEALTHCHECK` instruction uses a minimal dependency-free check (`wget --spider` or similar, whichever is already present in the chosen `debian:bookworm-slim` base without adding a new package) rather than pulling in `curl` solely for this — exact tool choice left to plan/implementation time based on what's already in the base image.

### Area 8: Image publishing scope for v0.1 (auto-accepted)

- **Self-build only**: the deliverable is a working `Dockerfile` + `docker-compose.yml` (+ `.env.example`) that any self-hoster clones and builds themselves — this alone satisfies every literal DEPLOY-01/02 success criterion (all three are phrased around "a built image" / "`docker run`," none require a *published* registry image). Pushing to GHCR/Docker Hub, setting up a CI release pipeline, semantic-version image tags, and multi-arch manifest lists are all explicitly deferred past v0.1 (see `<deferred>`) — consistent with PROJECT.md's "solo indie, pragmatyczna kolejność" constraint and the fact that no requirement (DEPLOY-01/02) or `ROADMAP.md` success criterion mentions a registry at all.

</decisions>

### Established Patterns
- `anyhow::Context`-chained errors with a specific `.context("...")` message at every fallible operational boundary (`build_pool`'s `"invalid PV_DB_URL"`/`"db connect"`/`"migrations"`, `main.rs`'s `"bind {addr}"`) — Area 3's new config-validation errors follow the exact same idiom, not a new error-handling style.
- Doc comments that explicitly forward-reference which later phase will consume a piece of groundwork (`config.rs`'s `rp_id` comment, `main.rs`'s WR-02 comment, `routes/mod.rs`'s CORS comment) — a convention this project has used consistently since Phase 3-5; Phase 7's own new code should where relevant continue writing forward/back-references (e.g. the new validation function's doc comment should reference DEPLOY-02 and ROADMAP.md's success criterion #2 by name).
- Small, focused functions — the config-validation logic should land as a separate `validate()` or `Config::validate(&self) -> anyhow::Result<()>` method callable independently of `from_env()`, mirroring `kdf.rs`'s validated-input-length pattern (validate, then use) rather than inlining checks into `from_env`'s constructor body.
- No workspace-level `[workspace.dependencies]` entry needed for anything this phase touches (no new Rust crate dependencies anticipated — `tower-http`'s `fs` feature is additive to an existing dependency, not a new one; URL parsing for Area 3 can plausibly reuse a crate already in the dependency tree transitively, e.g. `url` via `webauthn-rs`, or a minimal hand-rolled scheme/host split given the narrow validation surface needed — concrete choice deferred to plan time).

### Integration Points
- `crates/pv-server/src/main.rs`: gains a call to `cfg.validate()` (or equivalent) immediately after `Config::from_env()?` and before `build_pool`/`build_webauthn` — the earliest possible point, so a misconfigured deployment never even opens a DB connection before failing.
- `crates/pv-server/src/routes/mod.rs`: `router()` gains the `ServeDir`/`ServeFile` fallback nest — likely as a new parameter (`static_dir: Option<PathBuf>`) threaded through `router()`'s existing signature, or a new `Config` field (`static_dir`) read once in `main.rs` and passed alongside `AppState` — exact wiring shape (extra `router()` param vs. folding into `AppState`) is a plan-time call; either is consistent with existing conventions (the crate already threads config-derived values like `rp_id` through `AppState`).
- New top-level files this phase creates: `Dockerfile` (repo root), `docker-compose.yml` (repo root), `.env.example` (repo root, documenting `PV_RP_ID`/`PV_ORIGIN`/`PV_DB_URL`/`PV_SESSION_TTL_HOURS`/`PV_ADDR` with self-hoster-facing comments), `deploy/nginx.conf.example`, `deploy/Caddyfile.example`, and a new `docs/SELF-HOSTING.md` (or a `## Self-Hosting` section in root `README.md` if one exists — verify at plan time) walking through the full `docker run`/`docker compose up` + reverse-proxy setup end to end, since DEPLOY-01/02's success criteria are explicitly about a documented, testable operator experience, not just working code.
- `crates/pv-server/tests/`: gains integration tests for `Config::validate()`'s decision table (localhost exception passes untouched; non-localhost + bad scheme fails with a named error; `rp_id`/`rp_origin` host mismatch fails; https-required-for-non-localhost fails) — unit-testable without any network/DB setup, following the existing `span_uri_field` pure-function/pure-test pattern already in `main.rs`'s own test module.

- ROADMAP.md's Phase 7 success criterion #3 names "nginx/Caddy" reverse-proxy configs explicitly by example — both, not either-or, are in scope (Area 6).
- Phase 5's `05-02-SUMMARY.md` and `main.rs`'s WR-02 doc comment are the direct source requiring the access-log token-stripping documentation (Area 6) — this is not a new idea introduced by this phase, it's closing a gap Phase 5 explicitly deferred here by name.

<deferred>
## Deferred Ideas

- **Auto-TLS inside the container** (e.g. embedding a Caddy-as-library or acme-client directly in pv-server) — deliberately out of scope; TLS termination is the reverse proxy's job (Area 6), consistent with "1 kontener" meaning the *application* container, not reimplementing what nginx/Caddy already do well. Revisit only if user research post-v0.1 shows self-hosters specifically want zero-reverse-proxy TLS.
- **ARM64/multi-arch published images** — the Dockerfile itself should build fine on ARM hosts (no ARM-specific code paths anticipated), but testing and publishing a multi-arch manifest is deferred; homelab Raspberry Pi/Apple Silicon users can `docker build` locally on their own arch in the meantime.
- **PostgreSQL as an alternative backend** — PROJECT.md's context section names Postgres as a klocek/building-block option ("SQLx (SQLite domyślnie, opcja Postgres)") but no DEPLOY requirement or ROADMAP.md phase asks for it in v0.1; SQLite-on-volume is the only shipped path this phase.
- **Backup/restore tooling** (a `pv-server backup` subcommand, scheduled snapshot cron, S3-upload helper, etc.) — out of scope; the README's self-hosting doc documents the manual "copy `/data/pv.db*`" procedure (Area 5) as sufficient for v0.1, consistent with "no required external services."
- **Registry publishing / CI release pipeline** (GHCR/Docker Hub push, semver image tags, GitHub Actions release workflow) — Area 8's explicit scope decision; self-build-only for v0.1.
- **`/healthz` upgraded to a DB-touching readiness check** — Area 7's explicit scope decision; the current liveness-only shape ships as-is.
- **A `PV_PUBLIC_URL` env var alias** — Area 3's explicit scope decision; `PV_ORIGIN` remains the sole canonical name, no alias introduced.

</deferred>
