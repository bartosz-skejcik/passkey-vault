<objective>
Package the whole system into a single buildable Docker image and a reference `docker-compose.yml`: a three-stage `Dockerfile` (Rust+WASM builder → Node builder → slim runtime) that produces one binary serving the API, the sync WebSocket, and the static Next.js export on one port; a compose file with a named volume and the correct `PV_ADDR=0.0.0.0:8620`/`PV_DB_URL=sqlite:///data/pv.db` overrides; and a self-hosting quickstart doc a solo self-hoster can follow start-to-finish.

Per 07-CONTEXT.md (locked): single root-level `Dockerfile`, no per-arch variants, no `docker/` fragment directory — self-build only for v0.1 (no registry publishing). Per 07-RESEARCH.md Pattern 1 (the single most load-bearing fact this phase surfaced): `web/package.json`'s `prebuild`/`predev` npm lifecycle hooks invoke `scripts/build-wasm.sh`, which needs the Rust toolchain + `wasm32-unknown-unknown` + `wasm-bindgen-cli` — the Node-only build stage must never re-trigger that hook (`npm ci --ignore-scripts` + `npx next build` directly, consuming the Rust stage's already-built WASM artifacts via `COPY --from=rust-builder`). This plan depends on 07-01 because the Dockerfile's `ENV PV_STATIC_DIR` and the compose file's environment block are only meaningful once `router()`'s `static_dir` parameter and `Config::validate()` exist.

Purpose: DEPLOY-01 (buildable single container, one port, migrations-on-boot, SQLite-on-volume) and the documentation half of DEPLOY-02 (self-hoster-facing explanation of the fail-fast behavior Plan 07-01 implements).
Output: `Dockerfile`, `.dockerignore`, `docker-compose.yml`, `.env.example`, `docs/SELF-HOSTING.md`, a `README.md` link.

    `crates/pv-wasm` (confirmed by direct read). Cargo refuses to run ANY command — including

    `lib.rs` for either crate would let that `cargo build` "succeed" against zero real code, and `wasm-bindgen`
    would then happily emit glue with no crypto exports at all — silently baking a broken, non-functional WASM
    artifact into the image with no build-time error to catch it. So the stub trick applies to `pv-server` ONLY —
    the one workspace member this stage never actually builds — while `pv-core`/`pv-wasm` get their REAL source

## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Repo checkout / build context → Docker image layers | Anything not excluded by `.dockerignore` becomes part of the shipped image or its build cache |
| `.env.example`'s documented defaults → a self-hoster's own `.env` → `docker-compose.yml` | The reference file's defaults are the first thing a self-hoster copies verbatim — they must never be plausible-looking-but-insecure for a real deployment |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|------------------|
| T-07-04 | Information Disclosure | `.dockerignore` | medium | mitigate | Explicit `.env` exclusion (distinct from the committed `.env.example`) prevents a self-hoster's real secrets file from ever being picked up into a build context/image layer if one happens to exist at the repo root at build time |
| T-07-05 | Tampering (misconfiguration) | `docker-compose.yml`'s default `PV_RP_ID`/`PV_ORIGIN` fallbacks | low | accept | Defaults are `localhost`/`http://localhost:8620` — Plan 07-01's `Config::validate()` already treats these as the trusted zero-config case; a self-hoster who copies the compose file unmodified for a real deployment still cannot reach a broken-but-running state, since any change away from these defaults re-engages full validation |
| T-07-06 | Denial of Service (operational) | `docs/SELF-HOSTING.md`'s backup guidance | low | mitigate | Explicit WAL-sibling-file callout prevents the common "I backed up `pv.db` but lost my last hour of writes" self-host failure mode |
