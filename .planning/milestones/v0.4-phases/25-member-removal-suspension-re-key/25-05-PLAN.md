<objective>
Prove, with genuinely adversarial tests, the three hardest guarantees Phase 25 makes: that the re-key
transaction is actually atomic under a GENUINE mid-write fault (an injected failure firing AFTER earlier
writes in the same transaction already ran and would otherwise durably persist — not a pre-write
validation rejection, which is a real but DIFFERENT property this plan also tests and keeps distinct;
and not a SQL-level constraint, since no real constraint in this schema is reachable mid-batch under
SQLite — verified empirically this session, see Task 1); that a large batch of key rewraps never reuses
a nonce; and that removal cost and scope are provably bound to the target collection alone, even in a
database holding a much larger unrelated dataset. This plan is test-only work against Plan 25-03's
already-built `remove_member`, plus the `test-support`-feature-gated fault-injection hook Plan 25-03
exposes for exactly this purpose — no OTHER new production code unless a real bug is found.

Purpose: CONTEXT.md names the fault-injection test "the phase's sharpest deliverable" and explicitly
warns against a test that cannot fail against a broken implementation; KEY-06 and SC 6 are explicitly
two different proofs that must not be conflated; SEC-07 needs statistical teeth a small batch cannot
provide.
Output: a hardened `tests/family_removal.rs` and two new `pv-core` nonce-uniqueness property tests.
</objective>
