<objective>
Close v0.4 audit Blocker 2 (a direct-share capture-update silently mis-encrypts under the recipient's
own User Key, permanently corrupting the owner's item) and Warning 1 (the extension offers an edit
affordance on a `hidden_password` collection-scoped item that the server will always 403), plus the
dormant Warning-3 twin in the provider-ceremony write-back path — all three are the identical
`collectionId === null` / rank-comparison blind spot at slightly different call sites.

Per 28-CONTEXT.md B-4/B-5/B-10 and 28-RESEARCH.md §B/§C: mirror `web/src/lib/vault/itemCapabilities.ts`'s
already-server-verified-correct rule (`sharedToMe` refuses unconditionally; `hidden_password` is
structurally excluded from `edit`, never rank-compared) into `capture-handler.ts`'s
`confirmUpdateLogin` gate — the same gate 27-07's `ReadOnlyAccessError` already occupies, before any
encrypt call. The toast UI must announce the refusal proactively (at propose time, before an Update
button is ever offered), not react to a failed confirm.

Purpose: today this is silent data corruption (Blocker 2) and a UI that offers what it cannot honor
(Warning 1) — both are the milestone's signature failure mode (a server-correct boundary the client
never consults) recurring inside a single client.
Output: `capture-handler.ts`'s gate conforms to the server; the extension popup's capture-toast opens
directly in an honest blocked state for both cases; `persistUpdatedProviderItem` carries the identical
refusal, dormant but present.
</objective>
