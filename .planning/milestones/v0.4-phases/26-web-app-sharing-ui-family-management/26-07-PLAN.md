# The three dissolved backstops this plan owes (STATE.md Blockers/Concerns, Phase 24 entry)
#4 zero-one-many: zero shared folders -> `folder.pickerEmpty` renders in place of the `<select>`,
  WITH `folder.pickerCreateNew` still available (a picker with nothing to pick must still offer the
  way to create the first option, never a dead end). One or many render the same native
  `select select-bordered` — no special-casing exactly one option.
#5 long folder-name option truncation: every `<option>` carries a `title` attribute equal to its
  full visible text — the one truncation mechanism a real `<option>` element supports; DaisyUI/
  Tailwind classes do not apply inside native `<option>` rendering, so this is the correct tool,
  not a workaround.
#6 selected-folder value truncation: the picker's own containing element must not overflow for a
  long selected name (`w-full`, no fixed width shorter than a realistic long name) — the closed
  native-select value itself is browser-rendered and out of this component's control, so the test
  is about the CONTAINER never overflowing, not about the browser's own internal ellipsis handling.

# Existing precedent (native select idiom, do not introduce a custom combobox)

  `<select select-bordered>` idiom — CollectionPicker matches this exact native-select choice
  (UI-SPEC E8 explicitly requires staying with native `<select>` for the `title`-attribute
  truncation-handling reason above, never a custom listbox/combobox primitive).
web/src/lib/vault/collections.ts (Plan 26-05) — `useCollections()` — the real data source.
