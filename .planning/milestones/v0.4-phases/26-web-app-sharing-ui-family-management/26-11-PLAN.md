# The trap this plan must not fall into (RESEARCH.md Pitfall 2, explicitly flagged)
GET /api/families/members/{user_id}/access (getMemberAccess) is OWNER-ONLY
(FamilyMembership<RequireEdit>) and answers "what can this OTHER member reach" from the owner's
viewpoint -- it fails for a non-owner caller asking about their OWN sharing, and even for an
owner it answers the wrong question (not "what am I sharing"). Do NOT use it here. The real data
source is the caller's OWN GET /api/vault/collections (any member, RequireRead) plus each
collection's GET /api/vault/collections/{id}/access plus GET /api/vault/items/{id}/shares
(Plan 26-04) for the caller's personally-shared items.

# Client-side aggregation precedent to adapt (not copy wholesale -- different question)
web/src/components/settings/RemoveMemberDialog.tsx:241-303 (resolveAccess) -- its
dedup-at-higher-access idiom (via accessRank/higherAccess, Plan 26-06's shared module) is the
pattern to reuse for merging a folder-level grant and a direct item_shares grant for the SAME
item, appearing exactly once at the higher level -- but it solves "one target member's inbound
access from the owner's view"; this plan's aggregation is "everything the CALLER personally
shares, grouped by recipient" -- a different, new aggregation, not a drop-in reuse of that
function itself.

# Data sources (all already exist, already access-controlled server-side)
web/src/lib/vault/collections.ts (Plan 26-05) -- useCollections().
web/src/lib/vault/api.ts -- getCollectionAccessList(collectionId) (existing),
listItemShares(itemId) (Plan 26-04). The caller's directly-shared items are the subset of
useVaultItems() where isShared is true and collectionId is null or undefined.
web/src/components/vault/AvatarStack.tsx (Plan 26-06) -- reuse for the "By folder" tab's per-row
recipient summary.
