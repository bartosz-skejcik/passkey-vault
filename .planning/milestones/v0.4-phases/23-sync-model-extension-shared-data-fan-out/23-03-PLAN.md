<objective>
Give the server the ability to say WHO caused a stale-revision conflict (SYNC-06's "attributes the
conflict to the other member by name") without breaking `ApiError::Conflict`'s existing wire shape
for its other 15+ call sites (RESEARCH.md Pitfall B), and extend `collections.rs`'s membership-change
handlers to emit `EntityType::Collection` events — closing the other half of SYNC-05's live-effect
guarantee (a just-added member's WS starts receiving relevant events promptly; a just-removed
member's stops, and is never itself notified of the removal through that same channel, per Pitfall
17's closing warning, carried into CONTEXT.md as a hard constraint).

Per D-03 (CONTEXT.md, Bartek's decision): attribution is the member's full email, never local-part-
only or anonymous. Per D-04: personal items keep today's exact generic copy — attribution is added
ONLY where the item is actually shared.

Purpose: prove the "who" half of SYNC-06 server-side (client wiring is Plan 23-05's job), and prove
SYNC-05's add/remove-membership live-effect guarantee with a real test, not an inference from
`resolve_recipients` reading fresh every time.
Output: `ApiError::StaleRevisionShared`; `update()`'s conflict branch returns it for shared items;
`collections.rs::add_member`/`revoke_access` emit `EntityType::Collection` events to the correctly-
scoped recipient set; new Rust tests for both.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| conflict response -> caller | The 409 body now discloses another user's email address to a caller who has SOME access to the same item |
| membership-change event -> just-removed user | The event published on `revoke_access` must never reach the user being removed |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-23-09 | Information Disclosure | `StaleRevisionShared.last_editor_email` | medium | accept | Disclosure is scoped to a caller who already holds edit access to the SAME item (they triggered the conflict by attempting an edit) — revealing a co-editor's email to a fellow co-editor of the same shared resource is the explicit, locked product decision (D-03), not an incidental leak. |
| T-23-10 | Information Disclosure | `revoke_access`'s post-delete event | high | mitigate | Recipient set for the published event is queried strictly AFTER the DELETE commits, so the just-removed `target_user_id` is structurally absent — proven by the live test in Task 2, not merely inferred from query ordering. |
| T-23-11 | Repudiation | `last_editor_user_id` | low | accept | Column is set from the authenticated `SessionUser`/`Membership` extractor's own resolved caller id on every write — never client-supplied, so it cannot be spoofed to attribute a conflict to the wrong person. |
</threat_model>
