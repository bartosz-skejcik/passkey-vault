<objective>
Add the phase's three new read endpoints — the read half of SYNC-04's "becomes visible to every
other member" and SYNC-08's "shared data arrives via a separate, additively-introduced query,
personal scope unchanged" — expanding outward from Plan 23-01's proven fan-out core. Per D-01
(RESEARCH.md's Open Question 1 recommendation, adopted): the per-collection fetch is path-based
(`/api/vault/collections/{id}/sync`) so it reuses `Membership<Collection, RequireRead>` verbatim
with zero extractor changes, rather than a query-param design that would need a new axum extractor
variant and an unverified `serde_urlencoded` repeated-key assumption (RESEARCH.md Pitfall C). Per
D-02 (Open Question 2, adopted): direct item_shares-on-personal-items get their own reserved
"direct" bucket in the revisions-map response, with their own small dedicated fetch endpoint — not
folded into a per-collection shape, since they have no collection to key by.

Purpose: prove SYNC-07's zero-leakage-to-non-members guarantee and SYNC-08's "personal scope
literally unchanged" guarantee structurally (adversarial tests, not spot-checks), matching the
route-sweep's own "prove absence structurally" posture from Phase 22.
Output: three new GET endpoints, route-table registration, updated cardinality tripwires, and
adversarial Rust tests for SYNC-07/SYNC-08.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| unrelated authenticated caller -> shared read endpoints | Any logged-in user can call all three new GET endpoints; only membership resolution stands between them and another family's data |
| WS side-channel -> collection mutation | A non-member's open WS connection must never observe a frame about a collection they cannot query directly |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-23-05 | Elevation of Privilege | `pull_shared_collection` | high | mitigate | Gated by `Membership<Collection, RequireRead>` — a non-member's request never reaches the handler body (404 before any query runs), same discipline as every other `membership_routes()` entry. |
| T-23-06 | Information Disclosure | `pull_shared_collection`'s new item query | high | mitigate | Query is `WHERE collection_id = ?` with NO `user_id` filter (Pitfall A) — correctness depends entirely on the extractor's prior authorization, verified by the adversarial non-member test in Task 2. |
| T-23-07 | Information Disclosure | `pull_shared_revisions` | high | mitigate | `FamilyMembership<RequireRead>` gate + the SAME join shape `Collection::resolve_access` uses, scoped to `recipient_user_id = caller` — zero-leakage by construction, never a hand-rolled WHERE (SEC-06 precedent). |
| T-23-08 | Spoofing | `pull_shared_direct` | medium | mitigate | `SessionUser`-only gate mirrors `/api/sync`'s own scoping exactly — every row filtered by `item_shares.recipient_user_id = session.user_id`, never a client-supplied id. |
</threat_model>
