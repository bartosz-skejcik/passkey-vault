<objective>
Close 27-VERIFICATION.md Blocker 2 (a provider ceremony can present a partial candidate picker):
`handleCredentialsGet` (`provider-ceremony.ts`) currently snapshots `getItems()` immediately after
resolving the User Key, with no barrier on the shared-item/Collection-Key caches also having
settled this MV3 wake -- so a cold wake where a personal passkey matches the RP while a shared one
for the SAME RP is still resolving renders an incomplete picker as if it were complete. Add a
resolution barrier -- `ensureItemsHydrated()` (already exists, currently unused by this file) plus
a new `ensureSharedItemsHydrated()` -- that the ceremony awaits before its candidate snapshot. The
zero-candidate fallthrough (27-10, `27-10-PLAN.md`'s own pinned regression) is untouched: the new
barrier only changes WHEN `getItems()` is read, never whether a genuine zero-match falls through.

Purpose: a security ceremony that silently omits an eligible credential can make the user pick the
wrong one, or conclude the shared passkey is gone entirely -- exactly what this backstop, already
present in `must_haves` since 27-06's own plan, was meant to prevent, and what 27-06-SUMMARY.md's
own coverage block never actually addressed.
Output: `vault-store.ts::ensureSharedItemsHydrated()`, `provider-ceremony.ts`'s new await pair, a
regression test proving both the ordering and that it closes the race.
</objective>
