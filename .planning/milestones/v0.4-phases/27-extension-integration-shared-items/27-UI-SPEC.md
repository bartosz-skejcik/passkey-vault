# Phase 27 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **Scope note.** The surface this phase touches is the **browser extension popup** — a ~380px-wide
> WXT MV3 surface (`extension/entrypoints/popup/`) — not the web app. Phase 26 already shipped the
> full sharing UI (share dialogs, family management, avatar stacks) in `web/`; this phase does not
> re-litigate any of it and does not port it verbatim. The popup is picker-only (09-CONTEXT.md's
> "picker-only depth, not full CRUD," still true in Phase 27, EXT-06's "no in-popup forms" doctrine
> unchanged) — its job is to make shared items **fillable and legible**, never to manage sharing.
>
> `27-CONTEXT.md`'s four UX decisions (UX-1..UX-4) were offered to Bartek and dismissed — every choice
> below is Claude's own, applying the offered recommendation, and is recorded as such (not
> Bartek-locked). This UI-SPEC turns those four decisions into a precise, executable visual contract;
> it does not reopen them.
>
> `components.json` is absent and shadcn is not part of this stack (DaisyUI 5 + Tailwind v4 +
> `packages/pv-ui`, unchanged across every prior UI-SPEC, re-confirmed this session) — the shadcn
> init gate is not applicable and was not re-asked.
>
> **Surfaces this phase owns:**
>
> 1. **The shared-item corner badge** (UX-1/EXT-12) — the one new visual primitive this phase
>    introduces, applied consistently to every existing `h-8 w-8` icon-frame row in the popup:
>    `ItemListView.tsx`'s "Wszystkie" rows (`ItemIconTile`), `AutofillItemRow.tsx`/`TotpFillRow.tsx`'s
>    "Na tej stronie" rows (their own plain icon frame), `ItemDetailView.tsx`'s header tile (smaller
>    variant), and `ProviderCeremonyView.tsx`'s multi-match candidate rows.
> 2. **`ItemListView.tsx`'s shared-folder row subtitle** (UX-1/UX-2) — mixed inline into "Wszystkie",
>    existing sort control unchanged, badge + subtitle are the ONLY differentiators.
> 3. **`ItemDetailView.tsx`'s hidden-password masking** (UX-4/SHARE-03) — reveal+copy suppression for
>    a `hidden_password`-access field, the honesty note, the shared-folder note, and the explicit
>    (honest) answer to "what does read-only suppress that full-edit doesn't": nothing, because the
>    popup has no edit affordance at all, for any item.
> 4. **`ProviderCeremonyView.tsx`'s shared-passkey distinguishability** (EXT-09/EXT-10's UI ask) — the
>    badge + a one-line note on both the single-match and multi-match candidate presentations.
> 5. **The pending-decrypt (Collection Key not yet re-derived this MV3 wake) degraded row** — a
>    visible, non-interactive skeleton row, never a silent omission (inherited obligation, this
>    phase's own additional context).
>
> **Security-UI discipline (docs/UI-DESIGN.md):** the hidden-password honesty note is security UI —
> plain DM Sans, neutral tone, no alarm styling, no Fuzzy Bubbles. Everything else in this phase
> (the badge, the folder subtitle, the skeleton row) is ordinary product chrome and stays inside the
> popup's existing token set.

## Spacing Scale

Declared values (must be multiples of 4) — identical numeric scale to every prior phase, **no new exception to the scale itself**:

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Badge offset (`-bottom-1 -right-1`), icon-to-label gaps |
| sm | 8px | Row internal gaps (`gap-2`, unchanged from every existing row) |
| md | 16px | Popup content-card horizontal padding (unchanged) |
| lg | 24px | Unused new this phase |
| xl / 2xl / 3xl | 32/48/64px | Unused new this phase — the popup has no page-level spacing tier |

**Badge geometry (new, both multiples of 4):** 12px diameter (`h-3 w-3`), positioned at a −4px offset
(`-bottom-1 -right-1`) from its host frame's bottom-right corner — sized to sit legibly on the
smallest frame it must fit (`ItemDetailView`'s `h-6 w-6` header tile) without covering the tile's own
glyph/favicon center, and reused unchanged (same 12px/−4px pair) on every larger frame (`h-8 w-8` row
tiles, the ceremony's `h-8 w-8` `KeyRound` frame) rather than scaling per-frame — one constant badge
size across every host, matching this codebase's own precedent of a single fixed control size reused
across contexts (e.g. `ItemIconTile`'s own two fixed `SIZE` variants, never a continuous scale).

**Ring width — 1px (`ring-1 ring-base-100`), not a new exception.** `docs/UI-DESIGN.md`'s own geometry
section states the whole app's elevation language is "1px bordery + stopnie tła zamiast cieni" — this
is that existing doctrine applied to a new element, not a new one. (`AvatarStack.tsx`'s `ring-2` is
its own component's separation need at a different, larger 20px scale; it is not the app-wide default.)

**Icon glyph sizes are not drawn from this scale** (existing precedent: `ItemIconTile`'s row/header
icon sizes are 18px/14px, neither a multiple of 4) — the 4px-multiple rule governs layout spacing
(gaps, padding, offsets), not icon rendering size. The badge's `Users` glyph is sized `8` to fit its
12px circle, following that same precedent, not a spacing-scale violation.

## Typography

Reused, not reopened — identical roles/sizes/weights to the popup's existing type scale established
in Phases 9–13:

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 16px | 400 | 1.5 |
| Label | 14px | 400 | 1.4 |
| Heading | 20px | 700 for the `ItemListView` popup title; 600 for the `ItemDetailView` item-name heading | 1.2 |
| Display | not used | — | — |

- **Body (16px)** → item name / row primary text (`ItemListView` rows, `ItemDetailView` field values) — unchanged, shared items render at the identical weight/size as personal ones (the badge, not typography, is the differentiator).
- **Label (14px)** → the shared-folder subtitle (replaces the existing username/issuer subtitle for a shared row, same slot, same size/color — `text-sm text-base-content/60`), field labels, the hidden-password honesty note (`text-xs`, one step below Label — see note below), the ceremony's shared-passkey note.
- **Heading (20px)** → `ItemListView`'s title, `ItemDetailView`'s item-name heading — unchanged.
- **Display** → not used, same as every prior extension-popup phase (no hero/display-scale text exists in this popup at all).

**Existing 12px/500 micro-label scale (unchanged, not reopened):** `ItemListView`'s "Wszystkie" heading
and `OnThisPageSection`'s "Na tej stronie" heading already use `text-xs font-medium` (12px) — untouched
by this phase, listed here only so it isn't mistaken for an undeclared size when it appears in the
same views this UI-SPEC touches.

**Hidden-password honesty note — 12px (`text-xs`), one step below Label, not a new size tier:**
matches `web/src/components/vault/DetailPanel.tsx`'s own `hidden-password-recipient-note`
(`text-xs text-base-content/70`) exactly — this is the existing footnote-scale precedent for a
secondary explanatory line under a field, reused verbatim rather than promoted to Label scale (which
would visually overweight a footnote relative to the field it explains).

## Color

Unchanged 60/30/10 split and exact OKLCH/hex values from `docs/UI-DESIGN.md` / `packages/pv-ui/tokens.css`
— **no new hue.** One new *semantic* use of an already-reserved color, stated so it is not mistaken
for an oversight:

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | base-100/base-200 | Popup top strip + content card (unchanged) |
| Secondary (30%) | base-200/base-300 | Row hover/borders (unchanged) |
| Accent (10%, coral `#E16540`) | primary | Existing "Fill" CTA, "Full screen" pill, "+" FAB — **untouched by this phase**, no new coral usage introduced |
| **New use this phase — secondary (błękit `#8DCDFF`)** | text-secondary | **Reserved exclusively for the shared-item badge's `Users` glyph** (`text-secondary` inside the badge circle). This is the identical reserved bucket `web/`'s own `AvatarStack.tsx` icon variant already uses for the same passive "this involves other people" signal (`docs/UI-DESIGN.md`: secondary = "linki, info-akcenty" — an info-accent, not a call to action) — the same semantic applied to a second surface, not a new one. Teal (`accent`, `#00CDB7`) stays reserved for passkey semantics only (the app's own "konsekwentnie" rule) — never repurposed to mean "shared," which would collide with the passkey-type `KeyRound` glyph already rendered teal in the ceremony view and the item-type badge convention. |
| Warning (`#FFBE00`) | alert-warning | **Genuine, permanent decrypt-failure only** (the "row decrypted metadata but ciphertext integrity check failed" case — mirrors `web/`'s existing `undecryptable-item-banner`). **Never** used for the pending-decrypt-this-wake state (see below) — that state is transient and expected, not a fault. |
| Destructive (`#FF5861` error) | not used | No destructive action exists in this phase's own scope (EXT-06 keeps sharing management, including revocation, entirely in the web app). |

**The pending-decrypt (Collection Key not yet re-derived) row is deliberately neutral, not
amber/red — explicit deviation from a naive "loading = warning" instinct.** It is drawn with the
DaisyUI `skeleton` shimmer only (`bg-base-300`-family, theme-neutral, the same primitive
`OnThisPageSection.tsx`'s own loading branch already uses) — no `alert`, no icon implying a problem.
Re-deriving the Collection Key from the already-recovered User Key on an MV3 wake is expected to
resolve in well under a second; treating it as a warning would misrepresent an ordinary, momentary
state as a fault, the same "don't dress up a benign state as an error" discipline Phase 26 already
applied to `identity.fingerprintUnavailable`.

**Accent reserved for:** the existing Fill/Full-screen/FAB CTAs, unchanged, named above — nothing new
competes for that budget this phase. **Secondary reserved for:** the shared-item badge glyph only,
named above.

| Element | Copy |
|---------|------|
| `share.hiddenPasswordExtensionNote` — rendered under a `hidden_password`-access field in `ItemDetailView.tsx`, in place of the (suppressed) reveal/copy buttons. **Deliberately NOT a verbatim reuse of web's `share.hiddenPasswordRecipientNote`** — that string says "you can still copy and use it," which is false in this surface (copy is suppressed here, only autofill still works, per UX-4). A surface where the affordances differ needs its own accurate sentence; reusing the web string here would itself be dishonest. | PL: `Właściciel udostępnił to hasło jako ukryte — to okno je maskuje i nie pozwala go skopiować. Automatyczne wypełnianie na stronie nadal działa. To tylko zabezpieczenie interfejsu — klucz i tak jest w rękach odbiorcy, więc to nie jest ochrona kryptograficzna.` <br> EN: `The owner shared this password as hidden — this popup masks it and won't let you copy it. Autofill on the page still works. This is an interface protection only — you hold the key either way, so it isn't a cryptographic one.` |

**Copywriting honesty constraints (hard requirements, re-stated for the checker):**

1. `share.hiddenPasswordExtensionNote` must never be shortened to drop any of its three claims — that copy is suppressed *and* autofill still works *and* the recipient holds the key regardless. Dropping any one of the three makes the remaining two misleading (dropping the third makes it sound cryptographically enforced; dropping the second makes UX-4's own rationale for the level invisible; dropping the first would be simply false once reveal/copy are actually suppressed).
2. The pending-decrypt row must never render `alert-warning`/error styling or copy implying a fault — see Color.
3. `sync.itemUndecryptableWarning` is reserved for a genuine, non-transient decrypt failure; it must never fire for the ordinary MV3-wake pending-decrypt window (see Phase-Specific Notes §4 for how the two are told apart).
4. `sharing.sharedItemLabel` stays direction-neutral ("Shared item," never "Shared by you"/"Shared with you") — the popup has no data path this phase to reliably tell those apart for every row cheaply, and a wrong direction claim would repeat the exact CR-02-class lie Phase 26 already found and fixed once (see Phase-Specific Notes §5).

### 1. This discharges Phase 26's own carried-forward obligation

Phase 26's `AvatarStack.tsx` narrow-viewport caveat (D-3) explicitly recorded: "Phase 27 inherits the
obligation to choose its OWN narrow-popup fallback for the extension… it may not silently reuse the
full circle-stack verbatim in a ~360px popup without re-deciding." UX-1's corner badge (E1 above) is
that decision — discharged at both the decision level (27-CONTEXT.md) and, now, the implementation
level (this UI-SPEC), not merely re-flagged.

### 2. Data this UI-SPEC assumes exists — a plan/architecture dependency, not a rendering branch to invent around

`packages/pv-ui/vault/types.ts`'s `VaultItem` already carries `isShared?`, `collectionId?`, and
`accessLevel?` as optional fields (added in Phase 26 for the web app) — no type-level plumbing is
needed for those three. What this UI-SPEC's E1/E2/E3 do require, and what is **not yet implemented
anywhere in the extension** as of this session:

- A resolved, decrypted **folder-name lookup** for a given `collectionId` (A-1's ported collections
  store) — E1's subtitle and E3's `share.itemSharedOnCollectionNote` both need it.
- `AutofillMatch` (`extension/lib/autofill/types.ts`) gains an optional `isShared?: boolean` (and,
  for the folder-subtitle case, an optional `folderName?: string`) — currently metadata-only with
  neither field.
- `ProviderCredentialCandidate` (`ProviderCeremonyView.tsx`) gains the same two optional fields, for
  E4's badge/subtitle.

None of these are UI decisions — they are the minimum data contract this spec's rendering rules
depend on, called out so the plan does not treat E1/E4 as satisfiable from data that doesn't exist yet.

### 3. i18n promotion recommendation — `access.*` labels

`access.readOnly` / `access.fullEdit` / `access.hiddenPassword` / `access.unknown` currently live only
in `web/src/lib/i18n/dictionary.ts`, not in the shared `pv-ui/i18n/common.ts` (34 keys today, byte-
identical between both surfaces). These four are genuinely surface-independent constants (identical
PL/EN value regardless of where they render) — this phase does not strictly need them rendered
anywhere in the popup UI itself (no access-level pill is specified above; UX-4's masking is driven by
the raw `hidden_password` check, not a rendered label), but if a future plan wants to show one (e.g.
inside a debug/detail affordance), it should promote these four into `pv-ui/i18n/common.ts` rather
than duplicating them a second time into `extension/lib/i18n/dictionary.ts` — the same "one place"
discipline `accessLevel.ts`'s own header comment already states for its own logic.

### 4. Telling "pending" apart from "genuinely broken" (E2 vs. E3's backstop row)

E2's pending-decrypt row and E3's genuine-decrypt-failure banner must never be conflated (Copywriting
honesty constraint 3) — they are different signals with different honest copy. The distinguishing
condition is architectural, not visual-only: a row is "pending" exactly until the background's
Collection Key cache for that item's `collectionId` (or the identity keypair, for a direct share) has
completed its re-derivation attempt for this MV3 wake; it is "genuinely broken" only once that
re-derivation has succeeded (the key is available) and the decrypt attempt against the row's own
`enc_data` still fails. A plan that renders the warning banner merely because decrypt hasn't happened
*yet* — rather than because it was attempted and failed — would misfire this distinction and violate
constraint 3.

### 5. Why the badge stays direction-neutral

Phase 26's CR-02 code-review finding (`26-CONTEXT.md`/`ItemRow.tsx`) is the load-bearing precedent
here: rendering an outgoing-share indicator on an item the viewer does not actually own told the user
"you are sharing this" about something a third party owns — a genuine UI lie, found and fixed once
already. The popup has no per-row recipient-list fetch this phase (E1 is explicitly *not* `AvatarStack`
— UX-1 chose a badge precisely so the popup avoids that N+1 fetch shape), so it has no cheap, reliable
way to compute "shared BY me" vs. "shared WITH me" per row without re-introducing exactly that
`sharedToMe`/`isShared` direction-tracking machinery Phase 26 needed a dedicated field for. Rather than
risk a wrong or approximated direction claim, `sharing.sharedItemLabel` states only the fact both
directions share ("other people are involved with this item") — true regardless of direction, never a
claim this popup cannot back with real data.

### 6. EXT-10's signature-counter spike has no UI surface — stated so its absence isn't mistaken for a gap

EXT-10's shared-passkey signature-counter design spike (27-CONTEXT.md A-8) is entirely a server/RP-facing
protocol question — whatever the spike concludes, it has no user-visible consequence this UI-SPEC could
specify (no counter value, no anomaly state, is ever rendered anywhere in this product's UI, shared or
personal). This is the correct, honest absence, not an oversight — mirroring Phase 26 E9's own
"no dedicated surface is the correct answer" precedent for KEY-01's success case.
