<objective>
A-5's write-routing fix: `capture-handler.ts`'s `confirmNewLogin` needs no change (a browser-detected new capture is always personal by construction — there is no folder-picker in this flow), but `confirmUpdateLogin` currently re-encrypts an EXISTING item's new content unconditionally under the personal User Key regardless of that item's real scope — for a shared login, this silently corrupts it for every other collection member on the very next write.

Purpose: 27-CONTEXT.md's A-5 names this exact gap ("`capture-handler.ts` currently calls `vault-api.ts` create/update directly and lets the next sync pull reconcile... an unrouted write silently produces a row nobody can decrypt"). This is the write-side twin of 27-04's read-side fail-loud discipline — AEAD makes a wrong-key decrypt fail loudly (safe) but a wrong-key encrypt succeed silently (catastrophic), and this file's `confirmUpdateLogin` is the one remaining unrouted write path in the phase's file inventory.
Output: `confirmUpdateLogin`'s collection-aware encrypt dispatch + read-only refusal gate.
</objective>
