# Phase 24 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **Scope note.** This phase introduces exactly two new visual surfaces: (1) the invitee-facing
> `/invite/{id}#<secret>` landing/Join/failure state machine, rendered as a new top-level view
> inside `web/src/app/page.tsx`'s existing single-page shell (see `24-CONTEXT.md`'s "single-page
> shell" architectural note — a real Next route at this path is unreachable in production), and
> (2) a deliberately minimal owner-side "Invite someone" panel added as a new tab inside the
> existing `SettingsPanel.tsx` drawer. No new visual language is introduced — every token, class,
> and component below is reused verbatim from `docs/UI-DESIGN.md`, `packages/pv-ui/tokens.css`, and
> the existing `AuthCard`/`RegisterForm`/`LoginForm`/`SettingsPanel`/`DeleteConfirmDialog`/
> `CopyToast`/`ErrorToast` components. `components.json` is absent and shadcn is not part of this
> project's stack (DaisyUI 5 + `packages/pv-ui` is the standing, already-decided design system per
> `CLAUDE.md`/`docs/UI-DESIGN.md`) — the shadcn init gate is not applicable and was not re-asked.

## Typography

Same 4 roles, same sizes/weights/line-heights as every prior phase in this project — **not reopened**:

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Label | 14px | 400 | 1.4 |
| Body | 16px | 400 | 1.5 |
| Heading | 20px | 700 | 1.2 |
| Display | 28px | 700 | 1.15 |

- **Heading (20px)** → the invite Join screen's own heading ("Dołącz do {family}?" / "Join {family}?"), same `text-[20px] font-bold leading-[1.2]` treatment as `AuthCard`'s `h1`. **Explicit decision, matching Phase 15's precedent: stays at Heading, not Display**, even though this is a decisive one-time moment — the family name is user-chosen and variable-length, and escalating to Display would make an unusually long family name a real wrap/overflow risk in the 400px card for no functional gain (see UI Considerations' long-text row).
- **Body (16px)** → the fingerprint honesty sentence, the visibility-honesty note on the collection-scope picker, the failure-state message body, dialog/confirmation body copy.
- **Label (14px)** → all form field labels, the fingerprint value itself (monospace, see below), the "Invited by {email}" line, the current-account notice.
- **Display (28px)** → not used anywhere in this phase's scope (no dashboard/hero-metric surface exists here).

Unchanged 60/30/10 split and exact OKLCH/hex values from `docs/UI-DESIGN.md` / `packages/pv-ui/tokens.css` — **no new palette, no new hue**:

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | base-300 — `#1F1F1F` dark / `#EDEBE9`-class light | Page canvas behind the invite landing view (reuses `AuthCard`'s `bg-base-300` wrapper — the invite view is unauthenticated-adjacent chrome, no sidebar). **The `bg-base-300` class reference is authoritative**; resolve the light hex from `tokens.css` rather than from this annotation. (`#FCFBFA` is base-200 light, not base-300 — corrected after UI-checker review.) |
| Secondary (30%) | `#262626` base-100 dark / `#FFFFFF` base-100 light | The invite card surface itself; the "Family" tab's content area inside `SettingsPanel` (same drawer surface as every other tab) |
| Accent (10%, coral `#E16540`) | primary | The Join CTA button, the "Załóż konto i dołącz"/"Create account & join" submit button, the "Wygeneruj link"/"Generate link" owner-side button — all reuse `btn btn-primary`, the same class every other primary action in this codebase uses. Coral stays reserved for actions/brand per `docs/UI-DESIGN.md`; it is **not** used for the fingerprint. |
| Destructive | `#FF5861` error | "Unieważnij link"/"Revoke link" confirmation only (`btn btn-error`, mirrors `DeleteConfirmDialog`'s `AlertTriangle` + `btn-error` pattern) |

**Teal (`#00CDB7`, `accent` token) — reserved for identity/passkey meaning only, one new use this phase:** the `Fingerprint` icon in the invite-context header (icon only, `text-accent`, matching the existing "passkey/identity = teal" domain semantic already established by `PasskeyUnlockButton.tsx`/`EnrollPasskeyDialog.tsx`). The fingerprint **value text itself** stays neutral (`font-mono text-sm text-base-content/80`), not teal — only the icon carries the accent color, keeping the 10% budget disciplined (an entire 64-character hex string in accent color would visually overwhelm the card).

**Failure-state severity — explicit deviation, stated so it isn't mistaken for an oversight:** the single indistinguishable "invite no longer valid" message (Surface 3) uses `alert-warning` (amber `#FFBE00`), **not** `alert-error` (red). Rationale: the overwhelming majority of hits on this state are an honestly-expired or already-used link, not an attack — greeting an innocent latecomer with alarm-red contradicts `docs/UI-DESIGN.md`'s "communicate security through calm and clarity, not black/padlocks" principle, and mirrors Phase 15's own "a real heads-up is `alert-warning`, not automatically `alert-error`" doctrine for this exact class of non-catastrophic dead-end.

**Accent reserved for:** the `Fingerprint` icon (teal) and the primary-action buttons named above (coral). Nothing else in this phase's scope competes for either budget.

**Amendment (Quick task 260803-inv, post-ship taste review of the live invite card):**

1. `invite.joinHeading` changed to PL `Dołączyć do rodziny {family}?` / EN `Join the {family} family?` (was `Dołączyć do {family}?` / `Join {family}?`) — the bare family name alone read wrong in Polish.
2. `invite.fingerprintLabel` dropped its `{inviter}` interpolation — now a fixed PL `Odcisk tożsamości` / EN `Identity fingerprint` (was `Odcisk tożsamości {inviter}` / `{inviter}'s identity fingerprint`). `invite.invitedBy`, rendered directly above it, already names the inviter; repeating the same (often-truncated) email as this label's heading read as a templating accident. This also removes a truncation/overflow site that existed only because of the repeated variable text.
3. `invite.fingerprintHonesty`'s PL string had its second `{inviter}` occurrence ("z {inviter} telefonicznie") changed to "z tą osobą telefonicznie" ("with that person"), matching EN's existing single-mention-plus-pronoun structure. The honesty claim (rule 1 below) is unchanged in substance — this is a de-duplication of the literal email string within one sentence, not a weakening of the requirement.
4. Net effect on the invite-landing card: the inviter's email now appears **twice** (once in `invite.invitedBy`, once in `invite.fingerprintHonesty`) instead of four times, in both the fingerprint-present and fingerprint-unavailable branches.
5. Out of this UI-SPEC's nominal scope but rendered inside this phase's invite surface: `RegisterForm.tsx`'s shared master-password warning (`auth.irrecoverableWarning`) changed from `alert alert-warning` to `alert alert-warning alert-soft` (daisyUI 5's built-in softer alert treatment — 8%-tint background, no drop shadow, same `--color-warning` role) so it no longer outweighs the primary `btn btn-primary` CTA beneath it on the invite "register and join" screen. No new colour introduced; the warning stays fully visible and legible. This change applies to every `RegisterForm` render (also the normal `/` sign-up screen), since the component is shared verbatim.

**Copywriting honesty constraints (hard requirements of this phase, not polish — re-stated here for the checker):**

1. `invite.fingerprintHonesty` must never claim or imply that displaying the fingerprint constitutes verification. It states plainly that the two people must compare it themselves, out of band. This is the phase's single most safety-critical string.
2. `invite.honestVisibilityNote` must never claim or imply that the family owner cannot see what's shared with a member — the opposite is true (owner always retains access), and the copy says so explicitly. This generalizes CONTEXT.md's "hidden-password is a UI guarantee, never a cryptographic one" principle to the one sharing-adjacent moment this phase actually surfaces (the collection-scope invite); the literal hidden-password access level itself is Phase 26 scope and has no UI here.
3. `invite.failureMessage`/`invite.failureHint` must never interpolate or imply a specific cause (expired vs. consumed vs. revoked vs. concurrent-loser) or confirm the invite/family ever existed.

## UI Considerations

Runtime probe (`ui-consideration-probe`) proposed **34 applicable** state considerations across the 7
described surfaces. This section is the authoritative resolution of all 34 — it supersedes the
narrower 14-row table the researcher authored inline, which under-covered the per-element axis.

**Resolved: 27 covered, 7 backstop, 0 unresolved.** A `backstop` row is a real obligation, not a
pass: it means the resolution is "prove it with a held-out UI-state test" rather than a truth
statement the planner can lift directly. At verify time an unwired backstop routes to
`insufficient_spec → human_needed` — that surfacing is intended, not over-flagging.

Empty-state and error-state **copy** lives in `## Copywriting Contract`; rows below reference those
keys rather than restating them.

### E1 — Invite landing card (form · static-content · interactive-control)

| Category | Status | Resolution |
|----------|--------|------------|
| loading | ✅ covered | Centered `Loader2` + `invite.loadingLabel` while public metadata is fetched. No skeleton — the card is small and short-lived. Same idiom as `EnrollPasskeyDialog.tsx`. |
| error | ✅ covered | Any fetch failure (expired/consumed/revoked/unknown/malformed/network) collapses into the single `invite.failureMessage` state. Indistinguishability is the phase's core security decision — see E4. |
| empty | ⛑ backstop | The family name is required by the bootstrap form (E7) and non-null at creation, so an empty `{family}` should be unreachable. Not asserted anywhere today. **Backstop:** a test that renders the Join screen with an empty-string family name and asserts the heading does not collapse to `Join ?` or a bare verb. |
| partial | ✅ covered | Metadata arrives as one object — there is no half-loaded render. If any required field (`family`, `inviter`) is absent the view treats the response as invalid and routes to the E4 failure state rather than rendering a partial header. |
| overflow | ✅ covered | Card is fixed at `max-w-[400px]`; the heading stays 20px (not 28px) specifically so a long family name does not force reflow. Family name and inviter email both `truncate` with a `title` carrying the full value. |
| long-text | ✅ covered | Same `truncate` + `title` treatment. The fingerprint block is fixed-width by construction (a hash rendering), so it cannot be the overflow source. |

### E2 — Inline registration branch (form · interactive-control)

| Category | Status | Resolution |
|----------|--------|------------|
| loading | ✅ covered | `disabled` + busy label spanning **both** network calls (register, then redeem) as one continuous submit — the user must never see the button return to idle between them and think the flow stalled. |

## Phase-Specific Notes

### 0. View resolution & mount priority (`web/src/app/page.tsx`)

The invite view is resolved **once at mount**, the same idiom as the existing `extUnlockNonce`/`pendingUrlAction` state (`useState(() => ...)` reading `window.location` synchronously before first render), and is checked **before** the `authed === null` / `!authed` / vault branches — an invite link must work identically whether the visitor has no session, an existing session, or is already unlocked:

```
const [invite] = useState<{ inviteId: string; inviteSecret: string } | null>(() => {
  if (typeof window === "undefined") return null;
  const m = window.location.pathname.match(/^\/invite\/([^/]+)\/?$/);
  const secret = window.location.hash.slice(1);
  return m && secret ? { inviteId: m[1], inviteSecret: secret } : null;
});
```

`invite.inviteSecret` is held **only** in this React state (component-tree memory) for the lifetime of the flow — never written to `localStorage`/`sessionStorage`, matching `24-CONTEXT.md`'s explicit "the secret lives in the fragment, persisting it would create a durable copy of a credential" constraint. It must survive the inline-register round trip unchanged (the invite view stays mounted across that sub-flow — RegisterForm/LoginForm render as children of the SAME invite-view component, never as a navigation away from it).

When `invite !== null`, render `<InviteLandingView inviteId={...} inviteSecret={...} onDone={...} />` and return early — it takes over the **entire page**, same precedent as `ExtUnlockBridge`'s `extUnlockNonce` branch immediately above it in the existing code. `onDone` clears local invite-related URL state and lets the normal `authed`/vault branches render on the next tick (with `pendingSelectCollectionId` set — see §3).

**Hash hygiene:** never call `history.replaceState` in a way that drops `window.location.hash` while the flow is in progress (unlike `pendingUrlAction`'s cleanup, which only ever strips query params). After a *successful or already-consumed* redemption, it is safe and recommended to replace the URL down to the bare origin/path (secret is spent, no further value in keeping it in the address bar/history) — but never before.

### 1. Invite Landing + Join Confirmation (Surfaces 1–3)

**Container:** reuses `AuthCard`'s exact wrapper vocabulary — `flex min-h-screen items-center justify-center bg-base-300 p-4` outer, `w-full max-w-[400px] rounded-box border border-base-300 bg-base-100 p-6` card. No sidebar/top bar in any state, including the "session already exists" branch — this is a one-time landing moment, not the vault shell.

**State machine (one component, four states):**

1. **`loading`** — spinner + `invite.loadingLabel`. Fetches invite public metadata (inviter email, family name, inviter fingerprint if published) using only `inviteId` — never sends `inviteSecret` in any request (it's a client-side-only decryption key, per `24-CONTEXT.md`'s crypto decisions).
2. **`invalid`** (Surface 3) — renders on ANY of: 404/expired/consumed/revoked/malformed. **No context header renders in this state** — no family name, no inviter, no fingerprint (`24-CONTEXT.md`'s FAM-05 "no vault metadata pre-redemption" extends here: an invalid link must leak nothing, including whether it was ever real). Just: `AlertTriangle`-free (this is `alert-warning`, not an alarming icon — see Color) `invite.failureMessage` heading, `invite.failureHint` body, `invite.failureCta` linking back to the normal `/` sign-in.
3. **`valid`** — metadata loaded. Renders a **persistent context header** (present in every sub-branch below):
   - `Users` icon + `invite.joinHeading` (Heading role, interpolated family name, `truncate`+`title`)
   - `invite.invitedBy` (interpolated inviter email, `truncate`+`title`)
   - Fingerprint block: `Fingerprint` icon (teal) + `invite.fingerprintLabel` + the fingerprint value itself, grouped into 4-character chunks over the 64-hex-char SHA-256 digest (`xxxx xxxx xxxx …`, 16 groups), `font-mono text-sm`, wrapped across 2–3 lines inside the 400px card — **or**, if the inviter has no published public key, `invite.fingerprintUnavailable` in its place (see UI Considerations)
   - `invite.fingerprintHonesty` immediately below, Body role, `text-base-content/70`

   Below the context header, exactly one of two branches renders, decided by whether a session token already exists (`getSessionToken() !== null`, same helper `LoginForm`/`page.tsx` already use):

   - **(a) No session:** embeds `RegisterForm`/`LoginForm` in place (toggle between them exactly as `AuthCard`'s own login/register toggle works today), defaulting to `RegisterForm` per `24-CONTEXT.md`'s "brand-new user registers inline" framing. `RegisterForm` gains one new optional prop, `submitLabel?: string`, defaulting to its current `auth.registerSubmit` value when absent (zero behavior change for the normal `/` auth screen) and set to `invite.registerAndJoinCta` here. Both forms' existing `onAuthed` callback is wired to immediately call the redeem endpoint (not to the normal `page.tsx` vault transition) — from the user's perspective, submitting the form both creates/logs into the account AND joins the family in one continuous action, no second screen.
   - **(b) Session exists:** `invite.currentAccountNotice` (the CURRENT session's email — never assume it matches the invite) + a primary `invite.joinCta` button (`btn btn-primary`) + a secondary `invite.joinAsDifferentAccount` link/button (`btn btn-ghost btn-sm`). Clicking the latter clears the session client-side (same `clearSessionToken`/`clearStoredEmail`/`lockVault` sequence as `Sidebar.tsx`'s logout — **without** `window.location.reload()`, since a reload is unnecessary here and this view must stay mounted with `invite` state intact) and re-renders this same view into branch (a).
4. **`joining`** — busy variant of whichever branch was active (disabled buttons, `invite.joining` label).

**Redemption outcomes:**
- Success, newly joined → `onDone({ selectCollectionId })` (collection id only if the invite carried one) — the invite view unmounts, `page.tsx`'s normal authed/vault tree takes over.
- Success, already-a-member (server no-ops per `24-CONTEXT.md`) → brief `invite.alreadyMemberNotice` (reuse `ErrorToast`'s info-variant styling, `alert-info`), then the same `onDone(...)` transition.
- Failure after a fresh register/login → `invite.joinFailedRetryable` state (see UI Considerations), never the unified `invalid` message (the account is real; only the join attempt failed) — unless the retry itself now returns invalid/expired, in which case it falls through to state 2.

### 2. Owner-side "Invite someone" (Surface 4 — `SettingsPanel.tsx`)

Adds a fifth tab, `settings.tabFamily` (`Users` icon), to the existing `tabs tabs-bordered` strip in `SettingsPanel.tsx`, alongside Passkeys/Sessions/Security/Import-Export — same `tabClass()` helper, no new tab visual language.

Tab content, top to bottom:

1. **If no family exists yet** (owner has never created one — detect via `GET /api/families/members` returning 404): `family.bootstrapHeading`/`family.bootstrapBody`, one `family.nameLabel` input, `family.createCta` button (`btn btn-primary`). On success, falls straight through to step 2 below — no separate confirmation screen.
2. **`invite.sectionHeading`** (`UserPlus` icon).
3. **Scope picker** — `invite.scopeLabel` + a `select select-bordered w-full` with two options, `invite.scopeWholeFamily` and `invite.scopeFolder`. Selecting `scopeFolder` reveals a second `select` (`invite.folderPickerLabel`, populated from `useFolders()`) **and** the `invite.honestVisibilityNote` line directly beneath it (only visible in this sub-state — see the honesty constraint above). If `useFolders()` is empty, the `scopeFolder` option is disabled with `invite.folderPickerEmpty` as inline helper text.
4. **Expiry picker** — `invite.expiryLabel` + a `select select-bordered w-full` with three options (`invite.expiry1h`/`invite.expiry24h`/`invite.expiry7d`), **`invite.expiry7d` pre-selected by default** per `24-CONTEXT.md`'s locked decision. No indefinite/never-expire option exists.
5. **`invite.generateCta`** button (`btn btn-primary`).
6. **After generation**, replaces the form above with: a read-only `input input-bordered w-full font-mono` showing the full link, an `invite.expiresAt` line (interpolated formatted local date/time), a `Copy` icon button whose accessible name comes from the new key `invite.copyLinkAria` (PL `Skopiuj link zaproszenia` / EN `Copy invite link`), applied as `aria-label` since the button carries no visible text, that calls `copyWithAutoClear()` from `packages/pv-ui/clipboard.ts` and surfaces the result through the **existing `CopyToast` component** (field label `"Link zaproszenia"`/`"Invite link"`) — **not** a plain non-clearing toast, because the link's fragment is a decryption-capable secret, the same security class as a vault password (see Color/Design System). A `btn btn-ghost btn-error`-styled `invite.revokeConfirmTitle`-triggering button sits alongside it — it must carry a **visible** text label (PL `Unieważnij` / EN `Revoke`, reusing `invite.revokeConfirmConfirm`); if it ever ships icon-only, it needs its own `aria-label` key on the same pattern as `invite.copyLinkAria` — gated by a `DeleteConfirmDialog`-shaped confirmation (`AlertTriangle`, `invite.revokeConfirmBody`, `invite.revokeConfirmConfirm` as `btn-error`, reused `delete.cancel`).
7. **After revoke, or once the shown invite's own expiry passes,** the panel reverts to the create form (step 2) — no history, no list, matching the explicit "no pending-invite list/audit view" boundary. Generating a second invite is always allowed by the API; the UI simply never shows more than the most recent one.

### 3. Post-join redirect

`onDone({ selectCollectionId })` (§1) sets a one-shot flag in `page.tsx`, mirroring the existing `pendingUrlAction` idiom rather than inventing a new mechanism: if `selectCollectionId` is present (collection-scoped invite), the vault's `filter` state is set to that collection once `unlocked` becomes true, so the shared collection is the first thing the new member sees. A family-only invite (no collection) leaves `filter` at its default (`{ kind: "all" }`) — there is nothing collection-specific to select.

### 4. Cross-phase gap this UI-SPEC surfaces (flag for the plan, not silently assumed)

The Join screen's fingerprint block (Phase 22's own explicit design intent for "the member-join moment") can only render a real fingerprint if the **inviter** already has a published identity keypair. Per `.planning/STATE.md`'s KEY-01 traceability, the client-side "generate a keypair on first unlock if none exists" trigger is Phase 26/27 scope and does **not exist yet** when Phase 24 ships — meaning, without further action, `invite.fingerprintUnavailable` would be the *common* case rather than the exception, undermining the feature the moment it's introduced. **Recommendation for the plan:** have invite-creation (owner side, §2) opportunistically call the same idempotent `PUT /api/identity/keypair` Phase 22 already built (generating locally if the owner has none yet, no-op if they already do) before generating the link — a narrower, earlier trigger than Phase 26's "every unlock" one, scoped to exactly the moment this phase needs it. This is a planning recommendation, not a UI token; `invite.fingerprintUnavailable` remains the correct UI fallback regardless of whether the plan adopts it, since a pre-v0.4 inviter's very first invite could still race ahead of any lazy generation.

`24-CONTEXT.md`'s "specifics" flag a `Referrer-Policy` header check (the `invite_id` path segment should not travel to third-party origins via `Referer`) — this is a server/deployment-config concern, not a UI token, and is not re-specified here; it is repeated only so the plan doesn't lose it between documents.
