<objective>
Extend the server-origin ceremony window (`ExtUnlockBridge.tsx`, `mode="signin"`) with a
master-password sign-in path, so AUTH-01's locked mandate ("the ceremony window is the ONLY
sign-in surface, always") does not strand every account without an enrolled server passkey —
including the entire e2e test fleet, which currently signs in via the popup's own password
form (dying in Plan 15-03/15-04).

Per AMENDMENT (15-CONTEXT.md): the ceremony window offers BOTH passkey and password sign-in,
passkey-first presentation. Implementation follows RESEARCH.md's Assumption A1 (LOCKED by the
amendment): relay `{passwordB64, email}` through a new `unlock.serverCeremony.relay` payload
variant into the already-tested `handleUnlockPassword(passwordBytes, email)` — never
re-derive Argon2id material in the ceremony-window page (D-05's whole-project invariant: only
`entrypoints/background/*.ts` touches WASM/pv-core).

This plan is the risk-first foundation for the whole phase: it MUST land and be proven working
before Plan 15-03 deletes the popup's own sign-in form, so there is never a commit point with
zero working sign-in paths (phase sequencing guidance).

Purpose: prove the window-based full-sign-in path end-to-end before removing the popup's
password-sign-in fallback.
Output: a working password-sign-in branch through the ceremony window, covered by unit tests
on both the web (`ExtUnlockBridge.tsx`) and extension (`server-unlock.ts`,
`content-relay.content.ts`) sides.
</objective>
