# Phase 18 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Phase framing (read before the rest of this document):** this is a **behavioral formalization phase, not a visual redesign**. The consent window (`ProviderCeremonyView`, provider-ceremony popup/fallback-window) and the ceremony window (server-origin sign-in/unlock, `ExtUnlockBridge.tsx`) already exist and their *visual content* is untouched by this phase — it was built in Phases 9/12/13/15 and centering/self-close/scroll-cap already landed live in quick task 260720-16k (commit `40d1965`). UX-02's job is to verify that behavior live and add a durable regression check so it cannot silently drift; XBR-03's job is a security-review verdict, not a build. Accordingly this UI-SPEC's center of gravity is `## Window Geometry & Lifecycle Contract`, not typography/color/spacing — those sections below exist only to formally declare "carried over unchanged, do not touch" so the checker and executor have an explicit non-regression baseline.

## Window Geometry & Lifecycle Contract

The design contract for this phase. Two `browser.windows.create()` call sites exist in the extension, both sharing one pure centering helper (`extension/lib/window-geometry.ts`, `centeredWindowPosition()`). Neither call site is touched visually by this phase — the contract below is what "formalized" must mean: verified live once more, then locked behind a regression check so a future edit cannot silently break it.

### Surface Inventory

| Surface | Call site | Fixed size (W×H) | Opens via | Trigger |
|---|---|---|---|---|
| **Consent window** | `provider-ceremony.ts` → `tryOpenFallbackWindow()` | 380×460 | `browser.windows.create({ type: "popup", url: "popup.html", ... })` — mounts `ProviderCeremonyView` (create / single-match / multi-match `get()`) | Fallback path, tried only when `browser.action.openPopup()` (`tryOpenPopup()`, Chrome's native popup) is unavailable or throws. Firefox is the browser that empirically always takes this fallback (hence the code comments' "Firefox consent fallback window" naming), but the code itself is not browser-sniffed — Chrome would take the identical path under the same failure condition. |
| **Ceremony window** | `server-unlock.ts` → `startServerUnlock()` | 480×640 | `browser.windows.create({ type: "popup", url: "<baseUrl>/?pv-ext-unlock=<nonce>&pv-mode=<mode>", ... })` — opens the user's own configured `pv-server` web app, `ExtUnlockBridge.tsx` (PRF or password sign-in/unlock) | Always this path, on **both** Chrome and Firefox (per Phase 15's Vaultwarden-model unification — this is the sole full-sign-in / passkey-unlock affordance, not a Firefox-only fallback). |

### Centering Formula (shared, pure, unit-tested)

`centeredWindowPosition(current: WindowGeometry | null | undefined, newWidth, newHeight): { left?, top? }` — `extension/lib/window-geometry.ts`.

- `current` sourced from `browser.windows.getLastFocused()` at call time (wrapped in try/catch by each call site's own `getCurrentWindowGeometry()`; `null` on any rejection, never thrown).
- **Guard:** returns `{}` (no `left`/`top` keys at all) unless `current` is non-null/non-undefined **and all four** of `current.left`/`.top`/`.width`/`.height` are `typeof === "number"` and `Number.isFinite(...)`. A *partial* geometry object (e.g. missing `height` only) is treated identically to a fully-missing one — falls back to `{}`, never a partial computation.
- **Formula (when the guard passes):** `left = Math.round(current.left + (current.width - newWidth) / 2)`, `top = Math.round(current.top + (current.height - newHeight) / 2)`.
- **`{}` result contract:** callers spread the result into `windows.create()`'s options object; an empty `{}` means "let the browser pick a default placement," never a crash and never a guessed position.
- **Negative/off-screen results are intentionally NOT clamped** (13-REVIEW-3.md finding IN-02, accepted-not-a-defect): centering a wider new window (480 or 380) over a narrower/edge-positioned source window can legitimately compute a negative `left`/`top`. This is correct behavior for a monitor positioned left of/above the primary in a multi-monitor setup; Chrome/Firefox themselves clamp a genuinely off-screen window back on-screen. **The regression check added by this phase must not assert `left >= 0`/`top >= 0`** — that would encode a wrong invariant.

### Sizing Rationale (carried over unchanged — do not "round to the 8-point grid")

| Window | Size | Why this exact size |
|---|---|---|
| Consent window | 380×460 | Width matches `popup.html`'s fixed `width: 380px; overflow: hidden` body exactly — the real content width, not a round number. Height (460, revised from an earlier 420px pick in the same quick task) covers the worst case: multi-match picker = site row (20px) + title/body (60px) + scroll-capped candidate list (208px, `max-h-52`) + decline-only buttons (40px) + 3 gaps (48px) + `p-6` padding (48px) ≈ 424px, leaving ~36px headroom. The common single-match/create case is far shorter (~250–280px). |
| Ceremony window | 480×640 | Pinned in Phase 13-06 (`13-06-PLAN.md`), unchanged by this phase and by quick task 260720-16k (which added only centering + `focused: true`, not a resize). Sized for the web app's own sign-in/unlock form content (PRF and password branches). |

Both windows also set `focused: true` (added in 260720-16k) so they take input focus immediately on open.

### Self-Close / Lifecycle Contract

**Consent window** (`App.tsx`, `ProviderCeremonyView` mounted):

| Event | Behavior |
|---|---|
| Confirm (create, single-match, or multi-match row-click) | `resolveCeremony()` sends `provider.resolveChoice`; on send success, `window.close()` unconditionally. |
| Explicit decline | Same `resolveCeremony()` path (`itemId: null`) — same unconditional close on send success. |
| Ceremony resolved elsewhere (background's `WR-03` abandon-timeout fires while this popup instance is still showing the ceremony view, or a second popup/window races it) | `browser.storage.session.onChanged` listener detects `PENDING_CEREMONY_KEY` removal; if this instance's current view is `"provider-ceremony"`, calls `window.close()` too — never leaves a stale ceremony view behind. |
| `provider.resolveChoice` send itself fails (e.g. background unreachable) | **Does NOT close** — `ceremonyStatus` is set to `"failed"` and the window stays open showing that state, so the user can see/retry rather than the window vanishing on a failure they never saw. This is an intentional, documented exception to "always self-close," not a gap. |

**Ceremony window** (`server-unlock.ts` background + `ExtUnlockBridge.tsx` page, two independent closers):

- **Page-side** (`ExtUnlockBridge.tsx`): on an `ok: true` ack for either the PRF or the password branch, calls `window.close()` itself, best-effort (wrapped in try/catch — some environments don't allow script-initiated close).
- **Background-side** (`completeServerUnlock()`'s `closeWindowIfAny()`, `browser.windows.remove(windowId)`): closes on — timeout/expiry (`CEREMONY_TIMEOUT_MS = 120_000`, via `browser.alarms`), mode-mismatch rejection (`invalid-mode-payload`), `already-signed-in`, and every terminal outcome of the actual crypto step (PRF `unwrap-failed`/success, password `invalid-credentials`/`unwrap-failed`/success).
- **Intentionally does NOT close** on: `forbidden-origin` (the sender was never a legitimate ceremony to begin with — a later legitimate delivery of the same nonce must still be able to succeed, so nothing about the pending record is touched) and `args.failed === true` (`"ceremony-failed"` — `ExtUnlockBridge` is actively showing the user an explicit terminal message right now; yanking the window shut out from under someone reading it would be worse UX than leaving it open for manual dismissal). Both are documented, intentional exceptions — not to be "fixed" toward a universal auto-close by this phase.
- **Multiple concurrent starts:** the newest `startServerUnlock()` call wins — it closes any prior ceremony window and overwrites its (now orphaned) nonce, regardless of whether the two calls share the same mode.

**Chrome's native path is out of scope:** `tryOpenPopup()` (`browser.action.openPopup()`) never calls `browser.windows.create()` and has no centering/sizing/self-close behavior of its own to formalize — it is the browser's native toolbar popup, dismissed by the platform, not this code.

### Regression Coverage — what must be asserted, not how

Per CONTEXT.md's Claude's-discretion note, the *mechanism* (unit test over `centeredWindowPosition`/the `windows.create()` call args, a live-Firefox e2e assertion in the `e2e-firefox/` harness lane, or both) is the planner's call — prefer whatever is deterministic and CI-runnable, matching the established `run-core.cjs`/`probe-request-xray.cjs` npm-script-per-lane pattern (`extension/package.json`'s `test:e2e:firefox:*` scripts). This UI-SPEC fixes the **assertions**, so whichever mechanism is chosen is checked against the same truths:

1. Given a full, finite `current` window geometry, both call sites compute `{ left, top }` via the exact formula above (already unit-covered — `window-geometry.test.ts`, 7 tests — but the plan must confirm this coverage still holds live, not just via mocks: SC #1's "verified live" half).
2. Given missing/partial/non-finite `current` geometry, both call sites pass `{}` (no `left`/`top` keys) — the browser's default placement is observed, never a crash and never a guessed position.
3. Both windows open at their fixed size (380×460 / 480×640) and `focused: true`, unconditionally of geometry availability.
4. The consent window closes on confirm and on decline (both observable live — window handle/id no longer exists after the action) and stays open on a failed `resolveChoice` send.
5. The ceremony window closes on a successful PRF or password ceremony, and on the alarm-driven 120s timeout; it does **not** close on `forbidden-origin` or on an explicit `ceremony-failed` terminal message (assertion 5 must NOT regress those two into "always closes" — they are contract, not bugs).
6. A negative computed `left`/`top` (edge-positioned/multi-monitor source window) is passed through unclamped — the regression check must not assert non-negativity.

A live-Firefox verification pass (screenshot or probe-output evidence, per `13-FF-WEBAUTHN-RESEARCH.md`'s and `14-03`'s established evidence discipline: never `driver.executeScript()` for anything realm-sensitive, though geometry/window-count reads are not realm-sensitive so ordinary Selenium window-handle calls are fine here) is required alongside whatever automated check lands, per SC #1's explicit "verified live AND covered by a regression test."

## XBR-03 Decision Gate (Not a Design Spec)

Per the conservative policy locked in `18-CONTEXT.md`: an in-page closed-shadow-DOM consent panel ships **only** on an unambiguous security-review clear; otherwise the window model above stands and XBR-03 closes as rejected-with-reason. **This UI-SPEC deliberately does not design, size, token, or copy-contract the in-page panel** — doing so would front-run a review that has not happened yet and could bias the build toward a rejected design. If a future phase's review clears the panel, that phase gets its own UI-SPEC. The only artifact this phase owns for XBR-03 is the security-review verdict itself (a `18-SECURITY.md`-style document — outside this file's scope) and its mirror into `REQUIREMENTS.md`/`PROJECT.md`.
