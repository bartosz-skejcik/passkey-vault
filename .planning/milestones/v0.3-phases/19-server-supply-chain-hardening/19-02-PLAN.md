<objective>
Surface webauthn-rs's ALREADY-ACTIVE counter-regression rejection with a distinguishable log line
and a persisted DB flag, instead of letting it disappear into a generic `?e` Debug-printed
"ceremony failed" warning indistinguishable from a wrong signature or expired challenge (SEC-04).

Purpose: this session's research (19-RESEARCH.md Open Question 1, source-verified against
`webauthn-rs-core-0.5.5/src/core.rs:1154-1174`) found `require_valid_counter_value` defaults to
`true` and is never overridden in `build_webauthn()` — a genuine counter regression is ALREADY
hard-rejected with `WebauthnError::CredentialPossibleCompromise` today. CONTEXT.md's "do NOT
hard-fail ceremonies" instruction predates this finding; it is interpreted here as "do not newly
weaken the library's existing protection" (interpretation (a) from Open Question 1) — this plan
adds operator-visible signal on an ALREADY-rejected path, it does not change whether the ceremony
succeeds or fails. This is a deliberate deviation from a literal reading of CONTEXT.md's wording,
recorded here per the research's explicit recommendation to surface it to Bartek in the plan.

Output: a new additive `counter_anomaly_at` column; a shared `handle_finish_auth_error()` classifier
reused by all 3 finish handlers; a regression test proving both the fail-closed ceremony behavior
and the new flag/log signal.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Authenticated `SessionUser` (prf_wrap, unlock_finish) | `session.user_id` is server-trusted (bearer-token-resolved), never client-supplied |
