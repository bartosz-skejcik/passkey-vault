<objective>
Implement the extension-scoped PRF passkey locked by 09-CONTEXT.md's AMENDMENT 2026-07-15: a dedicated passkey with rpId = the extension's own ID (the ONLY rpId `navigator.credentials.get()` accepts from a `chrome-extension://` popup page — empirically proven via Playwright/CDP), enrolled post-unlock and used for real PRF unlock in the popup. This spans all three tiers: a new pv-core domain-separation constant + derivation function (`b"pv:ext-prf-unlock:v1"`, exported through pv-wasm as `WasmWrappingKey.fromExtPrf`), a minimal SessionUser-gated blob-CRUD endpoint on pv-server (`/api/extension-passkeys` — NO webauthn-rs involvement; the blob is opaque), and the extension background's enroll/unlock orchestration with five new message kinds.

Purpose: 09-04 built the popup/background split for PRF unlock assuming v0.1's server-registered passkeys would work from the popup. The empirical probe killed that assumption: `get()` from a `chrome-extension://` page throws `SecurityError` for ANY web RP ID and passes only for `rpId === <extension-id>`. Bartek's decision (superseding the popup-PRF assumption): a dedicated extension-scoped credential, the Bitwarden pattern — not web-app handoff, not password-only degradation. Without this plan, Phase 9's SC #2 ("unlock with a PRF passkey where the browser supports it") is unreachable in the popup. 09-04's `unlock.prf.*`/`auth.signIn.prf.*` kinds stay in the router (correct, tested background logic — Phase 12's provider context or a future options-page may legally run web-RP ceremonies) but the popup will not dispatch them (09-06 amended accordingly).
Output: `wrapping_key_from_ext_prf` + `INFO_EXT_PRF_UNLOCK` (pv-core, KAT-tested), `fromExtPrf` (pv-wasm), migration 0011 + `extension_passkeys.rs` routes + integration tests (pv-server), `ext-prf.ts` (pure popup-side ceremony-option builders), `ext-passkey.ts` (background handlers), router/ext-protocol extended with `extPasskey.enroll.start`, `extPasskey.enroll.finish`, `extPasskey.suppressPrompt`, `unlock.extPrf.start`, `unlock.extPrf.finish`, plus an enriched `session.status` response, and a pinned `manifest.key` in wxt.config.ts.
</objective>
