<objective>
Port v0.1's password + PRF unlock ceremony (`web/src/lib/passkeys/login.ts`'s `passkeyLogin()`/`passkeyUnlock()`, `LoginForm.tsx`'s `handleSubmit()`, `UnlockOverlay.tsx`'s `unlockFromPassword()`) into the background service worker, split across the popup/background DOM boundary exactly where WebAuthn requires it, and wire both the fresh-install SIGN-IN path (mints a session token) and the existing-token UNLOCK-ONLY path into Plan 09-02's session core.

Purpose: EXT-02's unlock requirement is the load-bearing feature the rest of the popup (Plan 09-06) and the sync client (Plan 09-05, which only starts once unlocked) depend on. 09-RESEARCH.md's Open Question 1 / Pattern 4 explicitly flags that `navigator.credentials.get()` has no DOM/WebAuthn access inside an MV3 service worker — this plan implements the recommended resolution: the ceremony call itself runs in the popup, only its public output crosses into the background. Equally load-bearing: `pv-server`'s `/api/passkeys/unlock/start`/`/finish` routes are `SessionUser`-gated (`crates/pv-server/src/routes/passkeys.rs`) — they require an already-valid bearer token — and the extension has no other way to obtain one, so this plan ALSO ports v0.1's unauthenticated `login()`/`passkeyLoginStart()`/`passkeyLoginFinish()` sign-in path. Without it, a fresh extension install (no token yet) could never reach the unlock endpoints at all.
Output: `auth-api.ts` (server-config-aware port of `web/`'s auth/passkey API clients), `unlock.ts` (background-side ceremony orchestration for both sign-in and unlock-only), `prf.ts` (shared pure PRF-extraction helpers usable from the popup), and `router.ts`/`ext-protocol.ts` extended with `unlock.password`/`unlock.prf.start`/`unlock.prf.finish` AND `auth.signIn.password`/`auth.signIn.prf.start`/`auth.signIn.prf.finish`.
</objective>
