<objective>
Give the extension a single, runtime-configured source of truth for the user's self-hosted `pv-server` URL — validated against a real `/healthz` response before it is trusted, normalized and scheme-restricted before it is ever handed to `browser.tabs.create` (Plan 09-06/EXT-06), and persisted where it belongs (`chrome.storage.local`, not the key envelope).

Purpose: EXT-05 is a hard prerequisite of every other extension-to-server call this phase makes (auth/unlock in 09-04, REST+WS sync in 09-05, "open full vault" in 09-06) — none of them can be written correctly without this module existing first. It has zero dependency on Plan 09-01/09-02's outputs, so it lands in Wave 1, ready the moment later plans need it.
Output: `server-config.ts` — the one place `extension/` reads or writes the pv-server base URL; `wxt.config.ts` extended with `optional_host_permissions` so the runtime permission grant (rather than a compile-time host list) is possible for an arbitrary self-hosted origin.
</objective>

  Create `extension/entrypoints/background/server-config.ts`. Export surface:

  ```typescript
  export class InvalidServerUrlError extends Error {}
  export class ServerUnreachableError extends Error {}

  export interface ServerConfig {
    baseUrl: string; // normalized: lowercased scheme+host, no trailing slash, http(s) only
  }

  const STORAGE_KEY = "pv-server-config"; // chrome.storage.LOCAL — NOT chrome.storage.session.
  // This is user-facing configuration, not vault-secret material (D-01/D-02
  // from 09-CONTEXT.md apply to the KEY ENVELOPE only): it must survive a
  // browser restart, unlike the session envelope which is deliberately
  // wiped on restart. Do NOT "simplify" this later by merging it into
  // session-storage.ts's single storage area (Plan 09-02) — that would
  // force reconfiguration on every browser restart and defeats EXT-05's
  // "persisted" requirement.

  export function normalizeServerUrl(rawUrl: string): string; // throws InvalidServerUrlError
  export async function probeServerHealth(baseUrl: string): Promise<boolean>; // never throws
  export async function configureServer(rawUrl: string): Promise<ServerConfig>; // throws InvalidServerUrlError | ServerUnreachableError
  export async function readServerConfig(): Promise<ServerConfig | null>;
  export function wsUrlFromBase(baseUrl: string): string;
  ```

  `normalizeServerUrl`: `new URL(rawUrl)` (catches the "not a url" case as a thrown `TypeError`, rethrow as `InvalidServerUrlError`), then explicitly check `url.protocol === "http:" || url.protocol === "https:"` — reject everything else including `javascript:`, `file:`, `data:`, `chrome-extension:`, `moz-extension:`. Rebuild the normalized string as `${url.protocol}//${url.host}` (drops any trailing slash/path/query the user pasted in by accident — this extension only ever needs the origin).

  `probeServerHealth`: wrap the `fetch`+`.json()` call in a `try { } catch { return false; }` — any network-level failure (including a non-JSON body) resolves `false`, never rejects the caller. Compare the parsed body with a strict shape check (`typeof body === "object" && body !== null && body.status === "ok"` — do not merely check `response.ok`).

  `configureServer`: call `normalizeServerUrl` first (synchronous, no I/O — invalid input never reaches `fetch`). Then `probeServerHealth`; on `false`, throw `ServerUnreachableError`. Then request the permission scoped to exactly this origin (`browser.permissions.request({ origins: [normalizedBaseUrl + "/*"] })`) — confirm the exact `browser.permissions` API shape against whatever `wxt/browser` or `@wxt-dev/browser` exposes at execution time (Phase 8's actual import convention, per read_first). Then `chrome.storage.local.set({ [STORAGE_KEY]: { baseUrl: normalizedBaseUrl } })`. Return the config.

  `wsUrlFromBase`: same single-leading-scheme-replace as `web/src/lib/vault/sync.ts`'s `wsUrl()` (`baseUrl.replace(/^http/, "ws")`) — do not duplicate the WS-URL construction logic in Plan 09-05; that plan imports this function.

Confirm it fails. GREEN: implement per the action above.

<assumption_delta_decision>
**Noun:** the pv-server base URL the extension talks to.
**Family:** `chosen` — a compile-time constant (v0.1's `NEXT_PUBLIC_API_BASE_URL`) becomes a runtime-chosen, per-user configuration value for the extension surface (EXT-05).
**Decision:** `promote`. `server-config.ts` becomes the ONE primary source of the base URL for all of `extension/`; every later call site (Plan 09-04's `auth-api.ts`, Plan 09-05's `vault-api.ts`/`sync-client.ts`, Plan 09-06's "open full vault" `tabs.create`) reads it via `readServerConfig()`/`wsUrlFromBase()` — none re-derives or hard-codes a URL. `add-alongside` (keeping a compile-time default next to the runtime value) was rejected: it would silently contradict EXT-05's "No server URL is hard-coded" and give a future contributor an easy wrong default to fall back to.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| User-typed server URL → `browser.tabs.create` (Plan 09-06, EXT-06) | The single most consequential trust boundary this module guards — a value normalized here is later opened as a real browser tab with no further validation downstream |
| Extension ↔ arbitrary self-hosted origin (network) | `configureServer`'s `probeServerHealth` fetch is the FIRST untrusted cross-origin request this extension ever makes to a user-supplied host |
| `chrome.storage.local` (persisted config) vs. `chrome.storage.session` (Plan 09-02's key envelope) | Two storage areas with very different sensitivity and lifetime — this plan's entire Task 1 module comment exists to keep them from ever being merged |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-09-09 | Spoofing / Tampering | `normalizeServerUrl`, later consumed by `browser.tabs.create` | high | mitigate | Allow-lists exactly `http:`/`https:` schemes; every other scheme (`javascript:`, `file:`, `data:`, `chrome-extension:`, `moz-extension:`) throws `InvalidServerUrlError` before the value is ever persisted or opened as a tab |
| T-09-10 | Spoofing | `probeServerHealth` accepting a non-pv-server that happens to answer HTTP 200 | medium | mitigate | Requires the exact `{"status":"ok"}` JSON body (matches `crates/pv-server/src/routes/mod.rs`'s real `healthz` handler), not merely `response.ok` — a captive portal, a misdirected DNS entry, or an unrelated web server returning 200 is rejected |
| T-09-14 | Elevation of Privilege | `optional_host_permissions` + `browser.permissions.request` | medium | mitigate | Requests exactly the single configured origin's pattern (`normalizedBaseUrl + "/*"`) at `configureServer()` time, never `<all_urls>` as a standing grant; re-configuring to a new server re-requests for the new origin only |
| T-09-15 | Information Disclosure | Confusing `chrome.storage.local` (this plan) with `chrome.storage.session` (Plan 09-02's key envelope) | low | mitigate | Explicit module-header comment in `server-config.ts` states the distinction and the reason (survives restart vs. wiped on restart); no code path in this file ever touches `chrome.storage.session` |

</threat_model>
