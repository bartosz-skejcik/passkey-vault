# Phase 11 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **Generated in autonomous mode** (no human review session — CAP-01/02/03, ROADMAP success criteria, and 11-CONTEXT.md/11-RESEARCH.md already pin the required product behavior; no new UX preference was invented beyond what's flagged in **Morning review notes** below). This phase introduces the project's **first content-script-injected UI** — surfaces rendered on top of third-party pages, not inside the extension's own popup/web-app document. Every security-relevant surface here (origin-mismatch confirm) follows the same sober, plain-DM-Sans rule Phase 2/3's `DeleteConfirmDialog`/enrollment-ceremony dialog established; nothing in this phase is Fuzzy-Bubbles-eligible — save/update/generate prompts are credential-adjacent, not onboarding/empty-state surfaces.

## Design System

| Property | Value |
|----------|-------|
| Tool | none — carried forward unchanged from the whole v0.1/v0.2 project. `components.json` still absent (extension project doesn't use shadcn either). **Not re-asked — standing project decision.** |
| Component library | DaisyUI 5, same theme (`vault-dark`/`vault-light`) as the web app and the Phase 9 popup — but this phase is the first to render DaisyUI-classed markup **outside** the extension's own document, inside pages the extension doesn't own. New component classes/patterns this phase: `dropdown`-shaped popover (generate-password suggestion — visually identical to the web app's Phase 2 `GeneratorDialog` popover, just anchored to a page field instead of a form field in our own app), `toast` (save/update prompt banner — DaisyUI's `toast` positioning classes, `toast-end toast-bottom`), `modal` (origin-mismatch escalation — same `fixed inset-0 z-50` + `bg-base-300/70` scrim shape as `DeleteConfirmDialog`/`EnrollPasskeyDialog`), `range`/segmented-radio (generator length + mode controls, reused verbatim from Phase 2), `alert alert-error` (mismatch modal banner body). **Delivery mechanism (new, load-bearing for this phase):** all three surfaces (suggestion popover, save/update toast, mismatch modal) render inside a single closed **Shadow DOM root** injected via WXT's `createShadowRootUi` with `cssInjectionMode: 'ui'`, so the extension's own compiled Tailwind+DaisyUI stylesheet (identical tokens/classes to the popup and web app) is scoped inside the shadow root and cannot leak into — or be leaked into by — the host page's CSS. One shadow-root UI container per tab, mounted once by the content-relay, reused across all three surfaces (not three separate injected roots). |
| Icon library | `lucide-react` (carried forward, same package already used by the web app and Phase 9's popup — no new dependency). Reused icons, same meaning as established: `RefreshCw` (generate/regenerate password trigger + in-popover regenerate — **identical meaning to Phase 2's web-app generator**, not a new icon concept), `AlertTriangle` (origin-mismatch warning — reused destructive/blocking-warning meaning from Phase 2/3), `X` (toast/popover dismiss), `Check`/`CircleCheck` (save-success confirmation flash inside the toast, reused from Phase 2/6's copy-confirm and import-done conventions), `Vault` (toast leading icon for both "save new login" and "update login" — reused login item-type icon, not a new meaning), `Eye`/`EyeOff` (reveal the suggested/captured password inside the popover/toast before confirming — reused Phase 2 meaning). **New icon this phase:** none — every icon reuses an established meaning. This is a deliberate constraint: introducing a new icon on a page the extension doesn't own raises the bar for "does this read instantly," so this phase leans entirely on vocabulary the user (and the checker) has already seen in the popup/web app. |
| Font | `DM Sans` only, plain, no `Fuzzy Bubbles`, no emoji — all three surfaces in this phase are credential-adjacent (generated passwords, captured logins, origin trust) and held to the same sober standard as the unlock overlay/delete dialogs, per `docs/UI-DESIGN.md` §1's "security UI zawsze czytelne" rule. **New requirement this phase:** DM Sans (and the `ui-monospace` stack used for the password preview) must be delivered as **self-hosted `@font-face` files bundled as extension web-accessible resources**, referenced by `chrome-extension://`/`moz-extension://` URL inside the injected stylesheet — the shadow-root UI runs on arbitrary third-party origins and must not trigger an outbound font fetch to Google Fonts (or any third-party host) from a page the user is actively viewing; the popup/web app may already do this via `next/font`'s local bundling, this note exists to make sure the extension's `cssInjectionMode: 'ui'` bundle doesn't silently reintroduce a CDN font URL. `ui-monospace` → the password preview/value shown in the generator popover and the save/update toast (matches Phase 2's "passwords are always mono" rule). |

Unchanged 60/30/10 split and hex/OKLCH values from Phase 1–10 (`vault-dark` default, full `vault-light` parity — the shadow-root UI ships both themes and follows the extension's own theme preference, not the host page's, since it must stay legible regardless of what CSS the host page is running).

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#1F1F1F` base-300 dark / `#FCFBFA` base-200 light | Toast/popover/modal canvas seen behind the surface's own card |
| Secondary (30%) | `#262626` base-100 dark / `#FFFFFF` base-100 light | Toast card, popover card, mismatch-modal card surfaces |
| Accent (10%, coral `#E16540`) | primary | Toast's **"Save"**/**"Update"** confirm button, popover's **"Use this password"** apply button, popover's active mode-toggle segment. **Nothing else** — the `RefreshCw` trigger icon, `Vault` toast icon, and dismiss `X` all stay neutral (`text-base-content/70`), matching the established "accent is reserved for the confirming action, not decoration" rule from Phase 2/3/6. |
| Destructive | `#FF5861` error | **Origin-mismatch modal only** — `AlertTriangle` icon, `alert alert-error` banner, and the modal's own confirm button reads as a deliberate warning-tier action, styled with the error/red register (not warning-yellow). Success (`#00A96E`) → a brief (~1.5s, non-blocking) `CircleCheck` confirmation flash on the toast after a successful save/update, before the toast dismisses itself — reused exactly as Phase 2's item-Save-button flash.

## Phase-Specific Notes

### Surface 1 — Generate-password suggestion (CAP-01)

- **Trigger:** a 40px-hit-area, 16-20px `RefreshCw` icon button absolutely positioned inside the trailing padding of any field the content-relay's form-detector classifies as `signup-mode` (new-password or confirm-password). **Click-triggered only — never auto-opens on focus** (Pitfall C: avoids visually racing the browser's own native "suggest strong password" popover, which already fires on the same `autocomplete="new-password"` signal). This is the phase's key discretion call — see Morning review notes #1.
- **Popover contents (top to bottom), 320px, anchored below the field:** title, mode segmented toggle (Characters/Passphrase, matches Phase 2's length-first framing), generated preview (`ui-monospace`, Body size, `Eye`/`EyeOff` reveal toggle since the popover sits on a page the user may be sharing a screen on), length control (`range`, same 8-64 char / 3-10 word bounds as the web app), character-set checkboxes (character mode only), strength meter (success/warning/error segments, identical logic/thresholds to Phase 2 — reused, not reimplemented per D-01/D-03), `RefreshCw` regenerate + coral "Use this password" apply button. Applying fills **both** the new-password and confirm-password field if the detector paired them, then closes the popover.
- **Generation is always a `generate-request` background message** (per D-01/D-07/11-RESEARCH.md's architectural-consistency finding), never computed in the content script directly, even though the generator itself has no WASM/key-material dependency.
- **Loading state:** none needed — `crypto.getRandomValues` and the ported generator are synchronous/near-instant; the popover renders its first suggestion immediately on open, no skeleton/spinner state.
- **Error state (rare):** if the background's `generate-request` handler throws (e.g., malformed options), the popover shows the `generate.failed` inline error text (red, `text-error`) in place of the preview, with the regenerate button still available to retry — never a blank/frozen popover.

### Surface 2 — Save-new-login toast (CAP-02) and update-existing-item toast (CAP-03)

- **Trigger:** the content-relay's submit-capture success heuristic (11-RESEARCH.md Pattern 1) fires `capture.propose-save`; background classifies `new` / `update:<itemId>` / `no-op` (Pattern 2). **`no-op` renders no UI at all** — no toast, no flash, nothing (Pitfall B: resubmitting an unchanged password is a non-event, not worth interrupting the user for).
- **`new` → save toast; `update:<itemId>` → update toast.** Same 360px card shape, same action-row layout, different title/body copy and confirm-button label (`Save` vs `Update`) per the Copywriting table above. Both show: `Vault` icon (neutral, 32px slot — same treatment as every other item-type icon), title (Heading not used here — Body-weight primary line per the toast's smaller footprint, matching DaisyUI `toast` conventions rather than a full dialog), the `{origin} · {username}` line (Label), a masked password preview with `Eye`/`EyeOff` reveal (mono, Label size — the user should be able to verify what's about to be saved before confirming), confirm button (coral) + `Not now` (ghost) side by side, and a top-right `X` dismiss.
- **No auto-dismiss (see Spacing Scale).** Dismissed only by explicit action. If the user navigates away from the tab before acting, the toast is simply gone with the tab (the content-relay's DOM, and any pending in-memory proposal, dies with the frame) — no cross-tab persistence of a pending save is attempted this phase (matches 11-RESEARCH.md Open Question #2's "re-send full payload on confirm" recommendation: nothing survives beyond the live tab).
- **Confirm re-sends the full field payload** (`capture.confirm-save`/`capture.confirm-update` carries username/password/origin fresh from the content script's own DOM-scoped closure, not a reference to prior background state) — sidesteps the SW idle-kill-between-propose-and-confirm risk per 11-RESEARCH.md's recommendation, without needing a new `chrome.storage.session` sub-schema.
- **Loading state:** while the confirm click's encrypt+REST round-trip is in flight, the confirm button shows a small inline spinner (reuses `loading loading-spinner loading-xs` inside the button, matching Phase 3's ceremony-in-progress treatment) and both buttons disable — prevents a double-submit race.
- **Success:** on a successful `createItem`/`updateItem` response, the toast body swaps to the `CircleCheck` + "Saved"/"Updated" confirmation (success green) for ~1.5s, then dismisses itself automatically (this brief post-success flash is the one exception to "never auto-dismisses" — the decision has already been made and confirmed at that point, there's nothing left to miss).
- **Error/conflict:** a network failure shows `save.failed` + a `Retry` button in place of the confirm/dismiss row (toast stays open). A 409 revision conflict on update (per `web/src/lib/vault/store.ts`'s `RevisionConflictError` pattern, D-09/PITFALLS.md's multi-device race) shows `update.conflict` instead — never a silent overwrite, matching the existing v0.1 conflict-handling precedent.

### Surface 3 — Origin-mismatch escalation (CAP-02/03, ROADMAP SC#4, D-06, PITFALLS.md Pitfall 7)

- **Whenever `frameOrigin !== topOrigin`** (background-verified via `sender.tab.url`, never the content script's self-report alone — see 11-RESEARCH.md Pattern 3), the flow **skips the toast entirely** and renders the 400px mismatch modal directly instead — same shape/weight as `DeleteConfirmDialog`/`EnrollPasskeyDialog` (centered, `fixed inset-0 z-50`, `bg-base-300/70` scrim, **not** dismissible via click-outside/`Esc`, only via the explicit `Cancel`/`Save anyway` buttons — mirrors the enrollment-ceremony's "no accidental dismiss mid-security-decision" precedent).
- Both origins (`frameOrigin` and `topOrigin`) are shown **explicitly, in full, as plain text** — never truncated/elided, never just "a different site" — per D-06's literal requirement.
- `AlertTriangle` (error color) + Heading title + Body warning text + `alert alert-error` banner + `Cancel` (`btn-ghost`, visually first/left, matching the project's existing "safe choice is easier to reach" convention) + `Save anyway` (`btn-error`, not coral — a mismatch confirm is a warning-tier action, not a branded CTA).
- Confirming re-runs the same save/update confirm path as Surface 2 (encrypt+REST), just gated behind this extra step — no separate persistence code path.
- This applies **identically** to both the new-save and update-existing flows — a password-change submitted from a mismatched frame gets the same escalation as a brand-new login.

### Shadow-root mount lifecycle

> **REPAIR 2026-07-16:** Freshness audit found the codebase has NO `createShadowRootUi`/WXT UI helper, Tailwind-in-shadow, or React path anywhere under `extension/` — the actual, already-shipped in-page-surface mechanism is `lib/autofill/inpage-overlay.ts`'s pattern: an imperative controller that calls `attachShadow({mode:'closed'})` on a host element it creates itself, styled with a single inlined `<style>` block of literal OKLCH CSS values (no Tailwind/DaisyUI classes, no React). This is the CANONICAL mechanism for every Phase 11 in-page surface (generate-popover, save/update toast, mismatch modal) — extend/reuse `inpage-overlay.ts`'s mount as the shared anchor rather than introducing `createShadowRootUi`. Read every `createShadowRootUi`/`cssInjectionMode`/Tailwind/DaisyUI/React reference below through this filter — those references describe an earlier, superseded design and must not be implemented literally.

- One `createShadowRootUi` instance per tab/frame the content-relay is active in, mounted lazily on first need (first signup-field focus, or first submit-capture success) rather than eagerly on every page load — avoids injecting DOM/CSS into pages that never trigger any of this phase's features.
- The suggestion popover, the toast, and the mismatch modal are three view-states of that **same** mounted root (not three separate `createShadowRootUi` calls) — consistent with 11-RESEARCH.md's single-message-registration discipline applied to the UI layer too.
- Z-index inside the shadow root is set high enough to sit above typical page chrome (sticky headers, cookie banners) but the shadow boundary itself is what actually guarantees visual isolation — page CSS cannot reach in, and the injected CSS cannot leak out, regardless of the host page's own stacking contexts.

## Morning review notes

Taste calls this agent made autonomously, per 11-CONTEXT.md's Discretion Areas — none affect data model, message-protocol shape, or the zero-knowledge/origin-verification invariants; all are presentation-layer and reversible.

1. **Generate-password affordance is click-triggered icon-in-field (40px `RefreshCw`), never auto-opening on focus.** This directly follows 11-RESEARCH.md's Pitfall C guidance to avoid racing the browser's own native strong-password suggestion, and mirrors D-04/D-06's "explicit user gesture" pattern used elsewhere in the milestone (autofill, mismatch confirm). If you'd rather the extension suppress/coexist with the native suggestion more actively (not currently possible via any browser API), that's a future research item, not something buildable in this phase.
2. **Origin-mismatch skips the toast and goes straight to a blocking modal, using error-red rather than Phase 6's export-dialog warning-yellow precedent.** Reasoned that a cross-origin credential-capture attempt is the actual attack PITFALLS.md Pitfall 7 describes (closer to `docs/UI-DESIGN.md`'s "wyciek" semantics than "hasło stare"), not merely attention-worthy. Easy single-token retint to warning-yellow if you'd rather keep every non-destructive confirm dialog in the yellow register for visual consistency across phases.
3. **No persistent "never ask again for this site" preference — only a per-instance `X`/`Not now` dismiss.** 11-CONTEXT.md explicitly left this open but flagged the schema-creep risk of a persistent version; this spec takes the conservative reading and defers persistent snooze to backlog, matching Deferred Ideas.
4. **Toast never auto-dismisses except the brief post-confirm success flash.** A silently-disappearing save-prompt would undermine CAP-02/03's entire purpose (the whole point is not missing a chance to save/update); the one exception (post-success) is a already-resolved state, not a missed opportunity.
5. **Save/update toast shows the captured password itself (masked, revealable)** before the user confirms — not just the username/origin — so the user can verify what's about to be written to the vault, consistent with Phase 6's TOTP-secret reveal pattern (mask-by-default, `Eye`/`EyeOff`, never a new interaction vocabulary).
