<objective>
Implement the scored, `autocomplete`-first, threshold-gated detector for credit-card (FILL-03) and identity (FILL-04) fields — the two families with no single standardized signal strong enough to trust deterministically.

Purpose: 10-RESEARCH.md Pitfall 1 is blunt that loose heuristics here are the failure mode that "has bitten every competitor in this space" — a fill affordance offered on the wrong field erodes trust faster than no affordance at all. D-05 locks the mitigation (autocomplete-first, scored, thresholded); this plan implements it and pins the boundary behavior with tests so a later tweak to the weights cannot silently lower the bar.
Output: `field-tokens.ts` (weights + threshold + vocabulary) and `detect-scored.ts` (`detectCard`/`detectIdentity`), with curated-fixture-backed jsdom tests.
</objective>

  <behavior>
    **Card (detect-scored.card.test.ts):**
    - Test 1: a well-marked checkout form (`autocomplete="cc-number"`, `cc-exp`, `cc-csc`, `cc-name`) resolves all four slots to the right elements.
    - Test 2 (BOUNDARY): a field engineered to score exactly `FILL_THRESHOLD` IS returned; the same field engineered to score `FILL_THRESHOLD - 1` is NOT. Assert both directions in one test so the comparison operator is pinned.
    - Test 3 (TIE / ADJACENCY): two inputs that score identically for the `number` slot ⇒ the `number` slot resolves to `null` (fail closed), while any other unambiguous slot on the same form still resolves.
    - Test 4 (FALSE POSITIVE): a form containing only `<input name="quantity" inputmode="numeric">` and `<input name="promo-code">` resolves ZERO card slots — this is Pitfall 1's canonical failure and must be a test, not a hope.
    - Test 5 (EMPTY): an empty document, and a document with inputs but no card evidence, both return a result with all slots null and `hasAny === false`.
    - Test 6: an unmarked-but-conventional form (`name="cardnumber"`, `name="cvv"`, no `autocomplete` at all) resolves via the fallback tier — proving the fallback still earns real coverage.
    - Test 7: a hidden/disabled input with a perfect `autocomplete="cc-number"` is NOT returned (the prohibition in frontmatter).
    - Test 8 (PRECISION): `cc-exp-month` + `cc-exp-year` as two separate inputs both map to the `expiry` slot and are reported as a split-expiry pair, so the filler can write `MM` and `YYYY` separately rather than dumping the stored `expiry` string into one of them.

    **Identity (detect-scored.identity.test.ts):**
    - Test 9: a well-marked address form resolves firstName/lastName/email/phone/address.
    - Test 10: a Polish-language form (`<label>Imię</label>`, `name="nazwisko"`, `name="telefon"`, no autocomplete) resolves via the Polish fallback vocabulary.
    - Test 11 (ORDERING): when two fields score equally for `email`, resolution is deterministic and documented — assert the same input produces the same output across repeated calls (no reliance on unstable ordering).
    - Test 12 (ENCODING): an identity value slot is resolved by markup only; the detector never inspects, normalizes or truncates a value — assert a field with an existing unicode value is still resolved and its value is untouched.
  </behavior>
  <action>
  Create `extension/lib/autofill/detect-scored.ts` exporting `detectCard(root: Document | Element): CardSlots` and `detectIdentity(root: Document | Element): IdentitySlots`, where each result maps every slot name to `HTMLInputElement | null` plus `hasAny: boolean` (and, for card, `expiryMode: "single" | "split"` with the month/year elements when split — Test 8).

  Scoring, per candidate input (10-RESEARCH.md Pattern 2):
  1. Skip non-fillable inputs up front, reusing `detect-login.ts`'s exported fillable-field predicate — do not write a second one.
  2. Read `input.autocomplete` (lowercased, trimmed). If it matches a token table entry exactly → that slot gets that full weight; short-circuit, do not consult the fallback for this field. This short-circuit IS the "autocomplete-first" guarantee.
  3. Only when the token is absent/unrecognized, build a normalized haystack from `name` + `id` + `placeholder` + `aria-label` + the associated `<label>`'s text (via `labels`/`for`/ancestor `<label>`), each **bounded to 200 chars before concatenation** (ASVS V5 — hostile input), lowercased with non-alphanumerics stripped. Match against `KEYWORD_FALLBACK` and take `floor(weight * 0.5)`, keeping the max across matches.
  4. Drop any field whose best score `< FILL_THRESHOLD`.
  5. Resolve each slot by highest score among surviving candidates. **On an exact tie for a slot, resolve that slot to `null`** — do not pick the first in document order. A tie means the page gave genuinely ambiguous evidence, and silently guessing is how a CVV lands in the wrong box. Comment this explicitly; a future reader will otherwise "fix" it into a first-wins.

  Do NOT import any crypto module. Do NOT read or write any input's `value` — this module resolves ELEMENTS only; writing values is plan 10-05's `fill-dom.ts`.

  Write both test files under jsdom with the 12 behaviors. Where a curated real-world fixture is used, place the sanitized HTML under `extension/lib/autofill/__fixtures__/` per Task 1's README rules. Synthetic fixtures are fine for the boundary/tie/empty cases; at least the "well-marked checkout" and "Polish identity form" cases should use curated markup shaped like real forms rather than a two-input toy, since 10-RESEARCH.md Pitfall 1 is explicit that a synthetic fixture alone does not validate the false-positive rate.
  </action>
